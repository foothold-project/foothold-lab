## G 가 무엇이었나

`UnitreeGo2GapWideEnvCfg`(B) 를 상속한다. 학습 지형은 B 의 `forward_gap`
그대로다.

**「B 에서 `heading_command` 를 껐다」는 틀린 설명이다.** B 는 **이미**
`heading_command=False` 다 (`gap_env_cfg.py:74`) `확인됨`. 설계 문서가
`heading_command False` 를 「G 의 전부」로 적은 것은 **D · E 와 견준 말**이지
B 와 견준 말이 아니다.

**B 에서 실제로 바뀌는 것은 넷이다.**

```
ranges.ang_vel_z     (0.0, 0.0)  ->  (-1.0, 1.0)   ← 이것이 G 의 알맹이다
ranges.lin_vel_x     (0.5, 1.5)  ->  (0.4, 1.5)
rel_standing_envs    0.0         ->  0.02
ranges.heading       (-pi, pi)   ->  None          경고를 막으려고 비운다
heading_command      False       ->  False         (안 바뀐다)
```

**G 는 「heading 을 끈 판」이 아니라 「heading 제어기 없이 요를 직접 명령으로
여는 판」이다.** D · E · F 는 셋 다 `heading_command=True` 라 `ang_vel_z` 가
**heading 제어기 출력의 상하한**으로 쓰이는데 G 에서는 **명령 그 자체**로
쓰인다.

**E 는 둘을 섞는다.** `rel_heading_envs=0.75` 라 **환경의 75 % 는 heading
제어기를 거치고 25 % 는 표집된 요 명령을 그대로 받는다.** D 와 F 는 1.0 이라
전부 거친다.

설정: `sim/policy/gap_g_env_cfg.py` · 등록 id
`Isaac-Velocity-GapG-Unitree-Go2-v0`.

## 물음과 답

> **물음** · D 의 rails 이득이 「방향 유지 압력」 때문인가.
> `heading_command` 를 끄면 재현되는가.

| rails | v1 | D | **G** |
|---|---:|---:|---:|
| 0.5 | 70 | 86 | **27** |
| 1.0 | 48 | 89 | **65** |
| 1.5 | 21 | 80 | **24** |

> **답 · G 의 설정으로는 재현되지 않는다.** 0.5 에서는 v1 아래로
> **진짜 하락**이다.

**「그러므로 요는 `heading` 으로 배워야 한다」까지는 못 간다.** G 는 D 와
**네 칸**이 다르다 · `heading_command` · `heading` 범위 · `rel_heading_envs`
(1.0 -> 0.0 · `heading_command` 가 False 라 동작에는 안 쓰인다) ·
`lin_vel_x` 하한. 게다가 E 와 견주면 **rails 1.0 에서 G 가 «진짜 상승»**
이다 (E 41 · G 65). 자세한 것은 판정문 4 절에 있다 `미확인`.
