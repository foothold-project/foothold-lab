## 2. 확인한 것: 주춤이 눈에 보인다 `확인됨`

`pit` env 44 한 판(6초 · 300프레임)을 실제로 만들어 열어 봤습니다.

| 언제 | 무슨 일 | 화면에서 |
|---|---|---|
| 0.00 ~ 0.26 s | 출발 | 속도 0 에서 오름 |
| 0.6 ~ 1.0 s | 명령 속도 근처까지 붙음 | 곡선이 점선에 닿음 |
| 1.02 ~ 1.56 s | **첫 주춤** | 최저 0.11 m/s |
| 1.94 ~ 5.52 s | **구덩이 앞에서 멈춤** | 3.6초짜리 주황 덩어리 |

**전진은 6초에 1.51 m 입니다.** 명령대로 갔으면 6 m 입니다. 통과선 3 m 짜리
막대가 절반에서 멈춘 채 4초를 서 있고, 그 옆에서 속도 곡선이 바닥에 붙습니다.
**「구덩이는 나왔는데 속도만 못 따라간다」가 표가 아니라 그림으로 보입니다.**

`still_t1.00.jpg` 와 `still_t5.50.jpg` 가 그 두 장면입니다.
(`sim/eval/results/20260909-pit-env44-overlay/`)

주춤 구간은 **사람이 눈으로 세지 않습니다.** `trace.slowdown_spans()` 가
「명령의 60% 아래로 0.15초 이상」을 구간으로 집어 그래프 바닥에 띠로 깔고,
왼쪽에 「주춤 3 / 3」으로 셉니다. 문턱값은 `--slowdown_ratio` ·
`--slowdown_min_s` 로 바꿉니다.

## 3. 무엇을 그렸고 무엇을 뺐나

| 그린다 | 왜 |
|---|---|
| 경과 시간 | 「몇 초에」를 말하려면 있어야 한다. 프레임 번호에서 공짜로 나온다 |
| **속도 · 명령 대 실제** | **이 도구가 있는 이유.** 화면에서 가장 큰 칸 |
| 전진 · 통과선까지 | 막대 하나. 「어디까지 갔나」가 한눈에 |
| 좌우 이탈 | 가운데 기준 게이지 하나. 방향이 새는 것이 보인다 |
| 판정 4축 | 램프 넷. **어느 축에서 떨어지는 중인지**가 보인다 |

| 뺐다 | 왜 |
|---|---|
| **발 높이 네 발** | 걸음 하나가 약 0.3초다. 50 fps 에서 15프레임이고, 6초 창에 네 줄을 겹치면 서로 뭉개져 안 읽힌다. 그리고 발 높이는 **chase 카메라가 이미 보여 준다.** `pit` env 44 의 2.0초 자리에서 앞발 둘이 0.22 m 로 들려 있는 것은 화면에 그대로 나온다 |
| 몸통 높이 · 기울기 | 같은 이유다. 그 자리의 pitch 는 -21도인데, 그것도 화면에 보인다. 숫자로 또 쓰면 칸만 늘어난다 |
| 보상 | 프레임마다의 뜻이 사람에게 안 읽힌다. 판 단위 표에 남아 있다 |
| 세계좌표 x · y | 출발 자세 기준의 전진 · 좌우로 이미 바꿔 그렸다. 두 벌을 같이 두면 헷갈린다 |

**뺀 것도 trace 에는 전부 들어 있습니다.** 화면에서 뺀 것이지 안 잰 것이
아닙니다. 나중에 발 높이 칸이 필요해지면 `hud.py` 에 칸을 하나 더 그리면 됩니다.

**전부 넣지 않은 것이 설계입니다.** 화면의 위 28% 만 씁니다.
로봇을 가리면 영상이 아니라 계기판이 됩니다.

### 판정 램프를 어떻게 읽나

`O` 통과 · `X` 실패 · `-` 아직 물을 수 없음.

**확정 판정이 아니라 「지금까지의 값으로 보면」입니다.** 그래서 «전진» 은 판
끝에 가야 참이 될 수 있고, «방향» 은 통과선을 넘기 전에는 `-` 입니다.
도착하지 않았는데 「도착했을 때 몇 cm」를 물을 수 없기 때문입니다
(`metrics.gate_direction_success` 와 같은 규칙).

## 4. 왜 후처리인가

**시뮬을 다시 안 돌립니다.** 입력은 mp4 하나와 CSV 하나이고 출력은 mp4 하나입니다.

`record_flat_baseline.py` 의 렌더 경로를 안 건드리므로, 그 파일이 검사로
보장하는 「영상 속 판 = 표 속 판」이 그대로 있습니다. 이미 만들어 둔 영상에도
나중에 붙일 수 있습니다.

## 5. 프레임과 줄을 어떻게 맞추나

`record_flat_baseline.py` 는 **시뮬 스텝 하나에 프레임 하나**를 찍습니다.
trace 줄도 같은 자리에서 적으므로 **trace 줄 번호 = 프레임 번호**입니다.
실제로 `pit` env 44 에서 프레임 300장 · trace 300줄이 나왔습니다.

그래도 줄 번호로 바로 집지 않고 **시각으로 집습니다.** 나중에 30 fps 로 다시
인코딩한 영상이 오면 줄 번호로는 조용히 밀리기 때문입니다.

그리고 그리기 **전에** 검사합니다.

| 검사 | 안 맞으면 |
|---|---|
| fps 가 서로 0.5% 안인가 | 멈춘다 (`--allow_fps_mismatch` 로 넘길 수 있다) |
| 길이가 서로 `--max_drift_s`(기본 0.1초) 안인가 | 멈춘다 |
| 프레임 수가 trace 줄 수의 ±2 안인가 | 멈춘다 |

**이 검사가 이 도구에서 가장 중요한 부분입니다.** 어긋나도 그림은 멀쩡히
나옵니다. 숫자만 틀립니다. 눈으로는 절대 안 잡힙니다.
거부하면 **출력 파일을 안 남깁니다.** 반쯤 만든 mp4 가 남으면 다음 사람이
그것을 결과로 봅니다.

## 6. trace 는 어디서 나오나

`record_flat_baseline.py` 에 `--trace_csv` 를 주면 영상과 **함께** 나옵니다.
안 주면 이 기능은 한 줄도 안 돌고 기존 동작 그대로입니다.

```
python sim/eval/record_flat_baseline.py \
    --checkpoint <policy.pt> \
    --raw_csv    sim/eval/results/20260909-pit-env44-overlay/generalization_raw.csv \
    --record_env 44 --record_episode 1 \
    --terrains pit --envs_per_terrain 10 \
    --eval_duration 6.0 --command_vx 1.0 --min_progress_m 3.0 \
    --max_lateral_drift 0.75 --max_velocity_mae 0.25 --seed 42 \
    --view chase --no_refline --headless --device cuda:0 \
    --output_dir <out> \
    --trace_csv  <out>/pit_env44_ep01.trace.csv
```

**trace 를 쓰기 전에 다시 접어 대조합니다.** 프레임별 값을 판 단위로 접으면
그 판의 `forward_progress_m` · `velocity_mae_mps` · `peak_lateral_drift_m` ·
`duration_s` 가 나와야 합니다. 하나라도 다르면 **trace 를 지우고 멈춥니다.**
`record_flat_baseline.py` 가 CSV 행과 대조하는 것과 같은 뜻이고, 실측에서
차이가 전부 `0.000000` 이었습니다.

## 7. 팀원이 쓰려면

### 준비물

```
pip install av pillow
```

**ffmpeg 을 따로 깔 필요가 없습니다.** `av`(PyAV) 가 ffmpeg 을 안에 담고
있습니다. 이 워크스테이션에는 ffmpeg 실행파일이 없는데도 돕니다 `확인됨`.

글꼴은 `fonts/` 에 심어 두었습니다. **시스템 글꼴에 기대지 않습니다.**
`fonts/README.md` 참고.

### 돌리기

`--video` `--trace` `--out` 세 개면 됩니다. 위 §1 이 그 한 줄입니다.

눈으로 확인할 때는 `--stills_dir` 을 주십시오. 몇 장을 PNG 로도 남깁니다.
**영상을 만들고 「됐다」로 넘어가지 말고 그 PNG 를 여십시오.**

### 시험

```
python -m unittest discover -s sim/eval/tests -v
```

Isaac 도 GPU 도 없이 돕니다. Pillow 나 PyAV 가 없으면 그 부분만 건너뜁니다.
