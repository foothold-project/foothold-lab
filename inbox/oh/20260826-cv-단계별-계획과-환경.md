## 1. 목적과 담당 범위

목표는 **로봇이 카메라·LiDAR로 주변을 관측하고, 그 결과가 정지·대기·목적지 이동에 쓰이는 과정을 구현하고 설명하는 것**이다. 전체 명칭은 카메라·LiDAR 기반 인지·Nav 통합으로 제안한다.

| 기능 | 분야 | 기여를 입증할 결과 |
|---|---|---|
| RGB에서 사람 검출, 깊이로 위치 추정 | 컴퓨터 비전(CV) | 검출 영상, 거리·좌표 계산, 인식 결과에 따른 행동 변화 |
| LiDAR에서 지면·벽·장애물 구분 | 3D 인지 | 점군 처리 전후, 장애물 지도 |
| 시각·좌표를 맞추고 관측 결합 | 센서 통합·융합 | 시각 차이와 좌표 정합 확인, 제어에 사용한 정보 명시 |
| 목적지까지 경로 계산·추종 | Nav | 경로, 속도 명령, 실제 궤적, 도달·접촉 기록 |
| 관측을 누적해 지도 작성 | Mapping | 입력 센서와 위치 정보의 출처를 밝힌 지도 |
| 센서로 지도와 자기 위치를 함께 추정 | SLAM | 추정 궤적·지도와 위치 추정 실패 기록 |

사전학습 모델을 사용해도 영상 인식은 CV다. 카메라 보정·깊이 역투영 같은 기하 처리도 CV에 포함된다. 다만 카메라 화면을 표시만 하면 Nav에 기여했다고 볼 수 없다. [OpenCV 기하 처리](https://docs.opencv.org/4.x/d9/d0c/group__calib3d.html), [Nav2 구성 가이드](https://docs.nav2.org/jazzy/configuration_and_development/first_time_robot_setup_guide/).

### 세 가지 구분 원칙

1. **측정용 정답 정보와 제어에 쓴 센서 정보를 분리한다.** 현재 통로 런은 판정 열과 배치도뿐 아니라 제어에도 시뮬레이터 root pose(정답)를 썼다: 러너가 플래너의 로봇 위치, LiDAR·카메라 센서 변환, 사람 위치 추정(person_est)을 root pose 로 계산했고, gap·rail 의 x 구간과 목표점도 사전 정보로 받았다. 이 사용처를 표로 공개하고, 실기 이행 시 각 항목을 무엇으로 대체하는지 적는다. 알려진 지도와 정답 위치로 ㄱ자 통로를 도는 것은 Nav 검증이지 SLAM이 아니다.
2. **깊이·LiDAR로 판단한 것을 RGB CV의 성과로 포장하지 않는다.** 벽·원통 우회는 LiDAR 점군 기반이고, RGB 검출은 사람 정지·감속과 그 해제에만 쓰였다(§1 현재 기준선). CV 기여를 주장하려면 사람 판별을 켜고 끈 비교에서 행동 차이가 있어야 한다.
3. **보행 정책 `foothold-v1.pt` 를 유지한다.** 검출 모델(detector) 교체와 RL 정책 교체는 별개다. 이 계획의 어느 단계도 정책 재학습·교체를 포함하지 않는다. 실기에서는 순정 Go2 보행 위에 Nav를 연결하는 팀 방향을 따르며, 시뮬 정책을 실기에 올리는 계획으로 해석하지 않는다.

팀 정본에서 오현민의 주 역할은 `B/인지` 이고 `B/항법` 은 별도 주담당이 있다. S3~S6의 Nav·SLAM은 개인 학습과 공동 통합 범위이며 담당 변경을 뜻하지 않는다. `확인됨` 근거: 역할·커리큘럼은 §8의 ROLES 및 팀 커리큘럼, 실험 수치는 §10의 런 폴더.

### S1. 센서 데이터를 읽고 설명하기

**배울 것.** RGB·깊이·점군·height_scan의 차이, NumPy 배열과 NaN/Inf, 카메라 내부 파라미터 K, 센서 장착 좌표, ROS2 노드·토픽·메시지, `header.stamp`와 `frame_id`. 우선 저장 데이터를 읽고, 이어 ROS2 메시지로 연결한다.

**실습.** 기존 rails의 같은 시각 데이터에서 RGB·깊이·XT-16·L1 비교 출력을 나란히 연다. shape·dtype·단위·유효 값 비율을 표로 만들고, 센서 시각과 저장 시각이 같은지 확인한다. RGB는 색, 깊이는 광학축 방향 거리인지 방사 거리인지 구분한다. `ros2 topic list`, `info`, `hz`와 RViz2로 연결 상태를 확인하되 토픽 이름은 실제 환경에서 조회한다.

**완료 기준.** “센서를 달았지만 왜 정책 입력은 여전히 235인가”, “L1 데이터가 있는데 왜 영상에는 없는가”를 설명하고, 저장 파일에서 해당 근거를 직접 찾을 수 있다. 무효 깊이를 0m 또는 빈 통로로 해석하지 않는다.

**자료.** 기존 팀 ROS2 기초·TF 정리(§8), [Isaac Sim 5.1 카메라 데이터 발행](https://docs.isaacsim.omniverse.nvidia.com/5.1.0/ros2_tutorials/tutorial_ros2_camera_publishing.html), [ROS2 geometry2/tf2](https://github.com/ros2/geometry2).

### S2. 사람 검출을 거리와 행동으로 연결하기

**배울 것.** 검출 박스·신뢰도·오검출·미검출, RGB와 깊이 정렬, 픽셀 역투영, 로봇 좌표로 변환, 정지/대기/재출발 상태 전이. 단순 검출과 사람의 이동 추적·예측은 다른 기능임을 이해한다.

**실습.** 기존 사람 정지 실행 코드를 읽고, RGB 박스 안의 유효 깊이를 이용해 사람의 위치를 계산한다. 광학축 깊이 Z와 정렬된 카메라의 경우 X=(u−cx)Z/fx, Y=(v−cy)Z/fy를 이용하되, 왜곡 보정·정렬·좌표축 조건을 확인한다. 박스에 배경 깊이가 섞이는 사례와 검출 지연도 기록한다. 이어서 §3의 검출 모델 비교를 같은 저장 영상에서 수행한다.

화면에 보이지만 경로 밖인 사람, 경로 안에 선 사람, 횡단하는 사람, 거리 계산이 무효인 경우를 비교한다. “화면에 보이면 무조건 정지”에서 끝내지 않고 진행 공간과 관측 신뢰도가 판단에 어떻게 쓰이는지 확인한다. 통로 실험에서는 정지한 사람 앞에서 고정 정지 구역이 우회를 영구히 막는 결함이 실제로 났고(코스 B 2회차, 71초 정지 후 시간 초과), 카메라 추정 사람 위치와 LiDAR 경로 사이 거리가 0.35m 이상이면 감속 통과하도록 고친 뒤 3회차에서 통과했다. `확인됨` 근거: §10 통로 실험 README. 횡단 방향 예측에 따른 선제 우회는 후속 기능이며 현재 구현으로 주장하지 않는다.

**완료 기준.** 각 조건에서 검출 여부·추정 위치·판단 이유·명령·실제 속도를 같은 시간축으로 설명한다. 정지 명령 시점과 실제 정지 시점, 재출발 조건을 구분한다. 사람이 사라진 경우와 센서 데이터가 끊긴 경우를 같은 상태로 처리하지 않는지 확인한다.

**자료.** [OpenCV 카메라 기하](https://docs.opencv.org/4.x/d9/d0c/group__calib3d.html), 로컬 `10-person-stop-demo/perception.py`, `person_fsm.py`, `evaluate.py`. 별도 검출 모델 학습은 필수가 아니다.

### S3. 속도별 명령 추종과 목적지 이동

**배울 것.** 지도·자기 위치·경로·속도 명령의 차이, 전역/지역 비용 지도, 경로 계획과 추종, `map`·`odom`·`base_link` 관계, 로봇 외곽과 여유 거리.

**실습 순서.** 먼저 §4의 순서대로 평지에서 직진·회전·정지·재출발 명령에 대한 실제 속도와 자세를 기록한다. 기존 0.5m/s 는 비교 기준으로 보존하고 목표 명령 속도 1.0m/s 를 같은 조건에서 잰다. 다음으로 알려진 ㄱ자 지도·정답 위치를 사용해 최종 목적지만 주고 경로를 계산한다. 마지막으로 벽 관측을 비용 지도에 반영한다.

상위 제어가 만드는 `vx, vy, wz`를 기존 정책의 이동 명령에 연결한다. 현재 구현은 자체 플래너이며, ROS2를 쓰면 Nav2 출력과 정책 사이의 어댑터에서 좌표·단위·메시지 형식·명령 만료·발행자 중복을 확인한다. ROS2 연결 전 별도 계획기로 구현한 것은 Nav 시연으로 기록하고 Nav2 구현이라고 부르지 않는다.

**완료 기준.** 회전 시각을 손으로 지정하지 않고 목적지까지 이동한다. 벽 접촉·낙상·시간 초과·목표 오차를 기록하고, 실패하면 인식·경로·보행 추종 중 어느 단계인지 분리한다. 직진용 고정 yaw 보정이 계획된 회전을 방해하지 않는지도 확인한다.

**자료.** [Nav2 첫 로봇 구성](https://docs.nav2.org/jazzy/configuration_and_development/first_time_robot_setup_guide/)에서 TF·odometry·센서·footprint·navigation plugins 순으로 읽는다. 문서의 바퀴 로봇 구동 예제를 Go2 관절 제어에 그대로 적용하지 않는다.

### S4. 사람·원통 회피와 혼합 지형 통합

**배울 것.** 관측 점군의 지면 분리, 통과 가능 공간, 장애물 지도 갱신, 경로 재계산, 사람 인식 결과와 기하 기반 장애물 처리의 역할 분담.

**실습 순서.** 평지 통로에 원통 하나를 두고 왼쪽 여유, 오른쪽 여유, 양쪽 막힘을 각각 시험한다. 원통은 사람 검출기의 출력에 의존하지 않고 깊이·점군의 기하 장애물로 처리한다. 사람을 넣은 뒤에는 정지·대기와 우회의 적용 조건을 비교한다. 그다음에만 요철, gap, rail을 하나씩 추가한다.

통합 코스는 유효 폭 2.0m, 양옆 벽, 평지·요철(±0.06m), gap 폭 0.20m, rail 높이 0.14m·진행 방향 두께 0.08m 로 이미 제작했고 치수는 메시 정점으로 실측했다. A는 초반 중앙 원기둥, B는 요철(x=3.0~5.5) 뒤 정지 사람(x=7.0), 그 뒤 틈(x=9.0~9.2)·레일(x=11.0~11.08) 순서이며(`navB_run03/manifest.json` features), 최종 B 런은 x=8.95 틈에서 추락으로 종료되어 레일에 도달하지 않았다. 결과는 §1 현재 기준선과 같다: 우회는 접촉 0으로 통과했으나 두 최종 런 모두 레일 걸림·틈 추락으로 목표 미도달이며, 직진 확인 런(레일 0.25/0.50, 틈 0.35/0.50 명령)에서도 같은 실패가 났다. 이는 해당 메시·폭·높이와 0.25/0.35/0.50 의 해당 실행 조건에서의 실패이며, 원인은 메시·제어 조건을 검증하기 전이라 **미확정**이다. 정책 한계로 단정하지 않는다. `확인됨` 근거: §10. 주변으로 돌아갈 공간이 없는 전폭 gap은 넘거나 멈춰야 하므로, gap 우회 실험에는 실제 우회로가 있는 별도 지도를 사용한다.

**완료 기준.** 같은 코스에서 장애물 위치를 바꾸면 관측에 따라 경로가 바뀌며, 통과 공간이 없으면 멈춘다. 외부 영상·로봇 RGB·점군·계획 경로를 같은 시각으로 연결하고 벽/장애물 접촉을 로봇 중심점만으로 판정하지 않는다(현재는 몸체별 접촉 센서 필터로 판정, 벽·원기둥을 kinematic 강체로 두어 검출 작동을 242N 접촉으로 증명). 카메라 사람 판별을 켜고 끈 비교에서 실제 행동 차이를 확인해야 CV 기여를 주장한다. 이 비교는 `미측정` 이다.

height_scan은 검사 대상 지형의 높이·틈을 담을 수 있으므로 “gap을 전혀 못 본다”고 설명하지 않는다(통로 실험에서 요철 ±0.06·틈 −1.0·레일 0.14 를 읽는 것을 확인). 센서 기반 gap 탐지는 가려짐·무반사·지면 부재를 구분해야 하며, 기본 장애물 비용 지도만으로 해결된다고 가정하지 않는다. 현재 플래너는 gap·rail 의 x 구간을 사전 지형 정보로 받아 그 열에서 직진만 허용한다(끌 수 있음). 이것은 센서 인식이 아니라 힌트이며 그렇게 표기한다.

### S5. 지도 작성·위치 추정과 공원 디지털 트윈

**배울 것.** Mapping·localization·odometry·SLAM 차이, 누적 오차, 루프 폐쇄, 2D 점유 지도와 3D 지형 표현, LiDAR·IMU 시각·외부 파라미터.

**실습.** 저장 로그에서 지도·위치 추정을 먼저 재생한 뒤 시뮬에서 온라인으로 연결한다. 정답 위치를 이용한 지도 누적과 센서로 위치까지 추정하는 실행을 별도로 기록한다. 평지 2D SLAM 학습은 [SLAM Toolbox](https://github.com/SteveMacenski/slam_toolbox)를 후보로 보고, 야외 3D LiDAR·IMU 위치 추정은 [Point-LIO](https://github.com/hku-mars/Point-LIO)를 조사한다. 두 도구를 모두 구현하는 과제로 고정하지 않는다. Point-LIO를 완결된 목적지 Nav 스택으로 취급하지 않는다.

공원에서는 보기 좋은 복원 화면과 로봇이 실제로 접촉하는 충돌 메시, 센서가 관측하는 표면을 대조한다. 평지에서 검증한 기능을 공원 일부 코스로 옮기고, 턱·경사·잔디·gap의 취급을 정한다. 3D 센서를 쓴다고 2D 비용 지도가 모든 험지를 표현하게 되는 것은 아니다.

**완료 기준.** 지도와 추정 궤적을 남기고 정답 위치가 어느 모듈에 들어갔는지 표로 밝힌다. 정답 위치를 사용한 구성과 센서 추정 구성을 구분해 드리프트·지도 겹침·위치 추정 상실을 평가한다. 선택 알고리즘의 입력 형식·ROS 버전·IMU 필요 여부를 확인한 뒤 구현을 확정한다.

### S6. 실제 센서와 순정 Go2 보행으로 통합

**배울 것.** 센서 드라이버·장착 외부 파라미터·시간 동기화, 실기 속도 명령 인터페이스, 시뮬과 다른 조명·노이즈·지연·보행 흔들림.

**실습.** 실물 RGB·깊이·XT-16·L1 중 접근 가능한 출력을 확인하고 정지 상태에서 기록한다. 저장 로그로 S1·S2를 재검증한 뒤, Nav 담당과 순정 보행의 속도 명령 및 정지 기능을 연결한다. 이후 제한된 평지 코스에서 목적지 이동, 사람 대응, 장애물 우회를 차례로 검증한다.

**완료 기준.** 실제 센서 모델·사용 출력·좌표계·갱신률·제어 인터페이스가 기록되고, 시뮬과 실기 차이를 설명할 수 있다. 검출 시연과 실제 제어 시연을 구분한 영상·로그를 제출한다. `foothold-v1.pt`의 실기 이전이나 새 RL 학습은 이 단계의 기본 요구가 아니다.

S5·S6의 1차 공동 통합은 팀의 `NAV 11/7` 관문에 맞추고, 이후 최종발표까지 재현성과 시연 구성을 보완하는 배정안이다. 실제 착수·완료일은 장비 접근 일정과 Nav 담당의 통합 일정에 따라 확정한다.

### 중간발표까지의 배정안

하루 집중 실습 약 3시간을 확보한다는 가정이며 개인 사정과 설치 시간을 반영해 조정한다. 날짜가 왔다고 미통과 단계를 완료 처리하지 않는다.

|---|---|---|
| 9/16~18 | S1 설명표, S2 검출 모델 비교(§3), S3 속도 실측 1단계(§4 평지) | 센서별 출력·정책 입력 설명표, 모델 비교표, 0.5 대 1.0 평지 추종표 |

## 3. 검출 모델 재선정 계획

### 현재 사용 모델 (코드와 실행 기록으로 확인)

| 항목 | 값 | 근거 |
|---|---|---|
| backend | torchvision (`detector.py` 의 `backend="torchvision"` 기본값) | 코드 |
| 모델·가중치 | `fasterrcnn_resnet50_fpn_v2`, `FasterRCNN_ResNet50_FPN_V2_Weights.COCO_V1`, 사람 = COCO label 1, `box_score_thresh` 0.5 | 코드 · 런 `manifest.json` 의 `detector` |
| 실행 환경 | torch 2.7.0+cu128 · torchvision 0.22.0+cu128 · cuda | 런 `manifest.json` |
| 추론 주기 | 5 스텝마다(스텝 0.02s → 10Hz) | 코드 `--detect_every 5` |
| 추론 시간 | 평균 32.8 / 34.2 / 41.7 ms (통로 최종 3런의 `t_infer_ms_mean`) | 런 `manifest.json` |
| GPU 메모리 | `미측정` | 런 기록에 항목 없음 |
| 대안 backend | `ultralytics`(YOLO) 분기가 코드에 있으나 실행 환경에 패키지 미설치, 통로·사람 정지 실험에서 사용 0회 | 코드 주석 · 런 기록 |

`확인됨`. 사람 정지 4런 중 정지 확인 1런(`run01b_stopcheck`)은 detector 미사용(`manifest.json` detector=null)이고, static·control·cross 3런과 통로 3런의 `manifest.json` 이 같은 detector 항목을 기록한다.

### 비교 계획

**동일한 저장 영상**(사람 정지 횡단 런과 통로 코스 B 런의 로봇 RGB 프레임과 정합된 깊이)에서 현재 모델과 가벼운 대안을 오프라인으로 비교한다. 폐루프 주행을 다시 돌리지 않고 같은 입력으로 재는 것이 목적이다.

| 후보 | 추가 설치 | 비고 |
|---|---|---|
| (기준) torchvision `fasterrcnn_resnet50_fpn_v2` | 없음 | 현재 사용 |
| torchvision `fasterrcnn_mobilenet_v3_large_fpn` | 없음 | 같은 API, 가벼운 backbone |
| torchvision `ssdlite320_mobilenet_v3_large` | 없음 | 1단계 검출기 |
| ultralytics YOLO 계열(예: `yolo11n`) | pip 설치 필요 | 후보일 뿐이며 이름으로 우수하다고 확정하지 않는다 |

| 비교 지표 | 측정 방법 |
|---|---|
| 검출 누락·오검출 | 정답 사람 가시 프레임 대비 recall, 사람 없는 프레임의 오검출 수(기존 평가 스크립트의 GT 가시성 판정 재사용) |
| 거리 추정 | 박스 안 유효 깊이로 계산한 전방 거리와 정답 거리의 오차 중앙값(현재 기준 0.111m) |
| 지연 | 프레임 수신부터 박스 출력까지 ms, 모델 추론만의 ms 를 구분 |
| GPU 메모리 | 추론 중 최대 할당량 |
| 전체 제어 반응 | 선정 모델 1개만 폐루프 1런(사람 정지 횡단 시나리오)으로 STOP 판정 시각·정지 거리 비교 |

**선정 규칙.** 누락·오검출이 기준 모델보다 나쁘지 않으면서 지연·메모리가 작은 후보를 고른다. 지표가 갈리면(예: 빠르지만 누락 증가) 바꾸지 않고 표로 남긴다. 새 모델 학습은 이 계획의 우선 요구가 아니다. **현재 비교 결과는 `미측정` 이며, 비교가 끝나기 전에는 기준 모델을 유지한다.**

## 4. 목표 명령 속도 1.0m/s 실측 계획

목표 명령 속도는 **1.0m/s** 다. 기존 0.5m/s(사람 정지 실험의 기본값)와 0.35m/s(통로 실험의 기본값)는 비교 기준으로 보존한다. **명령 속도와 실제 속도는 다르다.** 지금까지 실측한 명령 값은 0.25·0.35·0.50 뿐이고, 1.0m/s 에서는 추종비·자세·제동 거리 모두 `미측정` 이다. 검증 전에는 1.0m/s 를 어느 지형의 확정 운용 속도로도 쓰지 않는다.

### 기존 실측 (비교 기준, 명령 0.5m/s 이하)

| 지형 | 명령 vx | 실측 후반 평균 | 추종비 | 비고 |
|---|---|---|---|---|
| 평지 | 0.25 / 0.35 / 0.50 | 0.236 / 0.322 / 0.475 | 0.94 / 0.92 / 0.95 | roll·pitch 6.2° 이하 |
| 요철 ±0.06m | 0.25 / 0.35 / 0.50 | 0.236 / 0.329 / 0.432 | 0.94 / 0.94 / 0.86 | pitch 최대 19.4° |
| 평지 정지 | 0.50→0 | 0.4s 안에 정지 | | **2.7s 뒤 넘어짐** 1회 |
| 평지 정지 | 0.35→0→0.35 | 정지 0.18s·0.025m, 3s 유지 정상 | | |
| 요철 정지 | 0.50→0→0.50 | 정지 0.18s·0.041m, 3s 유지 정상 | | |
| 평지 옆걸음 | vx 0, vy 0.2 | 1.5s 뒤 넘어짐 | | vx=0 순수 옆걸음·제자리 회전 명령은 쓰지 않음 |
| 사람 정지(FSM 감속 포함) | 0.5, STOP 판정→정지 | 2.34s · 0.291m | | 정지 판정 후 `\|vx\|<0.05` 25스텝 유지 기준 |

`확인됨` 근거: §10 통로 실험 README 3a 표와 사람 정지 횡단 런 `result.json`. 명령 0 직접 투입(0.18s)과 FSM 감속 램프를 거친 정지(2.34s)는 정의가 달라 같은 값으로 비교하지 않는다.

### 실측 순서

| 단계 | 조건 | 재는 것 | 다음 단계 조건 |
|---|---|---|---|
| 1 평지 직진 | 명령 0.5 와 1.0, 각 8s 이상 | 실측 vx 평균·추종비, roll·pitch 최대, z 최소, 낙상·리셋 | 1.0 에서 낙상 0 |
| 1 평지 회전 | vx 0.5·1.0 + wz 0.2·0.4 | 실측 wz·추종비, 궤적 반경, 벽 여유 | 넘어지지 않음 |
| 1 평지 정지·재출발 | 0.5→0, 1.0→0, 8s 유지 후 재출발 | 정지 지연·이동 거리, 정지 유지 중 자세(평지 넘어짐 재현 여부), 재출발 지연 | 정지 중 낙상 원인 정리 |
| 2 제동 거리 재측정 | 1.0 에서 인식 지연(검출 주기 0.1s + 추론 ms) + 제어 지연 + 제동 거리 | 정지 명령 시점과 실제 정지 시점의 거리 | `d_slow`·`d_stop` 재설정 |
| 2 정지·감속 구간 조정 | 현재 `d_stop` 1.5m / `d_slow` 3.0m(통로), 2.0m(횡단 런) | 1.0 의 제동 거리 + 여유로 다시 정함 | 값과 근거를 표로 |
| 3 장애물 | 원기둥 좌·우 여유 | 우회 최소 거리, 접촉 | 접촉 0 |
| 3 gap·rail | 0.20m 틈, 0.14m 레일 | 통과·추락·걸림, 속도별 | 실패해도 기록(원인 미확정, 메시·제어 조건별로 분리 기록. 정책 수정은 이 계획 밖) |

### 시나리오 분리

한 영상으로 뭉뚱그리지 않고 아래를 각각 조건·판정 기준을 정한 뒤 잰다. 반복은 조건별 3회를 기본으로 하되 탐색용 최소 반복이며 통계적 보장이 아니다.

| 시나리오 | 확인할 것 | 판정 |
|---|---|---|
| 멀리 보이는 사람 | 경로 밖·먼 거리의 사람 때문에 무조건 멈추지 않는지 | 감속·정지 사유 로그, 통과 시간 |
| 정지한 사람 우회 | 통로가 있으면 감속 통과, 없으면 정지 | 접촉 0, 최소 거리, 정지 영구화 없음 |
| 좌우 여유 공간 | 여유가 왼쪽·오른쪽·양쪽일 때 경로 선택 | 관측에 따라 경로가 바뀜 |
| 막힌 길 정지 | 통과 공간이 없을 때 | 정지 유지, 벽·물체 접촉 0 |
| ㄱ자 주행 | 회전 시각을 손으로 주지 않고 목적지 도달 | 도달 오차, 접촉, 시간 |

1.0m/s 에서 실패하면 실패로 기록하고, 통과한 속도 범위만 그 지형의 시험 속도로 적는다. 실패를 숨기거나 낮은 속도의 성공을 1.0 의 성공으로 쓰지 않는다.

## 5. 실행 환경과 제약

| 작업 | 우선 사용할 환경 | 시작 전 확인 | 막혔을 때 가능한 일 |
|---|---|---|---|
| 문서·배열 해석·ROS2 기초·검출 모델 오프라인 비교 | 로컬 PC, 기존 Python/ROS2 환경 | OS·Python·ROS 배포판, 저장 파일 읽기, GPU 사용 가능 여부 | 저장 이미지·NPZ·CSV로 S1·§3 진행 |
| Isaac Sim 센서 렌더·보행 재생·속도 실측 | 기존 재현 환경을 갖춘 GPU/RunPod | GPU·드라이버·Sim/Lab 버전·확장·체크포인트·실행 명령, 살아 있는 다른 작업 | 기존 캡처로 인식·시각 분석. 새 주행 성공으로 표시하지 않음 |
| ROS2 Bridge·Nav2 | 선택 배포판과 호환되는 별도 프로세스/환경 | `/clock`, 시뮬 시간, TF, QoS, DDS 검색·네트워크 연결 | 한 기계에서 최소 발행/구독부터 확인 |
| 실제 센서·Go2 | 실제 장비와 드라이버 환경 | 센서 SKU·지원 출력·ROS 버전·제어 권한·사용 일정 | 로그 제공을 받아 오프라인 검증 |

기존 프로젝트의 기준 버전은 Isaac Sim 5.1.0 / Isaac Lab 2.3.2이다. 2026-09-16 실행 환경에는 ROS 2·Nav2·ultralytics 가 설치되어 있지 않았고(실험 README 기록), GPU 사양·실시간 성능은 이 문서에서 재측정하지 않았다. 새 실행마다 버전·장비·FPS·센서 주기를 기록한다. 시뮬에서 10Hz로 저장했다고 실제로 서로 다른 센서 관측이 초당 10개라고 가정하지 않는다. Isaac 인스턴스를 여러 개 동시에 띄우면 CUDA 메모리 부족이 실제로 났으므로(6개 동시 실행 중 1런 무결과) 동시 실행 수를 제한한다.

ROS 배포판은 현행 팀 문서에 Jazzy 계열 수업 설명과 Humble 기반 아키텍처 설명이 함께 남아 있으므로 일괄 변경을 제안하지 않는다. 실제 실기 드라이버·수업·Sim Bridge 조합을 확인하고 그 조합을 고정한다. [Isaac Sim 5.1 ROS2 설치 문서](https://docs.isaacsim.omniverse.nvidia.com/5.1.0/installation/install_ros.html)를 해당 버전 기준으로 대조한다. 서로 다른 Python용 패키지를 한 런타임에 무조건 import하는 방식은 피한다.

DDS 벤더가 다르면 반드시 통신 불가라고 단정하지 않는다. 도메인·QoS·인터페이스·방화벽·검색·메시지 호환을 실제 발행/구독으로 확인한다. 과거 아키텍처 문서의 강한 단정을 이 계획의 확인된 사실로 옮기지 않는다.

학습과 센서 렌더를 동시에 실행하면 자원 경합이 생길 수 있으므로 RL 담당의 실행과 GPU 사용 시간을 조율한다. headless는 GUI를 띄우지 않는다는 뜻이지 RGB·RTX를 얻기 위한 렌더가 필요 없다는 뜻이 아니다. GPU 가 꺼져 있어도 로컬 저장 데이터로 S1·S2 학습과 §3 오프라인 비교는 진행할 수 있다.
