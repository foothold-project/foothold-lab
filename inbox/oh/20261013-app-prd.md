## 1. 무엇을 왜 올리나

노트북과 휴대폰에서 로봇을 조종하고 임무를 관리하는 앱을 만들면서, 2026-10-12 에 방향을 두 문서로 정리했다. 지금까지는 시뮬 조종·목표 이동·STOP 같은 기반 작업을 진행 보고로만 공유했고, **무엇이 완성이고 어떤 순서로 가는지**를 팀이 볼 수 있는 문서가 없었다. 이 제출은 그 두 문서와, 두 문서가 기능 ID·검수 기준을 가져오는 문서팩(①~⑦ 등 10개)의 사본이다.

| 문서 | 역할 | 첨부 |
|---|---|---|
| 기획서 | 무엇을, 왜, 어떤 순서로 만드는지 쉬운 말로 정리한 상위 기획 | [PRODUCT-PLAN.md](20261013-app-prd/PRODUCT-PLAN.md) |
| PRD(제품 요구사항) | 기획서 방향을 요구 ID·검수 기준·현재 상태로 나눈 검수용 문서 | [PRD.md](20261013-app-prd/PRD.md) |

두 문서는 같은 방향을 다른 깊이로 쓴다. 기획서가 근거이고 PRD 가 그것을 검수 가능한 단위로 쪼갠 것이다. 두 문서 모두 같은 날 앱 검수 담당(Codex)의 읽기 검수 2회를 반영한 첫 판이다.

## 2. 읽는 순서

1. **기획서 1장 「무엇을 만드나」**: 앱이 하는 일 다섯 가지(보기·움직이기·멈추기·임무 운영·기록)와 완성 조건.
2. **기획서 9~10장**: 만드는 순서 6단계와 2026-10-12 12시 기준 진행 상태.
3. **PRD 0~1장**: 종료 조건 세 가지와 표 읽는 법(우선·구분·현재 낱말).
4. **PRD 3~12장**: 묶음별 요구 표. 관심 있는 묶음만 골라 읽어도 된다.
5. **PRD 13~14장**: 작성 시점 진행 중 작업과 개발 순서·관문.
6. **이 글 4~5장**: 첨부 작성 시점(10-12 12시) 뒤의 진행(4장 10-13, 5장 10-14 기술 스택·현황). 첨부와 출처가 다르다.

## 3. 핵심 내용 요약

### 완성 조건 (두 문서 공통)

아래 셋이 모두 통과해야 완성이다. 하나라도 빠지면 완성이 아니다. `확인됨`(PRD 0장·기획서 1장 원문 대조)

| 조건 | 내용 |
|---|---|
| PC 필수 화면 | 뎁스 영상, SLAM 누적 3D 점군, 로봇 상태 창, 지도가 PC 에서 검수 통과 |
| 휴대폰 필수 화면 | 가로 카메라 전체 화면, 왼쪽 회전 막대, 오른쪽 앞뒤 막대, 지도, 후진이 **실제 휴대폰**에서 검수 통과 |
| 첫 현장 임무 | 정한 첫 임무를 **실기 Go2**로 현장 조건에서 반복 통과 |

시뮬 통과·에뮬레이터 통과·«화면이 뜬다»는 완성이 아니다. 첫 로봇은 Go2 이고 다른 로봇은 그다음이다. 수익화·가격·시장은 두 문서 모두 범위 밖(추후 검토)이다.

### 요구 ID 체계 (PRD)

요구 ID 는 `R-묶음-번호` 이고 PRD 에 44개가 있다. `확인됨`(PRD 표 행 수 집계)

| 묶음 | 뜻 | 개수 | 우선 |
|---|---|---|---|
| R-SF | 안전·조종권 | 6 | P0 |
| R-RB | Go2 연결 | 3 | P0 (R-RB-03 다른 로봇은 P3) |
| R-PH | 휴대폰 화면·조작 | 6 | P1 |
| R-PC | PC 화면 | 4 | P1 |
| R-SN | 센서·시각 | 2 | P1 |
| R-MP | 지도·목표 이동·층 | 4 | P2 |
| R-MS | 임무·기록 | 6 | P2 (R-MS-06 첫 현장 임무는 P0) |
| R-NF | 비기능(정지 성능·영상 지연 등) | 8 | 수치 미정, 측정 방법과 고정 시점만 정함 |
| R-AI | AI·분석 | 2 | P3 |
| R-AP | 앱 형태(웹·설치형) | 3 | P1~P3 |

우선은 P0 = 안전·Go2 연결 기반, P1 = 필수 화면·조작, P2 = 지도·임무·기록, P3 = 후속이다. 기존 기능 ID(예: DRV-3, NAV-5)는 별도 기능정의서의 것이며 `R-` ID 는 그 위의 상위 요구다.

### 확정 · 제안 · 미정 · 후속 구분

PRD 의 각 요구 끝 괄호에 구분이 붙어 있다. 이 구분을 그대로 옮긴다. `확인됨`(PRD 표 원문 집계)

| 구분 | 뜻 | 해당 요구 |
|---|---|---|
| 확정 | 사용자가 정한 요구 | 44개 중 29개는 확정만 붙음 |
| 제안 | 확정 요구를 구현하려고 앱 담당 mentor 가 낸 설계안. 사용자가 직접 확정한 것이 아님 | R-PH-03(손가락 규칙), R-PC-04(패널 접기), R-SN-01(시각 표시 방식), R-SN-02(실기 센서 조합), R-NF-06(인증서·계정) |
| 미정 | 수치나 방식을 아직 정하지 않음 | R-SF-06(장비 STOP 계약), R-NF-01~05·07(정지 성능·영상 지연·점군·부하·배터리·기록 보존) |
| 확정과 제안·미정이 섞인 것 | 한 행 안에서 부분별로 다름 | R-PH-06(반투명·STOP 상시는 확정, safe area·대체 배치는 제안), R-MP-01(목표 이동 흐름은 확정, 경로 미리보기는 제안), R-MP-04(점군 보기와 층간 이동 분리는 확정, 다른 층 목적지 이동은 P3 미정) |
| 후속(P3) | 지금 순서 밖. 별도 설계 뒤 | 다른 로봇(R-RB-03), SpatialLM 선택 사용(R-AI-01), AI 목표물 인식(R-AI-02), 설치형 클라이언트(R-AP-02), iOS 설치 파일(R-AP-03), 다른 층 목적지 이동(R-MP-04 일부) |

### 현재 상태 (2026-10-12 12시 기준)

PRD «현재» 칸에서 «검증»은 4개뿐이고 전부 시뮬·에뮬레이션 전제다. `확인됨`(PRD 원문) 10-13 진행은 이 표를 바꾸지 않고 4장에 따로 적었다.

| 요구 | 현재 | 전제 |
|---|---|---|
| R-SF-01 로그인·조종권 한 명 | 검증 | Gazebo·로컬 |
| R-SF-02 명시 버튼으로만 조종권·해제 | 검증 | Gazebo |
| R-MS-02 도착 → 현장 확인 → 기록 | 검증 | TB3 시뮬 |
| R-AP-01 PC·휴대폰 공통 웹 화면 | 검증 | Gazebo·에뮬레이션 |

나머지는 부분·미충족·미구현·미착수다. 특히 아래는 원문에서 미구현·미검증으로 적혀 있다. `미검증`

- 앱 STOP 에 Go2 가 실제로 멈추는지: 미검증. 앱↔Go2 시뮬 연결은 사본 코드와 순수 모의 시험만 있다.
- 두 엄지 조작 화면(R-PH-02): 미구현. 지금 화면의 «두 번째 손가락 → 전부 해제» 규칙과 충돌해 R-PH-03 은 «미충족»으로 적혀 있다.
- PC 뎁스 영상·3D 점군(R-PC-01·02): 미구현.
- 후진(R-PH-04): 화면 입력·서버 설정은 있으나 운영 기본 꺼짐, Go2 시뮬 경로는 거부, Go2 후진 미검증.
- Go2 목표 이동(R-MP-01): Go2 쪽은 열지 않았다.
- 실기 Go2·현장(R-MS-06): 미착수.

| ② 같은 건물 아래 1층·2층 지형과 층별 지도 저장·선택 | 지도 이미지·경로·크기 상한·저장 계약 조사 |

### 5-4. 논의 중인 장기 방향 (제안, 구현 승인 아님)

설명 단계에서 나온 방향이며 새 기능이나 일정으로 확정한 것이 아니다.

- **시뮬별 어댑터**: 공통 웹·앱 → 공통 인증·조종 서버 → 시뮬별 어댑터(Gazebo·Isaac·MuJoCo 등) 구조. 상태·단위·좌표·시간·지원 기능을 공통 규격으로 두고 대상마다 명령·STOP·리셋을 검증한다. 지금 계약·문구·±10 m 지도·평면 기준 정답 위치·시험 속도는 Gazebo 전용 가정이라 범용 연결기는 없다.
- **웹 지형 편집**: PC 웹에서 계단 높이·경사·요철·크기·seed 를 설정·미리보기·저장하고 PC·GPU 서버에서 실행, 휴대폰은 조종·결과 확인. 공통 지형 설정을 시뮬마다 변환한다. 기존 Isaac 지형 생성 코드는 재사용 후보이고 웹 편집기는 미구현이다.
- **유의: 지형 입력 불일치**: 지금 Gazebo 보행 정책의 지형 입력은 평면 가정(flat_plane_gt)이다. 지형 충돌체만 바꾸고 높이 관측을 평면으로 두면 정책 입력과 실제 지형이 어긋나므로, 스캔·지형 입력 계약을 함께 고치고 검증해야 한다.
- 우선순위 메모: 화면 19개는 제품 완료가 아니다. 실제 조종 중 앱 숨김·복귀·몸 정지 검증, iOS 빌드·실폰 경로 조기 확인, 개발 APK와 최종 배포판 구분이 먼저다.

## 7. 미확인 · 한계

- **작성 시점 고정**: 첨부 문서의 상태는 2026-10-12 12시 기준이다. 그 시각 진행 중이던 Go2 시뮬 정지 시험 2차(c2)와 앱↔Go2 시뮬 연결 수정은 첨부 안에서는 «진행 중»으로만 적혀 있다. 그 뒤 진행은 4~5장에 따로 적었고 첨부 본문은 고치지 않았다.
- **가상 Go2 두 종류**: 첨부의 «Gazebo Go2 시뮬(A2)»(저수준 보행 컨트롤러 + 정지 관문)과 4장의 «foothold-v2 정책 Gazebo 가상 Go2»는 서로 다른 시뮬 대역이다. 4장 결과를 A2 정지 시험(c2) 결과로 읽으면 안 된다.
- **검증 전제**: «검증»은 Gazebo(TB3 바퀴 로봇 대역) 또는 헤드리스 Chrome 에뮬레이션 전제다. 실기 Go2·실제 휴대폰·현장 전제로 검증된 요구는 없다. 검수 통과는 실기·현장 실행 승인이 아니다.
- **Gazebo Go2 시뮬(A2)은 시뮬 대역**이다. 그 저수준 보행 컨트롤러를 실기에 옮기는 계획이 아니며, 실기 Go2 는 내장 보행 위에 SDK 고수준 명령만 보내는 계획이다.
- **비기능 수치 없음**: 정지 시간·거리, 영상 지연, 점군 밀도 등은 측정 방법과 고정 시점만 정했다. `미측정`
- **실기 센서 미확정**: D435i·L1·XT-16 조합은 제안이다. 실제 접근·장착이 확정된 뒤 요구로 올린다.
- **근거 원물 비공개**: PRD 13장과 문서팩이 드는 근거(앱 검토 기록·실험 폴더)는 작성자 로컬 기록이며 팀 열람 링크는 없다. 사본에서는 경로를 «작성자 로컬 기록»으로 바꿨다.
- **구현 상태 낱말의 시점**: 문서팩 ①~⑦은 10-06~10-08 에 쓰고 10-12 까지 고친 판이라, 문서마다 «구현»·«미구현» 낱말의 기준 날짜가 다를 수 있다. 각 문서 머리의 작성일을 함께 본다.
