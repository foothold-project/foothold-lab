## 한눈에

| 구간 | 무엇이 오가나 | 맡는 곳 |
|---|---|---|
| 운영자 화면(노트북·폰) → PC 서버 | 명령(command_id) | 임무 진행 화면은 보여 주기만 하는 층이다. 화면 표시를 정본으로 믿지 않는다 |
| PC 서버 안 | 누가 보냈나 확인 | phone_gate: 계정 확인, 신원 첨부 |
| PC 서버 안 | 임무 상태·기록의 정본 | mission_executor(SQLite) |
| PC 서버 → 화면 | 상태 사진(snapshot) + 사건(event) | mission_executor |
| PC 서버 → 로봇 | 이동 | app_gateway(STOP·제어권) → 다리 |
| PC 서버 → 장비 | 장비 명령 | 장비 어댑터 → 장비 |

- **정본은 서버**다. 화면은 서버 상태를 비추기만 한다. 앱을 닫거나 폰이 꺼져도 임무 상태는 서버에 남는다.
- 화면은 «바라는 것»을 보낸다. 실행할지는 서버가 정한다. 거절하면 이유를 돌려준다.
- **이동 안전**(STOP·제어권·누름 확인)은 지금처럼 `app_gateway` 가 맡는다. 임무 계층은 그 위에 얹고, 안전 판단을 우회하지 않는다.

## 1. 다루는 것 (데이터)

| 이름 | 무엇 | 핵심 필드 |
|---|---|---|
| **임무 양식** (template) | 미리 만든 임무 순서. 운영자는 고르기만 한다 | `template_id`, `version`, `title`, `steps[]`, `needs[]`(필요한 능력 목록) |
| **임무** (mission) | 양식으로 시작한 실제 한 번 | `mission_id`, `template_id@version`, `state`, `rev`(바뀔 때마다 +1), `current_step`, `created_by`, `created_at` |
| **단계** (step) | 임무의 한 칸 | `index`, `kind`, `params`, `confirm`(운영자 확인 필요?), `timeout_s`, `on_fail`, `optional` |
| **시도** (attempt) | 한 단계를 실제로 한 번 실행한 것. 다시 하면 새 시도 | `attempt_id`, `step`, `started_at`, `ended_at`, `result`, `evidence[]` |
| **명령** (command) | 운영자가 누른 버튼 하나 | `command_id`(화면이 만든 UUID), `mission_id`, `expect_rev`, `op`, `args`, `operator_id`(서버가 붙임), `device_id` |
| **능력** (capability) | 로봇·장비가 «할 수 있다고 검증된» 동작 | `cap_id`, `adapter`, `verified`(근거 경로), `safety`(motion / equipment / hazard), `params_schema`, `stop_contract` |
| **사건** (event) | 모든 변화의 기록. 지우거나 고치지 않는다 | `seq`, `t`, `mission_id`, `type`, `by`, `command_id`, `data` |

### 단계 종류 (`kind`) - 분야와 무관한 공통 6개
| kind | 뜻 | 끝나는 조건 | 지금 있는 것 |
|---|---|---|---|
| `prepare` | 투입 전 점검(연결·위치·센서·장비·배터리) | 필수 항목 모두 통과 | 단계로는 없음. 시작 조건(제어권·정지 해제·지도)만 화면에서 확인 |
| `move_to` | 지점·경유지로 이동 | Nav2 성공 **+ 위치 오차 확인** | **구현**(gateway 경유, 오차 0.5 m - MIS-3·NAV-3) |
| `observe` | 현장 확인(영상·센서 보기) | 운영자가 «확인» 또는 자동 판정(검증된 것만) | 없음(영상 F3) |
| `operator_check` | 사람이 판단해 고른다(계속/다시/중단) | 운영자 선택 | **구현**(F2, `missions.json` check_point 2단계 - MIS-4) |
| `equipment` | 장비 작업 | 장비 어댑터가 «완료+결과» 보고 | 없음(장비 미정). 양식은 있으나 능력 미검증이라 시작 거절(CAP-2) |
| `return` | 철수·복귀 | 복귀 지점 도착 | **구현**(출발 위치로, MIS-3) |

`equipment` 단계는 그 능력이 `verified` 로 등록돼 있지 않으면 **임무 시작 자체를 막고** 이유를 보여준다(아래 4).
[현재] 서버가 실행하는 kind는 `move_to`·`operator_check`·`return` 셋이다. 나머지는 «지원하지 않습니다»로 실패 처리한다.

## 2. 상태와 전이

### 임무 상태

| 지금 상태 | 일 | 다음 상태 |
|---|---|---|
| READY | 시작 | RUNNING |
| READY | 취소 | ABORTED(사유 기록) |
| RUNNING | 마지막 단계 성공 | SUCCEEDED |
| RUNNING | 일시정지, 또는 운영자 확인 대기·실패·timeout·연결 끊김·서버 재시작 | PAUSED |
| PAUSED | 계속(운영자) | RUNNING |
| PAUSED | 중단(운영자) | ABORTED(사유 기록) |
| RUNNING | on_fail=abort 인 단계 실패 | FAILED |

| 상태 | 화면에 쓰는 말 | 로봇은 | 누가 바꾸나 |
|---|---|---|---|
| `READY` | 준비됨 (**화면의 선택 단계** - 서버 상태 아님) | 정지 | 운영자(시작) |
| `RUNNING` | 진행 중 | 단계 실행 | 서버 |
| `PAUSED` | 멈춤 - 기다리는 중 (이유 함께) | **정지 유지** | 운영자(계속·중단) |
| `SUCCEEDED` | 완료 | 정지 | 서버 |
| `FAILED` | 실패 (이유) | 정지 | 서버 |
| `ABORTED` | 중단함 (누가·왜) | 정지 | 운영자 |

- [현재] 서버의 임무 상태는 `RUNNING`·`PAUSED`·`SUCCEEDED`·`FAILED`·`ABORTED` 다섯이다. 임무는 `mission.start`가 받아들여질 때 처음 생기므로 서버에 `READY`가 없고, 시작 전 «취소»도 서버 사건이 아니다.
- **자동 재개는 없다.** `PAUSED` 에서 다시 움직이는 길은 운영자가 «계속»을 누르는 것뿐이다. 서버가 다시 켜지면 `RUNNING` 이던 임무는 `PAUSED(서버 재시작)` 이 된다.
- 운영자 확인을 기다리는 것도 `PAUSED` 의 한 종류(`reason=await_operator`)다. 화면은 이것을 «확인해 주세요»로 다르게 보여준다.

### 단계(시도) 결과
`succeeded` · `failed(reason)` · `timeout` · `cancelled(by)` · `skipped(by)`(optional 단계만).
실패·timeout 때 할 일은 단계의 `on_fail` 이 정한다: `pause`(기본 - 운영자에게 묻는다) / `abort`(임무 실패) / `retry(n)`(이동처럼 다시 해도 안전한 것만, 최대 n번).
[현재] `on_fail`은 `pause`·`abort`만 있다. 다시 하기는 운영자가 «이 단계 다시 하기»를 누를 때만(MIS-8). 자동 `retry(n)`·`skipped`는 없다.

## 3. 명령 - 수락과 완료는 다르다

| 순서 | 방향 | 내용 | 뜻 |
|---|---|---|---|
| 1 | 화면 → 서버 | `{command_id, mission_id, expect_rev, op, args}` | 명령 |
| 2 | 서버 → 화면 | `ack {command_id, accepted \| rejected(reason)}` | 즉시 온다. 실행했다는 뜻이 아니다 |
| 3 | 서버 → 화면 | `event {seq, type: step_succeeded …}` | 실제로 끝났을 때 온다 |

| op | 언제 | 받는 조건 |
|---|---|---|
| `mission.start` | READY → RUNNING | 제어권 보유 + 점검 통과 + 필요한 능력 전부 verified |
| `mission.pause` | 진행 중 멈춤 | 제어권 보유 |
| `mission.resume` | PAUSED → RUNNING | 제어권 보유 + 멈춘 이유가 풀림(예: 연결 복구) |
| `mission.answer` | 운영자 확인 응답(계속/다시/건너뛰기/중단) | 그 질문이 아직 열려 있음 |
| `mission.abort` | 임무 중단 | 제어권 보유 |
| `stop` (기존) | **전체 STOP** | **누구나**(인증된 화면이면 제어권 없어도) - 지금 gateway 규칙 그대로 |

- **중복 방지**: 서버는 받은 `command_id` 를 기억한다. 같은 ID가 다시 오면(재전송·두 번 누름) **실행하지 않고 처음 ack 를 그대로 돌려준다.**
  - [현재, 10-07] ack·명령 사건·상태 사건은 한 트랜잭션으로 commit 되고, commit 뒤에만 ack·이동이 나간다(selftest 실패 주입). 같은 번호를 다른 주체·내용이 쓰면 거절. commit 뒤·이동 전 죽음은 재시작 때 PAUSED·자동 재개 없음. **Nav2·장비 쪽 «정확히 한 번 실행»은 보장·검증하지 않는다**(MIS-13, `5-system-design.md` §2-4).
  - [목표] 접수·상태 전이·기록을 한 번에 저장, 결과가 불분명한 명령은 자동 재시도하지 않고 운영자에게 묻는다. 장비 명령은 장비 쪽에도 중복 키·결과 조회가 있어야 한다.
- **낡은 화면 방지**: `expect_rev` 가 현재 `rev` 와 다르면 거절한다(`rejected: stale`) → 화면은 최신 상태를 다시 받아 보여준다. 예: 다른 폰이 이미 «다음»을 눌렀는데 내 화면이 늦게 같은 버튼을 누른 경우.
- `stop` 은 `expect_rev` 를 보지 않는다. 멈춤은 언제나 받는다.

## 4. 능력 등록 - «할 수 있다»는 증거가 있어야 버튼이 생긴다

```yaml
cap_id: move_to.nav2            # 예시 - 지금 실제로 있는 유일한 것
adapter: app_gateway/nav2
safety: motion
verified: 실험 기록(작성자 로컬 근거 기록, 팀 열람 링크 없음)   # 근거. 없으면 unverified
stop_contract: gateway STOP 래치 → /cmd_vel_mux 0 (S1 시험 §14)
```
- 등록이 없거나 `verified` 가 비면: 그 능력이 필요한 양식은 목록에서 **회색 + «이 로봇에서 아직 검증되지 않음: 장비 미연결»** 같은 이유를 보인다. 숨기지 않는다(운영자가 «왜 없지?»를 헤매지 않게).
- `safety: hazard`(분사 등 위험 장비)는 추가로 ① 장비 측 인터록 ② 전체 STOP 이 장비까지 멈춘다는 시험 기록 ③ 운영자 확인 방식(화면 흐름 문서의 «길게 눌러 실행»)이 모두 있어야 등록된다.

## 5. 멈춤 세 가지 - 이름을 섞지 않는다

| 이름 | 무엇이 멈추나 | 누가 | 풀기 |
|---|---|---|---|
| **일시정지** (`mission.pause`) | 임무 진행 + 이동(정지 유지) | 제어권 가진 운영자 | «계속» |
| **장비 중단** (`equipment.abort`) | 지금 장비 작업만 | 제어권 가진 운영자 / 장비 이상 시 서버 | 단계 다시 시도 또는 임무 결정 |
| **전체 STOP** (`stop`) | 이동 + 장비 전부, 임무는 `PAUSED(stop)` | **누구나** | «정지 해제» 후 임무는 따로 «계속» |

- [현재] **전체 STOP은 이동만 멈춘다.** 장비 어댑터·`equipment.abort`는 아직 없다(STP-3·4). 아래는 장비가 생길 때의 목표다.
- 전체 STOP 은 지금 gateway 래치(S1 §14 시험 통과)를 그대로 쓰고, 장비 어댑터에도 같은 순간 중단을 보낸다. 장비가 중단을 확인하지 않으면 화면에 «장비 중단 확인 안 됨»을 계속 띄운다(조용히 넘어가지 않는다).
- STOP 을 풀어도 **임무는 자동으로 다시 가지 않는다.** 두 단계(정지 해제 → 임무 계속)로 나눈 이유: 멈춘 원인을 운영자가 확인하고 다시 출발하게 하려고.

## 6. 운영자 신원 - 관문 로그인이 정하고, 화면 값은 믿지 않는다

- [현재, 10-07] 운영자는 관문(`ros/phone_gate.py`)에 **계정 + 비밀번호**로 로그인한다(서버에 scrypt 해시, IP별 실패 잠금, HttpOnly 쿠키 세션 8 h). 기기 id 는 **서버가 정해** 서명한 쿠키로 준다.
- [현재] 관문이 연결마다 `sid` 를 정하고, 명령에 sid·`actor`(계정·기기)를 붙여 서명한다. 화면이 보낸 sid·actor·`operator_id` 는 지운다. gateway·임무 서버는 서명만 권한 근거로 쓴다.
- [현재] 기록: 사건의 `by` = 그 sid(연결 단위), 명령 사건의 `actor` = 계정·기기(사람 단위). 남의 sid 를 적어도 조종·임무 명령이 안 된다(CTL-4·IDN-1·2, Gazebo fin-auth S1·fin-mission M1).
- [현재] 제어권(`owner`) = 관문이 정한 sid(+ 표시용 `owner_actor`). `take` 로 받고 `yield` 로 내려놓으며, 세션 만료·로그아웃이면 출력 0·정지 래치·주인 없음.
- [현재 한계] 실제 운영 계정 등록·실제 휴대폰 로그인은 아직 하지 않았다(시험은 일회용 fixture 계정).
- [목표 - 아직 없음] PIN 로그인, 장치 등록(처음 한 번 승인한 폰), 역할 권한(보기·운영·관리, IDN-3), 제어권을 (운영자, 장치) 단위로 넘기는 기록(IDN-4).
- [10-07 이전 기록] 휴대폰 관문은 공유 토큰 하나를 모두가 같이 썼고, sid 는 화면이 만든 값이라 검증되지 않았다 - 위 «현재»로 대체.
- 이 신원 계약은 이력·보고 화면(F4)이 기록 형식을 굳히기 전에 고정한다(`7-roadmap-decisions.md` D-3, 10-07 이행).

## 7. 저장과 다시 붙기

- **사건 기록(event log)이 정본**이다. SQLite 한 파일에 덧붙이기만 한다(수정·삭제 없음). 현재 상태는 사건을 순서대로 적용해 만든다.
  선택 이유: 표준 라이브러리(`sqlite3`)로 충분하고, 정전·재시작 후에도 남으며, «무슨 일이 있었나»를 그대로 재구성할 수 있다.
- 화면이 다시 붙으면: ① 현재 상태 사진(snapshot) ② 마지막으로 본 `seq` 이후 사건을 받는다 → **«끊긴 동안 있었던 일»** 을 화면에 보여준다(예: «12:03:41 연결 끊김으로 일시정지됨»).
  - [현재] snapshot은 `/app/mission` 토픽으로 오고(`/app/state`가 아니다), **최근 사건 40개·최근 임무 10개만** 담는다. 화면의 «끊긴 동안» 알림은 그중 30분 안·최근 6개 + «그 전 n건은 아래 임무 기록에». 그보다 오래된 것은 [10-07] 「임무 기록」의 seq 범위 페이지 조회(`page()`)로 끝까지 볼 수 있고 빠진 번호는 표시된다(REC-6).
  - [목표] seq 범위 요청 + 빠진 번호 표시 + DB 보존 기간·내보내기 기준(REC-6).
- 연결이 끊기면 로봇은 지금처럼 멈춘다(heartbeat 1.0 s → gateway 정지). 임무는 `PAUSED`, 이유 코드 `link`(gateway 정지 코드를 그대로 쓴다).

## 8. 감사 기록 - 사건 하나에 남기는 것

| 필드 | 예 |
|---|---|
| `seq`, `t`(서버 시각) | 1042, 2026-10-07T10:03:41.212+09:00 |
| `mission_id`, `step`, `attempt_id` | m-0007, 3, a-0007-3-2 |
| `type` | [현재] `created` · `step_started` · `step_done`(결과는 data) · `paused` · `resumed` · `answered` · `ended` · `command`(수락·거절 모두, data.ok) |
| `by` | [현재] 화면 sid / `server`. [목표] 운영자 ID + 장치 ID / `adapter:<이름>` |
| `command_id` | 운영자 명령이 원인이면 |
| `data` | 이유·위치·관측 근거(사진 경로·센서 값)·장비 결과 |

- [현재 한계] 기록은 SQLite 파일 권한으로만 보호한다. 해시 사슬·서명 같은 **변조 방지는 없다** - «지우거나 고치지 않는다»는 앱 코드의 약속이지 파일 수준 보장이 아니다(REC-1).

임무 «성공»은 명령이 도착했다는 것만으로 기록하지 않는다. 단계마다 **성공 근거**(도착 위치 오차, 운영자 확인, 장비 결과 보고)를 함께 남긴다.
