## 0. 종료 조건 (완성 제품)

아래 셋이 **모두** 통과해야 완성이다. 하나라도 빠지면 완성이 아니다.
첫 현장 임무만 통과하고 PC 필수 화면이 없으면, 그것도 완성이 아니다.

1. **PC 필수 화면 전체**가 PC에서 검수 통과: 뎁스 영상, 누적 3D 점군, 로봇 상태 창, 지도(R-PC).
2. **휴대폰 필수 화면 전체**가 실제 휴대폰에서 검수 통과: 카메라 전체 화면, 왼쪽 회전 막대, 오른쪽 앞뒤 막대, 지도, 후진(R-PH).
3. 정한 첫 현장 임무를 **실기 Go2로 현장 조건에서 반복** 통과(R-MS-06).

## 1. 읽는 법

- 각 절은 먼저 그 묶음의 **공통 전제·정상 동작·실패 동작**을 짧게 쓰고, 표에는 요구별 차이만 둔다.
- 표의 «요구» 칸 끝 괄호는 (우선 · 구분)이다.
  - **우선**:
    - P0 = 안전·Go2 연결 기반
    - P1 = 필수 화면·조작
    - P2 = 지도·임무·기록
    - P3 = 후속
  - **구분**:
    - **확정** = 사용자가 정한 요구
    - **제안** = 확정 요구를 구현하려고 mentor가 낸 설계안. 사용자가 직접 확정한 것이 아니다
    - **미정** = 수치나 방식을 아직 정하지 않음
- «현재» 칸은 [문서팩 안내](0-docpack-guide.md)의 상태 낱말을 쓴다: 검증·구현·부분·미충족·미구현·미검증·미측정.
- **검증의 전제를 넓히지 않는다.** 시뮬·에뮬레이터·헤드리스 Chrome 통과를 실기·실제 휴대폰·현장 통과로 쓰지 않는다.
- **검수 통과는 실행 승인이 아니다.** 실기 Go2·현장 시험은 따로 승인을 받는다.
- 기존 기능 ID(예: DRV-3)는 [④ 기능정의서](4-product-functional-spec.md)의 것이다. `R-` ID는 그 위에 놓이는 상위 요구다.

## 2. 시스템 연결 개요

| 흐름 | 내용 |
|---|---|
| 명령 | PC 웹 / 휴대폰 웹 → (로그인·서명 명령) → 관문 + gateway(로봇 PC) → (속도 명령) → 로봇 쪽 연결 → 로봇 |
| 판단 | 조종권·STOP·끊김 판단은 관문 + gateway(로봇 PC)가 한다 |
| 화면으로 오는 것 | RGB / 뎁스 / 점군 / 지도 / 상태. 센서 → 로봇 PC → 화면 |

| 로봇 쪽 연결 | 내용 |
|---|---|
| 실기 Go2 (계획) | Go2 내장 보행 + SDK 고수준 명령(이동·정지)만 쓴다 |
| Gazebo Go2 시뮬(A2) | 시뮬 대역. 저수준 보행 컨트롤러 + 정지 관문 두 계층 |
| Gazebo TB3 | 지금 앱 기능 시험용 대역(바퀴 로봇) |

- **A2는 시뮬 대역이다.** A2의 저수준 컨트롤러를 실기 Go2에 옮겨 심는다는 뜻이 아니다. 실기는 Go2 내장 보행 위에 고수준 명령만 보낸다. 오프라인 어댑터만 있고, 실기 연결은 없다.
- 영상 흐름(RGB·뎁스·점군)과 운영 명령 흐름(조종·목표·STOP)은 **따로 다룬다**. 영상이 느려져도 명령 판단은 로봇 PC에서 돈다.
- 어떤 센서를 실기에 장착할지는 **확정되지 않았다**(R-SN-02).

## 3. 안전·조종권 (P0)

**공통 전제**:
- 관문 로그인을 거친다.
- 안전 판단은 로봇 PC의 gateway가 한다. 브라우저는 믿지 않는다.

**상태별 목표 동작**:

| 상황 | 목표 동작 |
|---|---|
| 정상 손 뗌 | 앱이 즉시 0을 보낸다. 조종 준비 상태 유지 |
| 손 뗌 0 메시지 유실 | 서버 deadman(0.3 s)이 0으로 만든다. 조종 준비 상태 유지 |
| 화면 신호(heartbeat) 끊김 · 영상 장애 | 정지 + 잠금(장애 STOP). 사람이 해제할 때까지 움직이지 않음 |
| 재접속 · 서버 재기동 | 잠긴 상태로 시작. 자동 재개 없음 |

- 시한 값(0.3 s, 1.0 s)은 **구현 설정**이다. 현장 정지를 보증하지 않는다.

| ID | 요구 (우선 · 구분) | 검수 기준 | 현재 |
|---|---|---|---|
| R-SF-01 | 로그인한 사람만 조종, 조종권자는 한 명 (P0 · 확정) | 위조 sid·재생 서명·로그아웃 뒤 명령 거부 | 검증(Gazebo·로컬) |
| R-SF-02 | 조종권 받기·내려놓기·정지 해제는 명시 버튼으로만 (P0 · 확정) | 받기 직후 출력 0, 해제 없이는 안 움직임 | 검증(Gazebo) |
| R-SF-03 | STOP은 누구나, 항상 보임 (P0 · 확정). «누구나» = 관문에 연결해 앱을 보는 운영자·보기 전용 사용자. 미인증 인터넷 접속은 아님 | 모든 화면·패널 상태에서 보이고 눌림. 3D 화면 실패를 주입해도 동작 | 부분(2D 화면만) |
| R-SF-04 | 위 표의 상황별 목표 동작 (P0 · 확정) | 상황마다 따로 주입: 손 뗌·0 유실·hb 끊김·영상 장애·재접속·서버 재기동 | 부분: hb 끊김·영상 장애 잠금은 Gazebo 검증. 손 뗌·deadman은 준비 유지(설계대로). **TB3 경로 서버 재기동은 IDLE로 시작해 잠금 검증 아님**. Go2 시뮬 연결은 모의만 |
| R-SF-05 | 앱은 명령 잠금 상태를 표시하고, 물리 정지는 별도 측정으로 검증 (P0 · 확정) | 기록에 «잠김»과 «정지 측정값»이 다른 칸 | 미구현. Go2 정지 미측정 |
| R-SF-06 | 장비 STOP 계약 (P0 · 미정) | 장비가 정해진 뒤 정함 | 미구현(④ STP-4) |

## 5. 휴대폰 화면·조작 (P1)

**정상 동작**:
- 가로 방향에서 카메라 영상이 화면 전체를 채운다.
- 조작부는 영상 위에 겹친다.

**실패 동작**:

- 영상을 보며 하던 조종은 정지된다.
- 화면을 다른 상태로 바꾸면 조작 입력은 0이 된다.

## 6. PC 화면 (P1)

**공통 전제**:
- 노트북 브라우저에서 같은 웹 화면을 쓴다.

**정상 동작**:
- 네 화면을 한 화면에 둔다: 뎁스, 점군, 상태, 지도.

**실패 동작**:
- 3D 화면이 느리거나 실패해도 STOP·조종자·연결/준비 표시는 그대로 동작한다.

**상태 창 최소 표시 항목** (R-PC-03):
- 로봇/백엔드 구분(실기 Go2·Go2 시뮬·TB3 시뮬)
- 배터리
- 연결·준비
- 현재 모드
- 속도·위치·층
- 센서 상태
- 조종자
- 임무 진행

실제 출처가 없는 값은 «미연결» 또는 «미확인»으로 보인다. 숫자를 지어내지 않는다. 시뮬 값인지 실기 값인지, 명령 속도인지 측정 속도인지를 구분해 표시한다. 휴대폰과 PC에 같은 항목을 어떻게 나눠 배치할지 같은 세부는 제안이다.

## 8. 지도·목표 이동·층 (P2)

**공통 전제**:
- SLAM은 지도를 만든다.
- AMCL은 저장 지도 위에서 위치를 찾는다.
- Nav2는 한 층 안에서 경로를 짜 이동한다.

**정상 동작**:
1. 지도에서 목적지를 찍는다.
2. 목표를 확인한다(경로 미리보기는 제안).
3. 명시적으로 실행을 누른다.
4. 진행·도착·취소를 표시한다.
5. 언제든 운영자가 수동으로 넘겨받을 수 있다.

**실패 동작**: 이동하지 않고 이유를 표시한다.
