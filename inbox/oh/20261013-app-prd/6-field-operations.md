## 2. 개발 시험 절차 [현재 - 로컬 ROS PC]

전제: Ubuntu 24.04 + ROS 2 Jazzy, **Gazebo Harmonic(TB3 Waffle 대역 + 라이다 + 시뮬 카메라)이 기본**(`S1_SIM=gz`). 옛 loopback(물리·카메라 없음)은 `S1_SIM=loopback` 으로만. 실기 절차가 아니다. 상세 단계는 10-07 사용성 시험 안내(첨부 미포함).

- DDS: `run_s1.sh` 가 `ros/fastdds_local.xml`(127.0.0.1 UDP 만, 공유 메모리 없음)을 지정한다. 앱 스택 밖의 ROS 도구는 같은 설정을 주지 않으면 이 스택을 못 볼 수 있다 - 볼 때는 `FASTRTPS_DEFAULT_PROFILES_FILE=$PWD/ros/fastdds_local.xml ROS_AUTOMATIC_DISCOVERY_RANGE=SUBNET` 를 같이 준다. 인증·암호화는 아니다([신뢰 경계](TRUST-BOUNDARY.md)).
- Gazebo Nav2 설정 사본은 `sim/run_gz.sh` 가 기동마다 다시 만든다(`sim/nav2_params_app.yaml` 을 직접 고쳐도 덮인다). 사본은 goal checker `stateful: False` - 도착 불일치 원인 후보라서 바꾼 것이고 **원인은 확정되지 않았다**. 임무 도착 판정(반올림 전 오차 ≤ 0.5 m)은 그대로 둔다.
- 지도 작성 런은 `S1_SLAM=1`(slam_toolbox 를 lifecycle_manager 가 켬).

| 단계 | 명령·행동 | 확인 |
|---|---|---|
| 계정 (처음 한 번) | `python3 ros/phone_gate.py --add-user <이름>` | 비밀번호 두 번 입력 → `.gate/accounts.json`(0600) |
| 띄우기 | `cd <앱 폴더> && ./run_s1.sh` | `[run_s1] 앱 상태 수신: …` 뒤 `브라우저:  https://127.0.0.1:8443/  (로그인)` |
| 시험용 두 번째 스택 | `S1_DOMAIN=58 S1_WS=9190 S1_WEB=8100 ./run_s1.sh` | 사용 중인 57/9090/8000을 건드리지 않음 |
| 휴대폰 접속 | `S1_GATE_BIND=0.0.0.0 ./run_s1.sh` | `logs/<시각>/gate.log` 의 `열기: https://<PC 주소>:8443/` (주소에 비밀값 없음) |
| 방화벽 (ufw 가 켜져 있을 때만) | `sudo ufw allow 8443/tcp` → 끝나면 `sudo ufw delete allow 8443/tcp` | sudo 가 필요하면 현민님 |
| 끄기 | `run_s1.sh`에 Ctrl-C 한 번 | gateway가 꺼지며 출력 0 한 번(반례 R6). **몸 정지는 미측정** |
| 로그 | `logs/<YYYYMMDD-HHMMSS>/*.log` | 지우지 않음 |
| 임무 기록 | `.mission/s1-d<도메인>.db` | 비우려면 다른 이름으로 옮김(삭제 금지) |
| 프로세스 정리 | pid로만. `/proc/<pid>/environ`의 `S1_DOMAIN`·`ROS_DOMAIN_ID` 확인 후 | `pkill -f` 금지 |

- 백그라운드로 띄울 때 `( … &)`로 감싸면 SIGINT가 무시된다. 신호 기본값을 되돌리는 래퍼로 띄운다(10-07 함정).

## 3. 현장 절차 [목표 - 미실행]

### 3-1. 투입 준비 (출발 전, 현장 밖)
1. 버전 확인: 서버·화면의 버전 표기가 «고정 기록»(§5-5)과 같은지.
2. 서버 PC 기동 → selftest 3개(`app_gateway`·`phone_gate`·`mission_executor --selftest`) 통과.
3. 로봇 쪽 명령 끊김 감시(STP-5) 동작 확인, 그리고 **제조사 정지 수단·물리 정지 절차**(아래 3-4) 준비 확인 - 둘 중 하나라도 없으면 실기 투입 금지.
4. 배터리·통신 범위·지도 버전 확인. 확인 방법이 없는 항목은 «자료 없음»으로 둔다(«정상»이라 하지 않는다).
5. 운영자 로그인(IDN-1 구현 뒤), 단말 인증서 신뢰 확인.

### 3-2. 시작
1. 운영자가 제어권 받기 → 정지 해제.
2. 투입 점검(MIS-11 구현 뒤): 연결·위치·센서·장비. 빨강 항목이 필요한 임무는 시작이 막힌다.
3. 임무 양식 선택 → 지도에서 지점 → «임무 시작». 운용 중 Nav2 목표 송신자는 앱 하나(RViz 등 금지 - SYS-1 제약).

### 3-3. 운용 중
- 운영자는 위 줄(단계·상태)과 «확인해 주세요»만 따라간다. 답하기 전에는 로봇이 움직이지 않는다.
- 보는 사람도 STOP은 누를 수 있다.
- **운용 중 업데이트·재시작 금지**(§5-5).

### 3-4. 이상·STOP
| 상황 | 앱이 하는 일 | 운영자가 할 일 | 기록 |
|---|---|---|---|
| 위험을 봄 | - | **STOP** (확인 창 없음) | `paused(stop)` |
| 통신 끊김 | gateway 1.0 s 뒤 정지, 임무 PAUSED(`link`) | 로봇을 눈으로 확인 → 다시 붙으면 «정지 해제» → «임무 계속» | `paused(link)` |
| 앱 서버 죽음 | **앱은 멈추게 할 수 없다** → 로봇 쪽 감시(STP-5)가 0을 내야 한다 | 제조사 절차의 정지 수단 사용(어떤 수단인지는 제조사 문서로 확인 - 미확인) | 서버 재기동 뒤 `paused(gateway)` |
| 서버 재시작 | 임무 PAUSED(`server_restart`), 옛 목표 취소, 자동 재개 없음 | 위치 확인 후 «계속» 또는 «중단» | `paused(server_restart)` |
| 결과가 불분명한 명령 | [목표] PAUSED + «결과 확인 필요», 자동 재시도 없음(MIS-13) | 현장에서 실제 결과 확인 후 선택 | [목표] `paused(unknown_result)` |
| 위치 잃음 | [목표] PAUSED + 문구(MAP-4) | 직접 조종 또는 중단 | - |
| 장비 이상 | [목표] 장비 중단 + 확인 표시(STP-3) | 장비 쪽 인터록 확인 | - |

- **정지 수단은 세 겹으로 따로 준비한다**: ① 앱 STOP(gateway 래치) ② 앱 경로가 사라져도 남는 로봇 쪽 명령 끊김 감시(STP-5) ③ 제조사 정지 수단·물리 정지 절차. ③의 구체 방법(리모컨·버튼·전원 등)은 제조사 문서와 시험 환경에서 확인할 때까지 **미확인**으로 둔다. 앱 문서는 ③을 대신하지 않는다.
- **지금 STOP은 이동만 멈춘다.** 장비 정지 경로는 없다 - 장비가 붙기 전까지 장비 임무는 시작 자체가 거절된다.

### 3-5. 종료·기록
1. 임무가 끝나면(완료·실패·중단) 로봇 정지 확인 → 「조종권 내려놓기」(`yield`, CTL-5 - 출력 0·정지 래치·주인 없음). 「정지 해제」(`release`)는 정지만 풀고 owner를 유지하므로 놓기로 쓰지 않는다. 이어서 로그아웃.
2. 기록 확인: 임무 결과·단계별 근거·누가 눌렀나(로그인 계정·기기, IDN-2).
3. 기록 DB 백업(§5-4). 서버 종료는 Ctrl-C(SIGINT) - KILL 금지.

### 3-6. 복구
| 무엇이 | 복구 순서 |
|---|---|
| 앱 서버(gateway) | 로봇 정지 확인 → 다시 띄움 → 주인 없음·옛 Nav2 목표 취소 확인 → **제어권 받기**(받는 순간 정지 래치) → 위치 확인 → **정지 해제** → **임무 계속** |
| 임무 서버 | 다시 띄움 → PAUSED(server_restart) 확인 → 위치 확인 → gateway가 정지 상태면 **정지 해제** → **임무 계속** |
| 화면·단말 | 새로고침 → **서버 상태부터** 받음. 끊긴 동안 누른 버튼은 다시 보내지 않는다 |
| 기록 DB 손상 | 서버 멈춤 → 손상 파일을 다른 이름으로 보존 → 마지막 백업 복구 → 백업 이후 사건은 «잃음»으로 보고 |
| 업데이트 실패 | §5-5 되돌리기 |

## 4. 화면·단말 규칙 [목표]
- 웹앱 기본. 설치형 PWA는 선택이고, 캐시는 **화면 파일만**: 옛 상태를 현재처럼 보이지 않고, 끊긴 동안 누른 명령을 다시 붙은 뒤 자동 전송하지 않는다(SYS-6, 검수 Y5).
- 서버 버전 ≠ 화면 버전이면 조작을 막고 새로고침을 안내한다.
- 화면이 꺼지거나 백그라운드로 가면 heartbeat가 끊겨 정지한다 - 의도된 동작이다.

## 5. 설치와 유지 [목표 - 지금은 개발 PC 한 대]

### 5-1. 설치
- 서버 PC(또는 로봇 탑재 컴퓨터): Ubuntu 24.04 + ROS 2 Jazzy + 앱 코드 한 벌. 인터넷 없이 돌아야 한다(웹 화면은 같은 PC에서 제공).
- 설치 뒤 selftest 3개 + Gazebo 통합 시험(`test/auth_gz_run.sh`) 통과를 설치 기록에 남긴다(Y1).

### 5-2. 인증서·계정
- 지금(10-07): 관문이 처음 뜰 때 `.gate/`에 로컬 인증기관(`ca.crt`)·서버 인증서·서명 키(`hmac.key`)를 만든다(0600). 계정은 `--add-user` 로 만든다. 옛 공유 토큰(`?k=`)은 폐기했다.
- 단말은 `ca.crt`를 한 번 신뢰 등록해야 경고 없이 열린다(설치형 PWA의 전제).
- 한계: 실제 운영 계정 등록과 실제 휴대폰 로그인은 아직 하지 않았다(시험은 일회용 fixture 계정만).

### 5-3. 계정·현장망
- 계정: 운영자별 계정은 관문 `--add-user`(IDN-1, Gazebo 검증 - 실제 운영 계정 등록은 아직). 역할 권한(IDN-3)은 [목표].
- 현장망: 서버와 단말이 같은 현장 LAN/Wi-Fi. rosbridge는 127.0.0.1에만, 바깥은 관문 포트(예: 8443) 하나. **보호 없는 제어 포트를 열지 않는다.** 인터넷·클라우드는 필수가 아니다.

### 5-4. 로그·백업
- 로그: `logs/<시각>/` - 기동마다 새 폴더, 덮지 않는다.
- 임무 기록: `.mission/<스택>-d<도메인>.db`. 변조 방지는 없다(파일 권한뿐).
- 백업 [목표]: 임무가 없을 때 SQLite 백업(서버 정지 상태에서 파일 복사, 또는 `sqlite3 <db> ".backup <사본>"`) → 다른 저장소. 복구 확인 = 사건 수·마지막 seq 일치(Y4). 보존 기간 TBD.

### 5-5. 버전 업데이트·롤백 - 운용 중 업데이트 계약
지금은 버전 표기가 없다(개발 폴더를 그대로 실행). 목표 계약:

1. **정지 조건**: 진행 중 임무 없음(모두 SUCCEEDED·FAILED·ABORTED) + 로봇 정지(STOP 래치) + 조작 화면 없음. 하나라도 아니면 업데이트를 시작하지 않는다(Y3). 조작 화면은 「조종권 내려놓기」(CTL-5) 뒤 로그아웃.
2. **버전 고정**: 지금 버전(파일 해시 목록 또는 태그)과 기록 DB의 마지막 seq를 업데이트 기록에 적는다. DB를 백업한다.
3. **교체**: 서버를 SIGINT로 내리고(KILL 금지) 새 버전으로 바꾼다. 기록 DB 형식(schema)이 바뀌는 업데이트는 **이전 버전이 새 DB를 읽을 수 있는지(되돌림 호환)를 교체 전에 시험**하고 결과를 업데이트 기록에 적는다.
4. **복구 확인**: 다시 띄운 뒤 selftest 통과, 주인 없음, 임무 없음(또는 PAUSED), 자동 재개 없음, 마지막 seq가 2번과 같음.
5. **되돌리기**: 4번이 하나라도 실패하면 명령을 막은 채(STOP 래치·화면 접속 차단) 3번의 호환 결과를 본다.
   - **호환**(이전 버전이 지금 DB를 읽음이 시험됨): 이전 버전 + 지금 DB 그대로.
   - **비호환·미확인**: 이전 버전을 지금 DB로 띄우지 않는다. 실행을 멈춘 채 두고, 검증된 역변환(새 형식 → 옛 형식)과 «업데이트 뒤 새로 쌓인 사건을 보존하는 계획»이 있을 때만 되돌린다.
   - 2번 백업으로 복원해 **업데이트 뒤 기록을 조용히 버리지 않는다.** 백업 복원은 DB가 망가졌을 때만, 잃은 범위(seq)를 보고하며.
6. 단말: 화면 버전이 서버와 다르면 조작이 막힌다(§4). 캐시된 옛 화면이 새 서버에 명령을 보내지 않게.
