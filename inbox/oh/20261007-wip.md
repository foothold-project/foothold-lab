## 1. 무엇을 하고 있나

평가·인지 담당으로서, 센서 판단이나 목표 도달을 실제 이동·정지·임무 결과까지 검증하기 위해 앱과 목표형 교사를 진행한다. 임석헌은 팀 정책학습 담당이고 나는 평가 기준·센서 입력 계약·운영 통합 검증을 중심으로 맡되, 목표형 교사 학습의 코드 소유·후속 학습·최종 모델 채택을 임석헌과 어떻게 나눌지 확정한 팀원 간 합의 기록은 아직 없다.

노트북과 휴대폰에서 로봇을 조종하고, 지도 위 목표 이동과 임무의 시작·진행·중단·결과를 관리하는 웹앱을 만들고 있다. 최종 목표는 현장에서 사용할 수 있는 임무 운영 앱이며, 현재는 로컬 Gazebo의 TurtleBot3 대역으로 연결·정지·지도·인증·임무 흐름을 검증하는 단계다. Go2 실기와 실제 현장 임무는 아직 검증하지 않았다.

강화학습에서는 Go2가 지형을 보고 가까운 목표 위치와 방향에 도달하도록 교사 r3와 후속 S·T·A·B의 학습·평가를 마치고 개선·회귀 원인을 검토하고 있다. 기존 속도형 교사에서 정지·저속 추종·계단 통과 사이의 성능 엇갈림이 나타나, 명령과 보상을 목표 도달 중심으로 바꿨다. 앱의 현재 Gazebo 이동과 새 Go2 목표형 정책은 각각 검증 중이며, 두 시스템을 연결한 결과는 아직 없다.

과거 사람 인식·목표 접근 실험에서는 명령을 0으로 내려도 재이동하거나 자세가 무너져, 판단·명령 전달과 실제 정지를 분리해 검사할 필요가 생겼다. 센서 진단에서는 점군 기하가 맞아도 시각 동기가 미확정이고 틈이 미관측인 문제가 남아, 정확한 지도를 받는 교사와 센서 학생을 단계적으로 검증하도록 설계했다. 평가 하네스의 생성 치수·종료코드 오류는 현재의 manifest·소스 해시·실제 결과 파일 대조 방식으로 이어졌으며, 기존 제출 자료는 §9의 팀 열람 링크로 연결한다.

## 2. 기술적으로 어떻게 접근하나

### 앱: 화면과 이동·임무 판단을 분리한다

노트북 방향키와 휴대폰 터치를 같은 HTML/CSS/JavaScript 화면에서 처리한다. 화면은 HTTPS/WSS 관문 `phone_gate.py`와 rosbridge를 통해 ROS 2에 연결한다. 브라우저는 제한된 앱 명령만 보내고, Nav2의 경로 계산·목표 이동·취소 액션은 `app_gateway.py`가 대신 호출한다. 화면 코드가 직접 이동의 안전 조건을 결정하지 않도록 하는 구조다.

이동 명령 경로는 `app_gateway → /cmd_vel_mux → Nav2 collision_monitor → /cmd_vel → Gazebo 명령 만료 플러그인 → 차량`이다. 수동 조종과 자율 이동은 gateway에서 중재한다. STOP은 정지 상태를 유지하며, 연결이나 영상이 돌아와도 자동으로 이동을 재개하지 않는다. 도킹 서버가 최종 이동 토픽에 별도로 명령을 발행하던 문제는 비연결 토픽으로 분리해 최종 출력 경로를 확인했다.

gateway 자체가 죽으면 0 명령을 낼 수 없으므로, Gazebo 프로세스 내부에 명령 만료 플러그인을 구현했다. 마지막 명령이 0.5초의 시뮬 시간 동안 갱신되지 않으면 차량 입력을 0으로 만든다. 별도 Python 감시 프로세스는 그 감시 자체의 장애가 남아 있어 채택하지 않았다. 실제 Go2에는 별도의 로봇 측 명령 끊김 감시와 실측 정지거리 검증이 필요하다.

지도는 `map_manager.py`가 저장·목록·버전·불러오기를 관리한다. gateway는 지도 버전과 위치 추정 상태를 확인하고, 지도 교체 중·위치 미수렴·늦은 서비스 응답으로 결과가 불확실한 경우 목표 이동을 차단한다. 같은 지도 파일을 다시 불러와도 위치 확인 세대를 새로 만들어 옛 위치 추정과 목표를 재사용하지 않게 했다. 저장 지도는 AMCL로 위치를 추정하고, 새 지도 생성은 slam_toolbox를 사용하는 별도 실행 프로필로 나눴다.

인증은 scrypt 계정 확인, HttpOnly 세션, 서버가 서명한 명령·기기 식별값으로 구성했다. 재전송·끝난 세션·재시작 전 명령을 거부한다. 영상은 받은 프레임의 디코드와 촬영 시각, 화면에 표시한 프레임 확인을 서버에서 대조하고, 오래되거나 표시되지 않는 영상으로 이동하지 못하게 한다.

임무는 `mission_executor.py`의 상태기계와 SQLite 사건 기록으로 관리한다. 명령 수락과 작업 완료를 구분하고, 중복 명령·서버 재시작·운영자 개입·취소를 처리한다. 현재 시뮬 임무는 ‘지점 확인 다녀오기’이며 이동·운영자 확인·복귀와 이력 목록·상세 조회의 Gazebo 시험을 마쳤다. 영상 근거는 현재 메타데이터만 기록하며 영상 파일은 저장하지 않는다. 첫 현장 임무 방향은 안전 이동 후 카메라 목표물 인식으로 부분 확정했다. 인식 대상·성공 기준·실제 작업 장비는 미정이며 AI 인식은 보류하고 시뮬 카메라 수동 조종부터 확인한다.

### 강화학습: 목표형 MLP를 먼저 검증한 뒤 지형 인코더를 비교한다

이전 교사는 `vx, vy, wz, h`를 받아 이동·회전 속도와 몸 높이를 맞췄다. 새 `goal1r3` 교사는 몸 기준 목표 위치 `dx, dy`, 도착 방향 `sinΔψ, cosΔψ`, 이동 속도 상한 `v_cap`, 몸 높이 `h`의 여섯 값을 받는다. 목표는 세계 좌표에서 고정하고 움직일 때 몸 좌표로 다시 계산한다. 정책 입력의 목표 벡터 길이는 2m로 제한하며, 남은 시간은 행동을 선택하는 actor에 주지 않고 가치 평가용 critic에만 준다.

목표 도달 방식은 [Rudin 등의 목표형 보행 연구](https://arxiv.org/abs/2209.12827)와 [AME-2](https://arxiv.org/html/2601.08485v3)를 참고했다. 속도를 순간마다 정확히 맞추는 것보다, 지형에 따라 감속하거나 발을 옮긴 뒤 목표에 도달하는 행동을 학습할 여지를 주려는 선택이다. 목표형이 Go2에서 더 좋다는 결론은 아직 없으며 실제 비교로 확인해야 한다.

지형 정보는 시뮬레이터의 정확한 지도(GT)를 사용한다. 5cm 격자 33×17의 높이·상태와 네 발 주변 링 표본을 합쳐 1,222개 값을 입력한다. 이를 MLP로 64차원 특징으로 압축하고, 몸 상태·명령과 합쳐 [512, 256, 128]층의 정책으로 12개 관절 위치 행동을 출력한다. 이 첫 실행에는 CNN·attention·카메라 학생을 넣지 않았다. 먼저 과제 변경을 검증하고 같은 목표 과제에서 MLP, CNN-only, AME-2식 공간 attention을 비교하려는 순서다.

보상은 속도 추종 세 항을 제거하고 목표 위치·도착 방향·목표 쪽 이동·과속·도착 후 정지 항으로 바꿨다. 위치항의 실제 raw 식은 `I(t_left<2) / [2(1+d²)]`이며 매 제어 step에 가중치 10과 `dt=0.02초`를 곱해 누적한다. 여기서 I는 조건이 맞으면 1인 지시함수다. 방향 raw 항은 `I(t_left<1)·I(d<0.5)/(1+Δψ²)`이고 가중치 5와 dt를 곱한다. 위치·방향 가중치는 10·5, 목표 쪽 이동은 1, 과속은 −1이다. 몸 접촉·미끄러짐·급격한 동작·낙상 벌점은 유지한다. 시간 창과 가중치는 논문값을 우리 환경에 맞춰 줄인 값이다.

평지·요철·경사의 이동 목표 샘플 범위는 일반 0.8~2.0m, 저속 0.8~1.2m다. 출발부터 성공 반경 0.5m 안에 들어 있는 목표가 생기지 않도록 최소거리를 보완했다. 계단·턱의 일반 이동은 참조선의 끝 발판을 목표로 주므로 실제 거리가 2m보다 멀 수 있다. 2m는 actor 입력 벡터의 길이 제한이며 목표 위치를 2m 안으로 옮기는 것이 아니다. 저속은 참조선의 가까운 중간 목표를 준다. 속도 상한은 일반 0.5~1.0m/s, 저속 0.15~0.3m/s이며, 목표 시간은 거리와 상한에 따라 최대 20초까지 늘린다.

학습 알고리즘은 PPO다. 기존 환경·MLP·물리·PPO 설정을 유지하는 것을 기본으로 하되, ft1에서 도입한 끝 발판 기하 도착 latch·강등 사유 기록·reset별 마찰 재샘플도 포함되어 있다. 이 latch는 끝 발판 경계 안쪽 도착을 기록해 도착 상태를 유지하는 구현이다. 실제 속력·자세·몸 높이·발 지지가 1초 안정적인지는 별도 `safe_reach` 평가에서 판정하며 기하 도착만으로 성공 처리하지 않는다. 기존 체크포인트를 재개하지 않고 무작위 초기화로 시작했다. 명령 의미와 입력 차원이 달라졌기 때문이다. 기존 `model_2999`와 후속 실험은 비교 자료로 보존했다.



현재 기록은 첫 r3 설정과 후속 S·T·A·B를 구분한다. S는 목표 정지 보상을 조정해 방향·안정을 개선했으나 저속 과속·계단 안전성이 악화했다. T는 과속량을 cap으로 나눠 저속 벌점을 강화했고, 이후 A는 S 보상 그대로, B는 `max(0, |v|−cap)/max(cap, 0.5)`(cap>0, cap=0은 |v|)만 적용해 같은 S3499에서 각 300회 이어학습했다. B의 low 벌점은 S의 2배이며 0.5는 일반 속도 상한의 최솟값에서 고른 설계값이지 최적값으로 입증된 값이 아니다. 비교 질문은 ‘과속 보상 변경 효과’와 ‘변경 없는 추가 학습의 영향’을 구분하는 것이다.

평가 v2에서는 첫 도착 직후 1초 안정인 원래 `safe_reach`와, 종료 시점 1초 안정·방향 조건인 P2, 이후 안정 창을 찾는 보조 settle을 따로 보고한다. P1/P2의 주표는 평지류에서 목표 budget 끝까지 진행한 구간을 분모로 한다(낙상·cut 제외). 전체 목표 분모 표도 함께 보고하므로 이 비율을 전체 안전 도달률이라고 부르지 않는다. 방향 검토(목표·비교 질문·채택 기준)와 코드 검토(실제 호출·복원·SHA·평가 경로)를 구분한다.

## 7. 막힌 것 · 판단이 필요한 것

- **역할 분담:** 임석헌의 정책학습과 목표형 교사 작업의 코드 소유·후속 학습·채택·앱 연결에 관한 구체 팀 합의는 미확인이다. 평가지표·센서/앱 입출력 계약 중심으로 자료를 정리한다.
- **실폰·실기:** 오늘 서버 기동과 PC 조작 관찰은 실제 iPhone 터치·영상 끊김·STOP 검증을 대신하지 못한다. Gazebo TB3와 SDK mock은 Go2 보행·SDK 제어권·로봇 측 watchdog·정지거리의 증거가 아니다.
- **앱 간헐 실패:** 가로 화면 정식 런 30/30은 확인했으나 다른 런의 영상·임무 실패가 남아 있다. 부하 탓 또는 앱 결함이라고 확정하지 않았고, Nav2 성공인데 오차 0.53m인 원인도 미확정이다. 원오차 ≤0.5m 판정으로 해당 임무를 실패 처리한다.
- **첫 임무:** 안전 이동 후 카메라 목표물 인식 방향은 정했지만 인식 대상·시험 환경·성공 기준·복귀/재탐색은 미정이다. AI 모델 구현과 근거 사진 저장은 없음. 우선 시뮬 카메라 수동 조종을 확인한다.
- **RL 판단:** S는 방향·안정 개선과 저속 과속·험지 회귀가 함께 나타났다. B도 사전 기준 미달로 미채택이다. 변경 없는 A도 악화했으므로 보상 변경 하나로 악화 원인을 확정할 수 없다. 정지 RR 발 들기는 A에서도 24/24이며, 최소 세 발 접지 기준이라 한 발 들기 자체가 safe 실패는 아니다.
- **복원·통계 한계:** LR 보정 적용·옵티마이저 복원 근거는 있으나 resume 직후 0-update 재현은 미측정이다. 단일 seed 결과이며 추가 학습 변화와 난수 변동은 분리하지 못했다. 과속 tick은 같은 목표 안에서 상관되므로 수백만 독립 표본으로 해석하지 않는다.
- **평가 계약:** P1/P2는 full-budget 조건부 분모이며 전체 분모 표를 함께 본다. P2/보조 settle 개선을 원래 첫 도착 1초 안정 `safe_reach` 개선으로 바꾸어 주장하지 않는다. GT 교사·시뮬 결과로 실센서/실기 안전성을 주장하지 않는다.
