# foothold-v1의 rails 학습과 gap 실패 개선 기록

## 1. 지금까지의 결과

처음 목표는 **기존 지형을 걷는 능력을 유지하면서 rails도 잘 통과하게 만드는 것**이었다.

rails를 직접 학습시키자 rails 성공률은 크게 높아졌다. 하지만 gap을 0.5m/s로 걷게 했을 때 출발 직후 쓰러지는 문제가 생겼다. 이를 확인하기 위해 중간 모델을 평가하고, 지형 비율과 보상을 바꾸고, 다리별 행동도 조사했다.

현재까지의 핵심 결과는 다음과 같다.

- **rails 직접 학습은 효과가 있었다.** 시드 42 평가에서 rails 30%와 rails 10% 모델 모두 세 속도를 합쳐 300번 중 300번 성공했다.
- **gap 저속 문제는 남았다.** rails 비율을 10%로 낮춰도 출발 직후 쓰러지는 사례가 있었다.
- **기존 학습을 그대로 이어간 모델에서도 학습 중 비슷한 문제가 나타났다.** 따라서 rails 비율만을 원인으로 단정할 수 없다.
- **짧은 보정 학습은 덜 넘어지게 했지만, 최종 성공률은 낮췄다.** 새 시드에서 gap 저속 생존율은 92%에서 98%로 올랐지만, 옆으로 벗어나는 실패가 늘어 성공률은 92%에서 82%로 떨어졌다.

**지금은 보정 모델을 최종 모델로 선택하지 않은 상태다.** 아래에는 이 판단에 이르기까지 무엇을 바꾸고 무엇을 확인했는지 순서대로 정리했다.

이 문서에서는 `control`이라는 이름 대신 **“기존 학습 연장” 또는 `foothold-v1_3000`**을 쓴다. 기존 파일·폴더 이름은 그대로 두고 문서에서 부르는 이름만 바꿨다.

| **foothold-v1_3000** | **기존 7종과 학습 설정을 유지한 채 1500회 더 학습** | `0914_rough7_control` |

## 3. 성능표 읽는 방법

### 3.1 무엇을 성공으로 보았는가

모든 전체 평가에서 난이도는 **0.5**, 목표 속도는 **0.5·1.0·1.5m/s**였다. 지형과 속도의 조합마다 100번 평가했다. 따라서 표의 92는 **100번 중 92번 성공, 즉 92%**라는 뜻이다.

| 성공 조건 | 기준 |
|---|---|
| 생존 | 평가가 끝날 때까지 넘어짐 등으로 조기 종료되지 않음 |
| 전진 | 출발 방향으로 3m 이상 전진 |
| 속도 추종 | 목표 속도와의 평균 절대 오차가 0.25m/s 이하 |
| 방향 유지 | 3m 통과 지점에서 옆으로 벗어난 거리가 0.75m 이하 |

**네 조건을 모두 만족해야 최종 성공이다.** 살아남았다는 것만으로 성공은 아니다. 3m에 도달하지 못하면 방향 조건도 실패할 수 있으므로, 모든 방향 실패를 “옆으로 걸었다”는 뜻으로 해석하면 안 된다.

속도별 평가 시간은 12초·6초·4초다. 목표 속도로 걸었을 때의 기준 거리를 6m로 맞췄다. 정해진 시간까지 걸은 뒤 종료되는 것은 정상이며, 그때 네 조건을 만족하면 성공이다.

### 3.2 16종은 어떻게 나뉘는가

| 구분 | 지형 |
|---|---|
| 기존 험지 6종 | pyramid_stairs, pyramid_stairs_inv, boxes, random_rough, hf_pyramid_slope, hf_pyramid_slope_inv |
| 나머지 평가 10종 | gap, rails, pit, floating_ring, stepping_stones, discrete_obstacles, star, repeated_boxes, repeated_cylinders, wave |

기존 학습 7종은 **험지 6종＋gap**이고, rails 추가 후 학습 8종은 **험지 6종＋gap＋rails**다. 폴더 이름 `rough6`는 평가를 나눈 묶음 이름이다. gap은 다른 평가 묶음인 `unseen10`에 들어 있다. 그 이름만 보고 gap이 학습에 없었다고 해석하면 안 된다.

이 문서의 성능표는 각 칸을 **0.5 / 1.0 / 1.5m/s 성공률(%)** 순서로 적었다. 예를 들어 `92 / 100 / 96`이면 각 속도에서 92%, 100%, 96%라는 뜻이다.

### 3.3 왜 예전 MD와 foothold-v1 성적이 다른가

**같은 이름의 foothold-v1 모델을 평가했는데, 예전 문서와 이번 재평가의 성적이 달랐다.**

| 평가 기록 | gap 세 속도 성공률 | rails 세 속도 성공률 |
|---|---|---|
| `20260911-eval-protocol-v2.md`의 기록 | 90 / 100 / 68 | 70 / 48 / 21 |
| 0916에 다시 평가한 기록 | **95 / 100 / 70** | **55 / 57 / 24** |

예를 들어 rails 0.5m/s는 예전에는 70번, 재평가에서는 55번 성공했다. **재학습해서 달라졌다는 뜻은 아니다.** 지형 배치, 초기 자세, 난수 시드, 평가 코드나 실행 환경이 달랐을 수 있지만, 두 실행을 직접 대조하지 않아 정확한 이유는 아직 모른다.

이번 모델 비교에는 **0916에 다시 측정한 foothold-v1 성적**을 사용했다. 기존 학습 연장 모델과 rails 모델도 같은 평가 절차로 측정했기 때문이다. 70%와 55%의 차이를 단순한 우연이라고 넘기지는 않는다. 정확한 이유를 밝히려면 이전 실행의 모델 파일과 평가 설정부터 대조해야 한다.

또한 시드 42와 시드 43의 결과는 표를 나눴다. 시드는 평가에 쓰는 난수의 시작값이며, 시드가 바뀌면 지형 배치와 초기 조건도 달라질 수 있다.

## 4. 지형 비율과 rails 모양은 어떻게 설정했는가

### 4.1 각 지형의 학습 비율

| 지형 | 기존 학습 연장·보상 실험 | rails 30% | rails 10%·gap 보정 |
|---|---:|---:|---:|
| 정방향 계단 (`pyramid_stairs`) | 18% | 12.6% | 15% |
| 역방향 계단 (`pyramid_stairs_inv`) | 18% | 12.6% | 15% |
| boxes | 18% | 12.6% | 15% |
| random_rough | 18% | 12.6% | 15% |
| 정방향 경사 (`hf_pyramid_slope`) | 9% | 6.3% | 10% |
| 역방향 경사 (`hf_pyramid_slope_inv`) | 9% | 6.3% | 10% |
| gap | **10%** | **7%** | **10%** |
| rails | 0% | **30%** | **10%** |
| 합계 | 100% | 100% | 100% |

rails 30%는 기존 7종의 비율을 모두 0.7배로 줄여 자리를 만들었다. 따라서 gap도 10%에서 7%로 줄었다. rails 10%에서는 gap을 원래 10%로 되돌리고, rails에도 10%를 배정했다.

설정한 숫자가 실제 환경 수와 정확히 같지는 않았다. 지형을 20개 열로 나누어 배정하기 때문이다.

| gap 배정 | 기존 학습 연장 | rails 30% |
|---|---:|---:|
| 설정 비율 | 10% | 7% |
| 지형 열 | 2/20 | 1/20 |
| 환경 수 | 409/4096 | 205/4096 |
| 실제 환경 비율 | **약 10%** | **약 5%** |

**rails 30% 학습에서 gap 환경 수는 실제로 약 절반으로 줄었다.** rails는 1228/4096개 환경, 약 30%였다. 다만 환경 수가 절반이라고 해서 완료한 에피소드나 실제 장애물 통과 경험도 정확히 절반이었다는 뜻은 아니다.

### 4.2 rails 두께 8~18cm는 어디서 나온 값인가

**보내준 sim 폴더의 기존 rails 평가 설정을 학습 코드에 그대로 가져온 값이다.** 새로 두께 최적화 실험을 해서 정한 값은 아니다.

| 설정 | 사용한 값 | 확인한 원본 |
|---|---|---|
| 높이 범위 | **5~18cm** | `sim/eval/generalization_env_cfg.py`의 `rail_height_range` |
| 두께 범위 | **8~18cm** | 같은 파일의 `rail_thickness_range` |
| 시작 플랫폼 폭 | 1.5m | 같은 파일의 `platform_width` |

이 값들은 rails 30% 학습의 `train_rails.py`와 rails 10% 학습의 `0917_training/arms.py`에 모두 들어 있다. 기존 평가 코드의 주석에 따르면 두께는 난이도와 별개로 범위 안에서 무작위로 정해진다. 따라서 **높이만 달라지는 rails를 학습한 것이 아니라, 두께도 달라지는 rails를 학습했다.**

기존 평가에서 사용하던 모양을 학습에도 사용했다는 출처는 확인됐다. 하지만 **8~18cm가 가장 적절한 범위라는 실험 근거는 없다.** 두께를 고정한 학습과 비교한 결과도 없다. 앞선 설명에서 높이만 다뤄 두께까지 바뀐다는 점을 빠뜨렸으므로, 여기서 명확히 바로잡는다. 기존 평가의 지형 범위를 학습에 사용했다는 점도 일반화 성능을 해석할 때 함께 고려해야 한다.

## 5. 첫 추가 학습과 중간 체크포인트 평가

### 5.1 왜 두 모델을 함께 학습했는가

foothold-v1에서 두 가지를 시작했다.

- **기존 학습 연장:** 지형과 보상을 그대로 두고 1500회 더 학습했다. 추가 학습 자체의 효과를 확인하려는 모델이다.
- **rails 30% 추가:** 기존 지형 비율을 줄이고 rails를 넣어 1500회 더 학습했다. rails 학습의 효과와 기존 능력의 변화를 확인하려는 모델이다.

최종 모델만 보면 학습 중간에 언제 문제가 생겼는지 알 수 없다. 그래서 두 계열의 **1525·1750·2000·2250·2500·2750·3000**을 모두 평가했다. 출발 모델까지 합쳐 **15개 모델, 72000개 에피소드**다. 25회마다 저장된 모든 모델을 평가한 것은 아니며, 실제로 평가한 번호는 아래 표와 같다.

### 5.5 학습률과 지형 비율이 원인이었는가

두 학습은 적응형 학습률을 사용했다. 학습률을 자동으로 조절한다고 해서 성능이 항상 좋아지는 것은 아니다. 이전 옵티마이저 상태를 복원하는 기능과 이후 학습률을 조절하는 기능도 서로 다른 기능이다.

출발 체크포인트의 저장 학습률은 1.5e-5, 두 계열의 1525는 약 2.56289e-4였다. 그런데 rails 2750과 3000의 저장 학습률은 둘 다 1e-5인데 gap 저속 성공률은 **21%와 90%**였다. **저장된 학습률 숫자만으로 실패 이유를 설명할 수는 없다.** 처음 0914 학습의 옵티마이저 상태가 재개 시 완전히 복원됐는지는 제공 기록만으로 확정하지 못했다.

또한 rails를 30% 추가하면서 gap뿐 아니라 다른 지형 비율도 함께 줄었다. 이번 비교만으로 “rails가 너무 많아서”와 “gap 경험이 줄어서” 중 하나를 정확히 골라낼 수는 없다. 두 영향을 따로 확인하려면 다른 조건은 유지하고 한 가지씩 바꾼 학습이 필요하다.

## 6. gap은 왜 출발 직후 쓰러졌는가

### 6.1 원인을 좁히기 위해 한 실험

실패 영상만 보고 바로 과적합이나 지형 인식 오류라고 결론 내리지 않았다. 다음 순서로 확인했다.

| 실험 | 확인하려던 내용 |
|---|---|
| 실패 시점·초기 상태 기록 | 얼마나 움직인 뒤 쓰러지는가 |
| 같은 입력을 두 정책에 넣기 | 같은 상황을 보고도 서로 다른 행동을 내는가 |
| 도중에 정책 바꾸기 | 어느 시점까지 다른 정책이 회복시킬 수 있는가 |
| 이전 행동 입력 바꾸기 | 과거 행동 정보가 다음 행동을 어떻게 바꾸는가 |
| 발 위치·접촉·관절 기록 | 발이 gap에 빠지는가, 시작 플랫폼에서 자세가 무너지는가 |
| 다리별 행동 바꾸기 | 어느 다리의 초기 행동을 바꾸면 결과가 달라지는가 |

높이 스캔을 평지로 바꾸면 gap 정보 자체를 없애게 된다. 그래서 그런 변경의 결과를 실제 gap 통과 능력이 좋아졌다는 증거로 사용하지 않았다.

### 6.2 두 초기 사례에서 확인한 사실

rails 30%의 e016·e033을 자세히 봤다. 초기 약 1.2초 동안 발들은 시작 플랫폼 위에 있었다. 이 두 사례는 처음부터 발이 gap 안으로 빠져서 실패한 것으로 설명하기 어려웠다.

약 0.8초에 왼뒷발이 몸통 중심선을 넘어가는 등 발을 짚는 자세가 좁아졌다. 하지만 다른 개입으로 회복한 경우에도 비슷한 변화가 남았다. 따라서 발이 중심선을 넘었다는 사실 하나만을 결정적 원인으로 보지는 않았다.

**처음 0.4초 동안 오른앞다리의 세 관절 행동만 기존 학습 연장 모델의 출력으로 바꾸자 두 사례 모두 6초간 생존했다.** 다만 이 실험은 특정 상황에서의 개입이다. control 출력이라는 원래 이름은 여기서 `foothold-v1_3000`의 출력을 뜻한다. 반대로 그 다리의 rails 출력을 기존 학습 연장 모델에 넣었다고 항상 실패한 것도 아니었다.

즉, **초기 오른앞다리 행동이 결과를 바꿀 수 있다는 사실은 확인했지만, 모든 실패가 그 다리 하나 때문이라고 확정한 것은 아니다.**

### 6.3 rails 10%에서도 확인

나중에 rails10_2950의 기존 실패 8건을 같은 방식으로 확인했다.

## 8. 두 번째 학습: 비율 변경과 보상 변경

### 8.1 세 실험의 차이

세 실험은 모두 foothold-v1에서 시작했다. 기본 보상, 관측·행동 구조와 물리 설정은 유지하고 각 실험에서 필요한 부분만 바꿨다. 4096개 환경을 사용했으며 기존 옵티마이저·적응형 학습률 상태를 복원하도록 구현했다. 과거의 물리 상태를 그대로 이어가는 것이 아니라, 복원된 설정과 지형 난이도에서 새 에피소드로 시작했다.

| 실험 | 바꾼 것 | 바꾸려던 이유 |
|---|---|---|
| rails 10% | gap 10%, rails 10%, 나머지는 4.1절의 비율로 배분 | rails 능력을 유지하면서 gap 학습 기회를 확보 |
| 방향 보상 | 기존 7종 그대로, 회전속도 오차와 옆방향 속도에 벌점 추가 | 장애물 부근에서 몸이 돌아가거나 옆으로 흐르는 행동 감소 |
| 방향＋감속 보상 | 방향 보상에 목표 속도의 60% 미만으로 느려질 때 벌점 추가 | 방향 개선과 함께 지나친 감속도 감소 |

### 8.2 방향 보상은 구체적으로 무엇을 바꿨는가

높이 스캔에서 보이는 가장 높은 곳과 가장 낮은 곳의 차이로 지형이 울퉁불퉁한지 추정했다. 차이가 3cm 이하이면 추가 벌점을 적용하지 않고, 3~12cm에서는 점점 강하게, 12cm 이상에서는 최대 강도로 적용했다. 목표 이동 속도가 0.1m/s보다 클 때만 사용했다.

이 조건에서 다음 두 행동에 벌점을 줬다.

1. 명령보다 더 돌거나 덜 도는 행동: **실제 회전속도와 명령 회전속도의 차이**.
2. 명령한 이동 방향에서 옆으로 흐르는 행동: **명령 방향에 수직인 이동속도**.

두 항을 각각 정규화하고 0~1로 제한한 뒤 평균했다. 추가 보상 가중치는 **합친 항 하나에 -0.25**였다. 회전속도는 0.5rad/s, 옆방향 속도는 0.25m/s를 기준으로 정규화했다.

**이 보상은 “원래 바라보던 방향으로 다시 돌아와라”라는 보상은 아니다.** 이미 몸이 틀어진 뒤 그대로 걷고 있으면 회전속도 오차가 작을 수 있다. 또한 높이 스캔만으로 실제 장애물 통과 중인지 정확히 알 수는 없다. 문서에서 방향 보상이라고 부르더라도 이 한계를 함께 기억해야 한다.

### 8.3 감속 억제는 어느 때 적용했는가

명령 방향으로의 실제 속도가 **목표의 60% 아래**로 내려갔을 때만 추가 벌점을 줬다. 예를 들어 목표가 0.5m/s이면 0.3m/s보다 느려질 때 작동한다.

부족한 비율을 0~1로 제한한 뒤 제곱했고, 보상 가중치는 **-0.25**였다. 목표 속도 이상으로 달린다고 추가 보상을 주지 않았다. 기존 속도 추종 보상도 그대로 뒀다. 회전 명령이 큰 상황에서는 감속이 필요할 수 있어, 명령 회전속도의 절댓값이 0.3rad/s 이상이면 이 항을 적용하지 않았다.

방향 보상만 적용한 실험과 따로 둔 이유는 분명하다. **속도를 유지하려고 무리하면 접촉이나 충격이 늘 수 있기 때문**이다. 실제 평가에서도 성공률과 접촉 실패가 서로 다른 방향으로 바뀌는 조건이 나타났다.

재현에 필요한 계산식은 다음과 같다. `clip(x,0,1)`은 값을 0~1 범위로 제한한다. Δh는 스캔의 높낮이 차이, s는 목표 평면 속도, v∥와 v⊥는 명령 방향의 전진·옆방향 속도다.

```text
지형에 따른 적용 강도 g = clip((Δh - 0.03) / 0.09, 0, 1)
방향 벌점 = g × 0.5 × [clip((회전속도 오차 / 0.5)², 0, 1)
                       + clip((v⊥ / 0.25)², 0, 1)]
감속 부족분 = clip((0.6s - v∥) / (0.6 × max(s, 0.1)), 0, 1)
감속 벌점 = g × 감속 부족분²
각 추가 보상항의 가중치 = -0.25
```

### 8.4 왜 세 모델을 3000이 아닌 2950에서 비교했는가

방향＋감속 모델은 2950까지 저장됐지만, 2958 부근에서 **가치함수 손실이 inf로 커진 뒤 학습이 중단**됐다. 이후 행동을 뽑는 정규분포의 표준편차 관련 오류가 나타났다. 평균 reward가 약 33이었다는 것만으로 학습이 정상이라고 판단할 수 없었다.

추가 진단에서는 큰 행동값과 관측에 포함된 이전 행동의 영향을 조사했다. 문제 입력에서 이전 행동 항을 0으로 바꾸자 다음 평균 행동의 최대 절댓값이 **99.68에서 12.36으로 감소**했다. 이전 행동 정보가 출력 증폭에 영향을 준다는 단서지만, 왜 처음 큰 값이 생겼는지까지 모두 설명한 것은 아니다.

임의로 행동값을 제한해 학습을 끝내면 원래 실험과 조건이 달라진다. 그래서 비교에서는 변경된 복구 모델을 섞지 않고 **세 모델 모두 정상 저장된 2950으로 맞췄다.** 이 수치 발산과 이전 rails 모델의 gap 붕괴가 같은 원인이라고 단정하지 않는다.

## 10. gap 초반 행동을 짧게 보정

### 10.1 보정 학습을 시도한 이유

rails10_2950은 rails를 잘 통과했지만 gap 저속의 출발 실패가 남았다. 오른앞다리의 초기 행동을 잠깐 바꾸면 일부 실패가 회복됐기 때문에, 그 행동을 모델 자체가 내도록 짧게 보정해 보기로 했다.

출발점은 **rails10_2950**, 추가 학습은 **50회**, 결과는 **gap보정_3000**이다. 환경 보상과 지형 비율은 유지했다. 바꾼 것은 학습할 때 계산하는 손실이다.

### 10.2 어떤 행동을 배우도록 했는가

오른앞다리를 교체한 뒤 6초 생존한 e006·e011·e039·e041·e044·e062의 첫 0.4초를 사용했다. 총 **6개 궤적의 120개 관측**이다. 서로 이어진 프레임이므로 독립적인 120개 사례는 아니다.

기존 PPO 손실에 다음 세 항을 더했다.

| 추가 항 | 목적 | 가중치 |
|---|---|---:|
| 오른앞다리 3개 출력을 기존 학습 연장 모델의 참고 출력에 가깝게 함 | 초기 다리 행동 보정 | 0.1 |
| 같은 관측에서 나머지 9개 출력을 원래 rails 출력에 가깝게 함 | 다른 다리 행동 변화 억제 | 0.1 |
| 현재 학습 관측 최대 256개에서 전체 출력을 출발 rails 정책에 가깝게 함 | 원래 보행 능력 변화 억제 | 0.1 |

세 항 모두 평균제곱오차를 사용했다. **특정 다리만 배우게 의도했어도 신경망을 공유하므로 다른 행동이 바뀔 수 있다.** 가중치 0.1이 최적이라고 검증한 것은 아니다. 행동 크기를 새로 잘라내는 제한은 추가하지 않았고, 평가할 때 참고 정책이 대신 움직여 주지도 않는다.

e049·e064는 보정 자료에서 뺐다. 다만 이미 관찰한 사례이므로 완전히 새로운 시험 사례라고 하지는 않는다.

### 10.3 학습 자체는 완료됐는가

50회 학습은 완료됐다. 예제에서 오른앞다리 출력의 오차는 약 **0.70388 → 0.00355**로 줄었다. 이 마지막 진행 기록은 2999에 표시됐고 최종 저장 모델은 3000이다. 가치함수 손실도 기록된 50회 동안 유한한 값이었다.

하지만 **예제의 행동을 잘 따라 하는 것과 실제 gap을 잘 통과하는 것은 다르다.** 다음 전체 평가에서 실제 효과를 확인했다.

## 12. 지금 무엇이 확인됐고, 다음에는 무엇을 볼 것인가

### 12.1 확인한 사실

- rails를 학습하면 rails 통과 능력이 크게 좋아졌다.
- gap 저속 성능은 중간 체크포인트에서 떨어졌다가 회복하기도 했다.
- 출발 붕괴는 rails 30%에만 나타나지 않았다.
- 초기 오른앞다리 행동을 바꾸면 일부 실패가 회복됐다.
- 보정 모델은 덜 넘어졌지만 옆방향 이탈이 늘어 gap 저속 성공률이 낮아졌다.
- 일반 추가 학습 모델도 기존 실패 8건을 모두 6초간 버텼다.

### 12.2 아직 모르는 것

rails 비율, gap 경험 감소, 학습률 변화 중 무엇이 얼마나 영향을 줬는지는 따로 통제한 학습 없이 확정할 수 없다. 또한 보정 후의 방향 이탈이 **출발 때 몸이 틀어져서 계속 남은 것인지, 걷는 중 회전이 쌓인 것인지, 옆으로 미끄러진 것인지**도 아직 구분하지 못했다.

### 12.3 현재 결정과 다음 확인

**gap보정_3000을 최종 모델로 교체하지 않는다.** 학습을 무작정 더 하기 전에 저장된 보정 중간 모델 **2960~2990**에서 gap·random_rough 저속을 평가해 더 나은 시점이 있는지 확인하는 것이 다음 제안이다. 이 평가는 아직 하지 않았다.

방향만 실패한 e084·e058·e064의 영상 생성 코드도 준비했다. 3m 통과 시 옆이탈은 각각 **0.9446m, 0.8782m, 0.7517m**다. 기존에 저장한 몸통·관절 기록으로 자세를 재생하도록 했으며 정책을 다시 실행해 다른 궤적을 촬영하는 방식은 아니다. 원래 장면을 픽셀 단위로 복원하는 영상도 아니다.

이 문서 작성 시점에는 **영상 생성 코드 제공까지만 완료했고, 서버에서 만든 영상의 확인 결과는 아직 받지 않았다.** 영상과 시계열로 방향 이탈이 언제 시작되는지 확인한 뒤 다음 수정을 정한다.

표의 차이는 **이번 평가에서 관측한 차이**다. 100번 평가한 수치가 몇 %p 다르다는 이유만으로 언제나 한 모델이 우수하다고 단정하지 않는다. 같은 시드라도 모델마다 움직임과 종료 시점이 달라 에피소드 번호만으로 같은 초기 조건이라고 짝짓지 않는다. 또한 학습 시드를 여러 개 바꿔 반복한 실험은 아니므로 학습 방법의 일반적인 우열까지 확정하지 않는다.

원래 CSV의 `head_contact` 항목에는 알려진 문제가 있어 모델 선택 근거로 사용하지 않았다. 성능이 나빠진 원인을 설명할 때는 **실제로 확인한 행동 변화**와 **아직 검증하지 않은 학습 원인**을 구분한다.
