## 3. 수정해야 할 코드 결함

### P0 · 결손·다른 키의 자료로도 후보가 된다

**확인됨:** `verdict.py:89-94`는 없는 축 1 요약을 건너뛰고, `:249`는 하락 수가 모두 0인지만 본다. 48개 정확한 칸, 각 100행, 기준선 존재, 해시·규격 일치 검사 없이 `:264`에서 후보가 된다. 전부 없으면 `ref_nv`가 초기화되지 않아 `:142`에서 `UnboundLocalError`가 난다. 전부 없는 경우의 충돌과 일부 없는 경우의 잘못된 통과는 서로 다른 결함이다.

**실측:** `read_summary`에 체크포인트마다 `rough6/v0.5`의 `flat=100/100` 한 칸만 반환하도록 주입하고, 임시 폴더에 축 2 문턱을 만족하는 요약을 두었다. 결과는 `cells_measured=[1,1,1,1]`, `axis2_passed=[9,9,9,9]`, **`candidate=True`**였다. 축 2 per-env 파일이 없어도 막히지 않았다.

**확인됨·실측:** 축 2는 `verdict.py:177-185`에서 모든 시나리오의 모든 yaw 키를 더한다. 필수 `turn/+1.00`을 지우고 무관한 `extra/yaw_follow/x=1`을 넣었더니 `passed=9`, `counted=9`, `met=True`, 경고 없음이었다. 개수만 맞추는 검사로는 정확한 9개 항목을 보증하지 못한다. `:193`의 `>=gate`와 `:250`의 `==gate`도 서로 다르다.

**판단·관문:** 기대하는 `(지형집합, 지형, 속도, 체크포인트)` 집합과 축 2의 정확한 9개 키를 선언하고 집합 일치를 검사한다. 각 분모·유한수·성공 수·범위·중복·필수 원자료·체크포인트 SHA·평가 설정 SHA를 검증한 뒤에만 채점한다. 상태를 `INVALID / FAIL / PASS`로 분리하고 `INVALID`는 분기 입력으로 금지한다. 재현 전 상태는 `base_gates_met`처럼 한정하고, 재현까지 안 본 현재 `candidate`를 배포 승인으로 소비하지 않는다(`:265`, `:324`).

### P0 · 잠금 획득이 원자적이지 않고, 잠금 전에 작업 목록을 만든다

**확인됨:** `eval_runner.py:213-225`는 파일 존재 확인과 `open(...,'w')`가 분리돼 있다. watchdog의 PID 확인도 소유권 획득이 아니다. 두 호출이 동시에 없다고 보면 둘 다 쓴다. `:259-267`의 완료 검사와 목록 작성도 잠금 `:281`보다 앞이다. 뒤늦게 잠금을 얻은 실행이 낡은 목록을 수행할 수 있다. PID 재사용, 다른 소유자의 잠금 삭제(`:228-232`)도 방어하지 않는다.

**실측:** 시험 사본에서 `isfile(LOCK)`의 두 호출을 barrier로 맞춰 모두 False를 보게 했다. 두 스레드의 실제 `take_lock()` 반환이 **`[True, True]`**였다. 이는 경합 가능한 순서를 강제로 만든 재현이며 실운영 발생 빈도를 잰 것은 아니다.

**판단·관문:** Windows 프로세스 수명에 묶인 mutex 또는 트랜잭션 기반 단일 실행 소유권을 쓴다. 잠금을 얻은 뒤 상태와 완료 기록을 다시 읽는다. 작업별 idempotency key, attempt 번호, 소유자 토큰을 저장하고 소유자만 해제한다. 재시작 때 부모 PID만 보지 말고 자식 프로세스의 생성 시각·명령·실행 ID까지 대조한다.

### P0 · 평가 스레드가 죽어도 “실패 0”으로 끝난다

**확인됨:** `worker()`는 `run_job()` 예외를 잡지 않는다(`eval_runner.py:203-205`). `main()`은 스레드 join 후 **결과에 들어온 항목만** 센다(`:287-297`). 스레드 예외는 부모에 자동 전파되지 않는다. watchdog은 자식 stderr도 버린다(`watchdog.py:127`).

**실측:** `run_job`이 실행 실패 `OSError`를 내도록 주입하고 작업 하나로 `main()`을 호출했다. 스레드 traceback은 있었지만 로그는 **“끝 · 0 건 중 실패 0”**, 반환은 **0**이었다.

**판단·관문:** 모든 예정 작업에 terminal status를 기록하고 `완료+실패+취소=예정`을 확인한다. 예외를 부모에 전달하고 worker 시작 실패도 실패로 기록한다. 28개 중 27개만 돌아도 성공이 될 수 없게 한다. stderr는 attempt별 로그로 보존한다.

### P1 · 파일 존재가 완료 증명으로 쓰인다

**확인됨:** `eval_runner.py:263-266`은 완료 표시 파일이 있으면 내용과 직전 종료코드를 보지 않고 건너뛴다. `:196`도 exit 0과 파일 존재만 본다. 오래된 파일이나 빈 파일도 해당한다. 축 1은 CSV를 쓴 뒤 매니페스트를 쓰므로 둘 사이 장애도 고려해야 한다(`eval_generalization.py`의 `save_csv` 후 `save_run_manifest` 호출).

**실측:** 빈 marker 파일을 만들고 자식 종료만 0으로 모의했더니 실제 `run_job()`이 0을 반환했다.

**확인됨:** 축 2 하네스는 기존 시계열이 있으면 거부한다(`R:eval_command_response.py:378-414,712`). 실행기는 같은 폴더를 재사용하고 `--overwrite`를 주지 않는다. 중간 실패 후 일부 parquet이 남으면 다음 재시도도 거부될 수 있다. 단순히 overwrite를 넣으면 원자료가 사라진다. `--force`도 이 문제를 해결하지 못한다.

**판단·관문:** attempt마다 새 폴더를 쓰고 검증 완료 뒤 원자적으로 `completion.json`을 확정한다. 명령·입력 해시·코드 판·종료코드·기대 파일과 실제 개수·행 수를 넣는다. 재시도는 새 attempt로 만들고 이전 결과와 실패 로그를 보존한다. 요약 파일만으로 재개하지 않는다.

### P1 · 학습·평가 수명과 GPU를 함께 관리하지 않는다

**확인됨:** `training_done()`은 체크포인트 네 파일과 PID 소멸만 본다(`eval_runner.py:80-99`). 학습 exit 0, 파일 안정화·로드 가능 여부, NaN, 실행 ID는 확인하지 않는다. PID 조회 명령의 비정상 종료도 `check=True`가 없어 단순히 “yes 없음”으로 해석될 수 있다(`:102-114`). 평가 `wait()`에는 시간 제한이 없다(`:194`). 부모가 죽어도 평가 자식이 남는 상황을 회수·식별하는 기록도 없다.

**확인됨:** 일부 학습만 끝나면 즉시 ready에 넣고 양쪽 GPU 평가를 시작한다(`:248-285`). 다른 학습이 GPU를 사용하는지는 안 본다. `run_gap_train.ps1:136-146`의 detached exit 0은 launcher 생성 결과이며 학습 완료가 아니다. 학습의 실제 종료 기록을 별도로 수집해야 한다.

**판단·관문:** 실행별 `STARTING / RUNNING / SUCCEEDED / FAILED / STALLED / UNKNOWN` 상태를 둔다. PID+생성시각+실행 ID, 자식 목록, heartbeat, 체크포인트 증가, 종료코드를 함께 본다. GPU 예약은 **시뮬·신경망·영상 렌더 장치 전체**를 대상으로 한다. 정해진 동시 부하 조건을 보존하고, 자원이 사용 중이면 평가를 대기시킨다. 최대 시간·진행 정지 시간·재시도 수를 구분한다. NaN 같은 결정적 오류는 맹목적으로 재시도하지 않는다.

### P1 · 경로 선택과 감시 상태의 의미가 불안정하다

**확인됨·실측:** `run_dir()`의 정확한 디렉터리 입력은 그 부모를 반환한다(`eval_runner.py:117-124`). 임시 `actual_run`을 주어 부모 반환을 재현했다. wildcard는 여러 일치 중 정렬상 마지막 것을 택한다. 새 재시도가 같은 접미사를 쓰면 조용히 다른 학습을 평가할 수 있다. 디렉터리인지도 후보별로 검사하지 않는다.

**확인됨·실측:** 최초 watchdog은 선언된 실행이 있어도 큰 Python이 하나라도 있으면 개별 사망을 놓쳤다. 죽은 PID 하나와 무관한 큰 Python 하나를 넣은 `find_mismatch()` 결과가 `[]`였다. **7e75b12에서 PID별 대조와 30분 체크포인트 정체 경고가 추가됐다. 이 첫 결함은 부분 수정됐다.** 다만 수정판 `watchdog.py:175-180`도 “1 GiB 이상인 Python 목록에 없음”을 “죽었다”로 단정한다. 작은 작업 집합, 조회 실패, 정상 종료도 구분해야 한다. 상태 JSON을 실제 결과에 맞춰 전이시키는 기능은 여전히 없다.

## 5. 권고 구조와 대안 비교

**판단: 이 워크스테이션에는 Windows 예약 작업이 재기동하는 작은 Python 감독 프로세스, 로컬 SQLite 실행 원장, 독립 worker가 가장 적합하다.** 단일 호스트·두 GPU·수일짜리 한 공정에서 대규모 플랫폼 도입보다 현재 결함을 명확한 상태 전이로 고치는 비용이 먼저다. 서버 제품을 저장소에 새로 만들자는 제안이 아니라 이 PC의 실행 관리 도구다.

대안 표는 설치 견적이나 제품 성능 실측이 아니라 **현재 코드·호스트 수·공정 규모에 따른 판단**이다. 프레임워크 이름을 바꾸어도 3절의 실패를 자동으로 해결하지 못한다.

폰에서 필요한 것은 최신 성공 보고만이 아니다. 실행 ID·현재 단계·마지막 heartbeat·최근 checkpoint·예상 종료·실패 attempt·검증 대기·남은 실행 예산·다음 전이와 중단 이유를 한 장에 보여야 한다. 조회 시각과 원자료 시각을 따로 표시한다. 로컬 경로는 폰에서 열리지 않으므로, 접근 권한이 있는 Git 커밋 고정 링크 또는 별도 보고 저장소 링크를 쓴다. 비공개 저장소라면 폰의 인증도 확인한다. MP4·대형 자료는 artifact 저장소에 두고 Git에는 manifest·해시·링크를 남긴다.

텔레그램은 `run_id+event_seq+채널`로 중복 억제하고 실패 시 제한된 재시도와 대기열을 쓴다. 전송 성공 여부와 실제 수신·링크 접근은 구분한다. 이번 감사에서는 토큰을 열거나 메시지를 보내지 않았다. `_out/loop/tg.py`가 감사 중 존재했으므로 `PIPELINE.md`의 “아예 없다”는 현황도 다시 갱신해야 한다. 파일 존재만으로 작동을 보증하지는 않는다.

## 6. 자동화할 때 잃을 수 있는 것과 관문

| 자동화 자리 | 잘못되면 잃는 것 | 반드시 선행할 관문 |
|---|---|---|
| 학습 실행 | 수시간 GPU 예산, 비교 조건, 원본 checkpoint와 계보 | 사전 승인 계획·예산, 시작 checkpoint 해시, exact 실행 경로, 실현된 config diff, GPU 예약, 숫자 유효성, 시작·정체·최대시간 제한, 실패 보존 |
| 결과에 따른 분기 | 사흘 전체를 틀린 가설로 소비, 데이터에 맞춘 사후 설명 | 완전성 검증 뒤 채점, 규칙 판 고정, 조건 단일 일치, 독립 검증 통과, 재현 관문, 계획 밖 상태 중단, 전체 학습 수·시간·교체 횟수 상한 |
| 자동 commit·push | 다른 세션 작업 혼입, 원자료 덮어쓰기, 비밀·대형 파일 유출, 검증 전 발행 | 격리된 작업 사본과 전용 브랜치, 추가 파일 allowlist, 예상 diff 확인, 비밀·크기 검사, 정확한 경로만 add, main·force push 금지, 원격 실패를 기록과 분리, 팀장 머지 |

**판단:** 학습 자동화는 제한된 실행 명세 안에서 허용할 수 있다. 자동 분기는 사전에 정의하고 검증한 경로만 허용한다. 새 보상 코드·신경망 설계·새 기준의 자율 작성과 즉시 실행까지 같은 권한으로 묶지 않는다. 승인 범위 밖 설계가 필요하면 안전하게 멈추는 것이 정상 완료 상태다.

commit·push는 계산을 돌리는 권한과 별개다. 이 감사는 자동 게시 권한을 부여하지 않는다. 향후 운영 권한이 정해지면 매 실행마다 다시 사람을 부르지 않고 그 범위 내에서 집행하면 된다. 브랜치명도 저장소 규칙의 `feature/<작업명>-jay`를 따른다. 공유 작업 트리에서 `git add .`로 전체 변경을 잡는 방식을 버린다.

## 7. 한도와 수동 문맥 관리

**확인됨:** 설치된 `codex-cli 0.155.0`의 `--help`에는 usage·quota 하위 명령이 없지만 `app-server`는 있다. 이번에 `codex app-server generate-json-schema --experimental --out <임시폴더>`로 생성한 `ClientRequest.json:8483,10945,10975,10999`에는 각각 `thread/compact/start`, `account/rateLimits/read`, `account/rateLimitResetCredit/consume`, `account/usage/read`가 있다. 그러므로 **“하위 명령이 없으니 조회·리셋 자동화는 불가능”이라는 추론은 틀렸다.**

공식 문서에도 한도 조회·갱신 알림, 계정 사용량 조회, 스레드 사용량 알림, 리셋 소비 API가 있다. 리셋은 같은 논리 요청에 같은 idempotency key를 쓰고, 소비 후 한도를 다시 조회하도록 설명한다([OpenAI 공식 App Server 문서](https://learn.chatgpt.com/docs/app-server)). 이것은 인터페이스 존재 확인이다. **이 계정의 실제 응답·주간 잔여량·리셋권 수·소비 가능 여부는 미확인**이며 리셋 호출은 하지 않았다.

**판단:** 우선 이 설치판의 인증된 App Server에서 읽기 전용 조회를 검증한다. 계정별 bucket·window 길이·사용률·리셋 시각·관측 시각을 그대로 기록한다. null·조회 실패를 0으로 바꾸지 않는다. 주간 창은 이름이나 primary/secondary 위치를 추정하지 말고 반환된 window로 구분한다. 전해 받은 78%는 측정 시각이 불명인 수동 기록이며 현재값으로 표시하면 안 된다. 호출 횟수를 토큰이나 주간 사용률로 환산하지 않는다.

연동이 되는 범위에서 이벤트와 주기적 재조회로 **준실시간** 관측을 할 수 있다. 서버가 제공하지 않는 전체 한도, 다른 도구·다른 계정의 소비, 응답 전 진행 중인 요청의 확정 사용량까지 알 수 있다고 약속하지 않는다. 한도·누적 토큰·현재 문맥 점유는 서로 다른 지표다.

수동 문맥 관리는 작업 경계에서 `완료 사실 / 근거 경로와 해시 / 미결정 / 다음 입력 / 금지 행동`을 짧은 인계 파일로 확정하고, 그 파일로 새 세션을 시작하는 방식이 낫다. 자동 compact가 발생하지 않을 것이라고 보증하지 않는다. 긴 감사 한 회에 모든 자료를 넣는 대신 원자료 범위와 질문을 제한한다. 계측 가능한 문맥 여유가 작아지면 다음 큰 작업 전에 인계한다.

리셋권은 지원·잔여권·대상 창·사전 운영 권한이 확인되면 정책적으로 집행할 수 있다. 현재 감사에서는 소비하지 않는다. 조회가 안 되거나 검증 예산이 부족하면 `WAITING_REVIEW`로 둔다. 검증 없이 새 분기·승격으로 넘어가는 우회는 만들지 않는다. 정상 감시·수치 집계·이미 승인된 독립 작업은 LLM 한도와 분리한다.

## 8. 세션 공유와 재시작

**판단:** `state.json`을 super·lead·rl이 함께 덮어쓰는 구조를 버린다. 읽고 수정해 전체 저장하는 순간 lost update가 생기고, 쓰는 중 읽으면 잘린 JSON을 볼 수 있다. 파일 교체만 원자적으로 해도 두 작성자의 의미 충돌은 해결되지 않는다.

- 공정 상태의 작성자는 감독기 하나로 둔다. 세션은 요청과 관찰만 제출하고 전이를 직접 덮어쓰지 않는다.
- `sessions/<역할>/<session_id>.json`에는 담당 범위·현재 task·마지막 event 순번·heartbeat·만료 시각·막힌 이유를 적는다. 세션별 단독 작성, 임시 파일 후 원자 교체를 적용한다.
- 원장에는 작업 생성·claim·완료·실패·검증·분기 이벤트를 트랜잭션으로 남긴다. command ID 중복을 거부하고 상태 version이 맞을 때만 전이한다.
- 요청·응답에는 `request_id`, 대상 역할, 실행 ID, 만료, ack를 둔다. 관찰 시각이 오래된 세션은 활성 담당자로 보지 않는다.
- `STATE.md`와 JSON 요약은 원장에서 생성하는 읽기 전용 뷰다. Git 커밋 주기는 실행 중 상태 갱신 주기와 분리한다.

OS 재기동은 감독기를 다시 띄우는 것까지만 한다. 감독기는 원장의 RUNNING 작업과 실제 프로세스·산출물을 먼저 조정한다. 죽은 작업은 실패 또는 복구 대기로 전환하고, 완성된 자료는 검증 후 수용한다. 아직 살아 있는 worker를 새로 중복 실행하지 않는다. 네트워크 장애 동안 실행·기록은 로컬에서 보존하되 보고 대기열만 쌓고, 무한 대기열과 디스크 소진도 제한한다.

## 9. 구현 순서와 버릴 것

**판단:** 기존 PIPELINE의 “채점부터”보다 앞에 **실행 신원·입력 완전성·실패 기록**이 와야 한다. 틀린 자료를 정확히 채점하는 기능부터 만들면 다음 단계도 틀린 상태를 믿는다.

| 순서 | 만들어야 할 것 | 다음 단계로 넘어갈 증거 |
|---|---|---|
| 1 | v2b-s 실패 보존, 코드·규칙·입력 고정, 필요한 하네스와 의존 파일의 실행 사본 확정 | 누락 모듈·설정 차이 preflight 실패, 기존 학습은 보존 |
| 2 | 원장·원자적 실행 소유권·attempt별 출력·프로세스/GPU 수명 관리 | 동시 기동, worker 예외, 부모 종료, 재부팅 모의, 디스크 실패에서 중복·거짓 성공 없음 |
| 3 | 산출물 완전성 검사와 채점 수정 | 3절의 반례를 전부 거부하고 정상 v2a/v2b 수치는 그대로 재현 |
| 4 | 기계 규칙·분기 우선순위·재현·후보 교체·예산 상한 | 경계·누락·다중 일치·계획 밖 입력의 전이가 하나로 정해짐 |
| 5 | 검증 대기와 보고·알림 outbox, Git 발행 경계 | 원자료에서 독립 검증 통과, 보고 링크 폰 접근, 전송·push 실패 복구 |
| 6 | config diff guard와 학습 worker 연결, 선택 영상·시계열 보존 | 작은 승인 시험 한 바퀴가 실행·검증·보고까지 완료, 로그오프 후 동작 확인 |
| 7 | 제한된 실제 한 갈래, 이어서 48~72시간 운영 | 실패 주입·재기동·중단·한도 대기를 포함해 이력 손실과 중복 실행 없음 |

검증은 한 회 호출 자체가 관문이 아니다. 지적을 고치고 **다시** 원자료에서 검증해 통과해야 한다. 고쳤다는 주장도 재검증 대상이다.

**버릴 것:** PID 텍스트 파일의 비원자적 잠금, 임의 최신 디렉터리 선택, marker 존재만으로 성공 처리, 같은 출력 폴더 덮어쓰기, stderr 폐기, 공용 JSON 다중 작성, 산문과 수기 JSON의 이중 정본, “미검증으로 계속 분기”, 한도 조회 불가능이라는 단정, 프레임워크 도입만으로 신뢰성을 얻는다는 기대.

**유지할 것:** 기존 두 평가 하네스의 원자료와 평가 규격, 과거 결과의 회귀 대조, 순수 Wilson 함수, 명령 기록, 자동 학습을 아직 열지 않은 경계. 단, 함수 재사용을 입력 신뢰성 검증의 대체물로 쓰지 않는다.

## 10. 감사 제한과 발행 전 확인

이 감사는 코드 수정·운영 중단·자동화 설치를 수행하지 않았다. 요청한 감사문 한 파일만 산출한다. 격리 시험은 임시 사본에서 실행했고 실제 GPU 프로세스를 생성하지 않았다. 정상 자료 집계 2종과 결함 주입 결과는 2·3절에 기록했다. 동시 실행 환경이라 이 문서의 판정은 명시한 코드 판에 대한 것이다.

**미확인:** 48~72시간 연속 운전, 실제 재부팅 복구, 영상 유효성 전체 검사, 텔레그램 수신·링크 접근, 계정 한도 조회 실응답, 리셋권 소비, 원격 발행은 시험하지 않았다. 기존 예약 작업 설정도 권한 때문에 확인하지 못했다.

저장소 규칙에 따라 `git pull origin main`을 먼저 실행했다. 감사 이슈 생성은 정해진 두 분류 절을 넣어 시도했으나 GitHub API 프록시 `127.0.0.1:9` 연결 거부로 실패했다. 이슈가 생성됐다고 보고하지 않는다. 원격 PR·발행은 하지 않는다.

별도 발행 전 검증은 `codex exec --model gpt-6-astra -c model_reasoning_effort=high -s read-only --skip-git-repo-check`로 시도했다. **모델 검증이 시작되기 전에** `failed to initialize in-process app-server client: 액세스가 거부되었습니다. (os error 5)`로 종료됐다. 이 오류는 내용 검증 통과나 실패 판정이 아니다. 권한 우회는 하지 않았다. 따라서 이 파일은 요청한 로컬 감사 산출물이며, **저장소가 요구하는 별도 발행 전 검증은 미완료**다. 검증 가능한 환경에서 수치와 수정 주장을 다시 확인한 뒤 공식 보고로 승격해야 한다.

자체 형식 점검에서는 필수 머리 여섯 항목과 em dash 0개를 확인했다. 실행기·채점기 수정은 하지 않았으며, 결함이 고쳐졌다고 보고하지 않는다.
