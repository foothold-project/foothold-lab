# 루프 운영 설계 · 세션이 죽어도 돈다

> 분류: 계획
> 작성: 오흥재 · 2026-09-23
> 근거: `CronCreate` 도구 설명(세션 전용 · 7 일 만료) · Windows 예약 작업 등록 시험 · `BRANCH-TABLE.md` 분기 조건 · codex 쿼터 실측(팀장 제공)
> 요지: 루프의 기계적인 부분은 LLM 없이 스크립트가 돌린다. 상태는 저장소에 있고 세션에는 없다. LLM 은 분기표에 없는 결과가 나왔을 때만 부른다.
> 상태: 초안
> 판: v1.0

## 0. 무엇이 문제였나

팀장이 여러 번 말한 요구입니다. **문맥 한도 · 압축 · 주간 한도와 무관하게 루프가 돌아야 합니다.**

지금까지 제가 쓴 방식은 전부 그 요구를 못 채웁니다.

| 수단 | 세션이 죽으면 | 문맥이 압축되면 | 주간 한도에 걸리면 |
|---|---|---|---|
| Claude 세션이 직접 진행 | **멈춤** | 세부를 잃음 | **멈춤** |
| `CronCreate` | **같이 사라짐** (메모리 전용) | | **멈춤** |
| 백그라운드 `codex exec` | **같이 죽음** | | **멈춤** |
| 대화에만 있는 판단 | **사라짐** | **사라짐** | |

**`CronCreate` 는 세션 전용이고 7 일이면 만료됩니다.** 도구 설명에 그렇게 적혀 있습니다. 세션이 죽으면 깨워 줄 것이 없습니다.

## 1. 원칙 셋

```
1  상태는 «저장소» 에 있다. 세션에는 없다
   새 세션이 파일만 읽고 이어받을 수 있어야 한다

2  기계적인 일은 «LLM 없이» 돌린다
   학습 걸기 · 완료 감지 · 평가 · 채점 · 기록 · 커밋은 스크립트가 한다

3  LLM 은 «분기표에 없는 결과» 가 나왔을 때만 부른다
   그 외에는 표를 읽어 그대로 집행한다
```

**3 번이 핵심입니다.** 판단이 필요한 자리를 미리 없애 두었으므로(분기표), 루프가 도는 동안 LLM 이 거의 필요 없습니다. 그래야 주간 한도와 무관해집니다.

## 2. 무엇이 세션 밖에서 사는가

```
Windows 예약 작업        10 분마다 감시 스크립트를 깨운다
                         등록 권한 확인함 (2026-09-23)
                         세션 · 재부팅과 «무관» 하다

저장소의 상태 파일        지금 어디인지 · 무엇이 도는지 · 다음이 무엇인지
                         사람이 읽을 수 있고 스크립트도 읽는다

분기표                    결과별 다음 단계가 «미리» 적혀 있다
                         감시 스크립트가 이 표를 읽는다
```

## 3. 감시 스크립트가 하는 일

```
매 10 분

 1  상태 파일을 읽는다
 2  단계가 «학습 중» 이면
       프로세스와 체크포인트를 확인한다
       끝났으면 -> 평가를 걸고 상태를 갱신
       예상 시간의 1.5 배를 넘겼으면 -> 멈춤
 3  단계가 «평가 중» 이면
       끝났으면 채점 도구를 돌리고 결과를 상태에 적는다
 4  채점 결과를 «분기표의 조건» 과 대조한다
       맞는 칸이 있으면 -> 다음 단계를 걸고 상태를 갱신
       맞는 칸이 «없으면» -> 멈춤 · 사람 대기로 표시
 5  무엇을 했든 로그를 남기고 커밋한다
```

**멈춤은 실패가 아닙니다.** 표에 없는 결과가 나왔다는 뜻이고, 그때 사람이나 LLM 이 봅니다.

## 4. 상태 파일

두 벌을 둡니다. **같은 내용이고 하나는 사람, 하나는 스크립트용입니다.**

```
_out/loop/STATE.md      사람이 읽는다. 지금 무엇이 왜 도는지
_out/loop/state.json    스크립트가 읽고 쓴다
```

`state.json` 에 들어가는 것.

```
현재 단계        분기표의 어느 갈래인지 · 어느 국면인지(학습/평가/채점/대기)
돌고 있는 것     PID · GPU · 시작 시각 · 예상 종료 · 로그 경로
직전 결과        축 1 · 축 2 · 절대 최저 칸 · 미판정 수 · 0 인 칸
다음 후보        분기표에서 읽은 다음 단계
멈춤 사유        비어 있으면 도는 중 · 차 있으면 사람 대기
예산             학습 판 수 · 누적 시간 · codex 호출 수
```

**커밋마다 상태 파일도 같이 올립니다.** 그러면 새 세션이 `git pull` 만으로 따라잡습니다.

## 5. 새 세션이 이어받는 절차

문맥이 압축됐거나 세션이 바뀌었을 때 **이 순서만 따르면 됩니다.**

```
1  git pull origin main
2  _out/loop/STATE.md 를 읽는다      지금 어디인가
3  CRITERIA.md 를 읽는다             무엇을 통과라 부르는가
4  BRANCH-TABLE.md 를 읽는다         다음에 무엇을 돌리는가
5  멈춤 사유가 있으면 그것부터 푼다
   없으면 감시 스크립트가 돌고 있는지만 확인하고 «건드리지 않는다»
```

**대화 기록을 읽을 필요가 없어야 합니다.** 그것이 이 설계의 시험입니다.

## 6. 예산 정책

**codex** · 2026-09-23 기준 주간 한도의 **78 %** 를 썼고 세션은 2 일 1 시간 뒤 초기화됩니다. 리셋권이 하나 남았습니다.

```
필수      판정문 «확정» 전 검증 한 회차. 이것만은 뺄 수 없다
          지금까지 우리가 낸 잘못이 전부 이 회차에서 잡혔다

선택      설계 감사 · 원자료 재집계
          한도가 20 % 아래면 «건너뛰고 상태 파일에 미검증으로 표시»

금지      감시 스크립트의 정상 경로에서 codex 를 부르지 않는다
          기계적인 일에 LLM 을 쓰면 한도가 금방 닳는다
```

**한도가 바닥나면 루프가 멈추는 것이 아니라 「검증 없이 진행하고 표시」합니다.** 나중에 한도가 돌아왔을 때 표시된 것만 몰아서 검증합니다.

## 7. 이 설계가 «못» 하는 것

```
학습 자체의 실패 원인 진단      사람이나 LLM 이 봐야 한다
분기표에 없는 결과의 판단       그래서 멈춘다
설계가 틀렸을 때                루프는 틀린 설계를 성실히 집행한다
                              그래서 돌리기 «전에» 감사를 받는다
Windows 재부팅 중의 학습        예약 작업은 살지만 돌던 학습은 죽는다
                              상태 파일에서 「학습 중」인데 프로세스가 없으면
                              멈춤으로 표시하고 사람을 기다린다
```

**마지막 것이 중요합니다.** 죽은 학습을 스크립트가 «자동으로 다시 걸지» 않습니다. 같은 이름의 결과가 둘 생기면 어느 것이 무엇인지 알 수 없게 됩니다.

## 8. 만들 순서

```
1  상태 파일 둘과 그것을 읽고 쓰는 최소 도구
2  감시 스크립트 · «읽기만» 하는 판으로 먼저 (아무것도 안 건다)
3  Windows 예약 작업 등록 · 10 분마다
4  며칠 돌려 보고 상태 파일이 실제로 따라오는지 확인
5  그다음에 «거는» 기능을 켠다
```

**5 번을 마지막에 두는 까닭** · 잘못 걸면 GPU 세 시간을 잃습니다. 읽기만 하는 판으로 먼저 신뢰를 쌓습니다.
