# 1 · device 가 학습 결과를 바꾸는가 · **바꿉니다. 다만 GPU 품질 문제가 아닙니다**

## 무엇을 쟀나

| 비교 | 조건 | 결과 |
|---|---|---|
| `v2b-s` 대 `v2b-s2` | seed 43 · **둘 다 sim `cuda:1`** · 다른 날 | **공통 checkpoint 67 개 전부 일치** |
| `v2b` 대 `v2b-r` | seed 42 · **sim `cuda:1` 대 `cuda:0`** | `model_0` 부터 갈라짐 · 1000 판 뒤 86 배 |

`실측` · 67 개는 파일 SHA-256 67/67, 신경망 tensor 67/67, optimizer 상태 67/67 이 같습니다.

**그래서 「재실행하면 원래 조금 다르다」가 여기서는 성립하지 않습니다.** 오차가 0 입니다.

## 다른 게 정말 device 뿐이었나

`실측` · 전수로 훑었습니다.

```
env.yaml       양쪽 1088 줄 · 다른 줄 «2»  (sim device · log_dir)
agent.yaml     양쪽   50 줄 · 다른 줄 «1»  (run_name)
IsaacLab.diff  네 실행 전부 sha256 «동일»
출발 checkpoint  9/10 이후 mtime 안 바뀜
```

`v2a_env_cfg.py` 와 `v2b_env_cfg.py` 의 mtime 이 두 학습 사이(9/22 20:48)였는데, 3 차 검증이 **그 수정이 `v2b` 의 설정 «값» 을 바꾸지 않는 수정**이라고 코드로 확인했습니다.

## **그런데 기전은 「GPU 품질」이 아닙니다**

`확인됨` · 3 차 검증이 짚었습니다.

```
v2b     sim cuda:1 · PPO cuda:0   ->  난수 생성기가 «갈린다»
v2b-r   sim cuda:0 · PPO cuda:0   ->  생성기를 «같이 쓴다»
```

CUDA 의 기본 난수 생성기는 **장치마다 상태를 따로** 갖습니다. 그리고 난수를 쓰는 곳이 두 장치에 흩어져 있습니다.

| 무엇을 뽑나 | 어느 장치에서 |
|---|---|
| 속도 명령 · 정지 환경 표집 | **env(sim) device** |
| 초기 episode 길이 | **env(sim) device** |
| action 표집 (`Normal.sample`) | **PPO device** |
| minibatch 순서 (`randperm`) | **PPO device** |

**sim 을 옮기면 「두 소비 경로가 같은 생성기를 쓰는가」부터 바뀝니다.** seed 가 같아도 각 용도가 소비하는 난수열이 같지 않습니다.

## 그래서 **확정한 것과 안 한 것**

```
확정   두 학습의 성적 차이는 원자료에서 «재현» 된다
확정   같은 seed·같은 device 의 저장 checkpoint 는 비트까지 같다
확정   기록된 유효 설정의 차이는 sim device 와 실행 경로뿐이다

미확정 «device 배치가 단독 원인» 이라는 것
       실행 당시 전체 소스·asset·runtime 의 동일성은 소급 증명 불가
       (IsaacLab.diff 는 gap_training/ 을 «디렉터리 이름» 으로만 기록한다)
미확정 어느 GPU 가 «더 나은가». 그런 것은 재지 않았다
```

## **워크스테이션 셋업 자체가 문제인가 · 아닙니다**

`판단` · GPU 두 장 다 정상입니다. 난수·행렬곱을 재 보니 **비트까지 같습니다**(RTX 5080 · SM 84 · cc 12.0 동일). 문제는 **하드웨어가 아니라 「sim 과 PPO 를 어느 장치에 두는가」라는 «배치»** 입니다.

**그러니 장비를 바꿀 필요가 없습니다.** 배치를 고정하면 됩니다.

# 2 · 평가는 어느 device 에서 해도 되는가 · **됩니다 (확인된 범위 안에서)**

`실측` · 같은 checkpoint(`v2b` model_3000)를 `cuda:0` 과 `cuda:1` 에서 평가했습니다.

```
축 1 성공 수 차이      0 / 48 칸
원시 csv 4,800 행     «모든 저장 열» 이 같음
```

**통과 개수만 같은 게 아니라 원시 행 전체가 같습니다.**

**까닭** · 평가는 정책이 «고정» 이고 되먹임이 없습니다. 학습은 자기가 만든 데이터로 자기를 고치는 고리라 작은 차이가 증폭되는데, 평가에는 그 증폭이 없습니다.

```
확인된 범위   v2b iter3000 · 축 1 규격
안 잰 것      축 2 · 다른 checkpoint · RunPod · 저장 안 한 float 정밀도
```

**「평가 device 는 «언제나» 결과를 안 바꾼다」로 쓰면 범위를 넘습니다.**

# 4 · `v2a 대 v2b` 가 왜 문제인가 · **쉽게 다시**

## 계보의 핵심 주장이 이것이었습니다

> `v2a` 에서 **정지 학습 비율 하나만** `0.02 -> 0.10` 으로 올렸더니 축 1 이 좋아졌다 (하락 `2·1·2·0` → `0·0·0·0`)

## 그런데 **하나가 아니라 둘 달랐습니다**

```
v2a    정지 비율 0.02    sim cuda:0
v2b    정지 비율 0.10    sim cuda:1     <- 이것도 달랐다
```

9/21 에 두 판을 **두 GPU 에 나눠 동시에** 걸었기 때문입니다. **그때는 「GPU 는 영향 없겠지」라고 봤고 그게 틀렸습니다.**

```
그래서 「축 1 이 좋아진 것」의 원인이 둘 중 무엇인지 «말할 수 없습니다»
  정지 비율 때문인가
  sim 배치 때문인가
```

## 그런데 **더 나은 자료가 지금 생겼습니다**

```
v2a     정지 비율 0.02    sim cuda:0
v2b-r   정지 비율 0.10    sim cuda:0     <- «같은 device»
```

**이 둘은 정지 비율만 다릅니다.** `v2b-r` 을 돌린 원래 목적은 「device 효과 측정」이었는데, 뜻밖에 **「v2a 대 v2b 의 깨끗한 판」** 이 덤으로 생겼습니다.

```
v2a     축1 하락  2 · 1 · 2 · 0
v2b-r   축1 하락  2 · 0 · 0 · 0     <- 같은 device 끼리의 비교
```

**정지 비율을 올린 효과가 「2·1·2·0 → 2·0·0·0」 입니다.** 「0·0·0·0」이 아닙니다.

**다만 이것도 seed 하나짜리 한 쌍입니다.** 효과라고 확정하려면 seed 를 여러 개 써야 합니다.

## 교란이 있는 비교 전체 목록

`확인됨` · 각 실행의 `params/env.yaml` 을 직접 읽었습니다.

```
cuda:0   A · foothold-v1 · D · E · F · H · v2a · v2b-r
cuda:1   G · v2b · v2b-s · v2b-s2
```

| 비교 | 상태 |
|---|---|
| v1 대 G · v1 대 v2b | 교란 있음 |
| E 대 G · F 대 G | 교란 있음 |
| **v2a 대 v2b** | **교란 있음** |
| F/H 대 v2b | 교란 있음 |
| v1→D→E→F→H · F 대 v2a | **교란 없음** |
| **v2a 대 v2b-r** | **교란 없음 · 더 나은 쌍** |
| v2b 대 s · s 대 s2 | 교란 없음 (seed 비교와 반복) |

**`foothold-v1` 도 `cuda:0` 입니다** · 그 실행의 `model_1500.pt` 와 `models/foothold-v1.pt` 의 SHA-256 이 같습니다.

# 7 · Orca 로 세션 간 통신이 되는가 · **됩니다. 제가 안 쓰고 있었습니다**

```bash
orca orchestration run-create --objective "<목표>" --json
orca orchestration worker-start --spec "<명세>" --worktree current --agent codex --json
orca orchestration worker-start --spec "<명세>" --worktree current --agent claude --json
orca orchestration check --wait --types "worker_done,escalation,question" --timeout-ms 900000 --json
```

`check --wait` 가 **막혀서 기다리다가** 워커가 끝나거나 물으면 깨어납니다. **제가 오늘 한 폴링과 정반대입니다.**

| 오는 것 | 뜻 |
|---|---|
| `worker_done` | 끝났다 |
| `escalation` | 막혀서 올린다 |
| **`question`** | **되묻는다** ← 「맥락 못 짚는 워커」의 답 |

`reply --id <message_id> --body "<답>"` 로 답합니다. **워커가 모르면 추측하지 않고 묻습니다.**

## 작업 명세에 반드시 들어가야 하는 다섯

```
Target                 무엇을 건드리는가
Change                 무엇을 만들어야 하는가
Constraints            불변식 · 건드리면 안 되는 것
Ownership              이 워커가 고쳐도 되는 범위
Observable acceptance  «무엇으로» 완료를 증명하는가
```

**제가 오늘 띄운 의뢰서에 뒤 둘이 없었습니다.**

## 안전 규칙

```
worker-start 가 실패하면 «다시 띄우지 않는다»
빈 응답 세 번이면 worker-list 로 «열거» 한다
「응답 없음」은 중단·포기·재시도 권한이 «아니다»
끝난 뒤 셋 중 «정확히 하나» · 재사용 · worker-retain · worker-release
```

```
          실행마다 GPU UUID · 모델명 · CUDA_VISIBLE_DEVICES 를 기록한다
          「cuda:0」이라는 문자열은 기계마다 다른 GPU 를 가리킨다
```
