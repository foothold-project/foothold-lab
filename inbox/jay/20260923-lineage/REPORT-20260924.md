## 1. 장치 · 「GPU 가 다르면 결과가 다르다」는 틀렸다

### 무엇을 쟀나

같은 시드 42, 같은 지형, 같은 3001 판을 **배치만 바꿔** 두 번 돌리고
체크포인트 파일을 바이트로 비교했다.

| 판 | sim | PPO | 결과 |
|---|---|---|---|
| v2b-r | cuda:0 | cuda:0 | 기준 |
| v2b-p11 | cuda:1 | cuda:1 | **121 / 121 개 체크포인트가 완전히 같다** |

**GPU 번호는 아무 영향이 없다.** 0 번에서 돌리든 1 번에서 돌리든
짝을 맞추면 파일 해시까지 같다.

### 그럼 v2b 와 v2b-r 은 왜 달랐나

`train.py:127` 은 `--device` 로 **시뮬레이션만** 옮긴다.
`agent_cfg.device` 는 `:138` 의 `--distributed` 아래에서만 바뀐다.
그래서 `--device cuda:1` 만 주면 **sim 은 1 번, PPO 는 0 번**에 흩어진다.

CUDA 난수 생성기는 **장치마다 따로** 있다. 둘이 갈라지면 난수 흐름이
갈라진다. 실제 소비 지점 넷:

```
velocity_command.py:128   명령 표집      환경 장치
on_policy_runner.py:68    관측 잡음      환경 장치
actor_critic.py:148       행동 표집      PPO 장치
rollout_storage.py:167    미니배치 섞기  PPO 장치
```

**그래서 「GPU 를 바꾸지 마라」가 아니라 「sim 과 PPO 를 같은 장치에
짝지어라」가 맞는 규칙이다.**

### 실무로 무엇이 바뀌나

```
앞으로 모든 학습    --device cuda:N  agent.device=cuda:N   (둘을 같이)
두 GPU 병렬         열렸다. 0 번과 1 번에 서로 다른 실험을 동시에.
평가                장치 무관. 48 칸 4800 행이 0 개 다르다 (실측).
```

`_out/loop/eval_runner.py` 에 넣었던 「평가는 학습과 같은 장치에서」
제약은 **근거가 없어 철회했다.**

### 남는 교란 (astra 지적)

- `foothold-v1` 대 `v2b` 는 sim 장치가 갈라진 채 비교됐다. **깨끗한 짝은
  `v2a` 대 `v2b-r` 이다.**
- 4090(팀원 RunPod) 과 5080 을 등치할 수 없다. 장치가 다르면 커널 선택이
  달라진다. 비교 「안에서」 고정하는 것이 규칙이지, 전 세계를 맞추는 것이
  아니다.

## 2. 시드 43 · 원인을 찾았다

### 증상

seed 43 은 세 번 돌려 세 번 다 **같은 자리에서** 죽었다.

| 실행 | 마지막 판 | 오류 |
|---|---|---|
| v2b-s (09-23 14:42) | `Learning iteration 1670/3001` | `RuntimeError: normal expects all elements of std >= 0.0` |
| v2b-s2 (09-23 17:08) | `Learning iteration 1670/3001` | 같음 |
| v2b-s3instr (09-24 19:05) | `Learning iteration 1670/3001` | 같음 |

**결정론이 지켜졌다.** 같은 시드·같은 배치면 같은 자리에서 같은 오류다.

> 정정 · 제가 전에 「step 1578 에서 발산」이라고 보고했습니다. 틀렸습니다.
> 로그 실측은 1670 판이고, 계측 CSV 의 마지막 완료 `update()` 는 1671 번째입니다.

### 어디서 터지나

```
on_policy_runner.py:148   loss_dict = self.alg.update()
ppo.py:250                self.policy.act(obs_batch, ...)
actor_critic.py:152       return self.distribution.sample()
torch/distributions/normal.py:74
    RuntimeError: normal expects all elements of std >= 0.0
```

**롤아웃이 아니라 PPO 의 `update()` 안**이다.

### 왜 그것이 가능한가 · 소스

```python
actor_critic.py:31    noise_std_type: str = "scalar"       # 기본값
actor_critic.py:93    self.std = nn.Parameter(init_noise_std * torch.ones(num_actions))
actor_critic.py:140   std = self.std.expand_as(mean)
actor_critic.py:146   self.distribution = Normal(mean, std)
```

우리 설정(`rsl_rl_ppo_cfg.py:18`)은 `init_noise_std=1.0` 만 준다.
그래서 `noise_std_type` 은 **기본값 `scalar`** 이고, `self.std` 는
**아무 제약이 없는 맨 파라미터**다. Adam 이 그것을 **0 아래로 밀 수 있다.**
`Normal(mean, std)` 은 음수 `std` 를 받으면 torch 가 예외를 던진다.

대안 경로는 구조적으로 이것을 못 만든다.

```python
actor_critic.py:95    self.log_std = nn.Parameter(torch.log(...))
actor_critic.py:142   std = torch.exp(self.log_std).expand_as(mean)
```

`exp()` 는 **언제나 양수**다. `noise_std_type="log"` 이면 이 오류는
**일어날 수 없다.**

### 죽기 전 62 판에 무슨 일이 있었나 (계측 CSV)

| 판 | `grad_norm` | `std_min` |
|---|---|---|
| 1500 | 0.99999917 | 0.35734373 |
| 1600 | 0.35790494 | 0.35774231 |
| **1610** | **0.0** | 0.36009711 |
| 1650 | 0.12988402 | 0.36640480 |
| **1660~1670** | **0.0** | 0.36703002 (7 판 비트 단위로 고정) |
| 1671 | 0.99999982 | 0.36704677 |
| 1672 | (터짐) | |

**gradient 가 정확히 0 인 판이 23 개**다. 그동안 `std` 가 소수점 16 자리까지
얼어붙는다. 그러다 1671 에서 clip 한계(1.0)에 닿는 gradient 가 한 번 오고,
그다음 update 가 `std` 를 음수로 밀었다.

**비유한수(NaN/Inf) 는 1671 판 내내 0 개다.** v2b 가 보였던
`-2.70e+22` 보상 폭발과는 **다른 고장**이다.

### 내 계측의 한계 (먼저 적는다)

계측기의 「이상 감지」는 **한 번도 안 울렸다.** `update()` 가 반환한 뒤에
읽기 때문인데, 치명적인 값은 `update()` 안에서 생기고 그 자리에서
예외가 난다. 답을 준 것은 덤프가 아니라 **터지기 전 62 판의 CSV** 다.
관문을 만들었으면 깨뜨려 봤어야 했다.

### 처방

```
noise_std_type = "log"      한 줄. 이 고장 종류가 구조적으로 사라진다.
```

아직 **안 걸었다.** 기준선 셋과 배치를 바꾸는 변경이라 팀장 승인 뒤
별도 판으로 건다.

## 4. astra 검증 (AUDIT8-plan.md v1.1 · 68 KB · 21:46 완료)

### 가장 중요한 지적 · 1 순위는 「한 가지」가 아니다

| 변경 | 실제로 묻는 것 | astra 판정 |
|---|---|---|
| 백색 잡음 ±0.10 -> ±0.02 | 매 순간 셀마다 달라지는 오차가 학습을 방해했나 | **비용 낮고 우선할 가치 있음** |
| 드리프트 0 -> ±0.05 | 지속되는 위치·높이 오차에 「견디게」 할 수 있나 | **강건성 가설.** stones 0 % 를 고친다고 단정 못 함 |
| 격자 x 0 -> 0.2 | 앞을 더 보면 유리한가 | 관측 「범위」 변경. 뒤 0.2 m 를 잃는다 |

**셋은 같은 방향의 손잡이가 아니다.** 그래서 제가 짰던
「A 와 B 를 한 판에 같이 건다」는 **철회한다.**

### 그 밖의 확정 사항

- **「학습된 무시」는 유일한 해석이 아니다.** `enable_corruption=False` 는
  관측 manager 의 noise 항만 끈다. RayCaster 의 drift 설정은 그대로다.
  훈련 노출 부족·보상·학습량·포화 처리가 함께 남는다.
- **난이도 0.1 에서 틈이 사라지는 것은 heightfield 격자 절삭**이지
  센서 잡음이 아니다. 지형 격자와 관측 격자는 따로 다룬다.
- **`v2c` 를 그대로 쓰면 안 된다.** v2c 는 **v2a**(정지 0.02)를 물려받는데
  기준선 r 은 **v2b**(정지 0.10)다. 잡음 말고 정지 비율도 같이 바뀐다.
- **보상(v2g)을 먼저 시험한 것은 잘못이 아니다.** SYNTHESIS 6 절은
  「효과가 입증된 순서」가 아니라 당시 조사에 따른 제안이다.
  순서를 바꾼 이유를 기록하면 된다. v2g 의 단일 변수 비교는 유효하다.

### astra 의 최종 우선순위 (8 항)

```
1  측정·입력 진단 보강      횡보·후진 칸 · stones 실제 틈 · hit/miss/포화
2  v2g 결과를 기준으로 고정  보상 감도 시험으로 해석 · 폐기하지 않는다
3  stones 능력이 목표면 S    훈련 분포에 stones 10 % 교체
4  백색 잡음 감소 N 독립 대조 drift 는 0 유지 · ±0.10 -> ±0.02 만
5  장기 학습은 별도 물음      사전등록 10001 판 · 평탄하다고 버리지 않는다
6  명령 범위는 측정 뒤        후진 vx 와 횡 vy 를 구분
7  추가 발 보상·드리프트·격자 확인된 실패 원인에 맞춰 고른다
8  구조 변경은 그 뒤 병목에   고정된 계단으로 보지 않는다
```

### S 와 N 중 무엇이 먼저인가 · 목적이 가른다

```
stones 능력 획득이 목표      -> S (훈련 분포 교체) 먼저
미경험 일반화 유지가 목표    -> N (백색 잡음) 먼저
슬롯이 둘이면                -> 둘을 따로 병렬로. 묶지 않는다.
```

우리 주제가 「미경험 험지 적응」이고 **GPU 슬롯이 둘**이므로
**N 을 먼저 걸고 S 를 나란히 건다.**
