## 답해 주실 것

### 1. 코드 셋에 결함이 있습니까

`watchdog.py` · `eval_runner.py` · `verdict.py` 를 읽고, **돌려도 보면서** 봐 주십시오. 특히 이런 것들입니다.

```
경합      감시가 10 분마다 도는데 평가가 두 번 걸릴 수 있습니까
죽음      학습·평가가 중간에 죽으면 상태가 어떻게 됩니까
잘못된 성공  산출물이 없는데 성공으로 세는 자리가 있습니까
조용한 실패  오류 없이 틀린 결과를 내는 경로가 있습니까
장치       평가를 cuda:1 / cuda:0 에 나눈 근거가 타당합니까
```

`verdict.py` 는 `v2a` · `v2b` 의 기존 결과로 시험했고 계보 기록과 맞았다고 제가 주장합니다. **그 주장을 원자료로 확인해 주십시오.** 그리고 **맞았다는 것이 무엇을 보증하고 무엇을 보증하지 않는지**도 적어 주십시오.

### 2. 이 요구를 채우는 «최선의» 구조는 무엇입니까

제가 고려한 축은 이렇습니다. **여기에 없는 선택지를 들어도 좋습니다.**

```
세션 의존성   Claude Code 세션 안에서 도는 것은 세션이 죽으면 멈춥니다
              (CronCreate 는 도구 설명상 세션 전용 · 메모리 · 7 일 만료)
GPU 위치      학습·평가는 «이 워크스테이션» 에서만 됩니다
토큰 비용     루프가 도는 동안 LLM 을 얼마나 부를 것인가
재시작        재부팅·정전 뒤에 무엇이 다시 켜 줍니까
관측성        팀장이 밖에서 폰으로 무엇을 보아야 합니까
```

외부 오픈소스(Prefect · Airflow · Dagster · GitHub Actions self-hosted runner · systemd 류 · Windows 서비스 · n8n 등)를 쓰는 편이 나은지, 아니면 얇은 자체 데몬이 나은지 **판단과 근거**를 주십시오. 설치·운영 비용과 이 과제의 규모를 같이 보십시오.

### 3. 자동화하면 «위험한» 자리는 어디입니까

특히 이 셋에 대해 의견을 주십시오.

```
학습을 자동으로 거는 것
판정 결과로 분기를 자동으로 고르는 것
루프가 스스로 git commit · push 하는 것
```

각각 **무엇이 잘못되면 무엇을 잃는지**와, 그것을 막을 관문을 적어 주십시오.

### 4. 한도와 문맥

**저는 제 토큰 사용량이나 주간 한도를 조회할 도구가 없습니다.** `codex --help` 에도 usage·quota 하위 명령이 없습니다. 이 제약 아래에서 팀장의 요구(실시간 파악 · 리셋권 활용)를 **어디까지 채울 수 있습니까.** 채울 수 없는 부분은 그렇게 적어 주십시오.

### 5. 세션 간 공유

`super` · `lead` · `rl` 세 세션이 서로 무엇을 하는지 알아야 합니다. 지금은 `_out/loop/state.json` 하나뿐입니다. **어떤 구조여야 합니까.** 한 파일을 여럿이 쓸 때의 문제도 같이 보십시오.

### 6. 무엇부터 만들어야 합니까

빈 자리가 여럿입니다(`PIPELINE.md` 참조). **의존 관계를 따져 순서를 제시해 주십시오.** 그리고 **지금 있는 것 중 버려야 할 것**이 있으면 그것도 적어 주십시오.
