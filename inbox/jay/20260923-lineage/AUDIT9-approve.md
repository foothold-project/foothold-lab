## 2. log 전환 · 목적함수의 형태는 같지만 최적화는 달라진다

**`확인됨` · `actor_critic.py:95,142`는 `log_std`를 최적화하고 `exp(log_std)`를 유효 std로 쓴다.** `state_dependent_std=False`인 현재 설정에서 새 초기화 `init_noise_std=1.0`은 `std=1`과 `log_std=0`에 대응한다.

하지만 우리는 새 초기화가 아니라 NVIDIA checkpoint에서 시작한다. `L/nvidia_pretrained_source/nvidia_pretrained.pt`를 CPU로 읽으면 `std` 12개의 범위가 **0.4433040321~0.8098655939**다. 따라서 출발 분포를 유지하는 전환은 `log_std = log(기존 std)`여야 한다. 이 부분을 0으로 초기화하면 탐색 잡음 크기까지 함께 바꾼다.

**`판단` · log 전환은 최적화 좌표를 바꾸는 실험이다.** `ρ=log σ`에 Adam이 `Δρ`를 주면 `σ_new=σ_old×exp(Δρ)`다. 반면 scalar는 `σ_new=σ_old+Δσ`다. 같은 learning rate라도 같은 걸음이 아니다. `∂L/∂ρ=σ·∂L/∂σ`이므로 Adam의 moment와 전역 clipping에 들어가는 gradient도 달라진다. actor·critic까지 공유하는 clipping 비율도 영향을 받을 수 있다.

entropy는 `actor_critic.py:121~122`에서 동일한 Normal entropy를 합산한다. 같은 유효 `μ,σ`라면 그 **값과 목적함수의 정의는 같다**. 다만 Normal의 행동별 entropy는 `log σ + 상수`이므로 scalar에 대한 도함수는 `1/σ`, log 좌표에 대해서는 `1`이다. 현재 entropy 계수 0.01을 그대로 두어도 최적화 영향이 같지는 않다.

KL도 `ppo.py:260~266`에서 이전·현재의 유효 `μ,σ`로 계산한다. log 전환 자체가 KL의 수식을 바꾸지는 않는다. 그러나 학습 궤적이 바뀌면 KL과 adaptive learning rate의 변화도 달라진다. “entropy와 KL은 안 바뀌므로 학습도 동일”은 틀리다.

**“항상 양수”는 실수 연산의 수학적 설명으로만 맞다.** 실제 부동소수점에서는 exp가 0으로 underflow하거나 Inf로 overflow하고, NaN 입력은 NaN으로 남는다. Normal의 log probability에는 `log(std)`도 있으므로 0 역시 유효한 정상 학습 상태가 아니다. log는 **유한한 값의 음수 std 경로를 제거하는 설계**이지, NaN·Inf·학습 실패 전체의 방지책이 아니다.

## 3. checkpoint와 두 평가 하네스 · 현재 코드 그대로는 양립하지 않는다

**`확인됨` · 키가 바뀌고 자동 변환은 없다.** 새 policy의 저장 키는 `log_std`, 기존 NVIDIA checkpoint는 `std`다. `actor_critic.py:186~198`은 기본 `strict=True`로 상위 `load_state_dict`를 호출한다. `P/rsl_rl/runners/on_policy_runner.py:309~325`도 키를 변환하지 않는다. 학습 진입점 `I/scripts/reinforcement_learning/rsl_rl/train.py:207~210`은 그대로 `runner.load(resume_path)`를 부른다.

| 경로 | 현재 소스 기준 판정 |
|---|---|
| log policy에 기존 NVIDIA checkpoint를 직접 resume | **불가.** `log_std` 누락, `std` 예상 밖 키 |
| 현재 두 하네스로 기존 scalar checkpoint 평가 | std 형식 때문에 새로 깨지지 않는다. 기존 구조와 일치 |
| 현재 두 하네스로 새 log checkpoint 평가 | **불가.** 하네스가 scalar policy를 만들므로 반대 방향 키 불일치 |
| 전역 기본값만 log로 변경한 뒤 기존 scalar checkpoint 평가 | **불가.** 이번에는 옛 checkpoint 쪽이 안 맞는다 |

축 1은 `W/sim/eval/eval_generalization.py:698,791~794`, 축 2는 `W/sim/eval/eval_command_response.py:609~621,640`에서 registry의 기본 agent를 만들고 checkpoint를 읽는다. 각 실행의 저장 agent YAML이나 checkpoint의 std 형식을 먼저 읽어 분기하는 코드가 없다. 공식 Go2 Rough agent 설정은 `I/source/isaaclab_tasks/isaaclab_tasks/manager_based/locomotion/velocity/config/go2/agents/rsl_rl_ppo_cfg.py:18`에서 init std만 지정하고, `I/source/isaaclab_rl/isaaclab_rl/rsl_rl/rl_cfg.py:31,34`의 scalar/False 기본값을 받는다.

추론이 `act_inference()`의 actor 평균을 쓰므로 std를 샘플링하지 않는다는 사실도 **strict 로딩 실패를 우회해 주지는 않는다**. 정확한 표현은 “현재 옛 기준선은 유지되지만 새 log checkpoint를 평가할 수 없다”다. “지금 기준선 전체가 이미 깨졌다”는 아니다.

추가로 **`I/train_instrumented.py:86`은 `self.policy.std`를 직접 읽는다.** log policy에는 그 속성이 없어서, checkpoint 문제만 해결해도 첫 update 후 계측에서 AttributeError가 날 수 있다. 이 실행 경로도 호환성 대상이다.

**`판단` · 실행 전 충족할 조건은 다음과 같다. 이번 감사에서 구현하지 않았다.**

1. 원본 checkpoint를 보존하고, 유한·양수 std를 확인한 뒤 log로 변환한 별도 초기 checkpoint 또는 명시적 로딩 경로를 만든다. 원본 SHA, 변환식, 모델 설정과 optimizer 처리 방침을 남긴다. `strict=False`로 누락을 덮지 않는다.
2. 두 평가 하네스가 저장 설정 또는 `std`/`log_std` 키를 검사해 **맞는 policy 형식을 먼저 구성**하도록 한다. 키가 둘 다 있거나 둘 다 없는 예상 밖 형식은 오류로 처리한다. 평가에는 불필요한 optimizer를 읽지 않는 경로도 분리한다.
3. CPU 검증에서 옛 scalar·새 log의 strict load, 변환 전후 actor 출력과 유효 std의 일치 허용오차를 확인한다. 기존 하네스의 옛 checkpoint 동작도 회귀 확인한다. 이것은 제안된 검증이며 이번에 하네스를 실행한 것은 아니다.
4. 계측기를 두 형식에서 유효 std를 읽도록 하고, 1절의 실패 시점 기록 누락을 해결한다.

**optimizer는 키만 바꾸면 끝나지 않는다.** runner는 기본으로 optimizer도 불러온다. PyTorch `P/torch/optim/optimizer.py:833~885`는 저장된 파라미터 ID와 현재 그룹의 순서로 state를 연결한다. std와 log_std의 모양이 같아서 state가 들어간다고, scalar 좌표의 Adam moment가 log 좌표에서도 올바른 것은 아니다. 과거 gradient마다 당시 σ가 달랐으므로 현재 σ 하나로 moment를 곱해 정확히 복원할 수도 없다.

가장 명료한 첫 대조는 **같은 NVIDIA actor·critic·유효 std에서 scalar와 log 모두 optimizer를 새로 시작**하고 learning rate·scheduler 초기값도 맞추는 것이다. 그러면 std 좌표 차이를 비교할 수 있다. 다만 이 scalar 대조군도 옛 `v2b-r`의 optimizer resume과는 다르므로, 그 차이를 별도 연결 비교로 남긴다. 더 세밀하게 actor·critic state는 유지하고 std 관련 state만 양쪽에서 초기화할 수도 있지만 이름별 대응과 scheduler 상태를 검증해야 한다. 어느 방법이든 “log 한 줄 외에는 과거 학습과 완전히 같음”이라고 기록하지 않는다.

## 4. 기존 기준선과의 비교 · 성능 비교는 유지, 원인 비교는 새 대조군 필요

**`확인됨` · log 전환 자체는 입력·actor·critic의 구조나 평가 지형을 바꾸지 않는다.** 현재 상태 비의존 std 분기의 actor inference는 평균을 반환한다(`actor_critic.py:154~161`). `v2b-r`, `v2g-feetair1`, `v2n-noise02`의 저장 agent YAML은 모두 scalar/False다. 전환 이후의 정책은 기존 것과 최적화 경로가 달라진다.

**`판단` · 모든 과거 결과를 폐기하거나 기준선을 새로 정의할 필요는 없다.** 같은 평가 하네스·시드·지형·명령·판정식을 유지하고 3절의 로더 호환성을 확보하면 `foothold-v1`·`v2a`·`v2b`·`v2b-r`·`v2g`·`v2n`과 **최종 성능 비교**가 가능하다. 반면 “성능 차이 전부가 발 보상/지형 때문”이라는 **원인 해석**에는 std 형식과 optimizer 처리가 맞는 대조군이 필요하다.

계보에는 std 방식·변환 출처·optimizer reset 여부를 명시한 새 분기로 기록한다. “새 세대”는 운영상 이름을 붙일 수 있으나 기존 평가를 버려야 한다는 기술적 결론은 아니다. log 기준군과 S/log를 비교하거나 scalar 기준군과 S/scalar를 비교해야 한다. **S/log를 곧바로 과거 `v2b-r`과만 비교하면 지형·std 최적화·optimizer 처리 차이가 함께 들어간다.**

## 5. 더 작은 처방 · 존재하지만 각자 다른 부작용이 있다

**`확인됨` · 현재 PPO는 한 Adam에 policy 전체를 넣는다(`ppo.py:104`).** adaptive scheduler는 291~292행에서 **모든 param group의 lr을 같은 값으로 덮는다**. 따라서 std 전용 그룹을 만들고 낮은 lr만 지정하면, 뒤의 adaptive 갱신에서 그 비율이 사라질 수 있다.

**`판단` · 대안의 범위를 다음처럼 구별한다.**

| 대안 | 장점 | 한계·부작용 |
|---|---|---|
| clipping 전 비유한수 검사와 실패 직전 기록 | 원인 위치를 가르고 오염된 상태의 진행을 막는다 | 진단·중단 장치이며 안정적인 완주를 만들어 주지는 않는다 |
| std 전용 lr 축소 | 키와 추론 로더를 유지할 수 있다 | 음수 금지는 아니며 scheduler도 그룹 배율을 존중해야 한다 |
| optimizer.step 직후 std를 양의 하한으로 투영 | scalar 키를 유지하며 음수 진입을 막을 수 있다 | Adam momentum은 경계를 모른다. 경계에 계속 붙을 수 있고 NaN은 clamp로 없어지지 않는다 |
| 분포에 넣기 직전 std를 clamp | 분포의 유효 범위를 제한한다 | 범위 밖 원래 파라미터가 남고 그 구간의 gradient가 0이 될 수 있다. 저장 std와 실제 탐색 std도 달라진다 |
| std 고정 | 탐색 분산 최적화 경로를 제거해 원인 가설을 좁힌다 | 탐색 조절 능력을 없애므로 원래 PPO와 다른 실험이다 |
| log 또는 softplus 재매개변수화 | 양수성을 구조로 표현한다 | 좌표·checkpoint·optimizer 호환성 문제를 처리해야 한다. 극단값·비유한수 문제는 별도다 |

투영의 하한은 단순 0이 아니라 양수여야 한다. 상·하한 값은 물리적 행동 범위와 탐색량을 보고 사전에 정해야 하며 이번 자료만으로 최적값을 정할 근거는 없다. 우선 **실패 원인 진단을 바로잡고 호환성을 갖춘 log 대조 실험**으로 가는 것이 낫다. clamp로 완주했다는 사실만으로 원래 실패 원인을 증명하지는 못한다.

## 6. stones가 경험 지형이 되어도 기존 비교는 유효하다

**`확인됨` · `W/sim/eval/terrains.py:15~26`에서 stones는 세 번째 항목, 0부터 센 인덱스 2다.** 훈련에 같은 계열을 넣은 S에서는 미경험 지형이라고 부를 수 없다. 그러나 `unseen10`은 고정 평가 묶음 이름이지 모든 후계 정책에서 전부 미경험이라는 보증이 아니다. 이미 v2a/v2b는 그 묶음의 rails를 학습한다.

[CRITERIA.md](CRITERIA.md) v1.4의 2절은 이미 이를 처리한다. 정책의 학습 지형을 따라 경험 분류를 다시 하고, **판정은 전체 48칸으로 유지**하며, 개발용 집합을 독립 일반화 검증으로 부르지 않는 규칙이다. 1절의 네 checkpoint 전부 하락 0 규칙도 지형 미경험 여부가 아니라 배포본 대비 정해진 성능 비교다.

**`판단` · S에도 네 checkpoint와 48칸 규칙을 그대로 적용한다.** stones를 빼거나 이름·인덱스 순서를 바꾸지 않는다. S만의 다른 시험지로 교체하면 오히려 공통 비교를 잃는다. 본 제안처럼 다른 경험 분류가 유지된다면 학습 계열 21칸은 **24칸**, 도랑 경험이 닿는 gap 3칸은 **3칸**, 학습에 없던 24칸은 **21칸**이 된다. 판정 합계는 여전히 48이다. 각 정책의 저장 `sub_terrains`와 실제 생성 기하를 대조해 확정한다.

추가로 공통 미경험 계열의 성적, 학습 범위 밖 성적을 분리 보고할 수 있다. 이것은 기존 판정의 교체가 아니라 일반화 해석을 위한 보고다. 최종 독립 보류 집합이 필요하다면 S와 비교 기준선에 **같은 집합**을 적용하고 생성 규칙·시드·후보 선택을 결과 전에 동결한다.

단, Wilson 95% 구간 비겹침을 기준으로 한 “하락 0”은 **그 검사에서 하락을 검출하지 못했다**는 뜻이다. 성능 동등성이나 허용 차이 내 비열등성을 증명한 것은 아니다. 서로 겹치는 구간에서도 실제 차이가 있을 수 있다. 기존 규칙을 사용할 수 있다는 판단과 통계적 해석은 구별해야 한다.

## 7. 10%의 출처 · 한 가설은 분포 교체로 정의한다

**`확인됨` · `W/sim/policy/v2a_env_cfg.py:54~63`의 비율은 이미 합계 1이다.** 현재 `v2b-r` 저장 YAML도 같은 여덟 종이다. 10%를 더하고 나머지를 그대로 두어 합계 1.1로 만드는 안은 현재 검증 함수에 걸리며, 정규화해서 쓸 경우 실제 stones 비중도 10%가 아니다.

**`판단` · 첫 S는 다음 혼합으로 사전 고정하는 것을 권한다. 최적 비율을 측정한 결과는 아니다.**

| 지형 | 대조군 | S |
|---|---:|---:|
| pyramid_stairs | 0.15 | 0.15 |
| pyramid_stairs_inv | 0.15 | 0.15 |
| boxes | 0.15 | 0.10 |
| random_rough | 0.15 | 0.10 |
| hf_pyramid_slope | 0.10 | 0.10 |
| hf_pyramid_slope_inv | 0.10 | 0.10 |
| omni_gap | 0.10 | 0.10 |
| rails | 0.10 | 0.10 |
| stepping_stones | 0 | 0.10 |
| 합계 | 1.00 | 1.00 |

가설은 **“boxes와 random_rough에서 각각 5%p를 stones로 교체한 혼합이 stones 성적을 개선하면서 기존 관문을 유지하는가”**다. 계단·경사·도랑·rails 비중을 유지하고, 줄인 두 계열의 손실도 평가한다. 한 가설의 개입 단위는 **미리 정한 혼합 분포 한 개**이며 YAML 한 필드라는 뜻이 아니다. 다만 “stones 추가 효과만 독립적으로 측정했다”라고는 쓰지 않는다. 성적 변화에는 대체된 지형 노출 감소의 효과도 포함된다.

대조군은 같은 최적화 방식·초기 상태·학습량의 v2b 설정이다. 첫 분포 시험에서는 명령 범위, 발 보상, height_scan 잡음, curriculum 규칙, 환경 수, rollout 길이, 평가 시점을 같이 바꾸지 않는다. 별도 실험에서 선정된 설정을 새 부모로 삼고 싶다면 그 부모를 먼저 명시하고 고정한다. stones 순수 추가와 다른 지형 감소를 따로 가르려면 후속 대조 실험이 더 필요하다. 환경 수나 학습량을 늘려 “기존 노출 보존”을 하려면 그 늘어난 계산량에도 대응하는 대조군이 필요하다.

비율은 tile 열 배정에 쓰인다. `I/source/isaaclab/isaaclab/terrains/terrain_generator.py:237~261`과 저장 `num_cols=20`에 따르면, 기존 순서 뒤에 stones를 붙인 위 안은 열 수가 **3·3·2·2·2·2·2·2·2**로 나뉜다. 그러나 이것이 모든 시점의 성공 episode나 접촉 시간 중 stones가 정확히 10%라는 뜻은 아니다. 지형별 env 수·episode·실제 이동/접촉 노출·도달 레벨을 따로 기록해야 한다.

## 8. 상속과 설정 검사 · v2b 기준을 유지하되 마지막 완성 상태를 검사한다

**`확인됨` · `W/sim/policy/v2b_env_cfg.py:43~51`은 v2a를 상속하고 정지 비율만 0.10으로 바꾼다.** v2a의 값은 0.02다. S의 대조군을 v2b-r로 삼는다면 v2b에서 상속하는 것이 의도를 가장 잘 드러낸다. v2a를 상속하면서 정지 비율을 명시적으로 0.10으로 맞춰도 기능적으로 가능하지만, 누락 위험이 더 크다.

**부모 검사 함수도 함께 설계해야 한다.** `v2a_env_cfg.py:125`는 부모 `__post_init__` 끝에서 `self._verify_overrides()`를 호출하고, 161행 이후는 모듈 전역 `TERRAIN_PROPORTIONS`와 지형 키·각 비율·합계를 대조한다. 단순히 S의 검사 함수를 override하면 부모 생성 도중에도 자식 메서드가 호출된다. 그 시점에 아직 stones를 넣지 않았다면 완성된 S를 기대하는 검사가 잘못 실행될 수 있다.

**`판단` · S 완성 뒤의 최종 검사를 별도로 보장해야 한다.** 부모의 여덟 종 검사를 마친 뒤 S 혼합을 적용하고 S 전용 최종 검사를 하거나, 생성 전에 올바른 혼합 명세가 제공되는 구조로 설계한다. 어느 쪽이든 아홉 키·각 비율·합계와 함께 명령·정지 비율·리셋·보상·관측·센서 설정을 대조군과 다시 대조한다. **모듈 전역 `TERRAIN_PROPORTIONS`를 런타임에 바꿔 기존 v2a/v2b까지 바꾸는 방식은 피한다.**

그리고 환경 클래스 상속은 PPO 설정·출발 checkpoint·optimizer·시드·device 배치·학습량을 보장하지 않는다. 이것들은 저장 agent YAML과 실행 명세에서 따로 확인한다. 이번에는 S 구현과 저장 YAML이 없으므로 **상속 설계의 조건을 제시한 것이며 완성된 S가 단일 개입임을 확인한 것은 아니다.**

## 9. stones 기하와 난이도 · 같은 생성기는 가능하되 무엇을 학습했는지 밝힌다

**`확인됨` · “난이도 0.1에서 100%”는 전 속도에 대한 사실이 아니다.** `R/sim/eval/results/` 아래 원시 `generalization_raw.csv`에서 stones 행만 다시 세면 다음과 같다. 각 칸 100 episode다.

| v2b-r iter2500 | 0.5 m/s | 1.0 m/s | 1.5 m/s |
|---|---:|---:|---:|
| d=0.1 종합 성공 | 100/100 | 100/100 | **89/100** |
| d=0.5 종합 성공 | 0/100 | 0/100 | 0/100 |

원자료 경로는 `20260924-observe/sweep/v2b-r-iter2500/unseen10/d0.1/v*/generalization_raw.csv`, `20260923-v2rs/v2b-r-iter2500/unseen10/d0.5/v*/generalization_raw.csv`다. d=0.1의 1.5 m/s는 생존·진행·방향이 각각 100/100이고 속도 추종이 89/100이다. d=0.5의 종합 0도 전원이 넘어진다는 뜻은 아니다. 생존은 속도별 25·33·36/100이다.

현재 평가 설정은 `W/sim/eval/generalization_env_cfg.py:48~54,75~83`에 있다.

| 항목 | 현재 평가 설정 | 첫 S 제안 |
|---|---|---|
| tile 크기 | 8×8 m | 동일 |
| horizontal / vertical scale | 0.1 / 0.005 m | 동일 |
| stone_height_max | 0.12 m | 동일 |
| stone_width_range | (0.35, 0.65) m | 동일 |
| stone_distance_range | (0.08, 0.20) m | 동일 |
| holes_depth | -1.0 m | 동일 |
| platform_width / border_width | 1.5 / 0.25 m | 동일 |
| difficulty | 평가 시 0.5 고정 | v2b의 (0.0, 1.0)·10행 curriculum 유지 |
| 초기 terrain level | 평가용 배치 | v2b의 최대 초기 level 2 유지 |

난이도 숫자를 연속적인 틈 크기로 읽으면 안 된다. `I/source/isaaclab/isaaclab/terrains/height_field/hf_terrains.py:373~385`는 폭 `0.65−0.30d`, 간격 `0.08+0.12d`를 구한 뒤 각각 `horizontal_scale`로 나누고 **정수로 자른다**.

| d | 명목 폭 / 간격 | height field 격자의 폭 / 간격 |
|---|---|---|
| 0.1 | 0.62 / 0.092 m | 6셀 / **0셀** |
| 0.5 | 0.50 / 0.140 m | 5셀 / 1셀 |
| 0.9 | 0.38 / 0.188 m | 3셀 / 1셀 |

따라서 d=0.1은 깊은 틈 간격이 0으로 양자화된 조건이다. 이 결과를 “실제 틈이 있는 stones를 이미 100% 넘는다”는 근거로 쓸 수 없다. height는 이 함수에서 d로 줄이지 않는다. 또 위 셀 수는 height field 생성 단계의 값이며 삼각 mesh 경계·경사 보정까지 포함한 발 착지 유효 폭의 실측값은 아니다.

**`판단` · 첫 S는 같은 생성기·같은 범위로 시작하는 것이 질문을 가장 단순하게 만든다.** “이 기하를 훈련에 노출하면 현재의 약점을 배울 수 있는가”를 묻는 것이다. 동시에 돌 크기·높이·간격·해상도를 바꾸면 학습 노출과 기하 변경이 섞인다. 첫 안의 10행 curriculum과 초기 0~2행은 생성식상 대략 d=0~0.3 구간에서 시작하므로, 틈 없는 영역에만 머무르지 않는지 stones 전용 레벨과 실제 틈 노출을 반드시 본다. 전 지형 평균 terrain level로 대신하지 않는다.

첫 S가 실제 틈에서 학습하지 못하면, 다음 안에서 **stones에만** 더 쉬운 폭·높이 범위를 주는 curriculum 가설을 따로 세운다. 전역 `difficulty_range`를 쉽게 바꾸면 나머지 여덟 지형의 난이도까지 변한다. 이번 자료는 10%나 특정 쉬운 범위가 최적이라는 근거를 제공하지 않는다.

같은 생성기와 범위를 쓰는 것은 **지형 계열을 학습에 넣는 것**이 맞다. 다만 훈련과 평가의 무작위 tile·리셋을 분리하고 실제 생성물을 확인하면, 새로운 인스턴스에 대한 분포 내 성능을 시험할 수 있다. 같은 생성기라는 이유만으로 정확히 같은 평가 mesh를 복사했다고 할 수는 없고, 다른 시드라는 이유만으로 생성물 중복이 없다고 보장할 수도 없다. 생성 명세·시드·cache/mesh 식별자를 남겨 겹침을 확인한다.

이 경우 주장할 수 있는 것은 “경험한 stones 계열의 새 인스턴스 성능”이다. **“미경험 stones 일반화”는 아니다.** 정확한 평가 tile을 훈련에 재사용하면 그 tile에 대한 보류 평가 해석은 성립하지 않는다. 이미 여러 설계에 활용한 기존 집합은 개발용이며, 최종 일반화 주장은 사전에 동결한 별도 공통 보류 집합에서 확인한다.

## 10. 전체 설계 · 유효한 탐색 절차이지만 최적성의 증명은 아니다

**`확인됨` · CRITERIA v1.4는 공통 관문·보고 항목·기준 변경 절차·보류 집합을 이미 구별한다.** 이번 저장 YAML에서 v2g는 sim0+PPO0, v2n은 sim1+PPO1이고 둘 다 scalar다. 의뢰서의 “평가 56건”은 실행 계획의 집계이며, 이번 감사에서는 실행 완료 여부나 새 성적을 판정하지 않았다. 축 1 작업 건수 48과 **checkpoint당 판정 48칸**은 단위가 다르다. 축 2 작업 건수 8도 **checkpoint당 판정 9칸**과 구별해야 한다.

**`판단` · “가설 → 학습 → 두 축 평가 → 판정 → 분기”는 제한된 예산에서 후보를 찾는 방법으로 타당하다.** 하지만 관문 통과는 정의된 후보 조건을 만족한다는 뜻이다. 전체 설정 공간의 최적 모델, 임의의 미경험 험지에 대한 일반화, 실기 준비 완료를 뜻하지 않는다. 한 항목씩 탐색하면 상호작용도 놓칠 수 있다.

진행 순서는 다음과 같이 보완한다.

1. **원인과 실행 가능성을 먼저 분리한다.** log의 양수성 설계, 시드 43의 실제 실패 원인, checkpoint/계측기 호환성은 세 가지 검증 대상이다. 3절의 호환 조건이 충족되기 전에는 log 안을 실행 가능으로 승인하지 않는다.
2. **각 실험의 대조군과 바뀌는 묶음을 결과 전에 고정한다.** std 좌표 변경과 stones 혼합 교체를 한 대조에 합치지 않는다. S의 비율·기하·출발 모델·optimizer·학습량·평가 checkpoint를 명세로 남긴다.
3. **v2g와 v2n의 기존 평가를 마무리해 각각 부모와 비교한다.** 좋아 보이는 설정들을 한꺼번에 합쳐 그중 하나의 효과라고 부르지 않는다. 결합 효과가 필요하면 부모, 각 단독 변경, 결합의 비교를 별도로 설계한다.
4. **학습 중 진단과 최종 성능을 모두 남긴다.** 비유한수·실패 minibatch·지형별 노출·stones 성공 구성요소를 기록한다. 평균 reward나 terrain level의 평탄만으로 특정 가설을 기각하지 않는다.
5. **동일한 48칸·9칸·네 checkpoint 관문은 유지한다.** 경험 분류·절대 성공률·미판정 칸·0% 칸을 병기한다. 특히 기준선과 후보가 stones에서 모두 0이면 하락 0이 나와도 약점 해결은 아니다.
6. **유망한 변경은 독립 학습 시드로 확인한다.** 같은 시드의 반복과 동거 GPU 번호 교환은 독립 시드 반복을 대체하지 않는다. 예컨대 42·43·44를 사전에 정한 첫 확인 묶음으로 쓸 수 있지만 세 개로 충분한 정밀도가 보장되는 것은 아니다. 실패한 시드도 분모와 비용에서 빼지 않는다. 평가 episode 수와 독립 학습 횟수도 별도로 보고한다.
7. **최종 후보 선택과 일반화 검증을 분리한다.** 개발용 평가를 반복해 고른 후보는 별도 공통 보류 집합에서 한 번 확인한다. 후진·횡보·외란·장시간·험지 명령 응답 등 현재 관문 밖의 기능을 관문 통과만으로 보증하지 않는다. 관문을 바꿀 필요가 생기면 CRITERIA 4절의 변경 절차를 따른다.

최종 승인 조건을 한 줄씩 적으면 다음과 같다.

- **(ㄱ) 현재 그대로의 log 변경: 진행 보류.** 양방향 checkpoint 호환, optimizer 처리, 계측기 호환과 수치 진단을 먼저 설계·검증한다.
- **(ㄱ) 수정된 log 실험: 조건부 타당.** 같은 출발 분포와 맞춘 optimizer 방침의 scalar 대조군을 두고, 완주와 성능을 모두 평가한다.
- **(ㄷ) S 10% 실험: 조건부 타당.** v2b 기준의 명시적 혼합 교체로 시험하고, 최종 설정 검사를 통과시키며, stones를 경험 계열로 보고한다.
- **전체 탐색: 계속 가능.** 공통 관문을 보존하고 독립 시드·보류 평가로 보강하되 “최적 모델을 입증했다”는 결론은 내리지 않는다.
