## 장비 확인과 과장된 조언의 정정

MAI_UNIVERSE `01_IDENTITY/resources.md:37~44`에는 RTX5080 16GB 두 장·Threadripper7970X·TRX50 AI TOP·RAM256GB가 기록돼 있다.08:27 Windows CIM에서 CPU32코어64스레드·보드 제품명을, nvidia-smi에서5080두 장을 직접 확인했다. 당시 두 카드의 현재 PCIe 링크는 모두Gen5×16이었다. GALAX 세부 모델·PSU 모델·물리 슬롯 위치는 이번 도구로 독립 확인하지 않았고 팀장 제공 정보로 구분한다. 볼트의 드라이버/Ubuntu 예정 버전은 낡을 수 있어 설치 정본으로 사용하지 않는다.

- **16GB 두 장은 하나의32GB 연속 메모리가 아니다.** DDP는 모델을 각 GPU에 복제하고 데이터를 나눠 계산한 gradient를 동기화한다. 환경·rollout의 장치별 부담은 줄일 수 있지만 모델·optimizer·시뮬 고정 비용은 각 장에 남는다. [PyTorch DDP](https://docs.pytorch.org/docs/2.9/notes/ddp.html).
- **GPU0은 시뮬, GPU1은 학습만 담당하게 나누는 것이 우선 권고는 아니다.** 현재는 시뮬·추론·PPO·지각망을 같은 장치에 둔다(`runners/devices.py:1~20`). 반사적 제어는 매 틱 관측과 행동이 오가므로, 두 장으로 나누면 전송 비용과 직렬 의존이 생긴다. 병목을 재기 전 더 빠르다고 할 수 없다.
- **Gen5×16이어도 통신 병목이 없다는 뜻은 아니다.** 볼트는 과거 CUDA peer access 미지원 실측을 기록한다. 현재 Linux의 P2P/NCCL 전송 경로는 미확인이다. NVLink 없이도 DDP가 불가능하다는 뜻은 아니며, 실제 전송과 학습 처리량을 측정한다.
- **RunPod는16GB 고정 환경이 아니다.** 선택한 GPU의 메모리·렌더 지원·요금이 기준이다. 이번 문서는 유료 자원 생성이나 요금 예측을 하지 않는다.

## Linux에서 확인할 순서

[Isaac Lab 공식 문서](https://isaac-sim.github.io/IsaacLab/v2.3.0/source/features/multi_gpu.html)는 Linux에서torchrun 기반 멀티 GPU를 지원하며, 각 프로세스가 자기 시뮬·정책·rollout을 갖고 갱신을 동기화한다고 설명한다. 공식 표준 스크립트의 지원과 우리 실행기의 준비 완료는 다르다.

| 순서 | 환경 배정 | 한 갱신의 총 경험(rollout24) | 무엇을 비교하나 |
|---|---|---:|---|
| 단일 GPU 재측정 | 3072,이어4096 | 73728 / 98304 | 같은 스택·해상도의 시간·처리량·VRAM |
| 분산 동등성·비용 | 1536×2 | 73728 | 현재 총 배치를 유지한 분산 비용·갱신 일치 |
| 분산 확장 | 2048×2 | 98304 | 단일4096과 같은 경험량의 속도·메모리 |
| 추가 확장 후보 | 3072×2 | 147456 | 경험이2배가 되는 대신 수렴·갱신 수·메모리 변화 |

각 GPU에서 독립 학습을 띄우는 것만으로 한 정책의 DDP가 되지는 않는다. 총6144는 같은 회차에서도 현재의2배 경험이며 PPO minibatch·KL 기반 학습률·AdaSmpl 보상 통계·커리큘럼 시간축의 의미가 달라진다.「1000회가 빨랐다」만 비교하지 않고 총 환경 step,벽시계 시간,동일 평가 성과까지 함께 본다. 선형2배 속도나2배 성과를 약속하지 않는다.

현재 코드 판독:

- `runners/start_runner.py:91,205,493~533`:기반 runner의 PPO 분산 설정,지각 gradient 평균,전역 AdaSmpl 통계,초기 모델 broadcast 경로가 있다. 코드 존재는 실제2GPU 통과 증거가 아니다.
- `sol23f_contract.py:19~20`:현재 B/TopDown 진입점은`distributed`를 명시적으로 거절한다. 현 명령에torchrun만 붙여도 되지 않는다.
- 별도 Linux 경로에서 rank별 장치·시드·로그·원자료·난수·시뮬 상태를 분리하고,모든 학습망의 gradient 및KL/학습률·정규화가 같은 의미로 동기화되는지 확인한다. 한 rank의 NaN·마감·저장 실패가 다른 rank를 기다리게 하지 않아야 한다.
- 단일3072 체크포인트의 환경별 상태를1536×2로 재분배하는 것은 현재 단일GPU resume와 다르다. rank별 저장·복구,총 경험 카운터·지형 원점·AdaSmpl 상태를 별도 검증한다. current single-GPU snapshot을그대로복사해2rank재개 성공으로표현하지않는다.

Linux에서는 먼저 학습 상태 보존·원래 입력으로 단일GPU 확인,동일3072/4096 측정,작은분산 CPU/실제 점검,이후 위 배치 비교로 진행한다. OS·드라이버 설치나새장기학습은이문서로자동승인하지않는다. 새 관문을 반복해기존Windows학습을막는계획도아니다.
