# EX-42 지형별 승급과 측정 계획

현재 EX-40에 적용하지 않는다. EX-41/W72 구현은 아직 없으므로 여기의 어댑터·로그·자동 변경은 구현 계획이다. 15 문서의 회차 기반 p_advance는 최신 성과 기반 확대 요구로 대체할 자리이며, 원문 식과 우리 변경을 별도로 남긴다. 익숙한 명령을 유지한 채 지형 축을 먼저 늘리고, 어려운 지형·명령·DR 범위를 한꺼번에 늘리지 않는다.

## 1. 서로 다른 두 판정

**에피소드 배정**: 한 번 성공하면 같은 종류 L+1을 맛볼 수 있다. 이는 단계 졸업이 아니다. 이동 명령을 실제로 받았고(목표 경로 유효), 해당 지형 구간을 끝까지 지나 생존한 에피소드만 성공이다. 넘어짐·몸 충돌 종료·구덩이 착지는 실패다. 정지·제자리 회전만 받은 에피소드는 이동 실패로 강등하지 않는다. 기록 누락·유효하지 않은 목표는 성공/실패 분모에서 빼되 `invalid` 수와 원인을 반드시 남기고 판정 불가로 표시한다.

**종류별 노출 확대**: `(family,kind,level,direction,map_mode)`의 독립 종료 에피소드 64개 이상에서 아래 성공률과 유지 축을 확인한다. 제안은 성공 ≥52/64(81.25%), 생존 ≥60/64, 같은 조건 두 판정 창이다. 수치는 논문 확정값이 아니라 80% 안팎에서 다음 난이도를 소량 넣자는 팀장 방향의 **설계 가정**이다. Wilson 구간도 기록하지만 하한과 점추정치를 혼용하지 않는다. 동시 env·같은 지형의 상관 때문에 이를 독립 통계 검정으로 과장하지 않는다. 실제 반복 폭 측정 뒤 결과 전 고정한다.

제안 노출은 새 종류/다음 레벨 10%, 현재 수준 70%, 이미 통과한 쉬운 수준 20%다. 통과 두 창 뒤 새 수준을 20%로 올린다. 새 수준에 실패하면 새 노출을 5% 탐색으로 내리고 현재 75%·쉬움20%로 복귀한다. 기존 명령·지도 가림 유지가 떨어지면 확대하지 않는다. 실패를 숨기려고 레벨이나 비교 기준을 소급 변경하지 않는다. 이는 자동 실행 규칙이 아니라 W72 구현·승인 전 명세다.

## 3. 열 번호에 묶이지 않는 평가와 기록

lookup 키는 `(family,kind,level,geometry_seed,layout_sha)`이고 `env_id`는 그 순간 배정 결과일 뿐이다. 각 칸에 `row,col,origin_xyz,bounds_xyz,difficulty,physical_dimensions,mesh_sha,goal_surfaces`를 둔다. 요청 kind가 없으면 다른 지형으로 대체하지 않고 누락을 보고한다. 같은 kind 열이 여러 개면 geometry_seed와 열을 순환하고 선택된 목록을 남긴다.

시작 manifest: cfg·코드·mesh·metadata SHA, 종류 순서, 열별 kind, 실제 수치치수, 좌표계, 캐시 적중 여부, 높이/깊이 센서가 소비한 mesh path. 각 reset 뒤 `env→(kind,level,row,col)`가 실제 terrain_origins와 일치하는지 확인한다. 경계 로그는 종류별 env수·L0…9 분포·성공/실패/invalid 분모·명령방향·지도 소비모드·표본 노출 스텝 수다. 단계가 바뀌어도 앞 지형의 노출을 0으로 만들지 않는다.

현 코드 `foothold_s2/eval/axis_v2_run.py`:184~195는 terrain_tiles를 보존·대조하고 `fixed_terrain.py`:79,105~130은 실제 배정과 설명을 남긴다. 반면 같은 파일의 기본 `fixed_assignment`는 envid%열수라 EX-42에서 그대로 쓰면 안 된다. 배치 변경 전후에 같은 `(kind,level)` 요청이 같은 물리 지형을 가리키는 CPU 반례, 없는 종류 요청의 명시 실패, cache 재사용 후 metadata 복원, reset 이전/이후 원점과 목표 동기화를 시험한다.

## 4. CPU와 짧은 GPU1 사전 측정 계획

먼저 CPU에서 각 family L0/L5/L9 치수·mesh 수·삼각형 수·높이장·metadata·배치 표를 확정한다. 프로파일링은 **승인 후 별도 새 프로세스**이고 학습·PPO update는 없다. GPU1이 비었다는 관측만으로 실행 권한을 만들지 않는다.

승인 요청 묶음: (a) 단일 종류 1타일 (b) family별 전체 레벨·열 (c) 최종 후보 layout. 각 단계에서 생성 시간, CPU RSS, GPU allocated/reserved/최대사용, collision mesh/광선 mesh 업로드 시간을 측정한다. height 512+발100 ray/env 및 depth60×60 ray/env를 따로 재고 합쳐서 재며, 실제 cfg의 센서 주기·전처리·env수를 영수증에 남긴다. 128→512→3072 env 단계는 앞 크기에서 여유가 확인된 경우만 진행하고, 4096은 별도 요청한다. 숫자는 후보 계획이지 안전 보증이 아니다.

광선 warmup 20회 후 측정100회, CUDA event 동기화로 평균·p50·p95·최대, reset 포함/제외, cold/warm cache를 분리한다(횟수는 가정). 메모리 여유가 2GiB 미만이면 그 크기에서 종료하고 다음 크기를 띄우지 않는 것을 제안한다. 생성 실패·ray invalid율·NaN·메시 가림(천장이 있는 crawl의 위쪽 ray가 천장을 지지면으로 읽는 문제)을 기록한다. 이 2GiB도 실측을 대신하는 안전선이 아니며 lead 승인 전에 고정하지 않는다.

완료 조건은 속도 숫자 한 개가 아니라: 정확한 종류·레벨을 고름, 배치가 바뀌어도 평가 의미 보존, 접촉용 mesh와 두 센서 mesh 일치, reset metadata 일치, CPU 알려진 답 시험 통과. GPU 실행 여부와 비용·실제통과성능은 현재 모두 미확인이다.

## 5. 정본에 반영할 자리와 열린 결정

lead가 정할 것: family별 별도 layout 우선 여부, 가정 문턱과 반복 폭 측정 예산, GPU1 생성·측정 범위. 현재 자동 승급이나 새로운 학습 승인은 없다.
