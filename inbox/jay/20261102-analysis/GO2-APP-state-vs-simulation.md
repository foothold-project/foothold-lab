## 어디서 무엇을 계산하나

- **앱에서 확인된 것:** 입력 UI, 명령 요청·응답 처리, 모델/지도 로딩, 수신 pose·관절각 적용, 점군·복셀 표시 처리, 카메라 조작·애니메이션. `RobotModelLoader` 398~405행에는 모델 애니메이션·레이더 회전도 있으므로 화면의 모든 움직임을 센서값이라고 단정하지 않는다.
- **로봇 쪽으로 판단하는 것:** sport 요청을 수행해 실제 관절을 제어하는 서비스. 앱의 요청/상태 수신과 공식 SportClient 경계가 근거다. 이 서비스 내부가 RL 정책인지, 다른 제어기와 결합했는지, 어느 보드에서 계산하는지는 이번 자료로 미확인이다.
- **서버·중계:** WebRTC 객체를 통해 전달하는 코드가 있지만 이번에는 실제 접속 경로·중계 사용·서버 왕복 시간을 측정하지 않았다. 원격 인증/중계와 로봇 보행 제어 계산을 같은 것으로 취급하지 않는다.

네트워크 지연은 명령이 실기에 도착하는 시간과 실기 상태가 화면에 나타나는 시간에 각각 영향을 준다. 화면 FPS·UI throttle·애니메이션 갱신 간격을 실기 제어 주기로 읽으면 안 된다. store 8729·8744행에는 상태 UI 이벤트를 제한하는 코드도 있으나 그것만으로 전체 화면 지연이나 로봇 제어 지연을 계산할 수 없다.

## 우리 앱과 비교할 때

우리 `ame2-demo`는 MuJoCo 물리 상태를 정책에 넣고 출력 관절 명령으로 시뮬레이션을 진행하는 경로다. 공식 앱의 조사한 실기 화면은 그와 목적이 다르다. **공식 앱 화면에서 잘 걷는 모습을 보여 준다고, APK에서 같은 보행 정책을 꺼내 MuJoCo에 바로 붙일 수 있다는 결론은 나오지 않는다.**

실기 연결 때 우리도 상태 기반 표시를 구현할 수 있다. 그때 명령 시각·로봇 상태 시각·수신 시각·그림 표시 시각을 분리하고, 오래된 상태는 오래됐다고 표시해야 한다. 물리 시뮬레이션과 실기 상태 표시 모드는 이름·자료 출처를 명확히 나눈다.

아직 하지 않은 것: 실기와 앱을 연결한 왕복 지연 시험, 보호된 DEX/네이티브 전체 해석, 실제 계단 보행 촬영, 동작 제어기 추출. 정적 분석이므로 해당 런타임 성능을 확인했다고 보고하지 않는다.
