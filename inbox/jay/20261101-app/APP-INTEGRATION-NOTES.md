## 2. 명령이 실기로 가는 길 (지금)

1. 사람이 브라우저(노트북이든 휴대폰이든) 화면에서 키를 누른다.
2. 브라우저 → 서버(NaverCloud, FastAPI): WebSocket `wss://<서버>/api/v1/ws` 로 50 ms 마다 `rt.cmd`(vx, vy, wz).
3. 서버 → 에이전트: 서버가 같은 허용 표로 검사한 뒤 `/api/v1/agent/ws` 로 중계(`apps/server/fh_server/realtime.py:2242-2243`).
4. 에이전트 = Go2 와 랜선(10 m)으로 이어진 노트북에서 도는 프로그램. 에이전트가 먼저 서버에 wss 로 접속해 두고 명령을 받는다.
5. 에이전트 → Go2: `unitree_sdk2py` 의 `SportClient.Move(vx, vy, wz)` 를 부른다(`sdk.py:60-66`). 통신은 랜선 위 DDS(ROS 2 가 쓰는 것과 같은 통신 방식).
6. Go2 안의 Unitree 순정 제어기가 다리를 움직인다(sport mode).

ROS 2 는 이 길에 없다. ROS 2 가 쓰이는 곳: 서버 시뮬 연결(`ros_bridge` 가 `/v2_live/cmd_vel` 을 내고 `/v2_live/state` · `/v2_live/odom` 을 받음, `ros_bridge/node.py:179,264-297`) · Nav2 실행기(에이전트 안 `executor/nav2`, `/v2_map/map` · `/v2_map/scan` · `/tf` 구독).

그림: [APP-FLOW-DIAGRAM.html](APP-FLOW-DIAGRAM.html) 의 **그림 ①** 이 이 절을 그린 것이다. 노트북 · 서버 · 에이전트 · Go2 를 상자로, 인터넷(wss) 과 랜선(DDS) 을 색이 다른 선으로 그렸다(planner 11/02).

## 4. 팀원 전달 사항

1. 우리 보행 모드 추가: 지도 모드 셋(정답 · 복원 · 끔)을 고를 수 있게. AME-2 모드도 필요한 입력을 갖추게.
2. 3 절 입력 셋을 앱에 만든다: 10 걸음 이력 버퍼 · MuJoCo 깊이 렌더(카메라 값은 v0.3) · 높이 지도 격자 32 × 16.
3. 추론: ONNX + 브라우저용 ONNX 런타임 우선(D107). 같은 입력에서 PyTorch 와 출력 차이 1e-4 안 시험을 통과해야 모드로 연다. 기기별 속도 측정.
4. 명령 상한은 모델마다 다르다. 정책 파일과 함께 「명령 범위 파일」(JSON)을 내보내고, 앱은 그 범위로 자른다. 우리 학습이 넓어지면 파일만 바뀐다(D108). 지금 값은 5 절.
5. 키 입력은 누르는 길이에 따라 서서히 오르게(가속 제한). 실기 안전에도 필요.
6. 깊이 입력 경로(D435i)를 실기 쪽에도 만든다.
7. SLAM 은 control-app 이 아니라 foothold-app 안으로.
8. 도메인 이전 때 바꿀 곳: `FH_SITE` · `FH_WS_ORIGIN` · `FOOTHOLD_AGENT_WS_URL` · `FOOTHOLD_PHONE_ORIGINS` · `FH_SIM_AGENT_WS_URL` · 터널 허용 정규식(`phone/origins.py:10`, 지금 `*.trycloudflare.com` 만). 웹은 `location.host` 기준이라 그대로. 상세는 super2 문서(mai-os `os/site-domain-migration.md`).
9. API 주소 공유: 코드에 박지 않고 환경 변수 · `.env.example` 로. 비밀값은 저장소 비밀 설정으로.
10. 역할(팀장 11/02): 오현민 = foothold-app 주 개발(커밋 계정 less82) · 도메인 설정 반영. 이민우 = 실기 주행 + ROS 로 들어오는 관절 데이터 모으기(R2).
11. **넘어짐 판정 고치기(ame2-demo 계단 실패 원인 후보 1)**: 앱은 몸 높이가 지면에서 0.18 m 아래이거나 중력 z > −0.5 면 「넘어짐」을 걸고 그 뒤 정책을 멈춘다(`mobile/sim/sim.js:54-58,91-98` · `main.js:579-584`, 커밋 135a8469). 계단에서 몸이 잠깐 낮아지면 걸린다. 학습의 종료 기준(AME-2 env.yaml 2272~2306 행)과 같게 바꾸고, 넘어짐이 걸린 순간의 높이 · 기울기를 기록해 보여 줄 것. 근거: analyst `inbox/jay/20261102-analysis/AME2-app-stairs-analysis.md`(analyst-1102 worktree).
12. **지도 광선 시작 높이를 학습과 같게**: 학습은 몸 위 20 m 에서 아래로 쏘는데 앱은 몸 위 0.501 m 에서 쏜다(`ame2-adapter.js:40,58-70`). 높은 계단 단이 지도에서 빠질 수 있다. 우리 모델도 정답 · 복원 지도를 쓰므로 앱의 지도 · 깊이 생성은 학습 조건과 같아야 한다(광선 시작 높이 · 격자 · 축 · 원점 · 잡음).
13. **목표(AME-2) 입력은 다른 점으로 기록만**: 학습은 고정 목표까지 남은 거리 · 방향(2 m 넘으면 2 m 로 자름), 앱은 키 입력을 매 걸음 짧은 목표로 바꿈. 2 m 넘는 목표 학습은 석헌 님 실험과 다시 맞출 일(팀장 11/02).
14. **목표 찍기 개선**: 지금은 목표가 바닥(그라운드)에만 찍혀 3D 화면에서 계단 위 · 너머를 찍을 수 없다(SLAM 지도 위에서는 되는지 확인 필요). 계단 너머도 목표로 찍게 하고, 목표점 하나가 아니라 target 1 · 2 · 3 … 을 이어서 가는 구조로 바꿀 것(팀장 11/02).
15. **Kp 25 · Kd 0.5 를 저수준 제어(LowCmd)에도 같은 값으로**: 우리 정책은 이 PD 값을 전제로 학습한다. 실기 저수준 명령에 같은 Kp · Kd 를 넣어야 학습한 대로 걷는다.

- 에이전트는 0.30 s 안에 새 명령이 없으면 멈추고, 로봇 상태가 0.20 s 안에 새로 와야 0 이 아닌 명령을 낸다(`go2_direct/sink.py:13-14 · 65-67`).
- 서버 경로의 명령은 표 값 그대로 Go2 에 간다(1.5 · 0.5). 코드에 보이는 0.6 m/s 한도는 휴대폰 직결 경로용이다(`sink.py:16-20 · 180-181`).
- 에이전트는 랜카드 이름을 지정해 DDS 를 연다. 그래서 Go2 와 같은 랜에 있는 컴퓨터여야 한다(`go2_direct/sdk.py:43-50`).

### 7.2 어디서 계산하나: (가) 브라우저 ONNX · (나) 로봇 쪽 컴퓨터 · (다) 서버

정책은 20 ms 마다(50 Hz, `deploy.yaml:40` step_dt 0.02) 한 번 돌아야 한다. 「관절 상태 읽기 → 정책 → 관절 목표 12 개 → 모터」 가 이 20 ms 안에 끝나야 학습 때와 같은 조건이다.

| 자리 | 입력이 오는 길 | 20 ms 안에 드나 | 쓰는 곳 |
|---|---|---|---|
| (가) 브라우저 ONNX | 같은 탭 안 MuJoCo 상태 | 든다(한 프로그램 안) · 기기마다 속도는 재야 함(D107) | 시뮬(그림 ②) · 그림 ③의 시뮬 창 |
| (나) 로봇 쪽 컴퓨터 | 랜선 위 DDS(lowstate) | 든다(한 건물 안 통신) | 실기(그림 ③) |
| (다) 서버 | 인터넷으로 관절 상태 올리고 관절 목표 받기 | 보장 없음. 인터넷 왕복은 흔들리고(이번에 미측정) 한 번만 늦어도 로봇은 옛 명령으로 발을 디딘다 | 쓰지 않는다 |

실기가 반드시 (나) 여야 하는 이유 세 가지:
1. **시간.** 20 ms 예산 안에 인터넷 왕복을 넣을 수 없다. 랜선 DDS 는 들어간다(실측은 실기 받은 뒤).
2. **끊김.** 인터넷이 끊겨도 로봇 옆 컴퓨터는 마지막 명령을 0 으로 바꾸고 서 있을 수 있다. 서버에서 돌리면 끊기는 순간 다음 관절 목표가 없다.
3. **같은 조건.** 학습 · 배포 설정의 Kp 25 · Kd 0.5 · 50 Hz(`deploy.yaml:40-64`, 4 절 15 항) 를 그대로 쓸 수 있는 자리는 LowCmd 를 직접 내는 (나) 뿐이다.

그래서 서버의 역할은 ①에서도 ③에서도 같다. **명령 3 개와 상태를 나르는 중계** 이고 보행을 계산하지 않는다(`apps/server/fh_server/realtime.py` install(): `/api/v1/ws` · `/api/v1/agent/ws` 두 웹소켓, dev 2243~2244 행).

### 7.3 ROS 2 가 지금 실기 길에 없는 이유, 그리고 SDK2 와 ROS 2 는 같은 토픽

- 에이전트는 ROS 2 를 거치지 않고 `unitree_sdk2py` 로 바로 DDS 에 붙는다(`go2_direct/sdk.py:18-26 · 81-86`). ROS 2 가 쓰이는 곳은 서버 시뮬 연결과 Nav2 실행기뿐이다(2 절).
- Unitree SDK2 는 CycloneDDS 위에 만든 통신이고, unitree_ros2 도 같은 CycloneDDS 를 쓰라고 안내한다(unitreerobotics/unitree_ros2 README 6 · 42~48 행, 등급 읽기 · 공식 저장소).
- ROS 2 는 토픽 이름 앞에 `rt/` 를 붙여 DDS 에 올린다(ROS 2 설계 문서 「Topic and Service name mapping to DDS」: 토픽 `/foo` 는 DDS `rt/foo`, 등급 읽기). 그래서 SDK 가 구독하는 DDS 토픽 `rt/lowstate` · `rt/sportmodestate`(`sdk.py:21-23`) 는 ROS 2 에서 `/lowstate` · `/sportmodestate` 로 보이는 **같은 토픽** 이다(unitree_ros2 README 178 · 231 행).
- 따라서 `ros2 bag record` 로 기록하든 SDK 구독으로 기록하든 **같은 자료** 가 남는다. 다른 것은 파일 형식(ROS 2 bag 대 우리가 쓰는 JSON 등)과 시각 찍는 방식뿐이다.

### 7.4 「상태 구독 전용 수집기」 뜻과 따라 하는 절차

뜻: Go2 가 DDS 로 내보내는 상태(관절 · IMU · 몸 속도)를 **듣기만** 하고, `LowCmd` 나 sport 요청은 **하나도 보내지 않는** 프로그램. 로봇이 순정 조종기나 공식 앱으로 걷는 동안 옆에서 받아 적는다.

앱 저장소에 이미 이런 모드가 있다. `apps/agent/foothold_agent/go2_readonly/`(`__main__.py:1 · 21`: 「Go2 status only: no robot commands」, 랜카드 `--nic` 를 반드시 지정) 와 `go2_direct/readonly.py:1`(「two DDS subscribers, no SportClient/sink」) 이다(등급 코드). R2 수집기는 여기서 출발하면 된다.

따라 하는 절차(이민우 님 몫, 4 절 10 항):

(가) ROS 2 로 기록할 때
1. 노트북을 Go2 와 랜선으로 잇고 같은 대역의 고정 주소를 준다(대역 값은 7.8 의 「미확인」 참고. 실기 받은 뒤 공식 문서로 확정).
2. unitree_ros2 를 README 대로 설치한다. ROS 2 의 DDS 구현을 CycloneDDS 로 바꾸고(`RMW_IMPLEMENTATION=rmw_cyclonedds_cpp`), `CYCLONEDDS_URI` 에 랜카드 이름을 적는다(README 42~48 · 97~101 행).
3. `ros2 topic list` 로 토픽이 보이는지 확인한다(README 128 행). `ros2 topic echo /sportmodestate` 로 값이 흐르는지 한 번 본다(133 행).
4. 기록: `ros2 bag record /lowstate /sportmodestate /lf/lowstate /lf/sportmodestate /wirelesscontroller /api/sport/request` (토픽 이름은 README 178 · 231 · 276 · 292 행. `/lowcmd` 는 **구독만** 하고 발행하지 않는다, 311 행).
5. 영상을 같이 찍고, 시작 · 끝 시각을 bag 과 맞춘다.

(나) SDK 구독으로 기록할 때
1. 같은 랜 설정. `python -m foothold_agent.go2_readonly --nic <랜카드>` 를 띄우면 상태만 받는다(`go2_readonly/__main__.py:21-25`, 기본은 1 초마다 JSON 요약. 원시 값 전부를 파일로 남기는 기록기는 새로 짜야 함).
2. 직접 짤 때는 `ChannelSubscriber('rt/lowstate', LowState_)` · `ChannelSubscriber('rt/sportmodestate', SportModeState_)` 둘만 쓴다(`go2_direct/sdk.py:18-26` 와 같은 모양). unitree_sdk2 예제 `go2_low_level.cpp` 는 lowcmd 발행이 들어 있으니 통째로 돌리지 않는다(analyst R2 표).
3. 받은 메시지마다 로봇 시각(tick)과 수신한 컴퓨터의 시각을 함께 적는다. 둘을 같이 적지 않으면 나중에 영상과 못 맞춘다.

수집기를 믿기 전에 답을 아는 입력으로 시험한다(analyst R2 3 항): 빠진 표본 · 시계 점프 · 관절 순서 반전 · 정지 명령에도 남는 움직임.

### 7.6 real2sim 과 sim2real 은 반대 방향이다

| | real2sim(거울 표시) | sim2real(같은 보행) |
|---|---|---|
| 흐르는 것 | 실기 상태 → 화면 | 같은 ONNX · 같은 명령 → 시뮬과 실기 양쪽 |
| 화면의 로봇이 움직이는 까닭 | 받은 관절 12 개 · 자세를 그대로 그려서 | 시뮬 물리가 정책 출력대로 움직여서 |
| 물리 계산 | 없음(그리기만) | 있음(MuJoCo) |
| 지연의 뜻 | 화면이 실기보다 늦게 보임 | 정책 입력이 늦으면 보행이 달라짐 |
| 우리 계획 | 그림 ③의 거울 창. Go2 공식 앱이 이 방식(analyst GO2-APP-state-vs-simulation.md: `rt/lf/lowstate` 의 motor_state.q 를 화면 모델 관절에 넣음) | 그림 ③의 시뮬 창 + 실기. 같은 보행이 나오는지가 R3 의 성공 기준 |

거울 표시를 만들 때 지켜야 할 것(analyst 같은 문서): 명령 시각 · 로봇 상태 시각 · 수신 시각 · 그림 표시 시각을 따로 두고, 오래된 상태는 오래됐다고 표시한다. 물리 시뮬 모드와 거울 모드는 이름과 자료 출처를 섞지 않는다. 공식 앱의 관절 이름표 순서를 우리 actor 순서로 가져오면 안 된다(`deploy.yaml:1-37` Isaac 순서와 SDK 순서가 다름).

### 7.7 Go2 순정 보행을 시뮬에서 따라 하려면 모방 학습이 필요하고, 그것은 큰 일이다

- 순정 보행의 정책 파일을 꺼낼 길은 없다(analyst R2: 공식 앱 APK 와 SDK 헤더에 가중치를 주는 API 없음, 등급 읽기). 그래서 「보행을 보고 배우는」 모방 학습뿐이다.
- 모방에 쓸 정답이 약하다. 받을 수 있는 것은 측정 관절각 q 와 추정 토크 tau_est 이고, 순정 제어기가 실제로 낸 목표 관절각 · 목표 토크 · Kp · Kd 는 받지 못한다(R2 4 항). 그러면 「행동 모방」 이 아니라 「상태 궤적 모방」(보행 모양을 보상으로 삼아 RL 로 다시 학습) 이 되고, 이것은 우리 EX 학습 한 판과 같은 크기의 일이다.
- 자료 양 · 상황 설정이 크다. 조건(속도 5 가지 이상 × 좌우 대칭 × 지형) 마다 여러 세션, 세션 단위로 훈련 · 시험 분리(R2 5 항), 동기 영상, 넘어짐 · 개입 기록. 평지만 해도 하루 단위의 실기 시간(가정)이고, 계단은 별도 승인 뒤다.
- 순정 제어기의 내부 상태(기억)를 볼 수 없으므로 같은 관측에서 같은 행동이 나온다는 보장이 없다(R2 5 항). 모방이 끝나도 「비슷한 보행」 이지 「같은 보행」 이 아니다.

그래서 6 절 R2 의 첫 질문은 「순정 정책을 받았다」 가 아니라 「순정 보행의 상태 궤적을 선생 자료로 모을 수 있나」 이고, 수집은 11/9 실기 뒤다.
