그림 ① · 지금 · Unitree 순정 보행

키를 누르면 명령이 인터넷을 두 번 건너 Go2 옆 노트북에 닿고, 거기서 랜선으로 들어간다

이 길에서 걷는 법을 정하는 것은 Go2 안에 든 Unitree 의 순정 제어기다. 우리 코드는 「어느 방향으로 얼마나 빨리」 만 전달한다.

읽는 순서

  1. 키보드 · 단추. 화살표 키와 A · D 를 누른다. 누르는 동안만 값이 있고 떼면 0 이다. 앞 · 뒤 · 옆 1.5 m/s, 제자리 회전 0.5 rad/s 로 고정돼 있고 서서히 올리는 장치는 없다.
  2. 브라우저 화면. 50 ms 마다 명령 3 개(vx vy wz)를 서버로 보낸다. 0 도 보내서 「아직 조종 중」 임을 알린다.
  3. 서버(NaverCloud). 같은 허용 표로 값을 검사하고 에이전트 쪽 웹소켓으로 그대로 넘긴다. 서버는 보행을 계산하지 않는다.
  4. 에이전트 노트북. Go2 와 랜선(10 m)으로 이어진 노트북에서 도는 우리 프로그램. 서버에서 받은 명령을 SportClient.Move(vx, vy, wz) 로 바꿔 랜선 위 DDS 로 보낸다. 0.3 s 안에 새 명령이 없으면 스스로 멈춘다.
  5. Go2 본체. Unitree 순정 제어기(sport mode)가 다리 12 개를 움직인다. 그 안이 어떤 계산인지는 우리가 볼 수 없다.
  6. 되돌아오는 것. Go2 는 관절 상태(lowstate)와 몸 상태(sportmodestate)를 DDS 로 내보내고, 에이전트가 이를 받아 서버 · 브라우저로 올린다. 카메라 · 라이다 영상도 같은 방향으로 온다.

그림 ② · 우리 시뮬 앱 · 브라우저 안

같은 키 명령이 브라우저 안에서 우리 보행 정책에 들어가고, 물리와 화면이 그 안에서 돈다

여기에는 서버도 로봇도 없다. 물리(MuJoCo), 정책(지금은 손으로 짠 JS 추론, 계획은 ONNX), 그림(Three.js)이 모두 한 브라우저 탭 안에서 돈다.

읽는 순서

  1. 키 입력. ↑ ↓ ← → 와 W A S D 가 세 축(앞뒤 · 옆 · 회전)으로 바뀐다. 그림 ①과 같은 뜻의 명령 3 개다.
  2. 보행 정책. 명령 3 개와 몸 상태(관절 · 자세 등 45 개) 와 발밑 높이 지도를 받아 관절 목표 12 개를 낸다. 지금 모드는 foothold-v2 와 ame2-demo 둘이다.
  3. 물리 MuJoCo. 관절 목표를 PD 제어로 따라가며 로봇과 지형을 계산한다. 계산 결과(관측)가 다시 정책으로 돌아간다.
  4. 3D 화면. 물리가 낸 자세를 Three.js 가 그린다. 사람은 이 화면을 보며 다음 키를 누른다.
  5. 정책 파일. 학습한 가중치를 파일로 받아 둔다. 앞으로는 ONNX 파일 하나와 「명령 범위 JSON」 을 같이 내보낸다(그림 ③의 파일과 같은 것).

그림 ③ · 앞으로 · R3 저수준 제어

같은 명령을 우리 ONNX 정책이 로봇 옆 컴퓨터에서 받아 저수준 명령을 내고, 실기 관절을 화면에 거울처럼 비춘다

그림 ①과 다른 점은 두 가지다. 걷는 법을 정하는 것이 Unitree 순정 제어기가 아니라 우리 정책이 되고, 그 정책은 서버가 아니라 로봇 옆 컴퓨터에서 돈다.

읽는 순서

  1. 키보드 → 브라우저 → 서버. 그림 ①과 같다. 서버는 명령 3 개를 나를 뿐 정책을 돌리지 않는다.
  2. 로봇 쪽 컴퓨터. Go2 EDU 의 확장 컴퓨터(아래 「미확인」 참고) 또는 랜선으로 이어진 노트북. 여기서 우리 ONNX 정책이 50 Hz 로 돈다. 입력은 명령 3 개 + Go2 에서 받은 관절 · 자세 상태, 출력은 관절 목표 12 개다.
  3. LowCmd. 관절 목표 12 개에 Kp 25 · Kd 0.5 를 붙여 저수준 명령으로 보낸다. 학습 때와 같은 값이어야 학습한 대로 걷는다.
  4. Go2 본체. 이제 순정 보행 제어기가 아니라 모터 12 개가 우리 목표를 직접 따른다. 관절 상태(lowstate)가 매 주기 돌아온다.
  5. 거울 화면. 관절 12 개 값이 서버를 거쳐 브라우저로 올라가고, 브라우저는 그 값으로 로봇 모델을 그린다(Go2 공식 앱이 하는 방식). 옆에는 같은 ONNX 를 브라우저가 직접 돌리는 시뮬 화면을 나란히 둔다.
  6. 같은 파일 한 벌. 정책 ONNX 와 명령 범위 JSON 은 브라우저와 로봇 쪽 컴퓨터가 같은 것을 쓴다. 학습이 넓어지면 파일만 바뀐다.

어디서 계산하나 · 세 자리 비교

정책은 브라우저에서, 로봇 옆에서, 서버에서 돌 수 있다. 실기는 로봇 옆이어야 한다

(가) 브라우저 ONNX

  • 시뮬 전용. 물리도 정책도 한 탭 안에서 돌아 지연이 없다.
  • 기기마다 속도가 달라 측정이 필요하다(D107).
  • 실기 모터는 브라우저에서 못 만진다. 그래서 (가)는 실기 길이 될 수 없다.

(나) 로봇 쪽 컴퓨터

  • 50 Hz 는 20 ms 마다 한 번이다. 관절 상태를 읽고 → 정책 → LowCmd 까지 20 ms 안에 끝나야 한다.
  • 랜선 위 DDS 는 한 건물 안 통신이라 이 시간 안에 든다. 인터넷은 들쭉날쭉해서 보장이 없다.
  • 인터넷이 끊겨도 로봇은 마지막 명령 0 으로 서 있을 수 있다. 안전상 유일한 선택이다.

(다) 서버 계산

  • 관절 상태를 멀리 있는 서버로 올리고 관절 목표를 받아 오는 왕복이 매 20 ms 안에 끝나야 하는데, 인터넷 왕복은 그보다 길고 흔들린다(이번에 미측정).
  • 한 번만 늦어도 로봇은 옛 명령으로 발을 디딘다. 넘어짐의 원인이 된다.
  • 서버는 명령 3 개(vx vy wz)와 상태만 나른다. 이것이 그림 ①과 ③에서 서버의 역할이다.

ROS 2 가 지금 실기 길에 없는 까닭도 같다. 에이전트는 Unitree SDK2 로 바로 DDS 에 붙는다. SDK2 와 ROS 2 는 같은 DDS(CycloneDDS) 위에서 같은 토픽을 쓴다. SDK 가 보는 rt/lowstate 는 ROS 2 에서 /lowstate 로 보이는 같은 토픽이다(ROS 2 는 토픽 이름 앞에 rt/ 를 붙여 DDS 에 올린다). 그래서 ros2 bag record 로 기록하든 SDK 구독으로 기록하든 같은 자료가 남는다. 자세한 절차와 모을 것 목록은 APP-INTEGRATION-NOTES.md 7 절에 있다.
