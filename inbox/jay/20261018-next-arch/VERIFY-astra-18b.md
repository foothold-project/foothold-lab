## 1. 화요일·수요일 선택이라는 목적에 맞는가

**맞는다. 다만 P2에서 “고른 판 또는 둘”은 선택 결과의 의미를 갈라놓는다.** 같은 P1에서 출발한 M1/M2를 비교한 뒤 한 판만 P2를 학습시키고 그 결과로 그 판의 encoder가 더 좋다고 하면, 구조 차이와 추가 지형·학습량 차이를 구별하지 못한다. [D:60~61,78]

권고 일정은 **P1 공통 추가 갱신 수에서 비교 → 두 판 모두 같은 P2 예산 → 화요일 지정 시점의 공통 체크포인트에서 선택**이다. 한 판이 명백히 실패해 다른 판만 P2로 보내는 운영 판단도 가능하다. 그때는 “P1에서 고른 후보의 P2 적응 확인”이라고 쓰고, M1/M2의 P2 우열 비교는 미확인으로 둔다. 두 판의 같은 단계·학습량을 맞추는 데 다른 판의 GPU를 쉬게 할 필요는 없다. 빠른 판은 정해 둔 후속 작업을 수행하되 본 비교 체크포인트를 보존한다. [D:14,60~62,78,84~87]

**M0는 필요한 후속 대조이고 지금 학습의 선행 조건은 아니다.** M1−E1, M2−E1에는 지도 외에도 gap·보상·관측 부호·추가 학습·optimizer 재시작이 들어간다. M0 없이 지도 자체의 효과를 확정할 수 없다. M1−M2는 동일 학습 묶음 아래 모듈 간 비교다. 따라서 화요일에는 “우리 조건에서 채택할 후보”를 고를 수 있지만, 논문 전체의 우열이나 지도 추가의 순수 효과를 증명했다고 쓰면 틀리다. [D:32,35,39~44; 18a §7.1]

오늘 M3, 추정 머리, 별도의 head 수 탐색을 더할 이유는 없다. 추가 GPU 시간은 우선 P2의 공통 비교를 완성하고, 그다음 M0나 추가 seed에 쓴다. 화요일 결정을 수요일로 연장할 때는 이미 본 사례에서 가장 좋은 checkpoint를 재선택하지 말고, 지정된 추가 학습량과 별도 확인 사례로 구분한다. 한 seed의 사례별 신뢰구간은 학습 seed 간 변동을 포함하지 않는다. [D:33,44,79~80; 통계적 선택 편향에 대한 설계 판단]

## 2. M2는 AME-2의 핵심을 살리는가. 17×11이면 부족한가

### 2.1 속도 추종으로 가져오는 것은 기술적으로 타당

query가 명령을 포함한 몸 상태와 전역 지형을 읽고, 접촉에 필요한 지역 정보를 선택한다는 구조에는 목표 위치 명령이 필수로 들어 있지 않다. 현재 `single_obs` 45에는 속도 명령이 있으므로 명령 조건부 지형 선택을 구성할 수 있다. 그러나 원 논문의 목표 도달 보상과 행동 자유도를 가져오지 않으므로 원 논문의 도약·희소 지형 성적이 재현된다는 근거는 없다. **“AME-2에서 착안한 속도 추종용 지형 모듈”이라는 이름이 정확하다.** [env:168~230; AME:73~85,167~172; [AME-2 §IV-A·VIII-C](https://arxiv.org/html/2601.08485v3)]

### 2.2 작은 격자 때문에 CNN을 빼야 한다는 근거는 틀림

공식 공개 구현은 점별 FC와 높이 CNN을 결합해 지역 특징을 만들고, 별도 MLP와 max-pool로 전역 특징을 만든다. 입력 L/W를 실행 시 읽고 padding을 사용한다. **26×16이 최소 입력 크기라는 제한은 없다.** 실제 코드와 같은 `Conv2d(1,8,5,padding=2) → ELU → Conv2d(8,48,5,padding=2) → ELU`를 CPU에서 `[2,1,11,17]`에 적용해 `[2,48,11,17]` 출력을 확인했다. 공식 모델 전체나 GPU 처리량 시험은 아니다. [AME:51~68,149~169; D:50]

점 MLP도 학습 가능한 모델이다. 다만 이웃 높이의 기울기·틈 가장자리 등을 먼저 결합하는 지역 처리를 빼므로 “AME-2 핵심을 그대로 살린 축소판”이라는 설명은 약해진다. 오늘의 구체 권고안은 다음과 같다.

| 부분 | 권고 계약 |
|---|---|
| 입력 | 동일한 처리 후 height 187과 실제 scanner 순서의 x/y. M1과 정보량 동일 |
| 지역 특징 | 높이 CNN `1→8→16`, 3×3·stride 1·padding 1. 점별 `[x,y,h]→16`과 concat 후 `32→64` |
| 전역 특징 | 지역 특징에 `64→64` MLP를 적용하고 187점 max-pool |
| query | 기존 경로의 latent 32 + single_obs 45 + 전역 64를 `141→64`로 투영 |
| attention | query 1개, K/V 187개, d=64·head=4. dropout 0으로 시작 |
| actor 연결 | `[attention64, global64]→16`, actor 입력은 M1과 같은 93차원. 기존 77열 복사·새 16열만 0 |

이는 **설계 제안이며 효과 미확인**이다. 공식 폭·head 수를 복제할 필요는 없지만, head=4를 “격자가 작으니 정답”이라고 설명하지 않는다. 64/4=16차원 head의 비용과 표현력을 택한 초기값일 뿐이다. CNN과 attention 등을 함께 바꾸므로 결과가 좋아도 “attention 하나의 효과”로 분해해서 말할 수 없다. 그 분해 실험은 다음 단계다. [AME:51~85; D:50~54]

현재 초안대로 128차원을 바로 actor에 붙이면 첫 층이 M1의 93열과 달리 **205열**이고, 그 층만 M2에 57,344개 가중치가 더 생긴다. 따라서 D:35의 “지형 encoder 하나만 다름”은 엄밀하지 않다. 위 16차원 출력은 기존 actor 인터페이스를 맞추는 선택이다. 128차원을 유지해도 실험은 가능하지만 “encoder와 actor 입력 용량을 함께 바꾼 모듈 비교”로 기록해야 한다. 지도 encoder와 마지막 투영까지 모두 0으로 초기화하면 안 된다. [E1 actor CPU shape; 512×(128−16) 산술; 18a §1]

### 2.3 CTS query와 좌표의 두 함정

**query의 latent는 경로를 정해야 한다.** 원래 CTS actor는 teacher 환경에서 teacher latent, student 환경과 inference에서 student latent를 쓴다. 초안의 `student latent 32`를 모든 환경에 그대로 적용하면 teacher 경로에서도 student MoE를 추가 계산해야 한다. 이것도 가능한 설계지만 현재 비용 추정과 기존 경로가 달라진다. [actor:210~234; D:52]

권고는 teacher에는 기존 z_T, student/inference에는 z_S를 쓰고, **query용 latent만 detach**하는 것이다. 기존 actor로 가는 teacher gradient는 유지하고, 새 query가 student encoder를 PPO로 갱신하지 않게 한다. map CNN·MLP·query·attention·출력 projection은 PPO optimizer에 모두 등록한다. student 증류 optimizer는 원래 역할을 유지한다. teacher와 student의 query 분포 차이가 학습에 미치는 영향은 미확인이며, student 실측이 최종 평가다. [actor:210~246; PPO:94~101,380~405]

**scanner는 완전한 몸체 회전 좌표가 아니라 yaw 정렬 수평 격자다.** x는 −0.8~0.8 m, y는 −0.5~0.5 m다. 기본 `ordering="xy"`의 평탄화 순서는 x가 먼저 변하고, 원래 배열 shape는 **[11,17]**, 즉 [Ny,Nx]다. 187개를 단순히 [17,11]로 reshape하면 이웃이 달라진다. 코드의 `ray_starts`에서 x/y 순서를 얻거나 같은 pattern으로 생성하고, 전치한다면 높이와 좌표를 함께 전치한다. CPU에서 좌표 187개의 첫 행이 x 17개로 진행하는 것을 확인했다. [Lab `sensors/ray_caster/patterns/patterns.py:36~53`, `patterns_cfg.py:55`; `ray_caster.py:274~280`; env:65~71]

여기서 h는 `clip(sensor_z−hit_z−0.5)×2.5`인 **처리된 높이 특징**이다. xyz 물리 점군의 z와 같은 부호·단위가 아니다. 구멍 +2.5를 padding처럼 attention mask로 제거하면 필요한 위험 정보를 지운다. 이번에는 수치 계약을 그대로 유지하고 센서 고장용 validity와 실제 틈을 혼동하지 않는다. [D:40,50; 18a §2의 gap 함수 CPU 대조]

### 2.4 해상도와 메모리

**P1은 17×11·0.1 m 그대로 시작할 만하다.** 10 cm보다 작은 발판·모서리 위치는 격자 위상에 따라 빠질 수 있고, attention은 관측하지 않은 형상을 복원해 주지 않는다. 그러나 해상도부터 바꾸면 teacher 입력·계산량까지 바뀌고 오늘 비교가 커진다. DELTA Table III에서 AME의 미세 디딤돌 성공률은 해상도 증가에도 65.7→68.0%였고 DELTA는 84.0→95.9%였다. 이는 고해상도만으로 문제가 해결되지 않는다는 근거이지, 우리 187점이 불가능하다는 증거는 아니다. 로봇·학습 조건이 다른 외부 결과다. [[DELTA §III-B·Table III](https://arxiv.org/html/2608.22033v1)]

P2에서 좁은 발판 실패가 특정 격자 위상에 집중되면, 다음 단계에서 같은 장면을 몇 cm 옮겨 스캔 누락과 정책 실패를 분리한다. 고해상도가 필요하면 지도 갈래용 5 cm 격자 33×21을 별도로 추가하고 teacher/critic의 기존 187점 계약을 유지하는 방법이 있다. 그 비교에서는 M1/M2에 같은 새 정보를 준다. 단순 보간으로 점 수만 늘리는 것은 새 측정이 아니다. [env:65~71,225~230; 격자 간격·범위에 대한 설계 판단]

**M2의 현실적 위험은 head 수보다 PPO minibatch의 크기다.** cfg는 8192 env 기준 rollout 24, minibatch 4라 전체 minibatch가 49,152표본이다. float32 `[8192,187,64]` 한 텐서는 **374 MiB**, `[49152,187,64]` 한 텐서는 **2,244 MiB**다. 실제 CTS는 teacher/student 호출을 나누므로 개별 텐서 크기는 해당 분할을 따르지만, K/V·CNN 중간값·backward까지 합친 최고 메모리는 이 한 텐서 계산보다 크다. query 1개라 187×187 self-attention을 하는 구조는 아니다. [cfg:58~59,69,75; CPU byte 산술; PPO:237~275]

첫 기동에서 이미 예정한 메모리 확인으로 유효 batch를 정한다. 필요하면 두 판의 env 수를 같이 낮춘다. gradient accumulation으로 잘게 나눌 때는 teacher 평균+student 평균이라는 CTS 손실을 보존하고 optimizer step·gradient clipping·KL 결정을 유효 minibatch 단위로 해야 한다. 단순히 minibatch 개수를 늘리면 optimizer 갱신 수까지 달라진다. rollout에는 학습 graph가 붙은 token 특징을 누적하지 않고 PPO에서 재계산한다. 실제 메모리 최고치와 처리량은 미확인이다. [PPO:319~335; D:87]

## 3. 공통 iteration만 맞추면 되는가

**주 비교는 같은 학습 표본 수, 보조 비교는 실제 시간이다. 둘 다 필요하다.** env 수·rollout 길이가 같고 누락 없이 학습했다면 공통 추가 iteration은 표본 예산을 맞춘다. 숫자가 같은 checkpoint 이름만으로는 부족하다. P1/P2 각각의 추가 갱신 수, 유효 optimizer step과 조기 KL 중단 수, teacher/student 조우 수를 함께 남긴다. [runner:91~165; cfg:58~79; D:41,60~61,87]

표에는 공통 checkpoint 성적과 함께 학습 활성 시간, 전체 경과 시간, 평가·Kit 기동 시간, transition/s를 따로 둔다. GPU 1의 화면 부하와 두 실행의 CPU·디스크 경쟁이 있으므로 “GPU 0의 M1이 빠르다”만으로 encoder 자체가 더 빠르다고 일반화하지 않는다. 그래도 **같은 마감까지 실제로 얻은 성적**은 프로젝트 선택에 유용한 운영 지표다. 순수 구조 성능으로 분리해 쓴다. [D:84~92]

일요일 18:30부터 월요일 08:00까지는 13.5시간이다. 47,000 transition/s를 그대로 적용하면 약 11,618회지만, 이것은 checkpoint·평가·새 encoder 비용을 뺀 산술이다. 실제 P1 목표는 초기 실측으로 예측하되, 양쪽 동일 갱신 수와 마감 중 먼저 도달하는 조건으로 실행기에 명시한다. 더 빠른 판의 추가 학습 결과는 본 비교와 구분한다. [D:60,91; 47,000×13.5×3600/(8192×24) CPU 계산]

## 4. 판정 숫자는 합리적인가

### 4.1 gap +20%p는 실용적 목표일 수 있으나 통계에서 나온 값이 아님

**20%p는 이번 채택에 요구하는 효과 크기로는 사용할 수 있다.** 다만 자료에서 산출한 최소 효과나 검정력에 근거한 값은 아니다. 새 명령에서 E1이 이미 80%를 넘으면 +20%p는 달성 불가능하다. 그 기준선은 이번에 실측하지 않았으므로, 새 판 결과를 보기 전 E1의 천장 효과도 확인해야 한다. 기존 gap 20사례 전체의 짝 차이를 주 지표로 쓸지, 폭별 평균을 쓸지 먼저 명시해야 한다. 현재 문구의 “평균 차”는 모호하다. 권고는 **기존 등록 gap 20사례의 결합 성공률 차**를 주 지표로 두고, 폭별 결과는 별도 진단으로 두는 것이다. 학습 판 세 개를 평균하지 않는다. [D:67~68,76]

기존 CI 코드를 CPU에서 직접 호출한 결과다. b는 새 판만 성공, c는 E1만 성공인 짝 수다.

| b / c / n | 성공률 차 | Tango 95% 구간 |
|---|---:|---:|
| 4 / 0 / 20 | +20%p | +0.665~+41.602%p |
| 5 / 1 / 20 | +20%p | −4.913~+43.691%p |
| 6 / 2 / 20 | +20%p | −8.583~+45.701%p |

따라서 +20%p만 보지 말고 네 칸 짝 표와 구간을 함께 내야 한다. 이것은 현재 Tango 구현의 반환값 확인이며 작은 표본에서 정확한 95% coverage를 새로 보장한 시험은 아니다. 이번에는 추론 방식을 결과에 맞춰 바꾸지 않는다. [CI:19~60]

“0.30 m 이상 칸이 하나라도 높음”은 여러 칸 중 우연히 오른 칸으로 만족할 수 있다. 이를 별도 통계적 개선 증거로 쓰지 않는다. `0.30·0.40·0.50·0.60 m`의 동일 가중 요약과 모든 칸의 원시 성공 수를 함께 보여준다. **N은 빈칸으로 둘 수 없다.** 오늘 폭별 N=10을 탐색용 초기 예산으로 제안한다. 그 표본으로 칸별 우월성을 확정하지 않고, 화요일 선택에 쓸 어려운 폭 집합·가중치·평가 checkpoint를 결과 전에 고정한다. 이는 평가 명세이며 학습을 기다리게 할 승인 절차가 아니다. [D:68,76,78]

### 4.2 평지 “구간 전체로 나쁘지 않음”은 고쳐야 함

평지 10사례가 두 판 모두 10/10이어도 `tango(0,0,10)`은 **[−27.753,+27.753]%p**다. 따라서 D:77을 하한≥0으로 해석하면 동률의 완벽한 관측 결과도 통과하지 못한다. 이는 보행 실패가 아니라 **엄격한 보존 기준과 표본 수의 불일치**다. [CI:19~60; 이번 CPU 반례]

권고는 결과를 세 가지로 나누는 것이다.

- **관찰된 퇴행:** 추가 실패·정체·불필요한 도약 등 실제 악화가 있음.
- **관찰상 유지, 통계적 보존 미확인:** 소수 사례에서 악화는 없으나 구간이 넓음.
- **정한 허용 손실 이내의 보존 근거:** 결과 전 정한 비열등 한계와 충분한 표본으로 확인.

정식 선택 규칙에 비열등을 넣으려면 예를 들어 허용 손실 5%p를 먼저 선언하고 차이 구간 하한>−5%p로 정의할 수 있다. **5%p도 운영상 제안이지 실증된 허용치가 아니다.** 같은 Tango 구현에서 모든 짝 결과가 일치할 때 n=60의 구간은 ±6.017%p, n=73은 ±4.999%p, n=80은 ±4.582%p였다. 80사례를 쓰면 항상 충분하다는 검정력 보장은 없지만, 10사례가 무엇을 말할 수 없는지는 분명하다. 10사례는 빠른 퇴행 탐지로 남기고, 정식 보존을 주장할 후보에 확인 표본을 배정한다. 평가가 미완료여도 학습과 후속 실험은 진행할 수 있고 채택 표현만 “잠정”으로 구분한다. [CI CPU 계산; D:77~80]

### 4.3 대각 −15%p, 비행 +10%p는 근거가 약함

현재 E1의 속도·구간별 원자료 분포를 이번에 재측정하지 않았으므로 두 수치를 정상 보행 경계라고 승인할 근거가 없다. E1의 비행이 1%인 가상 예에서 +10%p는 11%까지 허용하는 큰 변화다. 대각 비율은 두 발 지지 분모가 적으면 요동치며, gap 통과의 필요한 도약과 평지 반복 도약을 섞으면 해석이 틀어진다. [D:70,77; 18a §6]

지금은 두 수치를 **주의 표시를 위한 잠정 한계**로 사용하고, 그것만으로 “보행 실패”라고 이름 붙이지 않는다. 평지의 생존·속도 추종·정체와 접촉 패턴을 함께 판정한다. episode별 비율을 구한 뒤 사례를 단위로 요약하고, 상관된 물리 step 수를 독립 표본 수처럼 쓰지 않는다. “구간이 0을 걸침”은 동등함의 증명도 아니다. 어려운 폭·P2 결과로 운영상 후보를 고를 수 있지만, 통계적 차이 미입증이라는 표기는 남긴다. [D:69~70,78~80; 통계·보행 해석에 대한 판단]

## 5. Isaac Lab 징검다리·평균대로 MARG를 근사해도 되는가

**우리 M1/M2의 P2 비교에는 쓸 수 있다. MARG 원 성적과 동등한 벤치마크라고는 할 수 없다.** 치수만 닮고 바닥·연결 구조·높이·명령·로봇이 다르면 같은 문제를 풀지 않는다. MARG Fig.4의 일부 수준 치수는 출발값으로 쓸 수 있지만 전체 수준·비율을 재현했다고 쓰지 않는다. [D:61; `PAPERS-architecture.md:133~143`; [MARG §IV-A·Fig.4](https://arxiv.org/html/2509.20036v2)]

코드에서 확인한 중요한 차이는 둘이다.

- `HfSteppingStonesTerrainCfg`의 기본 `holes_depth=-10.0`이고 생성기는 그 깊이로 height field를 채운 뒤 돌을 올린다. **실제 무바닥 틈과 다르다.** 광선 hit와 충돌 바닥이 존재할 수 있으므로 보이는 mesh, 높이값, 추락 종료를 구별해야 한다. [Lab `terrains/height_field/hf_terrains_cfg.py:168~182`, `hf_terrains.py:373~435`]
- `rails_terrain`은 두 겹의 솟은 테두리를 만들고 **전체 바닥 box를 추가**한다. MARG식 빈 공간 위 평균대라고 부르면 틀리다. 좁은 보행 지지면과 그 밖의 추락 공간을 가진 mesh가 필요하다. [Lab `terrains/trimesh/mesh_terrains.py:380~426`]

오늘 지형을 여섯 종류 전부 복원할 필요는 없다. P2는 넓은 돌에서 시작해 폭·간격·높이를 정한 한 징검다리 계열과, 곧고 충분히 넓은 평균대 한 계열이면 된다. 중앙 spawn 발판과 도착 발판을 두고, 바깥 평지 우회가 성공으로 계산되지 않도록 경로·통과선을 정의한다. 고정 전진 속도를 요구하면서 좌우 발판이 도달 불가능하게 배치되면 실패 원인은 encoder만이 아니다. 발판 간 연결성과 명령 방향이 양립하는 장면부터 쓴다. [D:20,60~70; 위 생성기의 중앙 발판·배치 코드; 시뮬레이션 과제 설계 판단]

지형 비율은 “P1+추가” 대신 합계 1인 숫자로 적는다. **초기 제안은 기존 8종 0.40, gap 0.30, stones 0.20, beams 0.10**이다. 실제 생성된 열·env 수를 기록하고 두 판에 동일 적용한다. 이 비율의 최적성은 미확인이다. P2 뒤에는 P1의 gap·평지도 다시 평가해 징검다리를 얻고 무엇을 잃었는지 남긴다. [D:60~61; 18a §5의 terrain 열 양자화 지적]

## 6. 평가마다 Kit을 띄울 것인가

**며칠 동안 반복 비교할 계획이면 매 사례 Kit 기동은 주 방식으로 부적합하다. 다만 오늘 바로 대규모 병렬 평가기로 갈아엎는 것도 위험하다.** 우선 **한 Kit에서 같은 모델·조건의 여러 사례를 순차 평가**하고, 이미 안정된 격리 평가를 소수 대조용으로 남기는 안을 권고한다. 그다음 여러 env의 병렬 실행으로 확장한다. 시드·지형을 유지한 채 초기화 비용부터 줄이는 순서다. [D:84~92; Eval `s2_eval_driver.py:85~125,176~188`의 현재 단일 env 계약]

현재 Eval loader는 S2의 A/B 체크포인트와 `map` 374차원을 전제로 한다. **새 M1/M2를 그대로 넣을 수 없다.** 재사용할 것은 사례 명세·지표·짝 집계이고, 모델 loader·관측 adapter는 실제 CTS student와 height 187 계약에 맞춰야 한다. 평가 기준선 E1과 두 새 판은 같은 명령·종료·통과 기준을 받는다. E1에는 원래 student용 proprio·이력 처리를 적용하고, 새 지도 갈래는 M1/M2에만 준다. E1의 student inference는 height를 직접 읽지 않으므로 critic용 +2.5 변경 자체가 E1의 추론 행동도 바꾼다고 해석하면 안 된다. teacher 평가를 student 기준선으로 섞는 것이 더 직접적인 오류다. [Eval `s2_eval_driver.py:96~122,180~188`; actor:225~234; D:29,40,66~71]

한 Kit를 재사용할 때는 이전 행동·450차원 이력·접촉 이력·명령 timer·난도·randomization·정상화 상태가 사례 사이에 남지 않도록 한다. 병렬화하면 reset 후 다음 episode의 관측을 첫 episode 마지막 프레임으로 집계하지 않도록 env별 완료 기록을 분리한다. 새 평가기의 첫 동일 사례에서 기존 평가와 초기 상태·첫 관측·행동·종료 이유를 직접 대조하는 것은 **구현 검증**이지 외부 승인 대기가 아니다. 수치적으로 완전히 같은 물리 trajectory까지 보장되는지는 미확인이다. [Eval의 단일 env shape 계약; actor의 이력 입력; 평가기 변경에 대한 판단]

**1,000회마다 별도 Kit 평가를 같은 GPU에 얹는 계획은 다시 설계해야 한다.** trainer가 GPU 메모리를 잡은 상태에서 두 번째 Kit를 띄우면 메모리 경쟁이 생긴다. trainer를 매번 껐다 켜면 아래 7절의 재개 문제가 반복된다. 오늘은 1,000회마다 기존 학습 rollout에서 지형별 성공 대용 지표·비행·정체·NaN·KL을 기록하고, 이를 독립 평가라고 부르지 않는다. 독립 사례 평가는 P1/P2 경계와 지정 선택 checkpoint에 실행하는 것이 현실적이다. 기존 프로세스 안에 독립 평가가 이미 구현됐다면 사용할 수 있으나, 환경 상태·RNG·curriculum 오염 여부는 별도로 확인해야 한다. [D:86; W runner:186~200,279~298]

폭별 N=10이면 P1만 E1/M1/M2 각 90사례, 총 270사례다. 설계의 “120건 약 2시간” 가정을 그대로 적용하면 총 4.5시간이며 ablation·영상·재기동은 별도다. 판별로 다른 GPU에서 겹칠 수 있어 총 경과 시간과는 다르다. 평지 확인 표본까지 늘릴수록 일괄 평가가 중요하다. 이 시간은 **설계 가정의 산술이며 실측이 아니다.** [D:67~68,92; 3×(20+10+6×10) 계산]

## 7. 가장 그럴듯한 실패 경로 셋과 예방

### 경로 1: M2가 rollout은 돌지만 PPO에서 메모리·학습 경로 문제로 실패

187점×64특징을 큰 minibatch로 역전파하는 비용을 빠뜨리거나, 지도 모듈을 student `no_grad` 안에 넣거나, teacher에서만 다른 query를 쓰는 경우다. 그 결과를 “attention이 안 좋다”로 해석하면 틀린다. **예방:** 2절의 shape·좌표·optimizer·query 계약을 구현하고, 첫 갱신에 메모리 최고치와 지도 파라미터 gradient를 기록한다. 메모리 감축은 두 판의 동일 표본 예산을 유지한다. 학습 loss 감소만으로 실제 student 지도 사용을 확인했다고 하지 않는다. [cfg:58~75; actor:210~234; PPO:94~101; 이번 374/2244 MiB 산술]

### 경로 2: 학습은 되지만 보상·과제·선택 기준 때문에 잘못된 판을 고름

평지 표본 부족을 보행 실패로 부르거나, 평지가 깔린 rails를 평균대로 부르거나, 정체해서 비행률이 낮은 판을 정상 보행으로 선택하거나, 한 판만 P2를 더 학습시킨 뒤 구조 우열을 선언하는 경로다. **예방:** 주 비교 checkpoint와 사례를 고정하고, 도달·생존·실제 속도·정체·보행 분모를 같이 보고, P2는 동일 예산으로 비교하거나 단일 후보 적응으로 명확히 분리한다. 기준 미충족은 후속 학습 중단 명령이 아니다. [D:61,69~80; Lab rails:422~426; 4절 CI 반례]

### 경로 3: 세션은 살아 있는데 큐가 재시작·정지·평가 전환을 잘못 처리

**현재 단회 launcher를 반복하는 것으로 다일 대기열이 되지 않는다.** 읽은 W 파일에서 확인한 내용은 다음과 같다.

- `launch_step1.py:35~39`는 매번 고정 E1을 넘긴다. `scripts_rsl_rl/train_step1.py:134~146,261~277`도 E1을 읽고 resume=False로 두며 두 optimizer를 새로 시작한다. 이는 최초 초기화 계약으로는 적절하지만, P1 결과를 이어받는 P2 계약은 아니다.
- W runner:112는 `step1_update_number = it - start_it + 1`로 호출마다 warmup 진행 수를 다시 시작한다. 저장 항목(186~200)에는 이 카운터·환경 curriculum·RNG가 없고, load(279~298)도 이를 복원하지 않는다.
- launcher:93~105는 child를 띄운 뒤 timeout 없는 `wait()`를 한다. 종료 코드 0과 예상 이름의 checkpoint 존재로 완료를 판정하고, 그 뒤 자동 평가를 호출하지 않는다. 프로세스 멈춤·부분 파일·평가 실패 후 복구를 해결한 증거가 아니다.
- `CREATE_NO_WINDOW | CREATE_NEW_PROCESS_GROUP`은 창·프로세스 그룹 설정이다. 이것만으로 재부팅 복구, 진행 감시, 가족 프로세스 수명 관리가 구현되지는 않는다. M2는 읽은 판의 launcher:77~78와 train:132~133에서 아직 pending 예외다.

이것은 작업 중 코드에서 확인한 공백이며 최종 구현이 영구히 불가능하다는 뜻이 아니다. **오늘 대기열 구현에 넣을 최소 계약**은 아래와 같다.

1. **첫 시작과 재개를 다른 경로로 둔다.** 첫 시작은 고정 E1+같은 optimizer 재시작. 이후는 해당 arm의 정확한 checkpoint·두 Adam·현재 lr/상한·누적 추가 update·warmup 진행·P1/P2 설정·환경 난도를 복원한다. 물리 상태까지 못 저장하면 episode를 명시적으로 reset한 재개라고 기록하고, 끊김 없는 궤적 재현이라고 주장하지 않는다. 난도·명령 상태를 매번 E1 끝값으로 되돌리지 않는다.
2. **LLM 없는 상태 파일을 둔다.** job별 부모 SHA·코드/설정 SHA·GPU·목표 추가 갱신 수를 저장하고 `대기 → 학습 → 체크포인트 확정 → 평가 → 결과 게시`를 구분한다. 게시 실패가 학습 재실행으로 이어지지 않게 한다. 체크포인트는 임시 파일로 쓰고 완료 후 교체하며, 닫힌 파일의 SHA·step을 결과와 연결한다.
3. **시간·오류를 GPU별로 격리한다.** stdout 유무가 아니라 update/checkpoint 진행 시각을 본다. 예정된 평가·저장 구간은 timeout에서 구별한다. 기존 STOP·절대 마감·장치 격리·USD 임시 경로 격리를 사용한다. 작업의 PID와 생성 시각 또는 기존 Job 객체로 해당 작업 가족만 관리한다. 다른 GPU 작업을 건드리는 전체 python 종료는 사용하지 않는다.
4. **실패 시 다음 일을 미리 정한다.** 재현 가능한 코드·관측 오류와 단순 기동 오류를 구별하고, 후자의 기존 위임 범위 내 유한 재시도만 한다. 성적이 낮다고 재추첨하지 않는다. 준비된 M0/다른 seed 등의 후속 job을 명세해 한 작업 실패가 두 GPU의 무기한 대기로 번지지 않게 한다.

위는 며칠 돌릴 실행기의 기능이지 매 실행마다 팀장에게 동의를 받는 절차가 아니다. 원본 E1 체크포인트를 읽었을 때도 저장 key는 model·두 optimizer·iter·infos뿐이었다. 따라서 저장되지 않은 환경 상태를 “resume이 알아서 복원한다”고 전제하면 안 된다. [이번 E1 CPU 판독; W runner·launcher 위 행]

작업 중 소스의 판독 대상 SHA256: W `launch_step1.py` = `85864709873470cc3481fce0d5418614161e85c10404b59157b590f3beaa27d5`, `scripts_rsl_rl/train_step1.py` = `a1190ad635a413f2618d4198a5b8002adfc5fca40132bf885e5245f54a9a6f1f`, W runner = `66a07d1e722562b45f5751dda862b14e3f89038bd6b138ce32b9652d00c69e82`. 이후 수정본에 같은 지적이 남았는지는 그 바이트를 확인해야 한다.
