## 2. 참고 사이트에서 실제 확인한 방식

[Benjamin Simon 사이트](https://www.benjamin-simon.dev/)의 공개 번들 `/_next/static/chunks/2b3861856b9a338d.js`를 읽었다. `FRAME` 장면은 다음 구현을 사용한다.

- `/assets/monolith_frames_optimized/frame_XXXX.webp` 이미지를 로드한다.
- Canvas 2D의 `drawImage`로 해당 프레임을 표시한다.
- GSAP 타임라인·ScrollTrigger가 스크롤 진행에 따라 프레임을 바꾼다.
- 프레임 317 등에서 유지하는 구간이 있다. 단순 HTML video 자동재생과 다르다.

이는 해당 장면의 구현에 대한 확인이며 사이트 전체가 실시간 3D를 쓰지 않는다는 뜻은 아니다. 공개 코드를 읽었으며 이번에는 사이트의 모든 인터랙션을 브라우저에서 실기 검증한 것은 아니다. 원본 코드와 이미지를 우리 발표 자산으로 복제하지 않고 재생 제어 방식만 참고한다.

우리 적용안은 **스크롤 대신 다음/이전 입력이 설명 상태를 선택**하는 방식이다. [GSAP tweenTo 공식 문서](https://gsap.com/docs/v3/GSAP/Timeline/tweenTo()/)는 지정 시간·라벨까지 재생 후 정지하는 기능을 설명한다. 웹 인터랙션을 발표자의 호흡에 맞추는 데 사용할 수 있다.

## 3. 어셋 제작과 HTML의 역할

|---|---|---|
| Go2 외형·턴테이블·부품 분해·관절 축 | 실제 USD/메시를 읽고 Blender에서 부품 계층·축·카메라를 정한 뒤 렌더 | 한 모델로 형상 일관성 유지. 원본 보존, 편집 가능한 .blend와 부품 대응표 저장 |
| 발표 중 3D 연출 재생 | 필요한 구간별 WebP/PNG 프레임 시퀀스 + Canvas + GSAP | 정확한 설명 위치에서 멈춤·역행. 실시간 물리 시뮬레이션을 발표 브라우저에서 돌릴 필요 없음 |

| 픽셀 Go2 진행 표시 | 공통 픽셀 원화·걷기/틈 넘기/오르기 스프라이트, CSS/Canvas 재생 | 우측 상단에서 접지와 몸통 동작. 목차 이동과 상태 복원. 구체 생성 도구는 테스트 후 선택 |

프레임 시퀀스는 메모리를 사용하므로 전체를 처음부터 모두 디코딩하지 않는다. 현재·다음 구간만 미리 읽고 과거 구간 캐시를 제한한다. 출력 크기·프레임 수·해상도는 한 구간의 화질과 실제 발표 기기에서 측정한 로딩·재생 결과로 정한다. 수백 장의 4K 시퀀스를 그대로 올리는 방식은 채택하지 않는다.

Three.js의 실시간 3D는 임의 각도로 돌려 볼 필요가 확정될 때 선택 가능하다. 현재 고정 발표 동선은 Blender 렌더 시퀀스를 우선 제안한다. React/Next.js로 전체 덱을 옮길 필요는 없으며 기존 HTML 진입점과 메모·단축키를 확장한다. CDN 연결이 없어도 쓰도록 라이브러리와 어셋은 로컬 제공을 기준으로 한다.

| 정면 | Go2 정면 공개 | 기체 정면과 제품 이름 |

## 5. 장비→관측에서 지킬 연결

사용자가 원한 정보의 출처 설명은 반드시 구현한다. 다만 모든 정책 입력을 센서 한 개에 직결하지 않는다.

- 관절 위치·속도는 실제 장비의 관절 상태 측정 경로와 연결해 설명할 수 있다. 현재 시뮬레이션에서는 시뮬의 관절 상태를 읽는다.
- 몸의 각속도·중력 방향·선속도는 실기 측정/상태 추정과 시뮬 상태를 구분한다. IMU 하나가 선속도를 그대로 제공한다고 그리지 않는다.
- 속도 명령은 제어 지시이고 이전 행동은 정책 실행 이력이다. 둘 다 센서 원시 측정이 아니다.
- 현재 187개 height scan은 ray casting 기반이다. D435i·HESAI-360이 바로 그 입력을 만든다는 실제 연동 완료 주장은 하지 않는다. 향후 센서 처리 경로를 설명한다면 계획으로 표시한다.
- Orin NX는 연산 장치다. 센서처럼 측정값을 생성하는 아이콘으로 연결하지 않는다.

로컬 `velocity_env_cfg.py`에 base_lin_vel·base_ang_vel·projected_gravity·velocity_commands·joint_pos·joint_vel·last_action·height_scan 항목이 존재하는 것을 이번에 다시 읽었다. 실제 선택 정책의 최종 순서·scale·정규화·관절 인덱스는 해당 실행 설정과 함께 확정한다.

## 6. 리모컨과 상태 제어

기존 `design/deck.js`에는 `current`와 `step`, 다음/이전, PageDown·PageUp·Space·화살표 입력이 있다. 지금 구현은 요소를 드러내는 수준이며 Canvas 시퀀스나 프레임 앵커를 제어하지 않는다.

제안하는 동작은 다음과 같다.

- 다음 한 번: 현재 장면에서 다음 설명 상태까지 재생한 뒤 정지.
- 그 상태에서 얼마든지 설명. 시간 경과만으로 다음 상태나 장으로 가지 않음.
- 모든 설명 상태가 끝난 다음 입력만 다음 슬라이드로 이동.
- 이전 입력: 이전 설명 상태로 복원. 영상·라벨·수치를 같은 상태로 함께 이동.
- 재생 중 다음 입력: 현재 전환의 끝으로 먼저 정착하고 정지. 한 입력으로 여러 장을 건너뛰지 않음. 키 반복·버튼 이중 입력 차단.
- 메모 별도 창도 같은 상태를 표시. 임의 페이지 이동·복귀 시 장면을 재구성.
- 리모컨이 어떤 키를 보내는지는 실제 장치로 최종 확인. 일반 PageDown/화살표/Space는 기존 구조에 연결.
- PDF에는 설명의 핵심 정지 상태를 선택해 출력. 웹에서 중간에 멈춘 상태가 인쇄되는 오류 방지.

이 제어는 영화 속 연출용 HUD와 구분한다. PPT의 기술 라벨·축·신경망은 의미와 위치를 정확히 통제할 수 있어야 한다.

## 7. Higgsfield Exploded-view 적용 가능성

공식 안내를 이번에 다시 조회했다. `/Exploded-view`는 `/use-blender`로 로컬 연결을 확인한 뒤 `bl_get_skill(name="blender-camera-led-assembly")`를 읽고 Blender에서 부품·카메라·조립을 작업하는 흐름이다. 단순한 이미지→영상 생성 모델 호출이 아니다.

[사용자 제공 미리보기](https://static.higgsfield.ai/skills/production/20260924/exploded-view.mp4)를 다운로드해 1920×1080·30fps·3초인 것을 확인하고 8개 시점 프레임을 열어 봤다. 작은 전자 악기의 케이스·키·보드 층이 분리되는 장면과 근접 화면이 있다. 접점과 부품 계층을 드러내는 접근은 Go2의 구조 설명에도 참고할 수 있다. 단, 이 미리보기만으로 우리 USD가 동일하게 분해 가능한 것은 확인되지 않는다.

현재 확인 상태:

- Blender 4.5·5.2 설치 폴더는 있다.
- 이 세션에 `bl_*` 도구가 없고, 읽은 두 Codex 설정에서도 Blender MCP 등록을 찾지 못했다. 라이브 연결 검증은 안 됐다.
- 로컬 Isaac Lab `unitree.py:142`가 `ISAACLAB_NUCLEUS_DIR/Robots/Unitree/Go2/go2.usd`를 가리킨다. 저장소와 `C:/isaac/assets` 검색에서는 원본 Go2 USD를 찾지 못했다. 다른 캐시·머신까지 부재를 입증한 것은 아니다.
- 저장소에 USD의 강체·관절을 읽는 probe 코드가 있다. 실제 source USD·payload·텍스처 수집 및 Blender import는 미수행이다.
- 현재 Python에서 Manim 패키지를 찾지 못했다. 다른 환경까지 미설치라고 단정하지 않는다.

따라서 **활용할 수 있는 제작 경로는 확인했으나 우리 Go2에서 실행 가능한 상태를 아직 입증하지 않았다.** 이번 요청은 활용 확인과 제작 계획 설명이므로 설치·씬 수정·유료 생성은 하지 않았다.

실제 제작 시 원본을 보존하고 사본으로 작업한다. 강체 링크와 시각 메시·충돌체는 다를 수 있다. 메시가 하나로 합쳐져 있거나 센서 내부가 없으면 없는 보드·기어를 발명하지 않는다. '몸통·다리·관절·외장 센서 수준의 분해'와 '실제 내부 설계 분해'를 구분한다. 추가 모듈은 공식 형상/치수 자료와 팀 장비를 별도로 확인한다.

## 9. 페이지별 발표 리허설과 맥락 보존 · U201

사용자가 첫 페이지부터 실제 발표하듯 말하며 부족한 점을 짚는다. 에이전트는 지시한 요소만 국소 수정하지 않고 현재 장면의 목적과 앞뒤 연결, 전체 연구의 흐름을 함께 판단한다. 매번 긴 체크리스트를 사용자에게 반복하지 않으며 판단에 필요한 핵심만 채팅에 설명한다.

### 매 페이지에서 답할 질문

| 검토 대상 | 답해야 할 것 |
|---|---|
| 현재 메시지 | 청자가 이 장에서 반드시 이해할 한 가지는 무엇인가? 어떤 '왜'에 답하는가? |
| 프로젝트 맥락 | 기획 당시 계획, 실제 실험에서 발견한 사실, 지금의 성과, 다음 과제 중 어디에 해당하는가? |
| 근거 | 사용자의 의도와 실제 결과를 구분했는가? 수치·영상·도식이 그 메시지를 뒷받침하는가? |
| 시각 전달 | 청자가 무엇을 먼저 보고 무엇을 이해해야 하는가? 보기 좋은 장식이 설명을 대신하고 있지 않은가? |
| 발표 조작 | 어느 말에서 클릭하고 무엇이 움직이며 어디서 멈추는가? |
| 앞뒤 연결 | 앞 장에서 생긴 질문을 받는가? 이 장의 결과가 다음 장으로 넘어갈 어떤 이유를 만드는가? |

### 전환의 방향

사용자가 말한 Prezi 느낌은 하나의 공간이나 대상을 따라 이동·확대·축소하며 정보의 관계를 보이는 연출로 적용한다. HTML·리모컨 발표를 유지한다. Go2 전체→관절→센서→관측→정책→다수 환경처럼 변화의 이유가 있는 곳에 적용한다. 동일 대상의 위치·크기·카메라를 연결하고 설명 상태에서 멈춘다. 모든 페이지에 같은 줌 효과를 반복하는 것으로 대체하지 않는다. 실제 이징·거리·속도는 장면 샘플과 발표 호흡으로 조정한다.

### 핵심 메시지와 추가 제안

- 사용자 확정 의도: 무엇에 집중하고 왜 해결하는가. 프로젝트의 당위성.
- 사용자 확정 의도: 어떤 성공과 실패를 보고 어떤 선택을 바꾸었는가. 연구 과정과 계보.
- 사용자 확정 의도: 앞으로 무엇을 탐구하는가. 학습 정책·신경망·관측, Digital Twin, 실기 항법.
- 에이전트 제안: 현재 어디까지 입증했는가. 비교 조건·성과·한계를 보여준 뒤 다음 과제의 이유로 연결. 반드시 독립 섹션 하나를 늘린다는 뜻은 아님.

정책과 신경망을 완전히 별개의 물건처럼 그리지 않는다. 향후 구조·관측 연구도 정책을 개선하기 위한 탐구이며 현재 검증한 변경과 앞으로 검증할 효과를 구분한다.

### 모든 턴의 기록과 어셋 작업 중 복귀

USER-REQUIREMENTS-LOG.md에 턴별 사용자 요구·에이전트 제안·승인/미결정·변경 파일과 실제 작업 상태를 누적한다. 전체 기획·흐름에 관한 메시지는 원문도 보존한다. 제작 제안을 사용자 승인으로 바꾸어 적지 않는다. 과거 기록을 현재 상태처럼 쓰지 않고 변경 이력을 연결한다.

어셋 제작에 들어가기 전에 해당 장면의 **메시지, 근거, 앞 장의 질문, 다음 장의 연결, 유지할 요소, 만들 어셋, 완료 기준**을 기록한다. 제작 중 새 피드백도 같은 요구에 연결한다. 돌아왔을 때는 그 기록을 다시 읽고 앞뒤 장면과 함께 검사한 다음 발표에 삽입한다. 도구 작업이 길어졌다는 이유로 앞서 합의한 서사를 재설계하거나 사용자에게 다시 구술을 요구하지 않는다.

현재 기준 자료는 사용자 원문·USER-REQUIREMENTS-LOG, 실제 기획 발표 proposal-deck-presented.html, MVP 보고서와 해당 원자료다. 기존 SECTION-MAP·STORYBOARD의 옛 순서가 최신 지시보다 우선하지 않는다.
