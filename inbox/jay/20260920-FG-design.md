## 1. 진단 · `heading` 은 손잡이 하나가 아니다

```
heading 범위 ─┬─ ① 로봇을 어디로 보내는가        (gap 노출)
              └─ ② 방향을 얼마나 꽉 붙들라는가    (rails 방해로 «추정»)
```

| | ① 노출 | ② 유지 압력 | 결과 |
|---|---|---|---|
| ±π (D) | 나쁨 | **느슨함** · 오차가 커서 `wz` 가 ±1.0 에 포화 | gap 나쁨 · rails 좋음 |
| ±0.5 (E) | 좋음 | **빡빡함** · 최대 `|wz|` 0.28 로 「지금 방향을 정밀히 유지」 | gap 좋음 · rails 나쁨 |
| ±1.5 | 중간 | 중간 | **둘 다 어중간할 것으로 추정** |

> **범위를 어디에 둬도 ①과 ②가 같이 움직인다. 그래서 `heading` 을 더 만지는 것은 막다른 길이다.**
> **①은 지형으로, ②는 명령 방식으로 쪼갠다.**

### 1-1. 다만 rails 의 인과는 «모른다» `미확인`

**앞 문서에서 rails 를 「좁은 빔 위 균형」으로 잘못 알고 썼고 v1.1 에서 물렸다.**

**실제 `rails` 는 평지 위로 솟은 사각 테두리 두 겹이다** `확인됨`. difficulty 0.5 에서 **턱 높이 0.115 m**, 첫째 테두리가 중심에서 ±0.75 m, 둘째가 ±2.7 m. 로봇은 **11.5 cm 턱 둘을 넘어간다.**

성공률 자체는 진짜다. `overall_success` 가 **생존 AND 전진(3 m) AND 속도추종(MAE ≤ 0.25) AND 방향(횡이탈 ≤ 0.75 m)** 의 AND 이고, 테두리가 사각 링이라 **3 m 를 갔으면 턱 둘을 넘은 것**이다.

**그러나 왜 명령 분포가 턱 넘기에 이렇게 민감한지는 모른다.** D > v1 > E 로 **단조롭지도 않다.** 그래서 G 가 필요하다.

### 1-2. rails 에는 측정 결함이 하나 있다 `확인됨`

`rail_thickness_range=(0.08, 0.18)` 은 **난이도가 안 건드리는 자리**다. 난이도를 0.5 로 고정해도 두께가 판마다 무작위로 뽑히고 **2.25 배 편차가 성공률에 섞인다.** `--rail_thickness` 인자가 있는데 우리는 안 썼다.

> **본 평가는 그대로 둔다**(기존 판과 나란히 놓기 위해). **두께 고정 스윕을 진단용으로 따로 돌린다**(3 절).

## 2. 설계

### 2-1. F · 지형을 사방으로 · **본 후보**

**충돌의 뿌리는 `gap` 이 `+x` 에만 있다는 것이다** (`gap_env_cfg.py:81`). 그것을 없앤다.

| 무엇 | D | **F** |
|---|---|---|
| **학습 지형** | `ForwardGapTerrainCfg` (+x 고정) | **`OmniGapTerrainCfg`** · **`mode="ring"`** · 스폰을 둘러싼 사방 도랑 (v1.1 에서 고침) |
| `heading` | (-π, +π) | **그대로** |
| `rel_heading_envs` | 1.0 | **그대로** |
| `ang_vel_z` | (-1.0, 1.0) | **그대로** |
| `rel_standing_envs` | 0.02 | **그대로** |
| `lin_vel_x` | (0.0, 1.5) | **(0.4, 1.5)** ← E 에서 「저속에 비용 아님」 확인된 값 |
| 그 밖 · 비율 · 보상 | | **D 와 완전 동일** |

**어디로 가든 틈을 만나므로 명령을 좁힐 이유가 없어진다.** trade-off 를 푸는 것이 아니라 **없앤다.**

#### 2-1-1. 「타일마다 무작위 방향」은 틀린 기구였다 · **정정 (v1.1)** `확인됨`

**앞 판은 「타일마다 무작위 방향으로 틈을 낸다」로 적었다. 그러면 노출이 안 늘어난다.** rl 세션이 잡았다.

`forward_gap` 의 노출이 낮은 이유는 **틈이 `+x` 에 있어서가 아니라 명령 방향과 틈 방향이 서로 독립이기 때문**이다.

| | 만날 확률 |
|---|---|
| 틈이 `+x` 고정 | `P(명령 방향이 +x 쪽)` |
| 틈 방향을 무작위로 | `P(명령 방향 ≈ 틈 방향)` |

**둘 다 균일 분포이고 독립이면 차의 분포도 균일하다. 돌려도 정렬 확률이 그대로다.** 타일마다 각도를 바꾸는 것은 「어느 타일이 잘 맞느냐」를 바꿀 뿐 **평균 노출을 안 바꾼다.**

**오히려 나빠질 수 있다.** 리셋이 로봇을 `+x` 로 세우므로(`yaw ±0.05`) **스폰 시점에는 틈과 정렬**돼 있는데, 틈을 돌리면 **그 이점까지 사라진다.**

> **이 문서가 「목표」로 적은 것은 「어디로 가든 틈을 만난다」였다. 그것을 하려면 고리여야 한다.**
> **스폰을 둘러싼 도랑이면 어느 방향으로 나가도 가로지르므로 노출이 약 100 % 다.**
> **「무작위 방향」과 「어디로 가든 만난다」는 같은 것을 말하지 않는다.** 앞엣것은 회전 도랑이고 뒤엣것은 고리다.

`OmniGapTerrainCfg` 에 `mode` 칸을 둔다. **기본은 `ring`** 이고 `rotated`(원안)도 한 줄로 돌아갈 수 있게 남긴다.

**학습을 걸기 전에 노출을 실제로 센다.** 생성된 타일에서 스폰을 두고 360 도를 훑어 몇 도가 틈을 가로지르는지 세고, **`forward_gap` · `rotated` · `ring` 셋을 같은 방법으로** 잰다. 하나만 재면 그 숫자가 큰지 작은지 모른다. **명령이 10 초마다 재표집되고 에피소드가 20 초이므로 에피소드 기준으로 센다.**

#### 2-1-2. 고리가 부르는 교란 하나 · 미리 표시한다

**평가 지형에 `floating_ring` 이 있다.** 학습 지형을 고리로 만들면 **모양이 닮는다.** 같은 것은 아니다 · `floating_ring` 은 **솟은** 고리이고 우리 것은 **패인** 고리라 물리적으로 반대다. 그래도:

> **F 가 `floating_ring` 에서 잘 나오면 「일반화」가 아니라 「모양을 봤다」일 수 있다.**
> **그 칸만은 「미경험 지형」이라는 말을 그대로 쓰지 않는다.** 매니페스트와 판정문에 적는다.

`gap` · `rails` · `pit` · `stepping_stones` 는 영향이 없다.

**구현 제약 넷.**

1. `forward_gap` **비율 0.1 을 그대로 둔다.** rough6 노출을 안 줄인다(기존 지형 무너짐 방지)
2. **틈 폭 범위를 B 와 같게 둔다.** 방향만 바꾸는 것이지 난이도를 바꾸는 것이 아니다. 자기검사로 막는다
3. **평가 지형(`unseen10` · `rough6`)은 안 건드린다.** 그래야 기존 판과 나란히 놓인다
4. **고리 반지름은 `vx` 하한에서 정한다.** 하한 0.4 면 20 초에 최소 8 m 를 가므로 고리를 그 안쪽에 두면 **어느 환경이든 한 번은 만난다.** 승급 문턱이 `distance > 4.0 m` 이므로 너무 멀어도 안 된다. 정한 값과 근거를 로그에 남긴다

### 2-2. G · 방향 유지 압력만 뗀다 · **원인 규명**

| 무엇 | D | **G** |
|---|---|---|
| **`heading_command`** | `True` | **`False`** ← 이것 하나만 |
| `ang_vel_z` | (-1.0, 1.0) | **그대로** · 이제 직접 명령으로 쓰인다 |
| `lin_vel_x` | (0.0, 1.5) | **(0.4, 1.5)** ← F 와 맞춘다 |
| 학습 지형 | `ForwardGapTerrainCfg` | **그대로** |
| 그 밖 | | **D 와 완전 동일** |

`heading_command=False` 면 `_update_command` 가 덮어쓰지 않으므로 **전 환경이 `_resample_command` 에서 뽑은 `uniform(-1.0, 1.0)` 을 그대로 받는다** `확인됨`.

> **요 능력은 있는데 방향 유지 압력은 없는 조건.** v1 · D · E 어디에도 없던 칸이다.

## 5. 기존 판과 비교되는가 · **된다. 조건 둘**

| | 같은가 |
|---|---|
| 평가 하네스 · 규격 2 · difficulty 0.5 · 100 판 · seed 42 | **같다** |
| 축 1 문턱 (`foothold-v1.json` 칸 값) | **같다** |
| 축 2 문턱 (원본 실측) | **같다** |
| 판정법 (Wilson) | **같다** |
| 평가 지형 정의 | **같다** (F 는 학습 지형만 바꾼다) |
| 매니페스트 · `compare_key` | **같다** · 정책 여섯이 한 표에 |

**갤러리 `models` 가 딕셔너리라 zero · v1 · D · E · F · G 여섯을 그대로 담는다** (site 규격 확인됨).

**지켜야 할 조건 둘.**

1. **F 의 gap 성적에는 주석이 필요하다.** 학습 때 본 gap 과 평가에서 보는 gap 이 다르다(방향). 「미경험 지형 성적」이라는 뜻은 v1 · D · E 와 같지만 **학습 노출의 성격이 다르다**는 것을 적는다
2. **학습 시드가 여전히 하나(42)다.** Wilson 100 판은 **평가 분산**만 본다. F · G 가 D · E 와 비슷하게 나오면 **노이즈와 못 가른다.** 판정문에 적는다

## 6. 실행

```
GPU 0    F 학습 97분 → G 학습 97분
평가     각 판마다 축 1(6) → 축 2 → 저속 고정 → Wilson 판정
진단     두께 고정 rails 스윕 · 정책 다섯
산출     영상은 «판정 뒤» 선정 · 갤러리 규격 · 종합 보고서 아티팩트
```

**장시간 프로세스는 rl 이 직접 건다.** `codex exec` 안에 두면 세션이 끝날 때 딸려 죽는다(E 에서 채택된 규칙).

| 작업 | 모델 |
|---|---|
| 지형 코드 (`OmniGapTerrainCfg`) · 설정 파일 | **`gpt-6-astra`** · 새 코드라 검증이 걸린다 |
| 학습 실행 · 관문 | **rl 직접** |
| 평가 · Wilson 판정 · 매니페스트 | **`gpt-6-astra`** |
| 영상 · 갤러리 산출물 | **`gpt-5.6-terra`** |

**모델 접두에 주의한다.** `sol` · `terra` · `luna` 는 **`gpt-5.6-`**, `astra` 만 **`gpt-6-`** 다. `gpt-6-sol` 은 「계정 미지원」 오류가 나는데 **계정 문제가 아니라 이름이 틀린 것**이다.

### 6-1. 관문 · 걸기 전에 선언하고 건 뒤 되읽는다

| 언제 | 무엇 |
|---|---|
| 지시 직후 | codex 가 실제로 명령을 받았는가 |
| 학습 16 초 | `params/agent.yaml` 의 `resume` · `load_checkpoint` |
| 학습 16 초 | `params/env.yaml` · **F 는 지형 방향 무작위 여부까지**, G 는 `heading_command: False` |
| 학습 1 분 | **GPU 에 메모리가 잡혔는가** |
| 평가 1 분 | 잡힌 지형 목록 · 목표 판 수 (`--terrains all`) |

**F 는 한 가지를 더 본다. 지형이 실제로 사방으로 났는가.** 설정만 보고 넘어가지 말고 **생성된 타일에서 틈 방향 분포를 세어** 로그로 남긴다. 「바꿨다고 했는데 안 바뀐」 것이 오늘 이미 여섯 번 있었다.
