# #546 작업 단위와 M1 · M3 2차 검증

**종합 판정: 고친 뒤 진행.** 빌드의 배포본을 faststart로 재포장하는 위치와 배포 뒤 실제 버튼으로 재생을 재는 방향은 타당하다. M2 결정을 기다리지 않고 구현을 준비할 수 있다. 그러나 현재 계획 그대로를 완료 기준으로 삼으면 **데이터가 달라진 영상이 동일성 검사를 통과하고, 검사 대상 버튼을 못 찾거나 다른 배포를 재도 결과가 남는** 문제가 있다.

아래의 진행 가능은 문서화·설계 논의를 해당 선행조건 아래 진행할 수 있다는 뜻이다. 아직 내려지지 않은 팀장 결정을 대신하거나 NAS 쓰기·배포·외부 발송을 승인하는 판정이 아니다. 이번 검증은 새 결과 파일 하나만 썼다.

## 3. M1 검증

### 3.1 위치 선택과 대상 수

**판정 · 추정:** 원본을 일괄 덮어쓰는 것보다 **배포용 복사본을 변환**하는 편이 이 저장소에 맞다. 원본 보존과 새 렌더의 자동 처리가 가능하다. Build:780 복사 뒤, 785~789 offload 앞이라는 위치도 맞다. 다만 그 복사 대상은 현재 운영 사이트 worktree다. 격리된 검증 없이 운영 빌드를 첫 시험으로 삼아서는 안 된다.

**확인됨 · 이번 로컬 전수 검사:**

| 로컬 `web/` MP4 | 수 |
|---|---:|
| 전체 | 153 |
| moov가 mdat 앞 | 55 |
| moov가 mdat 뒤 | 98 |
| 그 98개 중 git 추적 / 추적 밖 | 50 / 48 |
| 그 98개의 합 | 110,091,809 bytes |

P:14의 로컬 98개·50/48·약 110.1 MB는 재확인됐다. **NAS 345개 전체, NAS/foothold-site에만 있는 파일이 0개라는 전수 대조는 이번에 재실행하지 않았다.** Offload:35~42는 배포본에 없는 NAS 영상과 공개 응답을 이 관문이 못 본다고 명시한다. Build:177~184는 갤러리 뷰어만 복사한다.

따라서 **배포본에 tail-moov 0개라는 검사만으로 H:98의 “NAS 345개 모두 faststart”를 판정할 수 없다.** 처음 이행할 때 NAS 현행 목록과 경로별 배포본 해시·원자 구조를 대조하는 인수 단계가 필요하다. 이후에는 고정 숫자 345가 아니라 해당 배포의 명세를 기준으로 확인해야 한다. 추적 밖 원본 48개도 위치·해시가 있어야 다른 체크아웃의 재현 범위를 알 수 있다.

### 3.2 현재 패킷 검사는 화질 보존 증거가 아니다

**확인됨 · 메모리 반례:** 실제 `web/assets/video/v2/train-gap-omni.mp4`를 읽고 원본을 두 번 ffprobe해 결과가 같은지 먼저 확인했다. 이어 마지막 패킷 안 1바이트만 메모리에서 바꾸고 다시 검사했다. 디스크 원본은 수정하지 않았다.

| 비교 항목 | 원본 / 변형본 |
|---|---|
| 파일 크기 | 128,793 / 128,793 bytes |
| 스트림 / 패킷 수 | 각각 1 / 150으로 같음 |
| 스트림별 크기·PTS 목록 | 같음 |
| 위 목록의 MD5 | 둘 다 `0c774e8a1f8393fe86b42e61fc4a2bab` |
| 읽은 스트림 metadata | 같음 |
| 실제 패킷 payload SHA-256 | **1개 다름** |

따라서 P:30·42의 검사는 “같은 크기·시간을 가진 다른 payload”를 놓친다. MD5를 SHA-256으로 바꾸는 것만으로 해결되지 않는다. **해시의 입력을 실제 payload로 바꿔야 한다.**

**보완안 · 추정:** 스트림 대응을 먼저 확인한 뒤 모든 영상·음성·기타 유지 대상의 패킷 payload SHA-256, 패킷 수·순서, PTS/DTS/duration을 time_base에 따라 비교한다. codec extradata와 해상도·회전·화면 비율·색 정보·음성 채널·start time 등 재생에 영향을 주는 값도 비교한다. 파일 위치(pos)나 mux 전체 파일 해시는 재포장으로 바뀌므로 동일성 기준으로 쓰지 않는다. ffprobe의 `-show_data_hash sha256`은 `-show_packets`와 함께 payload, `-show_streams`와 함께 extradata를 검사할 수 있다. [FFprobe 공식 문서](https://ffmpeg.org/ffprobe.html#Main-options)

이렇게 확인한 **압축 데이터와 재생 조건의 보존**을 근거로 재인코딩 없는 변환이라고 말할 수 있다. 대표 영상의 디코딩 프레임·음성 및 브라우저 재생도 비교하면 표시 차이를 확인할 수 있다. 이번 반례는 검사 누락의 증명이며, 실제 변환 출력의 화질 저하를 발견했다는 뜻은 아니다.

### 3.3 MP4 판별기를 관문으로 쓰기 전 수정할 점

**확인됨:** Probe:2~14의 실제 함수를 메모리 입력으로 실행했다. 정상적인 앞/뒤 순서 표본 두 개를 먼저 맞춘 뒤 다음을 넣었다.

- 실제 24 bytes인데 mdat 크기를 10,000 bytes라고 쓴 잘린 구조: **faststart**.
- `ftyp → moov → moof → mdat` 표본: **faststart**.
- moov가 없는 구조: **MOOV-AT-END**.

이 도구는 탐색용 두 갈래 분류기다. 유효한 영상 확인기나 fragmented MP4 판별기가 아니다. P:36에 “못 잡는다”고 적는 것은 맞지만, 그 파일까지 **통과 수**에 넣으면 P:34와 H:98의 보증이 깨진다.

관문은 최소한 `정상 front / 정상 tail / fragmented / invalid·unknown`을 나눠야 한다. 상자 크기·헤더·파일 끝 범위와 필수 atom, 유효 스트림을 확인하고 invalid·unknown은 성공으로 세지 않는다. fragmented는 별도 검증 경로 또는 명시적 제외 목록과 수를 둔다. 이미 front인 파일도 구조·기본 재생 검사를 건너뛰지 않는다. FFmpeg의 faststart는 인덱스를 앞에 옮기는 두 번째 작업이며 fragmented 출력에는 그대로 적용되지 않는다. [FFmpeg 공식 문서](https://ffmpeg.org/ffmpeg-formats.html#mov_002c-mp4_002c-ismv)

**확인됨 · 재현 분기 시험:** Offload의 실제 `offload()`에 쓰기 기능이 없는 메모리 파일시스템을 주었다. 같은 해시 표본은 `already=1, removed=0`으로 맞았다. 배포본만 faststart 해시로 바꾸자 `missing=['clip.mp4'], copied=0, removed=0`이었다. 실제 NAS에서 변환·업로드를 실행한 시험은 아니다.

### 3.5 자기시험의 수정 범위

P:39~42의 정상 변환·이미 front 유지·단계 생략·변형 출력이라는 네 갈래는 적절하다. 다음을 포함해야 실수로 통과하는 길을 막는다.

- payload **크기는 유지한 채 내용만 바꾸는** 반례와 음성 누락·시간/재생 metadata 변경.
- 앞의 잘린 atom·moov 없음·fragmented·빈 대상 경로. 영상 0개가 정상인 배포와 잘못된 경로를 명세로 구분.
- 손상 cache hit, 변환 도중 실패·timeout, 같은 key 동시 실행의 불완전 출력.
- `write=False`에서 NAS 쓰기·공유 원본 쓰기가 발생하면 실패하는 시험. NAS에 원본만 있음/변환본 있음 두 경우.
- 신규 변환 관문 실패가 `main()`과 빌드의 실패 코드까지 전달되는 시험.

이것은 구현 시 필요한 시험 목록이다. 아직 없는 M1 관문이 이 시험들을 통과했다고 판정하지 않았다.

[WICG API 설명](https://wicg.github.io/video-rvfc/)

P:53의 값은 정확히는 **“클릭 후 0.3초 재생이 진행되기까지”**다. 이를 첫 프레임 시간과 섞지 않는다. 초기 진행만 검사한다면 이후 멈춤·중간 seek·오디오·끝까지 재생은 못 잡는 항목에 추가한다. 사용자 사례에 일부 멈춤이 있으므로 짧은 후속 관찰에서 칸별 stall·진행·오류도 함께 남기는 편이 낫다.

### 4.4 공개 DNS 고정의 의미와 한계

**판정 · 추정:** DoH로 공개 주소를 얻어 tailnet 내부 경로를 피하는 것은 **공개 Funnel 경로 진단**에 적절하다. 그러나 출발 PC·통신망·브라우저는 그대로이므로 “휴대폰과 같은 길”이나 LTE 성능 인증이라고 부르면 안 된다. P:68의 휴대폰·Safari 한계 표시는 유지한다.

실제 도착 호스트·remote IP·redirect chain·cache hit·protocol을 기록해 의도한 경로를 확인한다. A/AAAA·CNAME 처리, DNS 실패, 프록시 사용 때문에 고정이 적용되지 않은 경우도 성공으로 세지 않는다. 화면과 미디어 호스트의 관계가 달라지는 M2 뒤에는 일반 DNS 경로도 측정한다. IP를 고정한 시험 하나로 CDN의 실제 DNS·지역 라우팅까지 검증할 수 없다.

새 프로필과 cache 정책, 클릭까지의 준비/대기 시간을 고정한다. 보고서는 metadata preload이고 axis2는 none이므로 페이지 진입부터 preload한 양이 다르다. 실제 제품 동작은 유지하되, 페이지 준비 시간과 클릭 후 지연을 함께 기록해야 비교를 해석할 수 있다. LNA 검사를 끄는 시험은 진단용으로만 남기고 사용자 경로의 합격으로 쓰지 않는다. Chrome은 공개 페이지의 로컬 네트워크 요청에 별도 권한을 적용한다. [Chrome 공식 설명](https://developer.chrome.com/blog/local-network-access)

### 4.5 기록 모드·3초 기준·자기시험

**판정 · 추정:** 기록 모드부터 도입하는 것 자체는 관문 원칙에 어긋나지 않는다. Policy:562~598은 기존 위반과 고칠 수 없는 범위를 알림으로 다루도록 한다. 다만 P:59의 “M2 전에는 실패를 막지 않음”과 H:100의 “기준 넘으면 실패”를 같은 완료 상태로 두면 안 된다.

- **측정 성공/실패**와 **성능 통과/초과**를 별도 결과로 둔다. 브라우저 실패·버튼 없음·영상 없음·timeout·재생 오류를 정상 측정 성공으로 취급하지 않는다.
- 기록 모드의 느림은 배포를 막지 않아도 `성능 초과`로 남긴다. 기존 알려진 지연·대상·기준 판을 기록하고 새 재생 불능/미디어 누락을 별도로 알린다. M2 전이라고 오류 0 검사를 꺼서는 안 된다.
- 배포 뒤 관문은 이미 공개된 배포를 미리 막을 수 없다. 실패 시 완료 표시를 금지할지, 인수 보류·담당 알림으로 처리할지 정한다. 자동 rollback을 새로 허가받은 것으로 해석하지 않는다.
- M2 완료만으로 강제 관문을 켜기보다 동일 조건 실측·목표 합의·담당·전환 조건을 정한다. H의 M3는 “기록기 완료”와 “성능 관문 활성화”를 나눠 표시한다.

**확인됨:** P:59는 3초를 제안으로 적었고, H:99 M2 완료 조건은 3칸 **2초**다. 같은 지표라면 2.5초 결과가 M3에서는 통과하고 M2에서는 실패한다. 제품 목표와 경보선으로 구분할지 하나로 맞출지 결정해야 한다. 현재 3초를 사용자 체감의 정답이나 이미 승인된 기준이라고 할 근거는 없다. 표본 횟수·cold/warm·최대값/중앙값·timeout·오류 기준도 함께 정해야 한다.

P:62의 tailnet 실서버 시간은 네트워크 상태에 따라 변하므로 **답이 고정된 자기시험이 아니라 통합 대조군**이다. P:64의 0.01초 시험은 임계값 실패 경로만 확인한다. 정상 고정 fixture/주입 시계로 0.5초 통과·3.2초 초과·경계 3초를 확인하고, 누락 버튼·0영상·오류·정지된 영상·잘못된 배포 SHA·DNS 실패도 실패하도록 시험해야 계측 자체를 확인할 수 있다. 없는 영상 주소 시험(P:63)은 유지한다.

## 5. M2와의 연결 및 권고

**확인됨:** Offload:25~26의 “MEDIA_BASE와 vercel.json만 바꾸면 된다”는 설명은 **쓰기 저장소까지 NAS에서 R2로 옮기는 경우에는 충분하지 않다.** 실제 업로드·해시 대조는 Offload:61·100~149의 NAS 파일시스템에 고정돼 있다. 새 CDN 앞에 같은 NAS를 origin으로 둘 경우와 객체 저장소로 복사할 경우를 구분해야 한다.

**권고 · 추정:**

1. **M1은 변환기, 저장은 offload로 분리한다.** 원본 SHA → 변환 규칙/도구 판 → 배포 SHA/경로라는 명세를 만든다. M2로 옮길 때도 같은 faststart 결과를 사용하고 새 저장소의 실제 bytes·Range 응답·콘텐츠 형식·캐시/경로/query 정책을 인수한다.
2. **M1의 완료를 두 층으로 적는다.** 로컬 변환·동일성·관문 자기시험 완료와 NAS 현행 명세의 적재·공개 재생 확인 완료를 구분한다. 기존 공개 파일 교체와 manifest 갱신은 별도 게시 단계다.
3. **M3의 측정 계약을 먼저 고친다.** 올바른 세 화면·대상 칸, 배포 SHA, 공개 경로, 정확한 시간·상태·오류 형식, 호출 주체를 확정한 뒤 구현한다.
4. **3초는 임시 기록선으로 시작할 수 있다.** 2초 목표와의 관계를 적고 합의 전에는 최종 합격 기준이라고 표시하지 않는다. M2 전에도 실제 재생 오류와 측정 불능을 숨기지 않는다.
5. **M2 인수에 정상 DNS·실제 휴대폰 검사를 남긴다.** 새 호스트로 동적 redirect 대상이 달라졌는지 확인하고 기존 고정 NAS IP 시험을 재사용하지 않는다. 대표 3화면 시험은 #511에서 남긴 휴대폰·다수 동시 접근 검증을 대신하지 않는다.

Funnel에 변경할 수 없는 대역 제한이 있다는 것은 공식 문서와 맞다. 그러나 P:19의 “남는 대부분이 Funnel”이나 faststart가 일반적으로 1.3~4.5초를 절감한다는 인과·범위는 이번에 측정하지 않았다. 해당 3회 결과의 해석으로 제한해야 한다. [Tailscale 공식 문서](https://tailscale.com/docs/features/tailscale-funnel)
