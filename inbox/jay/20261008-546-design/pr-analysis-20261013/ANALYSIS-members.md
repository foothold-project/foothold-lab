## 1. 이민우 · Isaac Sim ㄱ자 코스에서 foothold-v2 + SLAM + Nav2 (PR #542)

### 1-1. 무엇을

`foothold-v2` 정책을 Isaac Sim 의 ㄱ자 코스에 올리고, SLAM(`slam_toolbox`) + Nav2 로 코스 `(0, 0)` 에서 `(5.0, 6.0)` 까지 스스로 가게 한다. 사람이 넣는 것은 목표 좌표와 시작 명령 둘뿐이다 〔민우 15~17〕 `확인됨`.

그래서: 「정책이 걷는다」 가 아니라 「지도를 만들며 스스로 길을 찾아 간다」 를 시뮬에서 처음부터 끝까지 이어 본 작업이다 (이번에 연 자료 중에서는 유일).

### 1-4. 잘된 점

- **「Nav2 성공」 과 「실제 도착」 을 갈랐다.** `SUCCEEDED` 를 성공으로 쓰지 않고 참값 0.367 m 를 따로 적었다 〔민우 95〕. 같은 결론이 현민 앱에서도 따로 나왔다 (Nav2 성공인데 0.53 m 오차 → 실패 처리, 〔현민 89 · 146〕). 팀 공통 교훈으로 쓸 만하다.
- **한 런에 하나만 바꾸기.** 의도한 변경과 의도 안 한 변경을 표로 갈랐다 〔민우 125~152〕. 「단일 변수 비교가 아니다」 라고 스스로 적었다.
- **측정 도구를 의심했다.** Jazzy 의 `Costmap.metadata.update_time` 이 0 (59/59) 이라 시각 대응이 안 되는 것, `slam_check` 가 `/clock` 전에 마감을 계산하는 결함을 찾아 고치고, 앞서 낸 서술 넷을 철회했다 〔민우 99~102〕.

- **좌표 변환을 상수로 박지 않았다.** 매 런 재고, 관문을 못 넘으면 목표를 안 보낸다 〔민우 50〕.

### 1-5. 위험

1. **저속 명령 구간.** Nav2 `cmd_vx` 중앙이 상한의 33.6 % → 약 0.168 m/s `계산`, p90 0.488 · 최대 0.500 〔민우 242〕. foothold-v2 는 학습 때 `lin_vel_x` 0.4~1.5 를 뽑았다 〔LD 95〕. 같은 방향의 기록이 둘 더 있다.
   - 현민 위키 9/28~29 「NVIDIA baseline vs foothold-v1 (Nav2)」: baseline 은 0.1~0.2 m/s 명령에서 거의 제자리, foothold-v1 은 회전 명령에서 거의 안 돎 〔위키 exp-baseline-vs-v1〕 `확인됨`.
   - lead E1 평가: 평지 0.1 m/s 에 실제로 움직인 비율 38 % (model_20000) (#546 댓글 6105758209) `확인됨`.
   - 그래서 「속도형 정책 + Nav2」 조합의 공통 약점이 저속 명령일 수 있다. 이것이 민우 주춤거림의 원인인지는 아무도 재지 않았다 `미확인`.
2. **위치 추정 2.2배 악화 · 라이다 4.4 Hz.** 원인 미확정 〔민우 120 · 186~188〕.
3. **각 1회 런.** 반복 안정성 없음 〔민우 9~11〕. 반복은 RunPod (유료) 에서 돈다. 유료 원격은 팀장 승인 대상이다 (#546 댓글 6059477202).

## 2. 맹라현 · ACC 3DGS 디지털 트윈 (PR #543)

### 2-1. 무엇을

국립아시아문화전당(ACC) 을 기존 촬영 자료로 복원한 공간을 더 실제처럼 보이게 다듬는다. 다루는 문제는 하늘 번짐 · 보는 방향에 따른 색 (SH) · 벽 · 바닥 사진 질감이 앞 구조물을 덮는 것 〔라현 11 · 15~19〕 `확인됨`.

풀이:
- **3DGS (3D Gaussian Splatting)**: 장면을 작은 반투명 타원 (가우시안) 수십만~수백만 개로 표현하는 방법. 사진처럼 보이지만 단단한 표면은 아니다.
- **SH (spherical harmonics)**: 보는 방향마다 색이 조금씩 달라지게 하는 숫자 묶음.
- **충돌 메시**: 로봇 발이 실제로 밟는 단단한 바닥 · 벽 모형. 3DGS 와 따로 만든다.

### 3-6. 위험

1. **일이 너무 많다** `추정`. 앱 (두 갈래: control-app · foothold-app) + 목표형 RL + exp33 + 교재 · 위키 + ROLES 상 `A/평가` · `B/인지` 주담당. 10/12 팀장 결정으로 11/7 SIM 관문에 dashboard · app 이 걸렸다.
2. **RL 분담 미합의가 계속된다.** 10/8 「합의 기록 없음」 〔현민 11 · 135 · 144〕 이후, 10/12 goal1e 에서 「공동 검토」 라고 적었지만 상대가 누구인지 위키에 없다 `미확인`.
3. **앱 두 갈래의 정본이 불분명하다.** PR #544 의 `control-app` (인증 · 임무 · 지도 · Nav2 · TB3) 과 `foothold-app` (시안 19화면 · v2 Gazebo · Nav2 미연결) 이 다르다. 저장소 README 는 「운영 서버는 이전 판(`83b25ca`)을 그대로 서빙」 이라 적는다 〔app README.md 15행〕.
4. **STOP 뒤에도 움직인다.** 시뮬에서 STOP 뒤 약 3.6 s 동안 0.32 m 더 움직였고 원인 미확인 〔app README.md 93행〕. exp33 에서 「별도 전진 기록에서는 적용 명령 0이 유지되어도 다시 움직였습니다」 〔위키 exp33〕. 실기는 순정 보행이라 이 수치가 그대로 옮겨가지는 않는다. 하지만 실기 정지거리는 아무도 안 쟀다.
5. **실기 다리가 mock 뿐이다.** `go2_adapter.py` 는 가짜 SportClient 로 `Move` · `StopMove` 만 시험했다. 「SDK import·실기 연결·실제 몸 정지는 미검증」 〔현민 113〕. 팀장 10/12 계획 (실기를 받으면 SDK 로 앱을 Go2 에 연결) 의 주 경로다.
6. **목표형 RL 이 지금 이음매와 안 붙는다.** 앱 · Nav2 · 트윈 시험은 모두 속도형 foothold-v2 를 쓰고, 현민 RL 은 목표형이다. 현민 위키 순서에서 「상위 목표 항법」 은 맨 끝이고 미측정이다.
7. **학습 시드 하나.** 모든 RL 결과가 학습 시드 1개 〔현민 150〕.

### 3-7. 팀장이 현민에게 물을 질문

1. 임석헌과 RL 을 어떻게 나눌지 이야기해 봤나. goal1e 의 「공동 검토」 는 누구와 한 것인가.
2. `control-app` (로컬) 과 `foothold-app` (공개 저장소) 중 11/7 dashboard · app 의 정본은 어느 쪽인가. `control-app` 의 gateway · 임무 · 지도 · `go2_adapter` 를 저장소에 올릴 계획이 있나.
3. foothold-app 을 Nav2 에 붙이는 일 (목표 보내기 · 지도) 은 민우 Nav2 스택과 맞출 생각인가. 앱이 보내는 목표 좌표의 기준 (map · 코스 · ACC) 은 무엇으로 할까.
4. 실기를 받으면 앱을 Go2 SDK 에 잇는 일 (팀장 10/12 계획) 의 안전 계약 (로봇 측 끊김 감시 · 조종권 · 리모컨 우선 · 정지거리 측정) 을 누가 정하고 누가 시험하나.
5. exp33 의 HOLD 낙상 · STOP 뒤 이동은 시뮬 체험용 문제인가, 실기에도 남는 문제인가. 실기는 순정 보행이라는 10/12 결정과 어떻게 맞출까.
6. 교재 (Go2 SLAM·Nav2·PPO 실습) 를 민우가 쓰고 있나. 교재 Ch10 어댑터 계약 (`/cmd_vel` · stale 0.5 s · clip) 을 팀 표준으로 삼아도 되나.
7. 실제 iPhone 조종 · STOP 확인은 했나 〔현민 157〕.
8. 11/7 까지 앱 · RL · 교재 중 우선순위는 무엇인가. RL 을 줄인다면 무엇을 남길까.
9. RL 원자료 · checkpoint (로컬 · Pod) 를 NAS 로 옮길 수 있나.
