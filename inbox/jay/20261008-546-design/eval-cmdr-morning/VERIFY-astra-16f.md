**판정: 고칠 것.** 기존 16d 2.1~2.5의 수정은 인정한다. 하지만 의뢰서의 “USD 임시 폴더 충돌도 고쳤다”는 결론은 강하다. 현재 구현은 시작 시점을 벌리고 일부 실패를 재시도하는 완화책이다. **같은 경로에 동시에 쓸 수 있다는 원인은 그대로다.** 11:55 시작 시험 통과는 확인했으나 충돌 예방이나 로봇 자산 무결성을 입증하는 시험은 아니다.

## 3. 남은 수정 사항

### 3.1 P1 · 30초 간격은 USD 이름 충돌의 해결이 아니다

근거는 `wait_start_slot()` 474~500과 로컬 Isaac Lab `asset_converter_base.py` 65~108이다. 변환기는 날짜·시각을 초 단위로 넣고 전역 `random.randrange(10000)`을 붙인다. `exist_ok=True`로 폴더를 만들며, `.asset_hash`를 쓴 다음 실제 변환을 한다. **경로를 독점하는 잠금도, 변환 완료 후 원자적으로 공개하는 장치도 없다.** `urdf_converter.py` 102~109도 바로 같은 `dest_path`로 가져온다.

11:38 두 로그에 `usd_20261013_113828_7028`이 실제로 나온다. GPU 0 로그에는 Robot 루트의 unresolved reference와 `No contact sensors added`가 함께 있고, GPU 1에는 해당 루트 오류가 없다. 공통 경로 경쟁이라는 진단은 소스와 기록으로 강하게 뒷받침된다. 다만 두 프로세스의 파일 쓰기 순서를 추적한 것은 아니다.

시작 간격과 변환 간격은 다르다. 시작 시각을 S, 변환까지 걸린 시간을 D라 하면 같은 이름이 생기는 시각은 `floor(S+D)`다. **S의 차이를 30초로 만들어도 D의 차이가 제한되지 않으면 같은 초가 될 수 있다.** 예를 들어 A가 t=0에 시작해 45초 후 변환하고 B가 t=30에 시작해 15초 후 변환하면 여전히 충돌한다. 이는 가능한 스케줄의 반례이며, 이 45초 지연을 실기에서 관측했다는 주장은 아니다.

현재 시작 시험의 첫 USD 경로 참조는 Kit 로그상 약 10.389~11.946초다. 이는 작은 표본의 첫 참조 시점이며 OS 프로세스 생성부터 변환 완료까지의 분포가 아니다. 변환 지연의 최대값·꼬리 분포·30초 상한의 근거는 **미확인**이다. 같은 seed 1000의 확인 표본에서는 접미사 7028이 반복되지만, 모든 seed에서 항상 7028이라고 일반화할 근거는 없다.

별도로 두 구멍이 있다.

- 14:00 전 v3.2는 잠금을 모르므로 GPU 0의 확인 직후 얼마든지 시작할 수 있다. 의뢰서도 인정한다. “GPU 0이 피하므로 예방됨”이라고 쓰면 틀리다.
- 14:00 후 양쪽이 v3.6이어도 잠금 안에서 **예약 시각을 기록한 뒤 잠금을 풀고** 534줄에서 실제 프로세스를 띄운다. 먼저 예약한 쪽이 스케줄링 등으로 지연되면 예약 간격과 실제 생성 간격도 달라진다. 게다가 변환 시점 문제는 그대로다.

**필요한 수정:** 실행 attempt마다 충돌할 수 없는 USD 디렉터리를 사용하도록 변환 입력에서 격리하는 것이 직접적인 해결이다. 고정 seed의 난수를 디렉터리 유일성에 쓰지 말고, 원자적 디렉터리 생성이나 검증된 실행별 식별자를 사용한다. 대안은 모든 참여자가 실제 변환 구간을 직렬화하고 완성된 자산만 읽게 하는 것이다. 시작 시각 기록만 공유하는 것과 다르다.

경로 격리를 넣을 때도 주의가 필요하다. `usd_dir`를 직접 지정하면 기존 `random.randrange()` 호출을 건너뛴다. 이 변경이 후속 Python RNG 소비나 비교 지문에 영향을 주지 않는지 확인해야 한다. 기존 evaluator는 뒤에서 seed를 다시 설정하지만, 그 이전의 변환·환경 생성 영향을 무조건 없다고 단정할 수 없다. 소스 pins·입력 버전·알려진 답 비교를 갱신해야 하며, ASTRA가 운영 소스를 직접 바꾸지는 않았다.

### 3.2 P1 · 시작 대기 중 마감·멈춤·입력 변경을 지나쳐 실행한다

`guarded()` 514~523에서 마감·pins를 한 번 검사한 다음 `wait_start_slot()`에 들어간다. 그 함수의 `while True`에는 마감·stop 검사도 대기 상한도 없다. 반환 직후에도 재검사 없이 subprocess를 띄운다. `.stop`은 main 루프 경계에만 있고 시작 시험·guard 재시도·간격 대기에서는 읽지 않는다.

실제 두 함수에 가상 시계와 메모리 잠금 파일을 넣고, subprocess만 실행 시각을 기록하도록 바꿨다. 답을 아는 입력에서 다음이 재현됐다.

| 입력 | 기대 | 실제 결과 |
|---|---|---|
| 현재 1000초, 다른 시작 990초, 마감 1010초 | 대기 중 마감이면 새 자식 없음 | **1020초에 실행**, `(0, 1)` 반환 |
| 같은 대기, 1002초부터 stop=True | 실행 전 대기에서 종료하고 남은 작업 기록 | **1020초에 실행**, stop=True인데 `(0, 1)` |
| 같은 대기, 1002초부터 pins 변경 | 바뀐 입력으로 새 평가를 시작하지 않음 | **변경 후 1020초에 실행** |

이는 “실행 중 평가를 중간에 죽여라”는 요구가 아니다. **아직 평가 자식이 시작하지 않은 대기와 다음 재시도 경계에서 새 시작을 막으라**는 것이다. pins 변경은 일반 process 경로의 사후 검사에서 무효가 될 수 있지만, 불필요한 실행 자체는 이미 발생한다. 시작 간격이 계속 확보되지 않거나 잠금이 계속 실패하면 마감 뒤에도 대기가 이어질 수 있다.

대기 루프와 실제 launch 직전, 시작 시험 각각과 재시도 경계에서 stop·마감·고정 입력을 확인하고, 중단 시 active/pending을 남기도록 고친다. `.stop`을 11:43 기동의 안전장치로 제시했다면 이 범위를 운영 설명에도 포함해야 한다. 현재 루프에 들어간 후 유휴 감시 상태의 stop은 동작하지만, 전체 생명주기의 중단 보장은 아니다.

### 3.3 P2 · 루트 참조 오류가 예외 없이 끝나면 성공으로 받아들인다

`guarded()` 538~546은 Python Traceback을 오류로 바꾼 뒤 **rc==0이면 먼저 반환**한다. `collided()`는 그 뒤에만 실행된다. `validate()` 580~654도 Traceback과 완료 문구 등은 검사하지만 Robot 루트 참조 오류는 검사하지 않는다.

두 CPU 반례를 확인했다.

1. 로그에 정확한 `COLLISION` 문자열과 완료 문구를 넣되 Traceback 없이 rc=0을 반환시켰다. `guarded()`는 `(0, 1)`이고 `collided()`는 True였다. 재시도·무효 처리가 없었다.
2. 실제 `cq_on24000_flat_stand_on_s1000`의 원자료를 읽어 `validate()==''`인 정상 대조군을 확인했다. 로그만 메모리에서 복사해 같은 루트 오류 문구를 추가하니 **여전히 validate()==''**였다. 디스크 원자료는 바꾸지 않았다.

이는 **실제 GPU 1 로그에 그 오류가 있었다는 주장이 아니다.** 현재 그 로그의 루트 오류 수는 0이다. 반례는 “앞으로 그 오류가 생겨도 검사에 걸리는가”에 대한 것이다.

Robot 루트 참조 오류는 rc와 독립적으로 실행 유효성을 판단하는 쪽에서 다뤄야 한다. 모든 visual 경고를 일괄 실패로 바꾸라는 뜻은 아니다. transient 경고 뒤 복구를 허용하려면 최종 로봇 stage의 유효성 증거가 필요하다. 또 그 문구 하나만으로 원인을 반드시 디렉터리 충돌이라고 확정할 수는 없다. 잘못된 경로나 자산 손상도 가능한데 현재는 모두 `collision=True`로 표시한다. “루트 참조 실패·충돌 의심”과 입증된 충돌을 구별하는 편이 정직하다.

네 번 연속 Traceback+루트 오류를 넣으면 `(1, 4)`로 끝나며 이전 세 시도의 log·guard 여섯 파일이 보존되는 것은 확인했다. 따라서 “충돌은 평가 실패로 기록하지 않는다”도 무제한 보장이 아니다. 최종 소진은 현재 process에서 invalid가 되며, 정책의 보행 실패율에 섞지 말아야 하는 수집 인프라 실패다.

## 4. 조용한 손상과 현재 지문의 한계

**실제 다른 로봇으로 평가됐다는 증거는 없다.** 동일 URDF·설정을 두 프로세스가 함께 쓰는 경우, 전혀 다른 로봇으로 바뀌었다고 말할 근거도 약하다. 현실적인 우려는 작성 중인 USD·하위 layer를 읽어 일부 참조·물리 설정·형상을 불완전하게 얻는 경우다. 이 일이 예외 없이 발생한 비율이나 “대개 예외로 끝난다”는 빈도는 **미측정**이다.

현 지문은 의미 있다. `q_eval_cmdr.py` 415~454와 드라이버 662~671은 초기 root pose·관절 위치·질량·stiffness·COM·재질·구동기 gain·delay·zero offset, 배치, 지형 mesh, traj0 등을 비교한다. 앞서 확인한 flat/stand 다섯 실행의 지문 일치는 이 범위의 이상이 없다는 증거다.

하지만 다음은 증명하지 못한다.

- `terrain_mesh`는 `/World/ground`만 해시한다. 로봇 collision mesh의 꼭짓점·인덱스나 최종 합성된 USD 전체를 해시하는 것이 아니다.
- 로봇 링크·관절 이름과 topology, 관절축·제한, inertia tensor, collider 형상·개수, contact sensor 구성의 완전한 manifest가 없다.
- traj0는 초기 프레임이다. 같은 초기 자세와 질량을 가진 서로 다른 충돌 형상도 초기 지문은 같을 수 있다. 양쪽에 같은 오류가 생기면 짝끼리의 일치만으로도 탐지할 수 없다.

그러므로 **“지문 일치 → 자산 충돌 손상 없음”은 잘못된 추론**이다. 반대로 지금 자료를 전부 오염됐다고 폐기할 근거도 없다. 충돌과 연관된 tag·시도·USD 경로를 보존하고, 고유 경로로 재수집하거나 최종 로봇 물리 구조를 정상 자산과 비교한 뒤 판단해야 한다. 단순히 v3.6 validate를 다시 통과시키는 것만으로 해당 불확실성이 없어지지 않는다.

의뢰서의 “시각 참조 경고 544줄이 모든 실행에 있는 평소 경고”도 그대로 재현되지 않았다. 확인한 GPU 1 stand와 v3.6 ka_copy 로그에서 `Unresolved reference`를 포함한 줄은 각각 **248줄**, 전부 `/visuals` 관련이었다. 544의 집계 정의는 기록 없음. 같은 유형이 정상 대조 실행에도 있다는 것은 확인했지만, 그것이 렌더링 자산까지 정상이라는 뜻은 아니다. headless 평가에서 어떤 참조가 물리에 영향을 주는지를 따로 구별해야 한다.

## 5. 11:43 기동과 14:00 전환 판단

**11:43 기동은 “기존 기록 결함 수정 후, 새 시작 시험을 붙여 재개한 것”까지는 근거가 있다. “USD 충돌까지 해결한 상태로 병렬 무인 수집을 재개했다”는 판단은 인정할 수 없다.** 두 주장은 다르다. 시작 시험은 실제 통과했지만 한쪽만 시작 간격을 지키는 잔여 위험이 알려진 상태였고, stop도 위 3.2처럼 모든 실행 경계를 덮지 못한다.

현재 실행을 ASTRA가 종료하거나 stop 파일을 만들지는 않았다. 담당자가 다음 작업 경계의 대응을 결정해야 한다. 새 코드로 실행 파일만 덮어도 PID 85080에 올라간 코드가 바뀌지는 않는다. 이미 만들어진 원자료·시도 로그를 보존하고, 인프라 실패와 정책 결과를 구별해야 한다.

14:00 전환은 16d 6절을 그대로 충족해야 하며, 특히 다음이 남는다.

1. 14:00이라는 시각이 아니라 기존 base와 guard·q_eval 자식·작성자의 실제 종료를 확인한다. 현재 v3.2 PID 89700은 살아 있었다. 조회 불가를 종료로 간주하지 않는다.
2. 재사용할 원자료·meta·stamp·guard·로그, checkpoint와 수집 pins의 manifest/해시를 동결해 보존한다. 입력 묶음 사본이라는 설명만으로 실제 보존 완료를 대신하지 않는다.
3. 양쪽 수집 pins와 checkpoint를 전환 직전에 대조한다. 이번 관찰에서는 같았지만 집계 v7 수정이나 후속 USD 수정 뒤에도 같을지는 미확인이다. 바뀐다면 옛 g0와 새 base를 자동으로 같은 판으로 결합하지 않는다.
4. 새 base가 잠금을 얻고 새 attempt를 공개하며 실제 재검사하는지 확인한다. 이 경로의 기존 결함은 수정됐지만, 실제 인계 자체는 아직 미래다.
5. **양쪽 v3.6이면 충돌이 해결된다는 전제를 버린다.** 고유 USD 경로 또는 실제 변환 직렬화가 필요하다. 이미 알려진 충돌 실행은 일반 재사용 검사와 별도로 이력을 남긴다.
6. 마감·stop 시 active/pending/invalid·마지막 base 해시와 attempt를 보존한다. 실행 중인 자식을 강제 종료하라는 뜻이 아니며, 결과를 확인한 범위에서만 complete라고 쓴다.

따라서 14:00 계획은 방향은 맞지만, **현재 v3.6 그대로의 두 드라이버 전환을 충돌 해결 완료로 승인할 수는 없다.** 실제 전환과 재수집 결과는 미확인이다.

## 6. 제공 시험에 대한 평가와 최소 보완

`test_v36.out`에는 PASS 46개와 FAILS=[]·exit 0이 있다. 변이 기록은 일곱 개가 잡혔다고 적는다. 파일 생성·복사·삭제를 수행하는 제공 시험 전체는 이번 읽기 전용 범위에서 다시 실행하지 않았다. 대신 위 2절과 3절의 실제 함수 경로를 별도 메모리 시험으로 확인했다. **변이 시험 일곱 개를 독립 재실행했다는 뜻은 아니다.**

- 시험 12~16은 기존 결함을 직접 겨냥했고 유용하다. 단순히 조건식 이름만 확인한 시험은 아니다.
- 시험 17은 이미 stop=True인 remeasure 루프 입구만 검사한다. 시작 대기·시작 시험 사이·충돌 재시도 중 stop은 다루지 않는다.
- 시험 18은 “30초가 지났는가”라는 구현 규칙을 그대로 검사한다. 실제 검증할 성질인 **USD 출력 경로의 배타성**이나 실제 변환의 비중첩은 시험하지 않는다. R6 변이가 걸려도 충돌 예방이 증명되지 않는다.
- 시험 19는 정확히 탐지 가능한 문자열+Traceback 뒤 성공을 넣고 시작 간격 함수는 대체한다. rc=0·Traceback 없음, 변환 지연 편차, 상대 v3.2의 뒤늦은 시작, 모든 재시도 소진은 제공 시험 범위에 없다.

최소 보완은 세 묶음이다. **① 경로 격리의 유일성과 RNG·알려진 답 보존, ② 대기 중 stop·마감·pins 변경 후 새 launch가 0회인 시험, ③ 루트 참조 오류의 rc/Traceback 조합과 재시도 소진의 인프라 실패 기록.** 그 뒤 필요한 실제 동시 실행 확인은 권한 있는 담당자가 원자료를 보존한 상태에서 수행해야 한다. CPU 시험만으로 USD/PhysX 런타임 전체를 검증했다고 쓰지 않는다.
