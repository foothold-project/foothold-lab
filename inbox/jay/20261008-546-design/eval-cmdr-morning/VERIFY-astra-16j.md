## 5. stand의 실제 결과와 도구의 남은 결함

### 5.1 실제 새 stand는 별도로 확인했다

검증 중 운영 hold 파일에 14:17 해제 기록이 추가되어 있었다. 이 파일을 수정하지 않고 읽었다. 지정된 새 attempt는 `g1-162660-1013140618-j1`이다.

직접 확인한 내용:

- 새 base 기록은 valid=True, reused=False, pair_fail 없음, matrix=valid.
- 새 USD 폴더는 `20261013_141457_7028`, origin은 hashed-at-collection.
- 새 네 출력 파일을 직접 해시해 **실제 파일 = stamp = 소유 기록**이 모두 같다.
- 새 stamp의 pins는 base와 H에 같고 checkpoint도 H의 on24000과 같다.
- 옛 보존 폴더는 `attempts/cq_on24000_flat_stand_on_s1000.dir.1013113904.162660`. 파일명 시각을 근거로 고른 것이 아니라 held stamp 해시로 골랐다.
- 옛 meta·cells·episodes·traj·env_origins·stamp **6개**를 직접 해시해 H와 모두 같다.
- 실제 대조는 output_content_equal=True, inputs_equal=True, new_run_valid=True, comparison_ready=True.
- cells·traj·episodes는 바이트도 같고, traj 배열 10개는 dtype·shape·값 모두 같다. 입력 비교 11항목도 같다.
- 해제 기록의 new_attempt는 실제 새 stamp·기록의 attempt와 같다.

따라서 **이 특정 새 실행으로 대체한다는 14:17 판단에는 근거가 있다.** 옛 의심 실행 자체를 소급해서 완전히 정상 인증하거나, USD 충돌이 영향을 주지 않는다고 일반화할 근거는 아니다. 현재 v17의 14:05 고정 묶음은 여전히 옛 stand를 제외한 스냅숏이다. 이후 새 집계에서 대체하는 일과 섞지 말 것.

| 기록·stamp의 traj 해시를 둘 다 0 64개로 변경, 실제 traj는 그대로 | new_run_valid=True, ready=True, 종료 0 | 인증 불일치로 보류 |
| 기록·stamp에서 out_sha256 둘 다 삭제 | None==None으로 ready=True, 종료 0 | 해시 누락으로 보류 |
| rec.valid=True는 유지하되 pair_fail 추가, matrix=pair_fail | ready=True, 종료 0 | 짝 검증 실패로 보류 |

이는 실제 이번 stand가 틀렸다는 뜻은 아니다. 5.1에서 빠진 조건을 직접 보충 확인했다. 하지만 **앞으로 이 도구의 ready=True만으로 정상 새 수집을 인정해서는 안 된다.**

최소 수정은 읽은 출력 바이트의 네 해시·키 검증, 소유 matrix=valid와 pair_fail 없음, pins·checkpoint 연결이다. 가능하면 집계 인증과 같은 검사를 공통 함수로 사용하되, stand에는 “실제 새 측정이고 reused가 아님”을 추가한다. 옛 파일도 H의 네 출력 및 env_origins 해시와 묶어야 한다. stamp만 옛 것이고 내용이 바뀐 폴더를 원본으로 삼으면 안 된다.

또한 입력 준비가 덜 된 경우 지금은 새 traj만 확인한 다음 다른 파일을 바로 읽는다. “아직 수집 중”은 명시적 ready=False로 처리하고, 읽는 도중 교체 가능성은 스냅숏/재검사로 제한할 것.

### 5.3 해제 기록의 문구와 실제 새 attempt가 연결되지 않는다

근거: [cmdr_post_v8.py](code/cmdr_post_v8.py) 312~318줄, [L5c](code/test_post_v8.py)의 입력.

`released`가 truthy면 해제한다. 독립 재현에서 다음 두 입력이 모두 이전과 동일한 의심 실행을 다시 포함했다.

- `released: true`
- `released: {by: "lead", why: "새 측정 확인", new_attempt: "NOT-THE-ACTUAL-ATTEMPT"}`

L5c도 stamp와 소유 기록을 새 측정으로 바꾸지 않고 `new_attempt: "NEW-j9"`만 적은 뒤 통과를 기대한다. L5b의 자동 해제 결함은 고쳤지만, L5c는 다시 **주장의 존재를 사실 확인으로 삼는 시험**이다.

16i에서 말한 “명시적 수동 해제” 자체는 허용 가능한 최소 대응이다. 모든 인간 판단을 코드로 증명하라는 요구가 아니다. 다만 이번 방식은 해제의 근거를 **특정 새 측정 attempt**라고 명시했으므로, 그것이 실제 인증된 attempt와 같은지는 확인해야 한다.

최소 조건은 필수 기록(by·why·new_attempt), 실제 인증된 소유 기록·stamp의 attempt 일치, 정상 새 측정 증거, 해제 대상 stamp 또는 수집 identity 연결이다. 인증 성공 뒤에만 `hold_released`로 적을 것. 동일 attempt 재사용 뒤에도 해제를 유지하려면 그 수집의 정상 재측정 근거를 보존해 확인하면 된다. 현재 마지막 rec가 reused=True로 바뀌었다고 무조건 영구 보류할 필요는 없다.

현재 14:17 실제 기록은 위 identity가 맞는다. 그래서 이번 수동 대체를 잘못됐다고 판정하지는 않는다. **다음부터도 자동으로 맞을 것이라는 코드 보장은 미달**이다.

## 6. 고정 묶음 비교 도구의 통과 조건은 아직 약하다

근거: [compare_frozen.py](code/compare_frozen.py) 21~43줄.

두 문제가 있다.

1. held tag의 model을 버려 held_cells를 만든다. on stand 한 실행만 보류했는데 기본 계약 비교에서 off stand까지 제외한다.

실제 고정 JSON을 메모리로 복사해 다음 하나씩 바꾸고 **원본은 보존**했다.

허용 차이를 tag에서 model·family·cell·noise·seed까지 추적하고, 각 파생 경로의 허용 변경을 명시할 것. off의 같은 cell은 그대로 대조한다. 일반 cells·completion·coverage는 “차이 있음”이라는 이름만 보고 통과시키지 말고 실제로 held 입력 삭제에서 예상되는 변경인지 검증한다. 예기치 않은 경로·값 차이는 실패시켜야 한다.

## 7. 445개 stamp 재작성 뒤 첫 집계의 공개 조건

운영 base 로그의 재검사 기록은 14:09:30, reused=445였다. 이 445개의 소유 기록과 현재 stamp를 직접 읽어 H와 대조했다.

- 네 출력 해시 = H의 당시 출력 해시: 445개 모두 일치.
- prev_stamp_sha256 = H의 이전 stamp: 모두 일치.
- origin은 기록·stamp 모두 legacy-origin revalidated.
- revalidated_by는 현재 base attempt.
- 불일치 0.

따라서 **수집 당시 해시가 없던 445개가 이번 재검사 시점의 해시를 갖게 됐고, 이관 전 바이트 identity와도 연결된다.** 이것을 “처음 수집 때부터 해시로 보장된 445개”로 올려 말하면 안 된다. `legacy_stamps=0`이어도 legacy-origin 개수는 사라지지 않는다.

공개 뒤 첫 v8 집계가 보장하는 것은 다음이다.

- 그 소유 로그가 valid로 공개한 마지막 기록과 읽은 출력 해시·attempt 일치.
- sidecar가 처음 읽을 때 revalidating이 아니고, 집계 동안 읽은 sidecar·hold 바이트가 마지막에도 같음.
- 기록된 stat 변경과 로그 바이트 변경이 감지되면 결과를 쓰지 않음.
- manifest로 사용 파일·출처를 다시 추적할 수 있음.

보장하지 않는 것은 과거 구형 수집의 물리적 정상성 전체, 최초 수집 당시 해시 존재, 모든 숨은 USD 오류 부재, 마지막 검사 직후까지의 원자적 전역 스냅숏, 미완료 평가의 완료다. stamp 재작성 자체는 재측정이 아니다.

확인한 실행 로그상 base 시작 시험은 14:14:40, g0는 14:16:14에 통과 기록이 생겼다. wrong_yaml 시험의 Traceback은 의도한 거부 시험으로 기록돼 있다. 이것을 정상 평가의 예기치 않은 실패와 혼동하지 않는다. 이번에는 그 시작 시험의 모든 배열 원본을 다시 비교하지 않았으므로 “시험 로그의 통과 기록 확인”으로 한정한다.

새 집계 공개 때는 완성된 출력 파일을 별도 판으로 보존하고, 코드 해시·두 로그 해시·sidecar·hold 해시·사용 manifest·페이지 입력 해시를 함께 남길 것. 종료 3/5인 실행에서 예전 cmdr_post.json을 방금 만든 새 결과처럼 게시하면 안 된다. 5절의 해제 연결을 고치거나, 이번처럼 해당 새 실행을 직접 확인한 근거를 명확히 유지해야 한다.
