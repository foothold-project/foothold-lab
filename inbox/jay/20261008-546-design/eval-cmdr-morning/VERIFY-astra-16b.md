## 2. 기동 전에 고칠 것

### 2.1 base를 못 읽으면 마감이 작동하지 않는다

**확인됨 · 재현:** `main_remeasure(:790~794)`는 `read_base() is None`이면30초 대기 후 바로 continue한다. deadline 검사는 `:810`에 있어 실행되지 않는다. 현재 시각100, deadline1, read_base는 계속None인 CPU 입력에서 **마감 뒤에도30초 대기를 세 번 반복**했다. 시험용 중단 장치로 끊었을 때 `stopped`, `ended`, `complete`가 모두 없었다. 세 번에서 저절로 끝난 것이 아니다.

v3.2는 `Q/cmdr_eval_driver.py:83~84`에서 JSON을 직접 덮어쓴다. 쓰는 중 잘린 JSON을 만나는 것은 예상 가능한 상황이다. 일시적인 실패는 재시도로 풀리지만, 작성 도중 v3.2가 죽어 깨진 파일만 남거나 파일이 없어지면 v3.4는20:00 뒤에도 무기한 기다린다. 「v3.2가14:00 이전 다른 이유로 멈출 때」라는 의뢰의 실제 대상 경로다.

**필수 수정:** 모든 반복의 입구에서 deadline을 검사하고, 읽기 실패에서도 마지막 정상 스냅숏·마지막 읽기 성공 시각·실패 원인·완료 아님을 기록하고 종료한다. 성공적으로 읽어야만 종료할 수 있게 만들지 말 것. 이후 누락 목록도 마지막 정상 스냅숏과 예상96칸을 기준으로 계산한다. CPU 관문은 「영구None + deadline 경과」와 「일시None → 정상 최종 스냅숏」 둘 다 필요하다.

### 2.2 같은 로그 작성자 검사가 허용된 CLI 표현을 놓친다

**확인됨 · 재현:** `driver_writers(:205~221)`는 다른 프로세스의 argv에 정확히 `--log` 토큰이 있을 때만 다음 토큰을 읽고, 그 문자열을 그대로 비교한다. 실제 함수에 가짜 프로세스 정보만 공급한 결과:

| 다른 프로세스 인자 | g0 로그 작성자로 탐지 |
|---|---|
| `--log cmdr_eval_driver_g0` | 예 |
| `--log=cmdr_eval_driver_g0` | **아니오** |
| `--log CMDR_EVAL_DRIVER_G0` | **아니오** |
| `--log ./cmdr_eval_driver_g0` | **아니오** |

argparse는 첫 두 표기를 모두 받는다. 이 Windows 환경의 일반적인 대소문자 비구분 경로에서는 뒤의 두 표현도 같은 파일을 가리킬 수 있다. 특히 `--log=...g0`는 기본 base 로그 작성자로 잘못 간주되어, g0 중복은 허용하고 반대로 base 시작은 잘못 막는 두 문제가 생긴다.

**필수 수정:** argv를 정상적으로 파싱하고 작성 대상의 절대 정규화 경로를 비교한다. 의도하지 않은 옵션 약어도 허용하지 않거나 같은 규칙으로 처리한다. 실제 검사 함수에는 이 네 가지와 정상 v3.2 기본 로그를 함께 시험한다. `test_v34`의4b는 `driver_writers=lambda: [4242]`로 바꿔서 start의 if만 검사하므로 이 결함을 못 잡는다.

프로세스 조회 실패를 조용히 「작성자 없음」으로 만드는 것도 소유권 보장이 아니다. 새 판끼리는 정규화 로그 경로에 대한 OS 잠금 등 실제 배타 관문이 더 확실하다. 이번 인계에서는 적어도 인자 표기를 고정하고, 기존 v3.2와 그 자식의 종료를 담당자가 확인해야 한다. **조회 한 번 통과를 일반적인 동시 작성 방지 보장으로 표현하지 말 것.**

### 2.3 재검증으로 빠진 선별 칸이 누락 목록에서 사라진다

**확인됨 · 재현:** `LOG['screen']`은 `:801`에서 매번 나온 칸만 갱신하며 사라진 칸을 지우지 않는다. 마지막 누락 계산(`:821~823`)은 마지막 스냅숏의 `sc`가 아니라 이 누적 사전을 사용한다.

CPU 입력에서 S0(v3.2)는96칸 모두 valid, S1(v3.4 종료)은 `wave/stand/on`의 on24000 seed1000을 재검증 탈락으로 제외하고 `complete=False`로 두었다. 실제 함수의 결과는 **`complete=False`지만 `screen_unmeasured=[]`, `remeasure_missing=[]`**였다. 최종 base에는 쌍이 없는데도 선별 누락0처럼 보인다. 전체 완료를 참으로 속이는 버그는 아니지만, 「무엇이 빠졌는지 목록에 남긴다」는 이번 수정 목적은 달성하지 못한다.

**필수 수정:** 현재 스냅숏의 유효 쌍 집합과 과거 선별 이력을 분리한다. 누락은 현재 스냅숏 기준으로 계산하고, 철회된 칸은 `invalidated/withdrawn` 등 별도 상태와 원인·source hash를 남긴다. 과거에 선별되어 이미 모은1001~1004는 삭제하지 말고, 최초100의 인증이 철회됐음을 연결한다. 이후 최초100을 다시 모아 결과가 바뀌면 기존 큐·최종 선별 상태를 명시적으로 조정한다.

**관련 제한:** `base_final(:637~641)`은 experiment 문자열만 같으면 과거 v3.4 attempt의 ended/stopped도 받는다. CPU로 이전 attempt의 종료 스냅숏 뒤 새 attempt 종료 스냅숏을 준비해도, 첫 읽기에서 작성자가 없으면 새 기록을 보지 않고 끝났다. 처음 v3.2→v3.4 전환에서는 버전 검사가 막으므로 동일 문제라고 과장하면 안 된다. 하지만 v3.4 재시작 중 예전 종료 기록을 보존하는 설계에서는 다시 해당한다. 종료할 때 작성자 없음 확인 후 스냅숏을 재확인하고, **그 최종 스냅숏을 다시 선별·대기열 처리한 뒤** 끝내야 한다. 단순히 종료용 두 번째 읽기만 추가하면16의 원래 버그가 돌아온다. 인계 대상 attempt와 입력 manifest를 묶는 방식이 필요하다.

## 3. 수정됐다고 과장하면 안 되는 제한

### 예외 종료·stamp 교체

**확인됨:** stamp를 임시 파일에 쓰고 replace하는 수정은 반쪽 JSON을 줄인다. 그러나 `write_stamp(:498~503)`에는 save와 달리 PermissionError 재시도가 없다. 메모리 파일과 교체 실패만 대체해 시험하면 PermissionError가 그대로 전파된다. 기존 stamp가 잘린다는 뜻은 아니며, **완료 상태 없이 드라이버가 죽을 수 있다**는 뜻이다. 실제 Windows 공유 위반은 이번에 일으키지 않았다.

`start`의 대기 마감(:668~670,679~681,687~688), `guarded`의 SystemExit, 재검증 도중 pins 변경도 공통 종료 정리 함수로 모이지 않는다. base 재검증 중에는 PUBLISH=False라 일부 `save()`가 억제되어 stopped가 디스크에 안 남을 수 있다. 정상 반환 때의 `not_run/not_valid`를 모든 실패 경로에서도 보장한다고 쓰지 말 것. 마지막 정상 자료는 보존하면서 실패 상태·pending·유효성 목록을 남기는 공통 종료 처리가 필요하다.

### job과 실제 재시도는 다르다

**확인됨 · 재현:** 실제 `process`와 `guarded`를 함께 사용하고 subprocess 결과만99→0으로 공급했다. 두 번의 subprocess 명령은 같았고, 최종 기록에는 `...-j1` 하나만 남았으며 guard 시도 횟수도 rec에 없었다. `Q/gpu_guard.py:28`은 같은 로그를 `w`로 연다. 따라서 첫 시도의 로그·guard 요약은 두 번째가 덮는다.

「서로 다른 job의 ID」는 고쳤다. 「실행 재시도마다 증거를 보존」한 것은 아니다. 바로 재측정을 막을 데이터 오류가 실측됐다는 뜻은 아니지만, rc99 등 오류가 나면 감사 근거가 사라진다. guard의 k까지 포함한 시도 ID·로그·요약, 최종 채택 시도의 연결을 보존할 것. 기존9번 시험은 다른 job 두 개만 호출해 이 경로를 검사하지 않는다.

### GPU 0 인계

**코드 확인:** 두 번 연속 확인은 기존 한 번 검사보다 낫다. 다만 `training_done(:185~202)`는 result.json의 내용·해당 실행 ID를 읽지 않고 파일 존재만 검사한다. 제공 시험7e도 `{}` result와1바이트 checkpoint를 넣고 통과하도록 되어 있다. 뒤의 `ready()`가 checkpoint 크기·안정 시간·bundle을 검사하므로 잘못된 checkpoint가 그대로 본 평가에 들어간다고 단정하지는 않는다. 그래도 result의 실제 종료 내용·최종 iter·현재 실행과 NIGHT DONE의 일치까지 검증한 시험은 아니다.

## 4. 운영 계획과 v3.2→v3.4 전환 답변

**판단:** v3.2를 죽이지 않고 자연 종료 뒤 base를 교체하며, g0가 먼저 v3.2 완료 행을 읽는 계획 자체는 가능하다. 태그·짝 묶음은 base와 remeasure가 겹치지 않는다. 정상적인 최초 전환에서는 구형 종료를 기다리는 코드도 작동했다. 아래 조건이 필요하다.

- **v3.2가 쓰는 동안:** 잘린 JSON의 재시도는 허용하되2.1의 시간 제한·상태 기록을 먼저 고친다. JSON 파싱 성공만으로 원자료의 특정 시도까지 인증한 것은 아니다. 선별에 쓴 base 스냅숏 hash·pin·양군 checkpoint hash·seed1000 출력 hash를 기록한다. v3.2 자료는 구형 증거라는 표시를 유지한다.
- **v3.2가 먼저 죽으면:** 유효 JSON이 남으면 현재 코드는20:00까지 기다릴 수 있고, 깨진 JSON만 남으면 지금은 마감 뒤에도 기다린다. 사망을 성공으로 처리하지는 않지만 자동 복구도 아니다. 담당자가 원인을 확인하고 자식 실행·기록 상태를 확인한 뒤 인계 시각을 정해야 한다.14:00라는 시각만으로 새 base를 강제 시작하지 않는다.
- **v3.4 공개 시점:** 원자적으로 새 JSON이 공개되는 점은 맞다. 그러나 인증 철회·재실행·입력 변경은 JSON 교체만으로 해결되지 않으므로2.3의 현재 상태와 이력 분리가 필요하다. 동일 experiment 문자열만으로 pin·checkpoint가 같다고 가정하지 않는다.
- **백업:** `_v32_until1400` 사본은 작성자와 해당 자식이 모두 끝난 뒤 만들고 hash·시각을 남긴다. 이번에 실제 사본은 만들지 않았다. 사본을 만들었다는 운영 완료 여부는 미확인이다.
- **20:00:** 두 명령에 명시적으로 --until을 넣는다. default는 여전히14:00이다. 마감은 작업 시작을 제한하며 진행 중 job을 그 시각에 강제 종료하는 설계가 아니다. GPU0 기동 후에도 연속 두 번 확인·checkpoint 안정 대기·시작 시험 시간이 더 들므로11:35를 첫 본 평가 완료 시각처럼 쓰지 않는다.

## 5. lead 시험에 대한 반박과 필요한 재시험

**좋아진 점:** 실제 반복문을 함수로 빼 CPU에서 호출하고, 실패 목록이 있으면 종료1을 반환하도록 한 것은16의 시험 공백을 줄였다. 이번 독립 시험에서도 정상 경로의 여러 수정이 확인됐다.

**여전히 약한 점:**

- 2c의 구형 종료 거부 시험은 선별된 칸의8개 작업이 있어서, 버전 검사가 없어도 반복이 여러 번 돈다. `read >= 2`만으로 버전 거부가 입증되지 않는다. **대상0개인 구형 종료 스냅숏**으로 시험해야 한다. 이번에는 그 조건으로 직접 확인했다.
- 3번 중단 시험은 대부분의 칸이 애초 미측정이다. 「이전에96칸 완료였는데 새 스냅숏에서 한 칸이 철회됨」은 검사하지 않아서2.3이 남았다.
- 4b는 작성자 함수를 통째로 대체한다. OS 프로세스 목록 전체를 모의하는 것은 가능하므로, 실제 argv 파싱과 경로 정규화를 시험에서 빼지 말 것.
- timeout 시험과 영구 읽기 실패 시험이 없다. stamp 정상 교체만으로 실제 접근 거부·공통 종료 상태가 검증된 것은 아니다.
- 9번의 다른 job 두 개로는 한 job의 rc99 재시도를 증명하지 못한다. 변이9개 통과는 이 누락들을 채워주지 않는다. 이번에 변이 전체를 재실행하지는 않았다.

**추가 관문:** 위 네 주요 반례(영구None 마감, 동등 CLI 경로, 선별 철회, job 내부 재시도)를 실제 함수에 넣고, 기존 정상 경로의 마지막8실행·96칸 완료·구형 종료 대기를 함께 유지할 것. 원자료 복사·GPU 없이 메모리에서 가능한 시험이다.

## 6. 수집을 먼저 하고 판정 코드를 나중에 고쳐도 되는가

**조건부로 가능하다.** 16의 500판 완료 확인, 개별/결합 표시, MAE 표시·결측 처리, 구간 계산 수정은 보존된 CSV·traj를 사용하는 별도 후처리로 해결할 수 있는 종류다. 그 이유만으로 같은 정상 rollout을 자동 재실행할 필요는 없다. 이번에는 별도 작성 중인 판정 파일을 읽거나 검증하지 않았다.

다만 다음을 지켜야 한다.

1. `V:103,163~170`의 pin 대상에는 **q_metrics.py·q_post.py**도 들어 있다. 판정 개선을 한다며 이 실행 파일들을 덮으면 이미 실행 중인 두 수집기가 pins 변경으로 멈추거나 재사용 관문에 걸린다. 새 분석 모듈·별도 결과 경로로 처리하고 수집 입력은 고정한다.
2. 수집 단계에서 raw hash·pairing·실제 episode 수·시도 연결을 보존한다. 입력/짝이 잘못됐거나 필요한 기록이 실제로 빠졌다면 해당 실행은 다시 필요할 수 있다. 「어떤 수정에도 재평가 없음」이라는 보장은 할 수 없다.
3. 독립400/500 추가 표집, 새로운 MAE 추가 측정 대상, 다른 평가 정의 등은 표시 수정과 다르다. 승인된 표집·수집 계약을 바꾸는 결정이면 추가 실행이 생길 수 있다.16의 선택 편향 문제는 후처리 숫자만 바꾼다고 없어지지 않는다.

**이번 재검의 실행 판단:** 2절의 수집 결함을 고친 뒤, 담당자가 실제 프로세스·학습 종료·인계·고정된 입력을 확인하는 조건에서 수집 진행을 검토할 수 있다. 이 문서는 실제 GPU 시험 통과나 새 실행 승인서가 아니다.
