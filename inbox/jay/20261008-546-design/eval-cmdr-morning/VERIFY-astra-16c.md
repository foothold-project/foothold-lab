## 2. 먼저 고칠 결함

### 2.1 필수 · 부분 MAE 결측을 정상으로 처리하고 페이지에서 숨긴다

근거: `C/cmdr_post_v5.py:100~113,196~220`, `F:115~128`.

`load()`는 finite 값만 평균낸다. `compare()`는 그 평균이 finite인지 검사할 뿐 `mae_n`이 기대 분모를 채웠는지 보지 않는다. `mae_n`을 기록하는 것과 판정에 사용하는 것은 다르다.

**독립 CPU 재현:** 양군 통과 배열을 같은 97/100으로 고정하고 실제 CSV loader부터 거쳤다.

| vx MAE 입력 | 실제 v5 결과 |
|---|---|
| off 100개 모두 0.1 · on 1개 0.1 + 99개 NaN | `n_finite=[100,1]`, `missing=False`, 「MAE 계약선 안」, **「전체 조건 충족」** |
| off 100개 모두 0.1 · on 99개 0.1 + 1개 NaN | `n_finite=[100,99]`, **「전체 조건 충족」** |
| off 100개 모두 0.1 · on 100개 모두 NaN | 「vx MAE 결측」, 「미확인」 |

첫 번째 결과를 페이지 함수에 넣으면 해당 행은 **충족한 칸으로 숨겨진다.** 의뢰의 「NaN은 결측」 수정은 전체가 NaN인 경우만 해결했다. 일부 실패 판의 MAE가 사라져도 유리한 나머지로 판정하는 길이 남았다.

수정 기준:

- seed·축·군별 기대 n과 finite n을 비교한다. 일부 결측도 명시하며, 별도 승인된 결측 처리 규칙이 없다면 충족 판정을 보류한다.
- 어느 군·어느 seed에서 몇 판이 빠졌는지 출력한다. 양군이 서로 다른 판의 평균을 비교하지 않도록 episode 수준 결측도 확인한다.
- 전체가 finite인 seed들의 평균과 부분 결측 seed의 평균을 같은 무게로 합쳐 원래 500판 평균인 것처럼 쓰지 않는다.

**실자료 영향은 구분한다.** 읽은 base 로그의 valid CSV 308개에서는 vx·vy·wz 비유한 값이 없었다. 로그 SHA-256은 `3dd126358ba7300d2d05f2a88e914d65ee18e0d0763c95592e8872b0b71395d3`이며 읽기 전후 같았다. 따라서 위는 확인된 코드 반례이고, 그 스냅숏에서 이미 결측 때문에 결론이 바뀌었다는 주장은 하지 않는다. 이후 수집 자료는 미확인이다.

### 2.2 필수 · 새 인증 자료가 없거나 깨져도 구형 자료처럼 통과한다

근거: `C/cmdr_post_v5.py:124~161`. 해시가 있는 파일의 내용 변경과 두 로그의 같은 pin 키 값 충돌은 잡는다. 그러나 인증의 필수 구조가 빠졌을 때는 막지 않는다.

**독립 CPU 재현:** 두 군의 100행 CSV, 드라이버 기록, stamp를 메모리에 만들고 원 집계의 입력 처리 경로를 실행했다. 새 형식에는 실제 키인 `version='3.4'`, `experiment`, `stamp_version='3.4'`를 사용했다.

| 변경한 입력 | 실제 v5 결과 |
|---|---|
| 정상 stamp 뒤 `cells.json` 내용 변경 | 해당 실행 제외. 정상 차단 |
| 두 로그의 공통 pin 값 충돌 | `AssertionError`. 정상 차단 |
| stamp 파일 없음 | 두 실행 수용 |
| stamp가 `{`에서 잘린 JSON | 두 실행 수용 |
| 새 stamp의 `out_sha256={}` | 두 실행 수용 |
| stamp의 `ckpt_sha256`이 해당 군 로그와 다름 | 두 실행 수용 |
| 한 로그의 `pins={}` | 두 실행 수용 |
| 두 로그의 `experiment`가 다름 | 두 실행 수용 |

앞의 두 정상 차단 시험에서는 각각 한 실행 제외·중단을 확인했다. 누락·깨진 stamp·빈 해시·잘못된 checkpoint·누락 pin은 전체 메모리 집계에서도 두 실행이 「전체 조건 충족」까지 갔다. `experiment`는 실제 키로 입력 병합 구간에서도 재확인했다.

문제는 `except ...: stp={}`와 「해시 dict가 있을 때만 비교」의 조합이다. 또 pin·checkpoint 비교는 존재하는 공통 키의 충돌만 찾는다. **필요한 값이 없다는 사실은 일치 증거가 아니다.**

수정 기준:

- 새 형식은 stamp·필수 필드·원자료 4개 해시가 모두 있어야 한다. 빈 dict·일부 키 누락·파싱 실패는 거부한다.
- 입력 로그의 실험 ID와 필수 pin을 확인한다. 실행별 모델에 해당하는 checkpoint hash가 원래 로그에 있고 stamp와 같은지 확인한다. 두 로그가 서로 다른 모델 집합을 맡을 수 있으므로 checkpoint 키 전체를 무조건 같게 만들라는 요구는 아니다.
- 진짜 구형 stamp는 명시적 구형 경로로 분리하고 근거 한계를 남긴다. **새 stamp 손상을 구형 호환으로 받아들이지 않는다.** 기존 원자료를 검토 없이 버리거나 GPU 재평가하라는 뜻은 아니다.
- 로그 hash와 `as_of`는 출처 추적에 유용하지만, 순차로 읽은 두 로그와 실행 파일들이 한 일관된 스냅숏이라는 증거는 아니다. 사용한 manifest·입력 세트와 후처리 판을 묶고, 읽는 동안 변경되면 보류해야 한다.

이는 16b의 수집기 재검과 겹치는 **소비자 쪽 관문**이다. 수집기가 stamp를 제대로 발행해도, 집계가 손상된 stamp를 허용하는 결함은 따로 고쳐야 한다.

## 3. Tango 식·구현·포함률

### 3.1 식과 구간 계산은 확인됨

[Tango 원 논문](https://www.site.uottawa.ca/~nat/Courses/csi5388/Tango.paired.pdf)의 식 (24)~(26), (33)에 `Δ=-δ`를 대입하면 소스의 통계량·제한 MLE·양 끝 해가 맞는다. 논문도 이를 근사 구간으로 설명한다. 구현의 부호는 `b=on만 통과`, `c=off만 통과`, `δ=on−off`와 일치한다.

별도 CPU 계산에서는 소스의 이차식 대신 다음 로그우도를 허용 구간에서 최대화했다.

`ℓ(s)=b log((s+δ)/2)+c log((s−δ)/2)+(n−b−c) log(1−s)`, `|δ|≤s≤1`.

그 제한 MLE로 계산한 score와 소스를 비교했다. n=1·2·10·100·500의 경계·난수 표에서 **3,640개 score의 최대 상대 오차 약 3.08×10⁻¹³**, 별도 근 찾기로 계산한 **520개 구간은 끝점 오차 2×10⁻¹⁰ 이내**였다. 이는 같은 함수를 두 번 부른 비교가 아니다.

불일치 0일 때도 확인했다. `n=100`은 약 `[-3.6993,+3.6993]%p`, `n=500`은 `[-0.7624,+0.7624]%p`다. 기존 구현의 0폭 반례는 해결됐다.

### 3.2 15개 포함률 시험은 맞지만 보장 범위가 좁다

`coverage()`의 근방 절단 합산을 그대로 믿지 않고 n=100의 **5,151개**, n=500의 **125,751개** 가능한 `(b,c)`를 전부 열거했다. 별도 다항 확률 계산으로 의뢰의 15개 모형 값을 재현했다. 예:

| n · 모집단 `(p_b,p_c)` | 실제 포함률 |
|---|---|
| 100 · `(0.01,0)` | 99.65676784% |
| 500 · `(0.001,0)` | 99.98306363% |
| 100 · `(0.10,0.02)` | 94.69412982% |
| 500 · `(0.02,0.01)` | 94.98046022% |

그러나 검사 격자를 넓히면 **n=100, `(p_b,p_c)=(0.99,0.0001)`에서 92.06083113%**다. 유효한 독립 다항 모형이며 전체 확률을 합산한 반례다. 따라서 「15점에서 93% 이상」은 전 모수 영역의 95% 보증이 아니다. 이 사실만으로 검증된 Tango 식을 틀린 구현이라고 부르지도 않는다. **명목 95% 근사 구간**과 **특정 모형에서 정확하게 계산한 포함률**을 구별해야 한다.

`test_paired_ci.py:66`의 시험 이름 「Tango 100%」도 실제 출력 99.657%·99.983%와 다르다. 이름을 고칠 것. `coverage()`는 12표준편차 근방 합산이며 전수 열거기가 아니고, `p_b+p_c=1` 경계는 확률 0인 항의 `log(0)` 처리도 없다. 이번 15점 결과를 부정하는 사안은 아니지만 범용 전수 검증기라고 소개하면 과장이다.

| 칸 | on만 통과 b · off만 통과 c | 차이와 Tango 95% 구간 (%p) | seed1000→1004별 차이 (%p) |
|---|---|---|---|
| stop03 | 44 · 10 | +6.8 `[+4.0857,+9.8362]` | +6 · +6 · +5 · +10 · +7 |
| fwd01 | 66 · 190 | −24.8 `[−30.5970,−18.8265]` | −23 · −33 · −31 · −17 · −20 |
| fwd02 | 4 · 43 | −7.8 `[−10.6768,−5.3966]` | −8 · −8 · −8 · −6 · −9 |

의뢰의 한 자리 소수 표기는 맞다. 이는 원자료 후처리 재현이며 새로운 로봇 평가가 아니다. 22,000은 여전히 중간 관찰이고 24,000 최종 판정을 대신하지 않는다.

### 3.4 지형 seed 공유는 별도 한계다

Tango는 **같은 episode의 두 군 사이 의존성**을 처리한다. **서로 다른 episode들이 공유하는 지형·배치에 따른 군집 변동**까지 처리하는 것은 아니다. 공유 지형이 있다는 이유만으로 모든 episode가 반드시 강하게 상관된다고 단정하지는 않는다. 실제 상관은 미측정이다. 다만 지형 seed로 일반화하는 불확실성까지 이 구간이 보장한다는 주장도 근거가 없다.

페이지 권고 문구:

> 구간은 episode 짝들 사이의 독립을 가정한 명목 95% Tango 근사 구간입니다. 평가 seed별 100판은 지형·배치를 공유하므로 지형 seed 간 변동까지 보장하는 구간은 아닙니다. 평가 seed 다섯 개의 결과를 따로 함께 보여줍니다. 학습 seed는 1042 한 쌍이며, 일반적 성능 효과의 확인은 별도 반복이 필요합니다.

실제 `per_seed`는 JSON에 있으나 F/H의 표에서는 보이지 않는다. 위 표처럼 다섯 값 또는 연결되는 원자료 표를 노출할 것. seed가 다섯뿐인 군집 bootstrap 등을 추가한다고 곧바로 충분한 모집단 보장이 생기는 것도 아니다. 이번 판은 사전 선별 규칙 적용과 그 한계를 함께 보고하는 수준이 정직하다.

## 4. 의뢰의 판정 질문에 대한 답

### 4.1 선별 비해당 100판의 「비퇴행」

**조건부로 가능하다.** 추가 측정을 안 했다는 사실만으로 100판의 구간 정보를 버릴 이유는 없다. 2(c)는 −5%p 선을 구간이 가로지르면 미확인이라고 정했으며, 모든 칸의 비퇴행 근거에 무조건 500판을 요구하지 않았다. 단 다음을 구별한다.

- `선별 비해당 · 추가 측정 없음`: 표집 단계.
- `100쌍 근사 구간에서 비퇴행선 충족`: 그 칸의 제한된 통계 서술.
- `전체 평가 완료·채택`: 별개이며 자동으로 따라오지 않는다.

`C:343~346`의 「자기 구간 하한 ≥−5%p인 경우만」은 예전의 무조건 「훑기 통과」보다 정확하다. 이를 모든 비해당 칸에 단지 「추가 측정 없음」만 남기는 식으로 되돌릴 필요는 없다. 다만 3.4의 한계와 실제 n을 반드시 붙이고, MAE·기본 계약을 포함한 포괄적 비퇴행 확인으로 읽히지 않게 한다.

선별된 500판에 첫 100판이 포함되는 문제는 새 400판 병기로 완화해 읽을 수 있다. **사후 선택 때문에 생기는 500판 구간의 포함률 문제가 수학적으로 교정된 것은 아니다.** 새 seed들의 난수·지형이 별개라는 조건 아래 400판이 선별 자료와 분리된 보조 비교다. 결과가 더 좋은 쪽의 구간을 사후 최종 판정으로 골라 쓰지 않는다.

### 4.2 MAE를 전체 판정에 넣는 방식

**완전한 자료에서의 진리표는 16의 권고에 맞는다.** 통과율 퇴행 또는 MAE 점추정 계약선 초과이면 미충족, 통과율 비퇴행 근거와 MAE 선 이내가 함께 있으면 두 퇴행 방지 조건 충족, 나머지는 미확인이다. MAE 초과를 별도 검정 없이 「통계적으로 확정된 악화」라고 부르지 않는 것도 맞다.

그러나 현재 구현은 2.1의 부분 결측과 2.5의 정확한 10% 경계 때문에 이 진리표의 입력 상태를 잘못 만든다. 「설계가 맞다」와 「구현이 안전하게 그 설계를 따른다」를 나눠 판정한다.

### 4.3 세 목표 완료 조건과 +10%p 결합

**확인됨:** `C:283~303`은 세 칸 모두 양군의 공통 seed가 정확히1000~1004이고 n=500일 때만 결합 판정을 낸다. +10%p 평균은 Fraction으로 비교한다. 독립 CPU 입력으로 다음을 확인했다.

| 입력 | 실제 결과 |
|---|---|
| 각 칸 100쌍 또는 400쌍 · 큰 양의 효과 | 결합 보류 · `mean_pp` 없음 · 빠진 seed 목록 |
| 각 칸 500쌍 · 차이 +5/+10/+15%p · 각 하한 >0 | 평균 정확히 +10%p · 개선 |
| 한 목표 칸에 양군 비교 자체가 없음 | 결합 판정 없음. 조기 개선 판정은 안 함 |

세 번째 경우에는 `target_verdict` 항목 자체가 비어 빠진 목표·seed 설명도 사라진다. 목표 세 칸의 상태는 수집 0쌍부터 항상 만들면 더 명확하다. 현재의 조기 판정 차단을 부정하는 결함은 아니다.

개별 칸은 차이·구간·n·seed·MAE를 서술하고, 결합 문장은 **「1042의 24,000 비교에서 사전 개선선 충족/미충족」**으로 쓴다. F의 이 수정과 「미충족은 효과 없음의 증명이 아님」은 맞다. Holm은 보조 결과이며 승인된 결합 규칙을 몰래 대체하지 않는다.

## 5. 시험 증거와 페이지 연결의 공백

**좋아진 점:** cell에 맞는 fixture, 다른 통과 열에 반대 답, 실패 시 exit1, 100/400판 보류, MAE 단독 악화, 넓은 −4%p 구간을 검사한 것은 이전의 우연 통과를 줄인다. 원 구간 함수와 일치하는지 보는 시험은 회귀 확인으로 쓰고, 별도 포함률 시험을 둔 것도 맞다.

**그럼에도 22 PASS가 충분한 관문은 아니다.**

- `test_post_v5.py:63`은 fixture의 stamp를 전부 지우고 `:68`에서 새 판 드라이버의 `valid`로 만든다. 잘못된 인증 상태를 정상 성공 fixture로 전제한다. 유효 fixture에는 실제 schema의 stamp·필수 pin·checkpoint·4개 해시를 넣고, 구형 호환은 따로 시험해야 한다.
- NaN 시험은 축 전체가 NaN인 한 경우다. 1/100·99/100 결측, 군별 다른 결측, seed별 다른 분모가 빠졌다.
- MAE 정확히 +10%·0 대조 절대한도의 위아래, 한 목표 칸 전체 누락, 잘린/빈/부분 stamp, 실험·checkpoint 불일치가 빠졌다.
- 500판 완료 여부를 JSON에서만 검사하고 F/H의 열 제목·offarm 문장까지 검사하지 않는다. 사용자에게 닿는 마지막 단계에서 500판 오류가 남은 이유다.
- `test_post_v5.py:181~195`는 base 로그만 전후 비교한다. g0 로그·stamp·원자료의 변경은 확인하지 않으며 세 번 모두 base가 바뀌어도 마지막 결과를 계속 비교한다. 같은 스냅숏의 회귀 시험임을 보장하지 못한다.
- 변이 6개의 파일은 변이 이름과 FAIL 사례 기록이다. 그 변이 시험 전체는 이번에 재실행하지 않았다. 실제 시험·생산 출력에 파일을 쓰는 원 시험 스크립트 대신 이번 보고서의 메모리 반례를 사용했다. 제공된 `.out`의 22 PASS는 제공 기록이며, 독립 재실행 22 PASS라고 전하지 않는다.

**현재 연결에서도 판 혼용을 확인했다.** 확인 당시 `O/cmdr_post.json`은 유효 실행263, `interval_method`·`as_of`가 없는 구형 산출물이었다. SHA-256 `bb3a5070e82de8297f4eccaa82e6923fe7be8fd98478ec46addc4f298d033a48`. 세 목표의 off/on22000은 각각500쌍이 있는데, F를 이 파일에 읽기 전용으로 연결하면 「22000: 두 갈래가 다 재지지 않아 아직 비교 없음」을 생성한다. 원인은 구형 자료에 새 `target_verdict`가 없기 때문이다.

새 집계 교체 전의 구형 파일이라는 사정은 이해하지만, 「다 재지지 않았다」는 진술은 틀렸다. 후처리 schema·구간 방법 판을 확인해 **「집계 판 불일치 · 새 판 집계 대기」**로 구별해야 한다. v5 JSON 발행과 페이지 갱신을 한 묶음으로 확인할 것. 고정된 숫자 문장뿐 아니라 구형/신형 입력 혼용도 테스트해야 한다.

기본 계약 JSON의 k/n·Wilson 병기는 개선됐다. 하지만 Markdown은 미충족 행만 자세히 출력하고(`C:438~441`), 페이지는 「구간은 집계 표에」라고만 쓰며 링크가 없다(`F:139`). 모든 측정 행의 k/n·구간과 누락 목록에 도달하는 실제 링크 또는 펼침 표를 제공해야 읽는 사람이 이를 검증할 수 있다.

## 6. 수집 쪽과의 경계 및 수정 우선순위

16b의 작성자 충돌·종료 감지·시도 식별·기존 선별 목록 문제는 이번에 해결됐다고 판정하지 않는다. 이번 범위는 **수집된 자료를 집계가 어떤 조건에서 믿고 어떤 문장으로 내보내는가**다. 공통 관문은 다음처럼 나눈다.

| 담당 층 | 필요한 증거 |
|---|---|
| 수집기 | 해당 실험·시도의 검증된 완료 기록과 온전한 stamp 발행. v3.5는 별도 재검 |
| 집계기 | 위 기록의 필수 구조·신원·현재 원자료 hash 확인, 불완전 입력 거부 또는 명시적 보류 |
| 페이지 | 집계 판·표본 수·seed·결측·미측정·근사 구간 한계 보존, 과도한 채택 문구 제거 |

24,000 공개 전 최소 수정 순서:

1. 부분 MAE 결측과 정확한 +10% 경계를 바로잡는다. 위 반례가 각각 보류·경계 허용으로 바뀌는지 확인한다.
2. 새 stamp 손상을 구형 호환으로 통과시키는 길을 닫고, 실험·필수 pin·해당 checkpoint를 확인한다. 구형 자료는 별도 신뢰 상태로 남긴다.
3. F/H와 Markdown의 실제 n 표시, offarm 고정500, 비퇴행/채택 문구, 집계 판 불일치 처리를 고친다.
4. 새 v5 결과 한 스냅숏으로 목표 표·퇴행 표·기본 계약·seed별 값이 사용자에게 동일하게 보이는지 확인한다. 소스 수정 성공이나 시험 출력만으로 페이지 반영 완료라고 하지 않는다.

Tango 계산과 목표 +10%p 완료 관문을 다시 처음부터 만들 필요는 없다. 검증된 부분은 유지하고 위 결함에 수정 범위를 집중한다. GPU 재평가를 이번 보고서가 요구하거나 승인하지 않는다.
