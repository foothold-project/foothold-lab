## 3. 남은 P1 · 로그가 승인한 출력과 실제 사용 출력의 연결이 없다

### 3.1 같은 바이트로 계산하는 문제는 고쳤다. 같은 검증 실행인가라는 문제는 남았다

근거는 C:157~185, 204~251, 485~490이다. 집계기는 로그에서 `matrix[tag] == valid`, pins·checkpoint를 읽지만 **그 tag의 `runs` 기록에 있는 출력 해시·attempt를 인증에 사용하지 않는다.** 새 stamp의 네 해시가 현재 파일과 맞으면 수용한다. 마지막에 같은 로그 해시를 다시 읽어도, 로그가 가리키는 실행 A와 현재 경로에 놓인 실행 B의 구별은 되지 않는다.

독립 메모리 반례는 다음과 같다.

1. 로그는 off 60/100·on 50/100 실행을 valid로 기록한다. on의 실행 기록에 `attempt=OLD-j1`과 네 출력 해시도 넣었다.
2. 집계기가 이 로그 바이트를 확보한 직후, on 파일을 새 실행의 100/100 출력으로 교체하고 **그 새 바이트에 맞는 정상 새 stamp**를 발급한다. stamp attempt는 `NEW-j1`이다.
3. 공용 로그는 아직 옛 바이트 그대로 둔다. 별도 attempt 파일은 NEW·revalidating으로 두었다.
4. 결과는 **+40 %p, auth_fail=[], legacy_stamps=0**이다. 최종 manifest의 CSV 해시는 로그 실행 기록의 옛 해시와 다른데도 통과했다.

원래 로그가 승인한 비교는 −10 %p다. 재현은 GPU 결과가 이미 이렇게 오염됐다는 주장이 아니라, **그런 갱신 순서를 집계기가 구분하지 못한다는 반례**다. 네 출력의 새 해시를 위조하지도 않았고 최종 로그 검사를 끄지도 않았다.

이는 의뢰서의 이관 질문과 직접 연결된다. 확인 대상 v3.6의 `process()`는 982~983에서 stamp를 쓰고 986~988에서 실행 기록·matrix·로그를 갱신한다. 짝 지문 실패도 stamp 쓰기 전에 판별하지만 stamp는 작성하며, matrix의 pair_fail 공개는 그 뒤다. 재검사 pass에서는 공용 로그 공개를 더 늦춘다. **stamp가 존재한다는 것만으로 그 출력이 현재 공개 로그에서 최종 valid로 확정됐다고 볼 수 없다.** 실제 운영에서 이 틈으로 잘못된 숫자가 공개됐는지는 미확인이다.

### 3.2 구형 조건은 호환 형식의 범위를 줄일 뿐, 출력의 불변성을 증명하지 않는다

v3.2 소유·새 형식 흔적 없음·pins와 checkpoint 일치는 임의의 새 stamp를 구형으로 격하하던 오류를 줄인다. 이 개선은 인정한다. 그러나 **충분한 무결성 조건은 아니다.** 구형 stamp는 검증 당시 출력 해시가 없고, 로그 버전이 없는 입력도 C:168에서 v3.2로 간주한다. “형식상 구형”과 “확인된 구형 실행 묶음”은 같은 말이 아니다.

별도 반례에서 구형 on의 옛 meta 바이트를 읽은 직후, writer 역할이 meta와 CSV를 새것으로 바꾸게 했다. stamp와 두 로그는 그대로다. 결과는 +40 %p·auth_fail=[]이고 manifest는 **옛 meta 해시와 새 CSV 해시**를 함께 기록했다. 한 파일을 한 번 읽는 것은 보장되지만 여러 파일이 같은 실행 시점의 묶음이라는 보장은 아니다.

이를 해결하기 위해 구형 자료를 모두 버리거나 GPU로 다시 평가할 필요는 없다. 이미 제안한 대로 **작성자가 없는 고정 묶음의 현재 원자료를 CPU로 재검사하고 그 검증 결과·manifest를 연결하는 방법**이 있다. 단, 지금 처음 만든 해시로 과거부터 불변이었다고 주장하면 안 된다.

### 3.3 최소 수정 기준

- 새 형식은 log의 **해당 실행 기록**과 stamp·읽은 출력 해시가 연결돼야 한다. record의 attempt/검증 식별과 판정 상태도 함께 확인한다. 같지 않거나 아직 로그에 공개되지 않았으면 보류한다.
- 단순히 `stamp.attempt == driver.attempt`라고 비교하면 정당한 재사용도 깨질 수 있다. 원래 실행의 식별과 이번 재검사의 식별을 나누고, 어떤 검증이 어떤 출력 묶음을 valid로 공개했는지 연결해야 한다.
- 재검사 중인 base가 옛 로그를 보존하는 전환 구간은 완료된 불변 스냅숏을 계속 읽거나, 새 attempt의 일관된 검증 결과가 공개될 때까지 집계를 보류한다. 두 로그의 전후 해시만으로 대신하지 않는다.
- manifest에 네 출력 해시만 두지 말고, 소유 로그·실행 기록·사용한 stamp의 해시/식별·구형 이관 여부도 남긴다. 현재 C:251은 stamp 해시와 attempt를 보존하지 않는다.

수정 목표는 모든 동시 쓰기를 포괄하는 거대한 프레임워크가 아니다. **독자가 실제 사용한 바이트와 작성자가 유효하다고 공개한 바이트를 같은 검증 기록으로 묶는 것**이다. 이미 새 로그에 있는 `out_sha256`을 버리지 않는 것부터 시작할 수 있다.

## 4. 구형 stamp를 새로 쓸 때 생기는 출처 문제

의뢰 2번의 답은 두 가지다.

첫째, 위 3절처럼 **옛 로그와 새 stamp가 공존하는 시간**이 생긴다. 최신 드라이버가 이 시간의 집계를 어떻게 차단하는지는 v3.7 범위이므로 미확인이다. v7 집계 자체에는 해당 차단이 없다.

둘째, 정상적으로 이관해도 **구형에서 온 자료라는 정보가 사라진다.** 원자료를 바꾸지 않고 구형 두 stamp를 새 해시·stamp_version=3.6·attempt=`v3.2 or earlier`로 바꿔 새 로그에 담는 CPU 시험에서, `legacy_stamps`는 2→0, manifest의 form은 모두 new가 됐다. manifest에는 원 stamp의 출처가 없었다.

새 해시는 **이번 재검사 시점부터의 바이트 고정**에는 유용하다. 그 자체가 잘못은 아니다. 그러나 “처음 수집할 때 출력 해시가 있었던 실행”으로 소급해서 읽혀서는 안 된다. `legacy-origin revalidated`와 새 수집을 구별하고, 원 tag·옛 stamp/로그 해시·재검사 시각·새 검증 식별을 남기는 것이 적절하다. 현재 페이지의 구형 수는 정확히는 **현재 stamp가 구형인 수**이며, 이관 뒤 모든 실행의 과거 무결성이 강화됐다는 뜻이 아니다.

## 5. 페이지 문구와 시험의 남은 한계

### 5.1 P2 · 결과 파일 없음은 “아직 학습 중”의 증거가 아니다

F:87~92는 result.json이 없으면 “아직 학습 중 (현재 시각 확인)”으로 쓴다. 메모리에서 파일이 없는 입력을 넣어 양군 모두 이 문장이 생성되는 것을 확인했다. **미기동·중단·실패·이동된 파일도 같은 문장으로 나온다.** 고정 종료 예상은 없앴지만 다른 형태의 상태 추정이 남았다.

이 경로는 “학습 완료 결과 파일 없음 · 현재 상태 미확인”처럼 관측 사실만 써야 한다. 진행 중이라고 쓰려면 해당 학습 attempt의 실행 증거가 필요하다. 현재 실자료에서는 정상 result.json이 있어 off 05:22·on 11:30 종료 문장이 나왔으며, 그 정상 경로가 틀렸다는 지적은 아니다.

### 5.2 제공 시험은 무엇을 검증했나

제공 출력의 50 PASS·FAILS=[]·exit 0과 변이 네 건 검출 기록은 확인했다. 독립 메모리 시험은 위 변경 경로를 검사했으며 **제공 50건·변이 네 건을 그대로 재실행했다는 뜻은 아니다.**

- R1·R2는 이전 결함을 직접 겨냥한 유효한 회귀 시험이다. 같은 바이트 파싱과 로그 변화 시 중단을 확인한다. 다만 R2는 **로그가 변하는 경우**만 넣고, 로그는 그대로인데 실행 묶음·stamp가 새 세대로 바뀌는 경우는 없다.
- D는 새 형식 흔적·소유 로그 버전 구분을 제대로 검사한다. v3.2 이름 아래 구형 raw가 갱신되거나 새 stamp가 먼저 발급되는 경우는 다루지 않는다.
- C14는 이전과 달리 arm·seed·finite 수를 실제로 assert한다. C15·C16도 기준 종류와 완료 수를 확인한다. 이 수정은 충분히 구체적이다.
- G5는 이제 군별 행 수를 따로 센다. 전보다 낫지만 같은 개수의 중복 행·다른 cell·잘못된 k/n도 통과할 수 있다. 군·cell 키와 값까지 비교해야 표의 내용 검증이 된다.
- G10은 토큰 존재와 옛 문구 부재를 확인한다. `result.json` 정상·없음·중단의 생성 문장은 검사하지 않아 5.1을 놓친다.
- F1의 v6와 v7 일치는 두 구현이 같은 입력을 읽었을 때의 회귀 확인이다. 같은 잘못된 출처를 양쪽이 수용할 가능성까지 배제하지 않는다.

낮은 우선순위의 표시 잔여물도 있다. C:505의 생성 Markdown 제목과 F:2의 원자료 설명이 아직 v6를 가리킨다. 실행 schema는 v7이라 수치 판정에는 영향을 주지 않지만, 감사자가 생성 판을 오인하지 않도록 고치는 편이 맞다. 절대 MAE 한도 문구에는 축 단위(m/s·rad/s)를 붙이면 명확하다.

## 6. 24,000 숫자 경로 재계산

[검토한 #546 댓글 6137346403](https://github.com/foothold-project/foothold-lab/issues/546#issuecomment-6137346403)은 직접 읽었다. 첫 실자료 집계 시도는 실행 중 base 로그 변화로 종료 3이 됐고 아무 출력도 쓰지 않았다. 다음 시도는 **12:31:55**에 로그 전후 해시가 일치하는 상태로 끝났다. 결과 JSON·Markdown은 메모리에만 생성했다.

| 입력 식별 | 값 |
|---|---|
| base 로그 SHA256 | `fa8fba057a15f6193e5ea56bba87cfa8208ab6da6e5a537662b4ee6cb22ca399` |
| g0 로그 SHA256 | `3db93e6a900ddd7a25c3180d58af7dcf450762975c9d4b480bb94df427670f19` |

`auth_fail=[]`는 v7의 위 제한된 인증을 통과했다는 뜻이다. 384개 전체의 과거 무결성을 독립 인증했다는 뜻이 아니다.

목표 계산은 집계의 `main_col`·`pooled`·`compare`를 재사용하지 않고 **30개 CSV를 별도로 다시 읽어** 확인했다. 각 파일은 해당 cell·flat family·episode 0~99가 한 번씩 있는지 확인했고, seed·episode로 양군을 짝지었다. stop03은 `span_q2_pass`, fwd01/02는 `span_q1a_pass`를 셌다. 다시 읽은 30개 CSV의 해시는 해당 집계 manifest와 모두 같았다. Tango 수치는 변경 없는 `paired_ci.py`에 별도로 센 b·c·n을 넣어 확인했다.

| 칸 | off 통과 | on 통과 | on만 / off만 | on−off %p | Tango 명목 95% 구간 %p | seed1000~1004 차이 %p |
|---|---:|---:|---:|---:|---|---|
| stop03 | 36/500 (7.2%) | 55/500 (11.0%) | 46 / 27 | +3.8 | [+0.4615, +7.2435] | +3 · +1 · +8 · +3 · +4 |
| fwd01 | 140/500 (28.0%) | 188/500 (37.6%) | 98 / 50 | +9.6 | [+4.8967, +14.3321] | +13 · +3 · +12 · +5 · +15 |

평균은 `(3.8 + 9.6 + 2.6) / 3 = 5.333333… %p`. 세 하한은 모두 0 위지만 +10 %p 평균 조건이 아니므로 **이번 1042·24,000 비교의 사전 개선선 미충족**이다. 댓글의 반올림·쌍 수·b/c·판정은 맞다.

MAE도 CSV의 유한 개수를 직접 세고 `math.fsum/500`으로 재계산했다. 세 칸·두 군·다섯 시드·세 축 모두 각 실행당 finite=100이었다. vx의 off→on은 stop03 `0.054033→0.039331`, fwd01 `0.061117→0.057572`, fwd02 `0.057168→0.047297` m/s이고, vy·wz까지 아홉 비교 모두 +10% 선 안이다. 댓글의 “목표 MAE 계약선 안”도 확인됐다.

해석의 한계는 유지해야 한다. **세 칸의 합산 비교에서 on이 높다**는 서술은 맞다. 모든 평가 seed에서 높다는 뜻은 아니며 fwd02 seed1000은 −1 %p다. 학습 seed 한 쌍의 결과로 일반적인 효과나 실기 성능을 확정하지 않는다. 특히 on의 멈춤 11.0%, 저속 37.6%라는 절대 통과율은 여전히 낮다. 상대적 개선 관찰을 사용 가능한 보행 정책이라는 결론으로 바꾸면 안 된다. 생존을 포함한 별도 기본 계약도 계속 분리해서 읽어야 한다.

댓글의 17칸·MAE 미충족 1칸은 과거 시점 관찰이다. 그 시점의 전체 입력 묶음은 별도로 받지 않았으므로 17칸 전체 상태를 소급 검증한 것은 아니다. **이번 12:31 묶음은 비교 34/99칸, 표본 충족 34칸, 퇴행 방지 충족 29·미충족 3·미확인 2**다. 미측정은 65칸이다. 이것을 옛 댓글 숫자 오류로 취급하지 않는다.

현재 미충족에는 flat/back03의 vx MAE `0.038210→0.053438`이 그대로 있고, obstacles/back03과 rough_slope/back03이 추가됐다. obstacles/back03은 500쌍 차이 −3.6 %p, 구간 [−6.9351, −0.3770]으로 **−5 %p 대비 비퇴행 미확인**, vx MAE도 선을 넘는다. 새 400쌍만은 −2.75 %p [−6.6898, +1.1045]다. 전체 통과를 선언할 상태가 아니다. 이 추가 상태는 v7 경로에서 읽힌 관찰이며, 목표 30 CSV처럼 모든 추가 칸을 별도 알고리즘으로 전수 재집계한 것은 아니다.
