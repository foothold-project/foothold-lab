# ASTRA 16i · 집계 v8와 인계 수정 재검

**고칠 것: `cmdr_post_v8.py`의 보류 해제와 소유 기록 연결, `handover_1400.py`의 stop 이동 범위, `facts5_cmdr.py`의 출처 문구.**

v8을 무조건 통과시킬 수 없다. 특히 **재검사 시각만 바뀌어도 “다시 측정한 실행”으로 취급하는 보류 해제는 틀렸다.** 제공 시험 L5b도 그 잘못을 성공으로 요구한다. 인계 스크립트는 대상 두 드라이버 외의 stop도 옮긴다. 실제 운영 폴더에 `hud_follow.stop`이 있어 가상의 위험만도 아니다. 이 파일의 소유 작업·이행 여부는 미확인이다.

반면 16h에서 직접 재현한 누락 파일·원본 변경·늦은 프로세스 탐지와 v3.6 경유 출처의 직접 분기는 고쳐졌다. 이 결과를 무시하고 드라이버 전체를 다시 설계할 이유는 없다. **인계 관문 수정, 수집 기동 조건, 집계 공개 조건을 구분**해야 한다.

## 3. P1 · 공개 보류가 재측정 없이 풀린다

근거: `cmdr_post_v8.py` 293~310줄, `test_post_v8.py` 379~400줄, 드라이버 `process()`의 재사용 시 stamp 재작성.

재현:

1. 정상 tag의 stamp 바이트 해시를 `cmdr_post_hold.json`에 등록한다.
2. 집계하면 `held=[tag]`, manifest에 tag 없음이다.
3. **출력 네 파일, 실행 attempt, 소유 로그를 그대로 두고** stamp에 `revalidated_at: "later"`만 추가한다.
4. 다시 집계하면 종료 0, `held=[]`, `hold_released=[tag]`, manifest에 tag가 돌아온다.

이것은 다시 측정했다는 증거가 아니다. 드라이버도 재사용할 때 `prev_stamp_sha256/revalidated_by/revalidated_at`를 넣어 stamp를 바꾸므로, **stamp 바이트 변경과 새 수집은 실제 코드에서도 다른 사건**이다. 현재 알려진 stand를 v3.7의 USD 검사까지 통과시켰다는 반례를 만든 것은 아니다. 그 실행은 별도 검사에서 막힐 수 있다. 그렇더라도 공개 보류 정책 자체가 틀린 것은 변하지 않는다.

L5b는 정확히 `revalidated_at="later"`만 추가한 뒤 보류 해제를 기대한다. P8 돌연변이 시험도 이 해제를 막으면 실패시킨다. 이는 안전 요구 검증이 아니라 잘못된 구현의 고정이다.

**최소 수정:** 당장 공개 보류를 tag에 고정하고 명시적으로 해제해도 된다. 자동화하려면 보류한 수집 attempt와 새 소유 로그의 마지막 실행을 비교하고, 새 실행이 `reused=False`, 다른 측정 attempt, 정상 검증·짝 조건을 충족한다는 근거가 필요하다. 새 attempt 문자열만 바꾼 것도 증거는 아니다. 해제 이유·승인 또는 새 수집 기록·출처를 남겨야 한다. 새 측정이 결정론적으로 같은 출력 바이트를 낼 수도 있으므로 “네 파일 해시가 달라야 한다”도 올바른 대안은 아니다.

현재는 인증 실패나 stamp 부재여도 먼저 `hold_released`에 넣는다. “해제 후보”와 “인증된 대체 실행으로 실제 해제”도 분리할 것.

## 4. P1 · 인계가 관련 없는 stop까지 이행 처리한다

근거: `handover_1400.py` 197~204줄.

`os.listdir(OUT)`의 모든 `.stop`을 옮긴다. 독립 정상 대조군에 `unseen_driver.stop` 하나만 추가했더니 종료 0·complete이며 다음 셋이 이동했다.

- `cmdr_eval_driver.stop`
- `cmdr_eval_driver_g0.stop`
- `unseen_driver.stop`

두 드라이버 인계가 다른 작업의 중지 요청까지 이행했다는 근거는 없다. **13:52:17 운영 폴더를 읽었을 때 실제로 `hud_follow.stop`이 있었다.** 사용 목적·현재 효력은 미확인이다. 이것을 옮겨도 된다고 추정하면 안 된다.

**최소 수정:** 대상은 두 명시적 로그 이름의 stop만으로 제한한다. 가능하면 인계 시작에 해당 파일의 존재·해시를 기록하고 이동 직전 같음을 확인한다. 중간에 생긴 새 stop은 옛 요청으로 삼지 않는다. 다른 stop은 그대로 두고 목록만 보고한다. 실패 시 유지하는 기존 동작은 맞다.

이 수정 전에는 현재 H를 그대로 실행해도 된다고 승인할 수 없다. 수정과 별개로 이전 프로세스·자손 소멸, 원본 재해시, 두 스캔 등 이미 추가한 관문은 유지한다.

## 5. 집계 인증과 상태 관문의 남은 결함

### 5.1 소유 로그의 마지막 기록이 아니라 전역 마지막 기록을 쓴다

근거: 집계 204~206줄과 274~282줄.

`drv["rec"][tag]`를 두 로그에서 순서대로 채운다. matrix의 소유자는 따로 정하지만 인증 기록 조회에 owner를 쓰지 않는다.

재현: base matrix에 tag가 있고, base runs의 마지막 기록은 invalid로 둔다. g0 matrix에는 그 tag를 넣지 않고 g0 runs에만 같은 tag의 정상 기록을 넣는다. matrix 중복 검사는 통과하고 g0의 기록이 base의 invalid를 덮는다. 결과는 **종료 0·auth_fail 없음·base 소유로 표시된 manifest에 tag 포함**이다.

현재 운영 로그의 교차 tag를 직접 읽어 보니 13:52에는 양쪽 모두 0개였다. 따라서 **현재 수치가 이 결함으로 오염됐다고 주장하지 않는다.** 그러나 의뢰서의 “소유 로그의 마지막 기록”이라는 보장은 구현되지 않았다.

최소 수정은 `rec[owner][tag]` 또는 `rec[(owner,tag)]`이며, 다른 로그의 잔존 실행 기록으로 인증을 대체하지 않는 것이다. 같은 로그의 valid→invalid, invalid→valid, 다른 로그의 동명 tag를 함께 시험할 것.

### 5.2 재검사 상태는 최초 한 번만 읽고, 깨진 상태 파일은 무시한다

근거: 집계 207~215줄 및 560~574줄의 마지막 검사.

독립 반례 두 가지:

- 정상 OLD/running 상태로 시작한 뒤, 파일을 읽는 중 sidecar만 NEW/revalidating으로 바꿈. 로그·결과 파일은 그대로. **종료 0으로 작성한다.**
- 새 형식 소유 로그의 sidecar를 잘린 JSON으로 둠. 예외를 `af=None`으로 삼아 **종료 0으로 작성한다.**

첫 반례가 곧 수치 오염이라는 뜻은 아니다. 이전 정상 스냅숏의 값일 수 있다. 하지만 “재검사 중에는 아무것도 쓰지 않는다”는 관문은 아니다. 로그 해시의 마지막 검사는 sidecar를 보호하지 않는다. hold 파일 역시 입력 해시·재검사 대상에 없다.

최소 수정: 구형 v3.2의 sidecar 부재를 허용하는 경우와 새 형식 소유자의 읽기 실패를 분리한다. 최신 로그의 sidecar가 누락·파손이면 보류하고, 읽은 바이트·존재 상태를 집계 끝에도 확인한다. 공개 보류 파일도 같은 입력 계약에 넣는다. 이것만으로 종료 검사 직후의 모든 경쟁을 없앴다고 하지는 말 것. 자동 공개는 쓰는 프로세스가 없는 묶음이나 세대별 불변 스냅숏을 기준으로 해야 한다.

### 5.3 stat 동일은 바이트 동일의 증명이 아니다

의뢰서가 물은 경우를 직접 시험했다. inode·size·mtime_ns가 같게 반환되도록 한 메모리 입력에서, meta를 읽은 뒤 `on24000`을 같은 길이의 `on99000`으로 바꿨다. 집계는 **종료 0**이고 manifest의 meta 해시는 끝의 파일 바이트 해시와 달랐다. 보통 stat 변경 대조군은 종료 3이었다.

이 시험은 “stat 관문으로 잡을 수 없는 변경”의 재현이다. 실제 디스크에서 이런 교체가 일어났다는 증거도, 이 반례에서 성공률 숫자가 틀렸다는 증거도 아니다. 새 형식은 읽은 바이트 자체가 이미 공개된 해시와 맞아야 하므로 보호가 더 강하다. 구형은 그 수집 당시 해시가 없어 같은 보장을 할 수 없다.

따라서 “사용 파일이 끝까지 같은 바이트임을 증명”은 과장이고, “해당 stat 속성의 변경을 감지”가 정확하다. 파일 내용의 마지막 재해시는 이 반례를 더 강하게 막지만 완전한 트랜잭션을 만들지는 않는다. 이번 14:00 계획의 **작성자 없는 상태 유지와 H 입력 manifest 대조**가 필요한 이유다.

### 5.4 v3.7의 stamp→기록 공개 틈

새 측정으로 출력·attempt가 바뀐 경우는 v8이 막았다. 다만 기존 수집을 재사용해 출력 해시·attempt를 유지하고 stamp의 origin·재검사 필드만 바꾸면, 옛 실행 기록과도 현재 인증 조건이 맞는다. v8은 소유 기록의 **정확한 stamp 해시 또는 재검사 세대**까지 연결하지 않는다.

base의 revalidating 상태가 최초 읽기 때 정상으로 보이면 보류하므로 일반 경로의 위험은 줄었다. 그러나 5.2의 재검사 시작 경쟁까지 닫힌 것은 아니다. 수치의 옛 수집 identity와 새 stamp의 재검사 provenance를 구분하고, 새 provenance 공개가 끝났다고 주장하려면 해당 세대의 소유 기록과 연결할 것. 기존 출력이 정상이라는 이유만으로 새 검사 결과까지 공개됐다고 쓰면 안 된다.

## 6. P2 · 페이지가 모르는 출처를 “수집 때 해시”라고 바꾼다

근거: `facts5_cmdr.py` 16~17줄과 상태 줄 생성.

새 stamp에 origin을 넣지 않은 정상 입력을 실제 집계→페이지 `build()`로 통과시켰다.

- manifest·개수: `hashed (stamp has no origin field): 1`
- 페이지: **“수집 때 해시 (출처 칸 없음) 1”**

출처 칸이 없으면 최초 수집 시점에 해시했는지, 나중에 재검사하며 해시했는지 이 집계만으로 모른다. 괄호가 앞의 단정을 취소하지 않는다. **“출력 해시 있음 · 최초 생성 시점 미확인”** 등으로 바꿔야 한다.

`legacy_stamps`가 현재 형식의 개수라는 구분, 명시된 `legacy-origin revalidated` 표기, 결과 파일 없음 문구는 제대로 반영됐다. 이들을 다시 바꿀 필요는 없다.

## 7. stand 대조는 기록 비교 도구이며, 통과 관문으로는 부족하다

근거: `compare_stand.py`의 `same`과 최종 exit.

바이트/내용을 나눠 보는 변경과 “차이가 있으면 원인 미확인”이라는 방향은 맞다. 그러나 마지막 판정은 cells·episodes·traj 배열만 사용한다. meta 비교, env_origins, 새 로그의 root reference 오류는 결과 요약과 종료값에 영향을 주지 않는다.

독립 반례: 세 출력 내용은 같게 두되 새 checkpoint 해시를 OTHER로 바꾸고, env_origins 바이트를 다르게 하며, 새 로그에 정확한 root unresolved reference 문구를 넣었다. 출력에는 차이가 표시되지만 **종료 0, “no difference found in the recorded outputs compared”**가 나온다.

이는 동일 입력에서 다시 수집한 정상 실행의 대조를 입증하지 못한다. 다만 도구가 내부 차이를 전혀 못 찾은 것은 아니다. 상세 JSON에는 checkpoint false·env_origins false·root_ref true가 있다.

수정 방향:

- 최상위 결과를 `output_content_equal`, `inputs_equal`, `new_run_valid`, `comparison_ready`로 나눠 기록한다. 입력 불일치나 새 실행 오류가 있으면 “동일 조건 대조 보류”다.
- 새 로그·stamp·완료 기록을 확인하기 전에는 비교 완료로 삼지 않는다.
- `old[0]`이라는 정렬상 첫 보존 폴더 대신, H가 보존한 의심 실행의 stamp 해시·attempt와 일치하는 원본을 명시적으로 고른다.
- 출력이 달라도 충돌 때문이라는 인과 결론은 내리지 않는다. 같아도 자산이 온전했다는 증명이 아니다.

이 도구의 현재 종료 0을 **보류 해제 또는 새 수집 정상 판정**으로 쓰면 안 된다.

## 8. 제출 시험에 대한 판단

- L1·L1b·L2·L3와 인계 누락/경쟁 시험은 기존 결함에 맞는 시험이다. 이번 독립 대조에서도 주요 동작을 확인했다.
- **L5b와 P8은 기대값을 바꿔야 한다.** “재검사 메타데이터만 변경”의 올바른 기대는 보류 유지다. 새 정상 수집을 별도 대조군으로 둬야 한다.
- G13은 명시적 legacy origin 전달만 본다. origin 없는 새 stamp가 사용자에게 어떤 한국어로 보이는지 시험해야 한다.
- G5는 행 개수만 본다는 미완료 사항이 그대로다. F1도 제공 기록상 22,000 목표 비교이며, 이번 운영의 24,000과 전체 퇴행·계약 행 검증을 대신하지 못한다.
- H의 정상 통과 시험에 대상 외 stop을 넣고 그대로 남는지 볼 것. 실패 시 대상 stop이 남는 기존 시험은 유지한다.
- 마지막 기록 시험은 소유자까지, 재검사 시험은 최초 상태뿐 아니라 집계 중 상태 변화까지 확장할 것.
- 제출된 “돌연변이 모두 검출”은 기대값 자체의 타당성 증명이 아니다. L5b가 그 반례다.

## 9. 14:00 전환 판단과 최소 조건

**완료된 인계 뒤 고정 묶음을 비교하고 새 수집으로 넘어가겠다는 순서는 맞다. 다만 현재 H의 complete와 현재 v8의 종료 0만으로 충분하다는 판단은 틀리다.**

| 단계 | 진행 조건 |
|---|---|
| 인계 | H의 stop 범위를 대상 두 개로 제한. 옛 드라이버·자손·외부 Isaac 없음, 필수 파일·원본 재해시·pins·체크포인트 일치가 모두 확인되어야 한다 |
| 고정 집계 입력 | 작성자 없는 상태 유지. H manifest와 실제 로그·사용 파일 해시 대조. 의심 stand의 현재 stamp를 확인한 보류 파일을 만들고 그 내용·해시도 보존 |
| v7/v8 대조 | 22,000·24,000 각각 목표 세 칸의 표본수·성공수·짝 표·구간·동일 가중 평균·결합 판정을 키로 비교. stand를 제외한 퇴행·계약 행의 키와 값 비교. 전체 실행 수 하나 차이만으로 통과시키지 않는다 |
| 공개 | stand 제외가 manifest·held·각 표에 모두 반영되고 보류 이유가 보인다. 출처 문구 수정. G5의 행 개수 확인 대신 실제 출력 내용 대조. 재검사 중 자동 갱신은 5절 관문 보강 전 보류 |
| 새 수집 | 위 고정 묶음과 이전 stamp 보존 후, 확인된 실제 v3.7 경로와 같은 잠금 위치로 시작. 이번 검증은 새 프로세스 기동·실제 잠금 경쟁·새 수집 정상 완료의 증거가 아니다 |
| stand 대체 | 새 측정·소유 기록·검증 통과·출처를 확인한 뒤 해제. stamp 해시 변경이나 compare_stand 종료 0만으로 해제하지 않는다 |

13:52 읽기 시점에 base 로그는 valid 439개, g0 v3.6은 16개였다. 이는 matrix 문자열을 센 것으로 **455개 실행의 정상성 재인증이 아니다**. 같은 시점 `cmdr_post_hold.json`은 없었다. 그러므로 “stand 보류가 이미 적용됐다”는 상태도 아니다. 보류 파일을 이후 만들 계획과 현재 적용 여부를 구분할 것.

이번에는 새 운영 데이터의 전체 성능 수치를 재계산하지 않았다. 14:00 고정 묶음 자체가 아직 확인되지 않았으므로 그 비교 성공·v17 공개·v3.7 기동을 승인 완료라고 적을 수 없다. 고정 묶음 대조가 실패하면 공개를 미루고 원인을 확인한다는 lead의 방침은 타당하다. 위 결함을 이유로 무관한 집계 수식 전체나 이미 통과한 수집 로직 전체를 다시 검토할 필요는 없다.

## 10. 작업 경계

운영 프로세스·GPU·Isaac·학습·평가를 실행하거나 종료하지 않았다. 기존 코드·원자료·stop·로그를 수정하지 않았다. 커밋·push·외부 전송 없이 이 보고서 한 파일만 만들었다. 이후 변경판은 이 문서의 해시와 구분하여 검토해야 한다.
