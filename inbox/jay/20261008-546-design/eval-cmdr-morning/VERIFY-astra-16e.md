## 3. 집계에 남은 결함

### 3.1 P1 · 새 stamp의 버전 키 누락을 구형으로 받아들인다

**근거: C:174~197, 특히 190줄의 키 존재 여부 분기.** pins와 checkpoint가 맞으면, `stamp_version` 키가 없다는 사실 하나로 `legacy`를 반환한다. 소유 로그가 v3.5인지, 해당 실행이 실제 v3.2에서 왔는지, 새 형식의 다른 필드가 남아 있는지는 확인하지 않는다.

양군의 주 통과를 각각 50/100으로 만든 뒤 on CSV만 100/100으로 바꿨다. 로그의 `valid`와 pins·checkpoint는 그대로 뒀다.

| on 입력 변경 | v6 결과 |
|---|---|
| 정상 새 stamp와 검사 전 원자료 변경 | 해시 검사로 제외하는 코드가 있음. 제공 시험도 해당 경로를 확인 |
| 새 stamp에서 `stamp_version`만 제거, 옛 `out_sha256`은 그대로 | `auth_fail=[]`, `legacy_stamps=1`, 양군 2실행 수용, 차이 **+50%p** |
| 새 stamp에서 `stamp_version`과 `out_sha256` 둘 다 제거 | 같은 결과로 수용 |
| 처음부터 구형 stamp였고 이후 CSV 변경 | 같은 결과로 수용 |

첫 번째는 고쳐진 경로이고 나머지는 독립 메모리 재현이다. 특히 두 번째는 **틀린 해시가 파일 안에 남아 있는데도 검사하지 않고 통과한다.** 새 판 손상이 구형으로 내려가는 길이 명백히 남았다.

**구형 stamp의 pins+checkpoint 일치만으로 충분한가: 충분하지 않다.** 그 값들은 어느 코드·모델이라고 기록됐는지 연결할 뿐, 지금 읽는 CSV·meta·trajectory가 검증 당시의 것이라는 증거가 아니다. 원래 v3.2 `write_stamp()`는 pins·시각·checkpoint·pair_ref를 쓰고 출력 바이트 해시는 쓰지 않았다 (`C/cmdr_eval_driver.py:330~337,494`). 이 형식의 실제 유래는 확인되지만, 필드가 없는 모든 JSON을 같은 신뢰로 받아들일 수는 없다.

수정 기준:

- 구형은 “버전 필드 없음”이 아니라 확인된 구형 실행 목록/출처와 연결해 한정한다. 신형 로그에 들어간 구형 자료를 지원하려면 그 이관 근거를 명시한다. 새 형식 흔적이 있는데 버전만 없어진 입력은 모호한 인증으로 거부한다.
- 구형 원자료를 버리거나 GPU로 다시 평가하라는 요구가 아니다. 변경되지 않는 입력 묶음에서 CPU로 현재 원자료·meta·짝·checkpoint·계약을 재검사하고, 그 **현재 검증한 입력 묶음**의 manifest와 해시를 남기는 방법이 있다. 지금 처음 계산한 해시가 과거부터 불변이었다는 증거가 된다고 쓰지는 않는다.
- 구형을 임시로 보고할 경우 신뢰 수준을 분리한다. 현재 `legacy_stamps`는 개수 하나이며, 페이지는 이를 노출하지 않고 모두 「유효한 평가 실행」으로 합친다. 구형 출처 확인과 신형 출력 해시 검증이 같은 보장인 것처럼 보이지 않게 한다.

### 3.2 P1 · 인증한 바이트와 실제 계산에 쓴 바이트가 다를 수 있다

**근거: C:194에서 네 파일 해시 검사 후, C:213→114~127에서 CSV를 다시 읽는다.** 검사가 통과한 뒤 로딩하는 동안의 변경을 재확인하지 않는다. 두 로그도 각각 한 번 읽고, 작업 끝에 사용 입력과 같은 상태인지 확인하지 않는다.

독립 메모리 반례는 새 stamp를 손상시키지 않았다. on CSV 50/100의 해시 검사를 통과시킨 직후, `load()`가 CSV를 텍스트로 여는 시점에 on 통과를 100/100으로 바꿨다.

**실제 결과: `legacy_stamps=0`, `auth_fail=[]`, 유효 실행 2개, on 통과율 1.0, 차이 +50%p.** 즉 새 형식으로 인증됐다고 보고하면서 다른 바이트의 숫자를 낸다. 이 반례는 작업자가 원자료를 동시에 갱신하는 상황을 메모리로 만든 것이며, 실제 운영에서 이미 그런 변경이 일어났다는 주장과 다르다.

16c:2.2의 “읽는 동안 변경되면 보류”가 아직 구현되지 않았다. 가장 분명한 해결은 한 번 확보한 불변 바이트를 해시 검사하고 **그 바이트를 파싱**하는 것이다. 큰 trajectory는 변경 불가 스냅숏/파일 소유권과 읽기 전후 확인을 묶는 방법도 있다. 적어도 입력 로그·stamp·사용 원자료의 manifest를 함께 기록하고, 읽기 일관성을 확보하지 못하면 해당 집계를 보류해야 한다. 두 로그 해시만 같은 것은 실행 파일 전체가 같은 스냅숏이라는 증거가 아니다.

### 3.3 P2 · 추가 seed의 MAE 결측 상세가 최종 JSON에서 사라진다

**근거: C:250~253은 `short`를 만들지만, C:263~267의 `mae_status()`와 404~408의 재측정 행은 축 이름·상태만 남긴다.** 원 `p5['mae']`를 최종 행에 보존하지 않는다.

`wave/fwd03/on`을 seed1000에서 −10%p로 선별하고 1001~1004를 채웠다. on seed1003의 vx만 1개 finite, 나머지 99개 NaN으로 했다.

- `compare()` 안에는 `short=[{arm:on24000, seed:1003, finite:1}]`가 있음.
- 최종 JSON에는 해당 정보가 없고, 이 fixture 전체 JSON에 `short` 키 자체가 없음.
- 페이지에는 500판·「vx MAE 결측」·「미확인」이 정확히 보임.

따라서 **판정은 고쳐졌으나 “군·시드·finite n 목록을 남긴다”는 의뢰 설명은 모든 경로에서 맞지 않는다.** 재측정 행에 결측 상세를 보존하면 된다. 이 누락 때문에 결측을 충족으로 판정하는 것은 아니므로 3.1·3.2와 같은 심각도로 취급하지 않는다.

## 6. 제공 시험의 평가와 최소 수정 범위

`test_post_v6.out`의 38 PASS·`FAILS []`, 변이 4건 검출 기록은 읽었다. 제공 스크립트는 임시 파일을 만들므로 그대로 재실행하지 않고 위 메모리 시험으로 변경 부분을 독립 확인했다. **제공된 38건 전부를 독립 재실행해 통과했다고 보고하지 않는다.**

개선된 점은 인정한다. 올바른 cell, 주 통과 열과 반대인 보조 열, 실제 stamp 형식, 부분 결측, 경계, 페이지 함수 시험이 추가됐다. 다만 다음은 아직 약하다.

- `test_post_v6.py:202~206`의 legacy 시험은 `Fake.go()`가 만드는 **v3.5 로그에 버전 정보 없는 stamp**를 넣고 무조건 수용을 정답으로 둔다. 구형에서 이관한 근거를 검증하지 않고, 3.1의 모호한 호환 동작을 그대로 인정한다.
- F1은 두 로그의 전후 해시를 확인하도록 개선됐지만 stamp와 원자료 동일성은 확인하지 않는다. 두 후처리가 같은 숫자를 내더라도 그동안 입력 파일 전체가 불변이었다는 증거는 아니다. 3.2의 변경 시점 시험이 필요하다.
- C9의 이름에 「short list」가 있지만 assert는 축 이름과 overall뿐이다. 최종 JSON에 arm·seed·finite n이 남는지는 보지 않는다. 특히 추가 seed의 결측이 빠졌다.
- G2는 「100 판」과 「수집 중」이 있는지만 보고 요약의 「다 재진」은 검사하지 않는다. G4도 「판)」의 존재와 옛 고정 문구의 부재만 보며 값과 분모의 대응을 검증하지 않는다. 이번에는 독립 fixture로 실제 n을 확인했다.
- G5는 HTML 전체 행 수가 off 측정 칸 수 이상이면 통과한다. on 쪽 누락이나 중복 행이 있어도 통과할 수 있다. 군·cell별 집합과 각각의 k/n을 비교해야 한다. 이번 실자료에서 74행이 나왔다는 사실이 약한 assert를 강하게 만들지는 않는다.
- G는 F만 부르고 H와 결합하지 않는다. 그 때문에 H:52의 옛 라벨과 H:11의 고정 상태 문구가 남았다. 변이 4건은 검사한 고장에 대한 감도이지, 이 경로들을 검증했다는 근거가 아니다.

24,000 공개 전 최소 대응은 네 가지다. 모호한 legacy 격하를 거부하고 기존 legacy의 출처와 검증 상태를 구분할 것, 인증한 입력과 집계 입력을 고정할 것, 추가 seed의 결측 상세를 보존할 것, 4절 문구를 고칠 것. 수정 뒤에는 이 경로만 재확인하면 되며 Tango와 목표 결합 규칙을 처음부터 다시 만들 필요는 없다. GPU 재평가를 요구하거나 승인하는 문서가 아니다.
