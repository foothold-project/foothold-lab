**현재 실제 stand의 대체 근거는 확인했다. 그러나 이번 네 도구를 모두 검증 완료로 선언할 수는 없다.** 특히 고정 묶음 비교는 통과하면 안 되는 숫자 변경과 행 누락을 여전히 통과시킨다. 해제 기록은 실제 stamp·소유 기록과 연결되었지만, 그것이 보류한 실행을 대체할 새 수집이라는 검사까지 끝난 것은 아니다.

## 3. P1 · compare_frozen은 계약 요약과 보류 행의 잘못을 통과시킨다

근거: compare_frozen.py 35~46·53~68·73~79·89~97줄.

| on24000 계약 unmeasured에서 stand만 삭제 | 종료 0·pass=True | 제외했다는 셀이 미측정 목록에서도 사라진다 |
| 일반 cells의 flat/stand/on 행 전체 삭제 | 종료 0·pass=True | 같은 행의 off 등 비보류 모델 정보까지 사라진다 |

| v8 regression에 보류 stand의 v7 행을 다시 삽입 | 종료 0·pass=True | 비교 대상에서 보류 행을 양쪽 모두 제거해 재등장을 놓친다 |

추가로 /가 든 예상 밖 최상위 키도 unexplained에는 나오지만 종료 0이다. 95줄이 차이 경로에 /가 있는지를 보고 최상위 차이 여부를 대신 판정하기 때문이다. 주된 문제는 이 특수 키보다 위 표의 실제 페이지용 필드다.

원인은 구체적이다.

- 계약 비교는 .cells만 검사한다. n_cells, planned, unmeasured, surv_below, pass_below는 검사를 건너뛴다.
- 일반 cells는 보류 행의 비교에서 if eb and ea != eb를 쓴다. 행 전체가 없으면 eb가 빈 dict라 실패하지 않는다.
- completion은 값이 같으면 허용한다. 이번처럼 정확히 하나를 제거해야 하는 경우도 “같음”으로 통과한다.
- regression은 보류 행을 양쪽에서 빼므로, v8에 그 행이 잘못 남아 있어도 보지 않는다.

**최소 수정:** 태그에서 보류 모델·갈래·칸·noise·seed를 유지한 채 v8에서 기대하는 키와 값을 만들어 비교해야 한다. 이번 stand 한 건에서는 다음이 결정적이다.

1. off 계약 전체는 동일. on 계약의 셀 수·미측정·미달 목록 변화도 해당 한 칸에서만 파생되어야 한다.
2. 일반 cells에서 on24000과 해당 파생 비교만 제거하고 다른 모델은 그대로 남는다. 행 전체 소실은 실패다.
3. completion은 해당 한 칸만 정확히 1 감소한다. regression 보류 행은 v8에 존재하면 실패다.
4. 설명하지 못한 차이가 하나라도 있으면 최종 pass=False다. 문자열 모양으로 무시하지 않는다.

다른 seed 일부만 보류된 경우에 집계 행 전체를 삭제하는 규칙으로 확장하면 안 된다. 그 경우는 남은 입력으로 n과 파생값을 계산해야 한다. 이번 검증은 실제 stand 한 건에 대한 반례이므로 다른 경우 전체를 시험했다고 주장하지 않는다.

제출 C1~C6은 의미 있는 회귀 시험이다. 하지만 **대표 오류 몇 개가 막혔다고 전체 차이 분류기가 검증된 것은 아니다.** 계약 요약, 행 통째 누락, 보류 행 재등장에 대한 음성 시험이 없었다.

## 4. 질문 2 · L5c는 좋아졌으나 “새 수집으로 해제” 검사는 미완료

근거: cmdr_post_v8.py 312~347줄, test_post_v8.py 416~434줄.

L5c는 이제 CSV 값을 바꾸고, 새 출력 해시·새 stamp·새 소유 기록·해제 attempt를 함께 만든다. 이전처럼 release 문구만 넣고 기대값을 통과시키는 시험에서는 벗어났다. 또한 새 출력의 **내용이 옛것과 달라야만 한다는 조건은 필요 없다.** 실제 정상 재측정도 결정론적이면 같은 출력일 수 있다.

직접 실행한 집계 경로의 결과:

**P1의 정확한 범위:** “현재 파일이 인증된 로그와 맞는다”는 연결은 생겼다. “보류한 실행과 다른, 확인한 새 수집을 해제했다”는 연결은 아직 약하다. 320줄은 동일한 기존 실행의 attempt를 쓰는 것만으로도 만족한다. auth는 현재 바이트와 기록의 일관성을 보지만, 해당 실행의 보류 사유를 해소하지는 않는다.

같은 ID 아래 출력을 새로 서명한 마지막 반례는 현재 드라이버에서 실제로 일어났다는 주장이 아니다. **해제 기록이 승인한 수집 바이트에 고정되어 있지 않다는 한계**를 분리해서 보여준다. v3.7이 ID를 재사용하지 않는 운영 가정을 신뢰한다면 위험이 줄지만, 앞의 “보류 원본 자체를 해제” 반례는 그 가정으로 막히지 않는다.

권고하는 최소 연결:

- 해제에 by, why, 승인한 collection attempt, 네 출력 해시, pins·checkpoint identity, 정상 새 측정 증거의 해시를 둔다. 예를 들어 보존한 비교 결과와 reused=False 수집 기록을 해제 근거로 연결한다.
- “재측정으로 대체”라면 보류 원본과 다른 수집임을 확인한다. 내용 차이가 아니라 collection identity와 그 근거로 구별한다.
- 보류 원본을 직접 검토해 사유를 철회하는 별도 정책을 허용하려면 그 사유와 승인 유형을 명시한다. 이를 새 측정이라고 기록하지 않는다.
- 이후 재사용에서는 현재 rec가 reused=True라는 이유만으로 다시 보류하지 않는다. 이미 승인한 최초 수집 증거와 출력 identity가 그대로 유지되는지 확인한다. 현재 stamp 해시 하나만 고정하면 정상 재검사 때 stamp가 바뀌는 문제와 충돌한다.

**현재 실제 stand를 반려하는 결론은 아니다.** 2.1의 직접 확인과 보존된 실제 새 수집 기록이 이번에는 부족한 자동 검사를 보충한다. 향후 자동 보증이 충분하다는 주장만 반려한다.

문구도 하나 바로잡아야 한다. 의뢰서의 “인증 실패면 보류 유지·release_rejected”는 그대로 구현되어 있지 않다. 일치하는 해제 ID가 auth에서 실패하면 실행은 제외되고 auth_fail에 들어가지만, held와 release_rejected에는 남지 않는다. 데이터가 포함되는 결함은 아니지만, 보류·실패 현황을 설명할 때 둘을 함께 세어야 한다.

## 5. 질문 3 · 앞뒤 해시의 한계와 base_view

**“원자적 스냅숏이 아니다. 변경 후 원복하면 못 본다”는 설명은 맞다. 다만 그 문장만으로 결과를 무조건 유효하게 만들 수는 없다.**

독립 시험에서 대상 외 tag 추가는 종료 0, 대상 마지막 기록 변경은 종료 3이었다. 현재 비교가 실제로 읽는 의존성은 대상의 마지막 record·matrix·pair_fail, pins, 해당 model checkpoint다. 이를 base_view로 재검사하는 것은 타당하다. 다른 tag가 끝날 때마다 전체 base 로그 바이트가 바뀐다는 이유만으로 stand를 영구 보류할 필요는 없다.

한계와 사용 조건은 다음과 같다.

- 여러 파일을 서로 다른 시각에 읽는다. 읽은 순간의 내용과 해시 시점 사이에 바뀌었다가 되돌아오는 경우는 배제하지 못한다.
- 마지막 검사 직후의 변경은 검출하지 않는다.
- 파일이 사라지거나 JSON이 쓰다 만 상태면 “not ready”가 아니라 예외로 끝나는 경로도 있다. 성공으로 오인하면 안 된다.
- 미래에 비교 조건을 추가하면 base_view에도 그 의존성을 함께 추가해야 한다.
- 종료 3에서도 이전에 계산한 ready·equal 값이 JSON에 남을 수 있다. 실제 대상 기록 변경 시험에서는 ready=True가 남았다. **호출자는 종료 0과 result를 먼저 확인해야 한다.** 종료 3의 ready=True를 승인으로 쓰면 안 된다.

실무상 보장할 수 있는 표현은 “비교에 사용한 파일·대상 기록의 앞뒤 변경 검사에서 차이를 찾지 못했다”다. 원자성을 보장한다고 쓰면 틀리다. 20:00 이후 작성자가 멈춘 고정 묶음에서 다시 수행하고 사용 바이트 해시를 결과와 연결하면 현재 목적에는 충분히 현실적이다.

## 6. 질문 4 · scans.json은 개선이지만 원래 판별을 완전히 재현하지 못한다

근거: handover_1400.py 85~119·125~137·213~219줄.

임시 파일 시험에서 스캔 두 번이 저장되고 manifest의 scans_sha256이 실제 파일과 맞는 것까지 확인했다. 실제 운영 동결에 새 코드가 사용된 것은 아직 미확인이다. 14:00 때 없었던 원문을 사후에 복구한 것도 아니다.

**인자 값을 버리는 방향은 타당하다. 하지만 현재 변환은 판별에 필요한 의미도 바꾸거나 지운다.** 원 함수 alive_in을 합성 스냅숏에 적용한 결과와, 저장된 python_kit 행의 argv를 다시 cmdline으로 바꿔 적용한 결과를 비교했다.

| 합성 입력 | 원래 판별 → 저장 기록 재판별 |
|---|---|
| python.exe q_eval_cmdr.py --headless | 차단 → 차단 |
| cmdline=None | 읽을 수 없는 argv로 차단 → 동일 |
| cmdline=[] | 빈 argv로 차단 → 동일 |
| 확장자 없는 cmdr_eval_driver_v37 | 스크립트 접두로 차단 → 누락 |
| 실행 인자가 ["python"] | 차단 사유 없음 → 빈 argv로 오인 |
| 안전한 스크립트와 --headless=false | 정확한 토큰 --headless 없음 → 저장 때 --headless로 바뀌어 차단 |
| old PID → 비python 중간 프로세스 → 안전한 이름의 python 자식 | 원래는 자손 검출 → 비python 행이 없어 계보 복원 실패 |

첫 셋처럼 현재 일반적인 Windows .exe·.py 실행을 재판별하는 데는 도움이 된다. 그러나 **“이 기록으로 원래 규칙을 다시 적용할 수 있다”는 일반 주장은 틀리다.** old PID와 자손 검사도 판별의 일부인데, 비python 프로세스를 개수로만 보존해서는 그 부분을 독립 재현할 수 없다. 원래의 alive 결과를 함께 저장하는 것은 당시 함수의 결론을 보존하는 것이며, 근거를 독립 재확인하는 것과 다르다.

또한 “값은 남기지 않는다”는 보장도 완전하지 않다. scan_record의 argv는 필터링하지만 alive는 그대로 저장한다. alive_in 116줄은 첫 세 인자를 basename 처리해 문자열로 넣는다. **합성 옵션값을 두 번째 인자에 둔 시험에서 그 값이 scans.json의 alive에 남는 것을 확인했다.** 실제 비밀값이나 운영 argv를 읽어 출력하지는 않았다.

최소 수정 제안:

- 원래 cmdline의 읽기 가능 여부·빈 목록 여부를 별도 필드로 남긴다.
- --headless의 정확한 토큰 존재 여부, 매칭한 스크립트 basename과 규칙을 보존한다. --headless=false를 같은 증거로 만들지 않는다.
- 모든 프로세스의 pid·ppid·필요한 생성 시각을 남기고, python·kit에는 위 판별 근거를 덧붙인다. 실행 인자 전체를 보존할 필요는 없다.
- 자기 프로세스 제외를 재현할 수 있도록 스캔 실행 PID와 규칙 코드 해시도 명확히 연결한다.
- alive도 안전한 reason·pid·매칭 규칙으로 구조화하고 임의 인자 문자열을 넣지 않는다.
- 스캔 시작·종료 시각을 남겨 수집 구간을 표현한다. 두 번의 스캔은 그 사이 작성자가 한 번도 없었다는 연속 증명이 아니다.

H9는 저장 유무·해시·보통 인자값 삭제에 대한 유효한 시험이다. 하지만 원래 판별과 저장 기록의 판별 동치, 비python 계보, alive 경유 값 유출까지 확인한 시험은 아니다.
