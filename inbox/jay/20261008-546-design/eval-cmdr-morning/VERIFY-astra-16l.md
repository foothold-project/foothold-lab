## 3. 해제: 무엇이 막혔고 무엇이 남았나

### 3.1 P1 · 재검사 시 collection attempt가 바뀐다는 설명은 틀렸다

근거: `code/cmdr_eval_driver_v37.py:1224,1230,1241,1247,1265`, `code/cmdr_post_v9.py:340`, `code/test_post_v9.py:460`.

실제 v3.7은 재사용 갈래에서 다음처럼 처리한다.

```python
attempt = prev.get("attempt", "v3.2 or earlier")  # 기존 수집 ID 유지
# 새 평가를 실행하는 갈래에서만 ATTEMPT-jN을 만든다.
rec["attempt"] = attempt
# stamp에도 같은 attempt. 검사를 수행한 인스턴스는 revalidated_by로 구분한다.
```

분리한 실제 함수의 직접 결과:

| 이전 stamp | 현재 기록·stamp의 attempt | revalidated_by | 새 평가 횟수 |
|---|---|---|---|
| APPROVED-NEW-j1 | APPROVED-NEW-j1 | NEXT-OWNER | 0 |
| attempt가 없는 구형 stamp | v3.2 or earlier | NEXT-OWNER | 0 |

따라서 **정상 재검사를 보존하려고 collection attempt 불일치를 허용할 필요가 없다.** 정상 재검사는 attempt가 같고 stamp 해시만 바뀐다. 의뢰문 2절, v9의 341~342줄 주석, L5g의 전제가 모두 잘못됐다.

L5g는 스스로 stamp와 기록을 `LATER-j1`로 바꾸고 그것이 통과해야 한다고 기대한다. 실제 드라이버의 동작을 재현한 시험이 아니라, 잘못 추가한 예외에 맞춘 시험이다. 이 PASS는 정상성 근거가 아니다.

### 3.2 독립 재현

합성 실행 하나에 정상 네 출력, stamp, 소유 로그, 원본 stamp 사본, 전체 해제 기록과 증거를 구성했다. 표의 수는 `n_valid_runs / held / hold_released`다.

| 입력 | 실제 결과 | 판단 |
|---|---|---|
| 승인한 새 수집·현재 attempt·출력·증거 모두 일치 | 1 / 0 / 1 | 정상 |
| 승인 수집을 실제 v3.7 방식으로 재검사, 승인 attempt 유지 | 1 / 0 / 1 | 정상. 다른 attempt 예외 없이도 가능 |
| 보류 stamp를 그대로 두고 그 기존 attempt로 완전한 해제 기록 작성 | 0 / 1 / 0 | 16k의 직접 반례 차단 |
| 출력·증거 없는 이전 형식의 해제 | 0 / 1 / 0 | 차단 |
| 승인 ID 유지, 출력 변경 후 stamp·기록까지 새 해시로 다시 서명 | 0 / 1 / 0 | 차단 |
| **보류 원본 재검사: 현재 기록·stamp=HELD-OLD-j1, 해제·증거=APPROVED-NEW-j1, 네 출력은 같음** | **1 / 0 / 1** | 잘못 포함 |
| 구형 보류 원본을 재검사해 현재 attempt=v3.2 or earlier, 해제는 새 ID | 1 / 0 / 1 | 같은 결함 |
| 다른 attempt와 `prev_stamp_sha256="not-a-real-hash"`, reused=True | 1 / 0 / 1 | 연결 사슬 검증이 아니라 참인 문자열만 검사 |
| 승인과 출력은 일치하지만 pins 인증 실패 | 0 / 0 / 0, auth_fail=1·release_auth_fail=1 | 제외와 공개 실패 목록 수정 확인 |

핵심 반례의 구성은 다음과 같다.

1. 보류 stamp 사본의 attempt를 OLD로 두고 그 해시를 hold에 연결한다.
2. 해제와 해시가 맞는 증거는 NEW를 가리킨다. 두 수집의 출력 바이트는 같은 것으로 둔다.
3. 현재 stamp는 OLD를 유지하며 `revalidated_by=NEXT`, `prev_stamp_sha256=보류 원본의 실제 해시`를 추가한다.
4. 소유 기록도 OLD·reused=True·동일 출력 해시로 둔다.
5. v9는 현재 포함한 `inputs_manifest.stamp_attempt=OLD`와 `hold_released.released.new_attempt=NEW`를 동시에 출력한다. auth_fail은 없다.

340~345줄 예외가 이를 허용하고, 350줄은 보류 원본의 attempt를 **현재 attempt가 아니라 rel.new_attempt와** 비교한다. stamp 자체의 바이트도 재검사로 달라졌으므로 원본 stamp 해시 비교로는 막지 못한다.

**최소 수정:** 현재 stamp·소유 기록의 collection attempt를 승인한 new_attempt와 정확히 같게 요구한다. 재검사자는 revalidated_by로만 구분한다. 정상 재검사에서 stamp 해시 변경은 허용하되 출력 네 해시와 승인 수집 ID는 유지한다. 구형 수집에는 새 측정으로 얻은 ID와 증거가 있어야 한다. 보류 원본을 직접 승인하는 별도 정책을 새 수집 해제와 섞지 않는다.

### 3.3 P1 · 해시를 검사한 증거와 판정에 쓴 증거가 다를 수 있다

근거: `code/cmdr_post_v9.py:319,346,352,355` 및 파일 끝의 입력 재검사.

증거를 `_sha_file()`로 읽어 해시를 검사한 뒤, 다시 `json.load(open(...))`로 읽는다. 보류 원본 stamp도 같은 이중 읽기다. 집계 끝에는 로그·sidecar·hold 등을 확인하지만, 이 두 의존 파일은 재검사하지 않는다.

직접 구성한 반례:

- 해제에 등록된 증거 A는 `comparison_ready=False`.
- 해시 읽기는 A를 반환한다. 다음 JSON 읽기 전에 같은 경로의 내용을 ready=True인 B로 바꾼다.
- 해제의 evidence_sha256은 계속 A의 해시다.
- 결과: **유효 1·보류 0·해제 1**. 집계 종료 때 B의 실제 해시는 승인 해시와 다른데도 실패하지 않는다.

메모리 파일시스템에서 두 읽기 사이의 변경을 결정적으로 주입했다. 실제 운영 파일을 바꾸지 않았다. 이미 바뀐 증거를 읽기 시작하는 경우는 제대로 보류됐으므로, 제출 L5h의 성공과 모순되지 않는다. L5h는 이 두 읽기 사이를 시험하지 않았다.

**수정:** 파일 하나에서 읽은 바이트 하나로 해시 계산과 JSON 해석을 모두 수행한다. 동결 입력으로서의 안정성까지 주장하려면 두 의존 파일도 시작·끝 검사와 manifest에 넣는다. 시작·끝 검사는 잠금이나 원자적 스냅숏과 같지 않다는 한계는 유지한다.

### 3.4 P1 · 명시한 보류 파일이 없으면 조용히 보류가 사라진다

근거: `code/cmdr_post_v9.py:312~314`.

정상 기본 목록에 해제되지 않은 보류 한 건을 두면 0 / 1 / 0이었다. 동일 입력에 `CMDR_POST_HOLD=<존재하지 않는 H-TYPO>/cmdr_post_hold.json`만 지정하면 **1 / 0 / 0**, auth_fail=0이었다. 끝 검사도 없는 파일과 없는 파일을 같다고 보므로 중단하지 않는다.

새 옵션은 바로 마감 후 동결 목록을 고르는 운영 경로다. 오타·복사 누락을 “보류 없음”으로 처리하면 안 된다.

**수정:** CMDR_POST_HOLD를 명시했다면 파일 존재·읽기·객체 형식·예정된 해시를 요구한다. 실패하면 집계 파일을 쓰기 전에 중단한다. 보류가 0인 경우도 명시적으로 동결한 `{}`와 “파일 없음”을 구분한다.

## 4. 고정 비교 · 정확 비교는 수정 확인, 필터 기준의 출처는 별도 관문

근거: `code/compare_frozen.py:21~33,54~66`.

16k에서 통과했던 다음 변형을 각각 넣어 모두 종료 1·pass=False를 확인했다: off 계약 n_cells=999, pass_below 비움, on unmeasured의 stand 삭제, flat/stand/on cells 행 전체 삭제, on/flat completion을 10에서 11로 복원, 보류 regression 행 재등장. 예상 밖 / 키도 실패했다. 정상 같은 표는 종료 0, 보류는 있는데 세 번째 기준이 없으면 종료 2다.

이 접근은 내가 16k에서 제안했던 복잡한 차이 추정보다 낫다. 임의로 “설명 가능한 차이”를 확대하는 대신 같은 입력에서 재계산한 기준을 요구한다.

다만 **도구는 세 번째 JSON이 실제로 해당 보류 실행만 제외한 v7 재계산인지 증명하지 않는다.** n_valid_runs의 수와 표의 일치만 본다. C21도 v7을 실제로 다시 계산한 통합 시험이 아니라 구성한 정답 JSON의 비교 시험이다.

- 다음 동결에서 보류 0이면 같은 manifest·입력의 v7/v9 정확 대조를 사용한다.
- 보류가 남으면 종료 2를 유지한다. v9를 복사해 기준처럼 꾸미거나 표의 숫자를 수작업으로 맞추지 않는다.
- 보류를 정확히 제외한 v7 재계산이 준비되면 코드 해시·명령·입력 manifest·제외 tag·출력 해시를 함께 남긴다. “손으로 처리”는 이 입력 구성과 재실행을 뜻해야 한다.
- BOOK으로 뺀 입력·출처 필드가 같음을 이 비교가 보증하지 않는다. 같은 동결 자료를 사용했다는 확인과 held·release_auth_fail 현황 검사는 따로 필요하다.

### 5.1 스캔 수정은 이번 지적 범위에서 충분하다

근거: `code/handover_1400.py:89~154`.

정상 headless, 읽을 수 없는 argv, 빈 argv, 확장자 없는 드라이버, 실행 파일 토큰만 있는 python, --headless=false, 비 Python 부모를 거친 자손, 합성 비밀값을 포함한 argv의 8개 입력을 직접 검사했다. 기대한 판정과 모두 일치했고 JSON 왕복 뒤 저장한 사실만으로 같은 판정이 나왔다. 합성 값은 alive를 포함한 전체 기록 어디에도 없었다.

rejudge_equal은 같은 함수를 다시 호출한 것이므로 독립 정답 증명은 아니다. 하지만 저장 단계에서 판별 정보가 사라지는 16k 문제를 점검하는 용도로는 맞다. 제출 H10과 독립 정답 시험이 판별 의미를 보충한다.

의뢰문의 “모든 프로세스 create_time”은 필드가 있다는 뜻으로만 맞다. 실제 snapshot은 Python·kit 외 프로세스에는 None을 넣는다. 모든 프로세스의 생성 시각을 측정했다고 쓰면 틀리다. 이번 재검은 기존 판별 규칙의 적정성 전체가 아니라 저장·재판별 손실에 한정했다.

### 5.2 보류 목록 복사는 필요하지만 그것만으로 입력 동결은 끝나지 않는다

근거: `code/handover_1400.py:177~179,223`, `code/cmdr_post_v9.py:346,352`.

기존 목록의 복사·끝 해시 비교는 제출 H11/H11b 재실행에서 확인했다. 그러나 처음 없던 목록이 복사 단계 뒤 생기면 기록 대상 자체에 없다. 제출 시험의 가짜 트리를 만든 뒤 HANDOVER_TEST_TOUCH로 이 경우만 추가했다.

명령 형태: `python -`에서 test_handover.py의 fixture 함수만 불러, 임시 HANDOVER_EV와 가짜 프로세스를 사용해 handover_1400.py를 실행. 임시 위치: `%TEMP%/astra16l_hold_wl7lvjao/`.

결과는 **종료 0·complete·problems=[]**, 원본 위치에는 새 hold 파일이 있지만 manifest와 동결 사본에는 없었다. 이 시험에서 새 파일은 공백 한 바이트이며, 의도는 유효한 새 보류의 의미가 아니라 **부재→존재 변경을 아예 검사하지 않는 것**을 보이는 데 있다. 현재 운영 목록은 이미 존재하므로 이번 운영에서 이 조건이 생겼다고 주장하지 않는다.

필수 입력의 부재도 시작 상태에 기록하고 끝에 비교해야 한다. 현재 운영에서는 3.4의 명시 경로 필수 검사와 인계의 hold 사본 필수 확인을 먼저 적용하면 된다.

### 5.3 증거를 작업 트리 절대 경로에만 묶으면 동결 묶음은 독립적이지 않다

현재 증거의 해시 연결은 유효하다. 절대 경로 자체가 파일의 진위를 훼손하는 것은 아니다. 하지만 작업 트리를 옮기거나 정리하면 같은 동결 묶음으로 재현할 수 없다. shared checkout에서 새 증거로 덮여도 의존성이 바뀐다.

최소한 다음을 함께 보존해야 한다.

- 승인한 증거 JSON의 **바이트 그대로인 사본**, 원 경로, SHA-256.
- 보류 원본 stamp 사본과 그 SHA-256. 현재 release_check는 이를 OUT/<과거 handover>/stamps에서 별도로 찾는다.
- 증거가 인용한 이전 인계 manifest·보존된 원자료의 위치와 해시 연결.
- 원본 hold 바이트와 해시. 묶음 안 경로로 바꾼 별도 입력이 필요하면 원본을 덮지 말고 파생본 및 경로 변환 기록으로 구분한다.

가급적 묶음 루트 기준 상대 경로나 해시로 참조한다. 집계가 실제로 이 사본을 읽어야 하며, 복사만 해 놓고 여전히 작업 트리 경로를 읽으면 목적을 달성하지 못한다. 현 코드는 CMDR_POST_HOLD만 바꿔도 evidence 및 과거 stamp 의존성이 자동으로 새 인계 폴더에 옮겨지는 구조가 아니다.

새 compare_stand 결과는 승인 증거를 덮지 말고 추가 관찰로 저장한다. 원 증거 사본의 바이트 해시 일치와 새 비교의 수집 ID·출력 네 해시·준비 상태 일치를 따로 검사한다. 정상 재검사로 현재 기록이 reused=True가 되면, 신선한 수집만 요구하는 compare_stand가 not ready를 낼 수 있다. 이것을 승인된 수집의 출력 변화로 오해하거나 원 증거를 새 결과로 덮지 않는다.

### 6.1 이번 실제 stand의 대체 근거는 유지된다

15:49~15:55 읽기 전용 확인:

### 6.2 마감 뒤 순서에서 보완할 관문

lead의 “시각 대신 실제 종료 → 동결 → 대조 → 페이지 → 다음 작업” 순서는 맞다. 다음을 채워야 한다.

1. 두 드라이버 END·PID·자손 종료를 확인하고 동결 중 새 writer가 들어오지 않게 운영한다. 스캔이 시작·끝 두 시점이라는 사실과, 코드 잠금으로 전체 구간을 배타화한 것이 아니라는 한계를 기록한다. ASTRA가 운영 프로세스를 종료하지 않는다.
2. 동결의 complete·problems=[]에 더해 hold 사본이 반드시 존재하고 원본·manifest와 같은지 확인한다. 증거와 보류 원본 stamp까지 5.3의 연결로 보존한다. 새로운 보류 파일 등장·의존 파일 변경도 실패여야 한다.
3. **3.1·3.3·3.4를 수정한 집계 판**으로 같은 동결 입력을 읽는다. 이번 실제 stand는 승인 수집 ID와 네 출력 해시가 같아야 한다. held=0만 보지 말고 auth_fail·release_auth_fail·예상 release tag가 inputs_manifest에 존재하는지 함께 확인한다.
4. 같은 입력을 사용한 v7과 수정 판을 정확 비교한다. 보류 0이면 두 인자, 보류가 남으면 실제 필터 재계산 없이는 종료 2 유지. 성공을 위해 표를 손으로 맞추지 않는다.
5. 승인 증거를 보존한 상태로 stand를 재대조한다. 새 결과가 종료 0이어도 수집 ID와 네 해시를 승인 기록·동결 manifest에 연결한다. 비교 결과의 내용 동등성, 증거 파일의 바이트 동등성, 새 수집 인증을 한 문장으로 합치지 않는다.
6. 페이지는 그 집계 출력 한 판만 읽게 하고, 코드·manifest·scans·로그·sidecar·hold·증거·출력·페이지 입력·조립 HTML·게시 판의 연결을 남긴다. 현재 schema 문자열만 맞는 것으로 데이터의 올바름이 보장되지는 않는다.
7. 이 검증이 끝나기 전에 기존 out을 새 작업이 덮지 않게 한다. 자료를 독립 보존했는지 확인한 뒤 팀장 결정에 따라 다음 GPU 작업으로 넘어간다.

**질문별 답:** 16k의 정확 비교·스캔 반례는 막혔다. 해제는 직접 반례 일부만 막혔고 재검사 예외가 새 구멍이다. 작업 트리 절대 경로의 증거는 현재 유효하지만 동결 사본과 실제 읽기 경로가 필요하다. 위 세 P1과 동결 입력의 완전성 확인이 빠진 마감 관문이다.

운영 원자료·드라이버·stop·상태 파일 수정, GPU·Isaac·학습·평가 실행, 프로세스 종료, 커밋·push를 하지 않았다.
