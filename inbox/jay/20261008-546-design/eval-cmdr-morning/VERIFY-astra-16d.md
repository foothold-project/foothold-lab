# ASTRA 16d · 수집 드라이버 v3.5 확인 검증

**고칠 것: `code/cmdr_eval_driver_v35.py` · 잠금을 얻지 못한 remeasure가 기존 로그를 덮는다. 같은 버전의 옛 완료 기록과 새 실행을 구분하지 못한다. 작업을 큐에서 꺼낸 뒤 예외가 나면 그 작업과 재시도 이력이 종료 기록에서 사라진다.**

lead의 “16b에서 기동 전에 고치라고 한 셋과 3절 제한을 고쳤다”는 포괄적인 결론은 틀렸다. 일부 수정은 실제로 작동한다. 그러나 공통 종료 처리에서 새 결함이 생겼고, 16b의 동일 버전 재기동 문제는 남았다. 이는 실제 GPU 결과가 틀렸다는 판정이 아니라, 수집 절차가 신뢰할 수 있는 완료·중단 기록을 보장하지 못한다는 판정이다.

## 1. 검증 대상과 실제 대기 상태

## 2. 수집 관문을 막는 결함

### 2.1 P1 · 기동을 거부한 remeasure가 남의 로그를 덮는다

**근거: 160, 163~171, 760~769, 988~1016줄.** `PUBLISH`가 remeasure에서는 잠금 취득 전부터 참이다. `start()`가 로그 충돌이나 잠금 실패로 `SystemExit(6)`을 내면, `main()`은 `exit_record()`를 호출하고 이것이 소유권 없이 `save()`를 실행한다.

기존 로그에 `attempt=OTHER_LIVE_WRITER`, `matrix={keep: valid}`를 둔 뒤, 실제 `main → start → exit_record → save` 경로를 세 입력으로 시험했다. 파일 I/O와 잠금·프로세스 조회만 메모리 대역이었다.

| 입력 | 실제 결과 |
|---|---|
| 같은 로그의 작성자 PID가 이미 있음 | 종료 코드 6이지만 기존 attempt와 matrix를 덮음 |
| 작성자는 보이지 않지만 `take_lock()`이 실패 | 종료 코드 6이지만 잠금 없이 기존 로그를 덮음 |
| remeasure의 `--log`와 `--base_log`가 동일 | 충돌을 거부하면서 바로 그 base 기록을 덮음 |

세 경우 모두 `LOCK=None`, 새 `matrix={}`, `stopped='exit 6'`가 저장됐다. **“중복 기동을 거부했다”는 로그만 확인하면 데이터 보호에 성공한 것으로 오판한다.** 실제로는 거부 직후 보호 대상에 쓴다.

수정 기준: 로그 소유권 취득과 재검사 완료 여부를 별도 상태로 둔다. 소유권을 얻지 못한 프로세스는 정본 로그와 공용 중단 파일에 쓰면 안 된다. 기동 거부는 stderr 또는 충돌하지 않는 attempt별 기록에 남긴다. `main()` 전체 경로에서 기존 바이트가 그대로인지 검증해야 한다. 현장에서 두 번째 드라이버를 띄워 이 반례를 시험하지 말 것.

### 2.2 P1 · 새 base가 재검사 중 죽으면 옛 v3.5 완료를 새 실행 완료로 받아들인다

**근거: 743~749, 920~924, 926, 951~955, 983, 998줄.** `base_final()`은 버전·experiment·끝 표시·작성자 부재를 보지만, 기대하는 **이번 base attempt와 입력 manifest**를 확인하지 않는다. 재검사 중 실패는 `.stopped.json`에 쓰는데 remeasure는 이를 읽지 않는다.

다음 반례를 실제 `main_remeasure()`와 선별 함수로 시험했다. 96칸 모두 seed 1000의 on/off 100판씩 유효하며 양쪽 통과 수는 같아 추가 재측정 대상은 없다.

1. 디스크에는 `version=3.5`, 올바른 experiment, `attempt=OLD_FINISHED`, `ended`와 `complete=True`를 가진 옛 기록이 있다.
2. 첫 읽기에는 새 base 작성자가 있다. 새 base는 재검사 중이라 옛 기록을 보존한다.
3. 새 base가 재검사 중 실패해 잠금을 풀고 별도 중단 기록만 남겼다고 가정한다. 두 번째 읽기의 base JSON 바이트는 여전히 옛 기록이고 작성자는 없다.

**결과: 두 번째 읽기에서 `base_seen.attempt=OLD_FINISHED`, `base_seen.final=True`, `complete=True`, 미측정 0으로 종료했다.** 새 실행이 끝났거나 그 입력을 재검사했다는 근거는 없다.

별도 입력 `[같은 완료 기록, 읽기 실패, 같은 완료 기록]`도 세 번째 읽기에서 완료됐다. 읽기 실패 때 `prev_hash`를 초기화하지 않기 때문이다. 첫 읽기에서 작성자가 살아 있어도 해시를 저장하므로, “작성자 없는 상태에서 두 번 연속 안정된 읽기”를 보장하지도 않는다. 의뢰문의 “두 번 연속”은 실제 코드보다 강한 표현이다.

초기 v3.2에서 v3.5로 넘어갈 때는 버전 조건이 옛 v3.2 완료를 막는다. 이 점은 고쳐졌다. 위 반례는 **동일 v3.5 재기동**에서 남은 결함이다. 현재 첫 전환에서도 반드시 즉시 발생한다고 과장하지 않는다.

수정 기준: 시작할 때 기대 base attempt와 입력 manifest를 합의하고, 재검사 중·실패·완료를 그 attempt의 상태로 추적한다. 이전 완료 파일은 보존하되 새 실행 완료 근거로 사용하지 않는다. 읽기 실패와 작성자 존재 시 안정 읽기 횟수를 초기화한다. 다만 “두 번 읽기”만 고쳐서는 attempt 혼동을 해결할 수 없다. 재검사 실패 뒤 오래 기다려도 옛 파일은 계속 안정적이기 때문이다.

### 2.3 P1 · 실제 실행한 작업이 중단 기록의 어느 목록에도 없다

**근거: 838~860, 885~886, 963~964, 993~994줄.** `pending.remove(pick)`을 먼저 수행하고 `process()`를 부른다. `process()`는 시도 이력을 `TRIES.pop()`으로 꺼낸 뒤, stamp 저장까지 성공해야 `runs`와 `matrix`에 작업을 넣는다.

실제 `main → main_base → process` 경로로 작업 하나 `on24000/wave/fwd03/noise on/seed 1001`을 넣었다. GPU 실행은 대역으로 성공을 반환하고 검증·해시도 정상으로 돌려주되, 실제 stamp 호출 위치에서 `RuntimeError('could not replace stamp')`를 내도록 했다. 재사용 경로는 선택되지 않게 했다.

**결과: `exit_code=1`이지만 `runs=[]`, `matrix={}`, `not_run=[]`, `not_valid=[]`, `PENDING=[]`, `TRIES={}`였다.** guard 시도를 했던 작업인데 어느 목록에도 tag가 없고 그 시도 이력도 종료 기록에서 잃었다. 원자료가 디스크에 남을 가능성과 드라이버 기록이 완전하다는 것은 다른 주장이다.

수정 기준: 큐에서 꺼내기 전에 active job의 tag·attempt·현재 단계·guard 시도를 기록한다. 작업별 기록을 안전하게 남기기 전에는 시도 이력을 제거하지 않는다. 종료 기록은 pending뿐 아니라 active/미완료 작업을 포함하고 `complete=False`를 명시한다. stamp 저장 실패를 유효 결과로 승격하라는 뜻이 아니다. “실행했지만 인증·기록 완료 전 실패”라는 상태를 보존해야 한다.

### 2.4 P2 · “읽지 못한 argv는 작성자로 친다”는 설명은 사실이 아니다

**근거: 263~280줄.** `cmdline=None`은 빈 목록으로 바뀌고 드라이버 파일명을 못 찾으므로 건너뛴다. `AccessDenied`도 생략된다. 실제 함수에 `{'pid':123, 'name':'python.exe', 'cmdline':None}`를 넣으면 작성자 목록은 `[]`였다.

반면 드라이버 파일명은 보이고 `--log`의 값만 없어 파싱에 실패하는 경우는 작성자로 잡는다. 이 두 경우를 의뢰문이 혼동했다. 표기가 달라도 같은 파일을 찾는 다섯 입력은 제대로 작동했다.

읽을 수 없는 모든 Python을 실제 작성자라고 단정할 필요는 없다. 그러나 **“작성자 없음이 확인됐다”와 “프로세스 정보가 불명”은 분리**해야 한다. 불명 상태에서 소유권을 전제로 기동하지 않는 기준이 필요하다. v3.5 OS 잠금은 개선이지만 이를 사용하지 않는 기존 v3.2의 생존 확인을 대신하지 않는다.

### 2.5 P2 · 모든 출구가 공통 종료 기록을 지난다는 주장도 과하다

**근거: 880~892, 916~918, 977~984, 1002~1017줄.** base의 정상 마감과 remeasure의 deadline break는 함수가 정상 반환하므로 `exit_record()`를 지나지 않는다. CPU 시험에서 remeasure 읽기 실패 마감은 `stopped=deadline`, `complete=False`였지만 `exit_code`는 없었다. base의 deadline 종료에는 `stopped`도 별도로 설정하지 않는다.

미완료를 성공으로 바꾸는 동일한 결함이라고 확대하지 않는다. 다만 “모든 출구에 stopped·exit_code·not_run·not_valid가 있다”는 보장은 구현과 다르다. 정상 완료·마감 미완료·예외를 구분한 종료 계약을 정하고 실제 필드를 맞춰야 한다. 2.3의 active 작업 누락과 함께 고치는 편이 맞다.

## 4. lead 시험에서 놓친 경로

제공 `test_v35.out`에는 PASS 32개와 `FAILS []`, `exit 0`이 있다. 변이 기록은 12개를 잡았다고 적고 그중 넷은 예외로 멈췄다고 구분한다. **이 기록의 존재를 확인했으며, 제공 시험 전체를 직접 32개 재실행했다는 뜻은 아니다.** 파일·임시 폴더를 만드는 시험 전체 대신 앞 절의 읽기 전용 메모리 반례를 실행했다.

- **11e는 `start()`만 부른다** (`test_v35.py:317~323`). 그래서 거부 뒤 `main()`의 예외 처리기가 원래 로그를 덮는 2.1을 못 본다. 종료 코드 6만 맞으면 통과하는 시험은 보존 요구를 검증하지 않는다.
- **7a는 `start`를 즉시 SystemExit하는 대역으로 바꾸고 base 모드만 확인한다** (`199~212줄`). remeasure의 `PUBLISH=True`와 소유권 미취득 조합이 없다.
- **7b는 큐에서 작업을 꺼내기 전 전체 `main_remeasure`를 예외 대역으로 바꾼다** (`213~226줄`). 그래서 pending에 남은 항목은 잘 기록되지만, 실제 `process()` 중간 실패로 작업이 사라지는 2.3은 못 잡는다.
- **2b는 작성자가 있던 직전 읽기를 안정 읽기 첫 회로 인정하는 결과를 기대한다.** 제공 출력 자체가 “writer alive on reads 1-3, ends on read 4”다. 새 base가 성공 종료했는지 실패했는지, old/new attempt를 구분하지 않는다. 이것은 요구사항에서 독립적인 통과 기준이 아니다.
- **9는 일시적인 stamp 실패 후 성공만 본다.** 재시도 소진·stamp 실패와 job 기록·시도 이력의 관계는 시험하지 않는다.
- 변이 12개 검출은 그 변이들에 민감하다는 근거다. 위처럼 빠진 상태 조합이나 실제 프로세스 전환을 검증했다는 근거는 아니다. 예외 검출 넷 자체를 무효라고 할 이유는 없지만 통과 범위를 넓혀 말하면 안 된다.

추가 회귀 시험의 최소 단위는 ① 소유권 거부 세 경로에서 기존 로그 바이트 보존, ② 같은 버전 새 attempt 재검사 실패 후 옛 완료 거부, ③ 실제 process의 stamp 영구 실패에서 active tag와 tries 보존, ④ 정상·마감·예외 종료 계약이다. 매번 전체 평가를 다시 돌릴 이유는 없다.

## 5. 10:55 사전 대기 기동 판단

**CPU에서 학습 종료를 기다리는 프로세스를 미리 띄우는 발상 자체는 잘못이 아니다.** 실제 관찰에서도 기다리고 있다. 그러나 “16b 6절에 따라 기동 전 조건을 충족했다”는 판단은 근거가 부족하다. 16b는 수집 결함 수정과 담당자의 인계·입력 확인을 조건으로 했고, GPU 실행 권한을 새로 부여한 문서가 아니었다. 2.1~2.3 때문에 수정 완료 전제는 아직 성립하지 않는다.

내용 검사를 추가한 `training_done()`은 옛 판보다 낫다. 하지만 고정된 tag의 결과·night 문자열·checkpoint 크기는 **현재 학습 attempt의 인계 증명**과 같지 않다. 같은 tag의 재실행에서 옛 성공 파일이 남는 경우, 별도의 attempt/시각/해시 연결이 필요하다. `<3000 MiB`와 두 번의 관찰은 자원 사용 징후를 보는 것이며 GPU 독점 예약이 아니다. 다른 작업이 이후 시작하지 않도록 담당자 수준의 소유권 조율이 필요하다.

이번 검증으로 현재 GPU 충돌이나 오염을 확인한 것은 아니다. 반대로 대기 문구만으로 이후 자동 인계와 무인 수집을 승인할 수도 없다. **책임자는 실제 평가 진입 또는 다음 작업 경계 전에 이 검증 결과를 반영해야 한다.** 실행 중 소스만 교체해 이미 뜬 프로세스가 고쳐졌다고 간주하면 안 된다. 교체가 필요하면 원자료를 보존하고 권한 있는 담당자가 프로세스와 재개 상태를 관리해야 한다. ASTRA는 프로세스를 종료하거나 실행 파일을 고치지 않았다.

## 6. 14:00 v3.2 → 새 base 전환에 빠진 확인

의뢰서의 “기존 프로세스와 자식이 끝난 뒤, 기록 사본·해시를 남기고 띄운다”는 방향은 맞다. 아래가 빠지면 안전한 전환으로 볼 수 없다.

1. **시계가 아닌 실제 종료를 확인한다.** 14:00은 작업 경계의 중단 기준이다. base PID뿐 아니라 해당 guard·q_eval 자식, 같은 tag/로그의 작성자가 모두 끝났는지 확인한다. 조회 거부는 종료 증거가 아니다. 비정상 종료면 완료로 다듬지 말고 중단 사실을 남긴다.
2. **정지한 입력 묶음을 보존한다.** v3.2 JSON 한 장만 복사하지 않는다. 실제 재사용 대상의 원자료·meta·stamp·guard 기록과 checkpoint·소스 pins의 manifest/해시를 남겨, 재검사 전후를 대조할 수 있게 한다. 실행 중 파일은 움직이거나 수정하지 않는다.
3. **운영 중 g0와 새 base의 입력이 같은지 대조한다.** `q_metrics.py`, `q_post.py` 등 수집 pins와 checkpoint 해시를 양쪽 기록에서 직접 비교한다. 별도 집계 v6 수정이 수집의 고정 입력을 바꾸면 자동으로 같은 실험이라 부를 수 없다. 수집 코드와 별도 판정 코드의 경계를 지킨다.
4. **기동 전 소유권과 새로운 attempt를 연결한다.** 2.1을 고친 새 실행이 base 로그 잠금을 얻고, 이번 attempt의 재검사 중 상태를 명시한 뒤 remeasure가 그 attempt를 기다리게 한다. 옛 완료 파일을 보존하면서도 실패·완료 상태는 새 attempt와 연결해야 한다. 로그 사본만으로 2.2를 막을 수 없다.
5. **재사용은 파일 존재가 아니라 재검사 결과로 결정한다.** 새 base가 실제로 재검사한 matrix, 누락·철회된 칸, 실패한 stamp를 확인한다. 이미 g0가 수집한 추가 seed 원자료는 보존하되, 현재 base 입력과 일치하는 것만 유효하게 연결한다.
6. **checkpoint와 GPU 인계는 별도 확인한다.** 학습 결과 내용, 이번 night 실행의 정상 종료, checkpoint 쓰기 종료·안정된 해시·bundle 일치, 실제 소유 프로세스를 확인한다. 결과 JSON이 생겼다는 것 또는 메모리 숫자 하나만으로는 부족하다.
7. **최종 상태의 누락이 없어야 한다.** base 현재 96칸 선별과 추가 seed 작업 목록, active/pending/invalid, 마지막 정상 base 해시·attempt를 남긴다. 마감이면 미완료로 끝내며, 20:00이라는 시각을 이유로 실행 중 평가를 강제 종료하는 절차로 바꾸지 않는다.

따라서 현 시점의 결론은 **수집 v3.5 통과 보류**다. 입력 실패와 철회 처리의 개선은 인정하지만, 기록 소유권과 실행 식별, 작업 중단 기록을 먼저 고쳐야 한다. 집계 v6의 판정·수식은 이 문서에서 검증하지 않았다.
