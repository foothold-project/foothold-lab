### 9.1 요청된 반례는 차단됨

### 9.2 완료 줄은 결과 쓰기 뒤에 있음

**확인됨:** `q_eval_cmdr.py:641~659` 순서는 `traj.npz` 저장 → meta 쓰기 → `q_post.postprocess()`의 episode/cell 출력 → 필요한 full record와 meta 갱신 → `[Q-EVAL] done ...`이다. **주요 결과를 쓰기 전에 done을 찍는다는 반박은 이 코드에 해당하지 않는다.** done 뒤에는 진단 출력·summary·env/app 종료가 남는다. 따라서 done 자체만으로 전체 프로세스 종료를 뜻하지는 않지만 v3.2는 guard 종료와 Traceback도 함께 검사한다.

**확인됨:** `gpu_guard.py:28`은 새 프로세스를 띄우기 전에 로그를 `w`로 연다. 같은 tag를 정상 경로로 새 실행하면 옛 로그는 그대로 이어 붙지 않는다. 「동일 tag 재실행이면 항상 옛 done이 남아 통과」라는 주장은 틀리다.

**확인됨:** 그래도 `log_done()`은 tag·N의 문자열만 확인한다. 완료 manifest의 attempt ID, 시작·완료 시각, guard command, 파일 크기·해시, 결과 schema를 한 묶음으로 검증하지 않는다. 입력 코드 pins는 있지만 출력물 각각의 digest는 없다. 기록 복구·수동 복사·중단 뒤 재시도에서 서로 다른 시도의 자료가 섞여도 같은 입력과 shape를 충족하면 발견하지 못할 수 있다. guard 변조 fixture는 그 결합 검사 부재를 직접 보였다. **실제 이번 자료에서 혼합이 발생했다는 증거는 미확인**이다.

**추정 · 다음 안전한 수정 시점의 권고:** 시도마다 새 attempt ID·별도 출력 경로를 두고, 모든 파일을 닫은 뒤 입력·코드·체크포인트·출력 해시·행수·shape·명령·장치·시각을 담은 완료 manifest를 마지막에 원자적으로 확정한다. guard 종료 기록과 그 attempt ID를 결합한다. 재사용은 같은 manifest와 출력 해시를 검증했을 때만 허용한다. 현재 실행 파일을 중간에 바꾸라는 요구가 아니다.
