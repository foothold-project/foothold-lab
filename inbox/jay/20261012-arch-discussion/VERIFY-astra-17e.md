## 1. 질문 3 · 지금 full을 띄워도 되는가

**추정 · 답: 안 된다. 현재 v2를 그대로 둔 full 기동을 승인하지 않는다.** CPU 후처리의 성공은 실행 중 공유 쓰기를 막는 근거가 아니다. GPU 1이 비어 있었다는 사정은 과학적·운영적 승인 조건을 바꾸지 않는다.

**확인됨:** 이번 사본과 실행본의 `isaac_slot.py`, `usd_isolate_run.py`는 17c에서 반례가 확인된 판과 해시가 같다. 현재 slot은 다음과 같다.

## 3. 남은 결함과 수정 범위

### 3.1 등록된 명령과 실제 저장 명령을 대조하지 않는다 · P1

**확인됨:** RV `:375~380`은 cell 이름·길이만 검사하고 `cmd`, `kind`, `switch_s`를 고정 계약과 맞추지 않는다. `:91,395~410`은 `cmd_a`, `cmd_b`, `sw`, `act_abs_mean`의 키 존재를 요구하지만 내용 검사는 하지 않는다. 실제 수집기가 항상 저장하는 `cmd_hist`는 필수 키 목록에도 없다. 이후 q_post가 읽어 계산할 수 있다는 사실은 명령 계약을 검증했다는 뜻이 아니다.

| 별도 CPU 입력 | 실제 결과 |
|---|---|
| `gap/fwd05` 세 군의 `cmd_a`, `cmd_b`, `cmd_hist`를 모두 0으로 변경. meta에는 fwd05 유지 | 세 실행과 칸 모두 **valid** |
| 세 군의 `cmd_hist[10,0,0]`에 NaN 삽입 | 세 실행과 칸 모두 **valid** |
| meta cell의 `cmd`만 `[99,99,99]`로 변경 | 세 실행과 칸 모두 **valid** |
| 진단 7칸 21실행의 저장 명령을 모두 0으로 만들고 새 재검사 보고를 공개 `main --stages full --reval ...`에 제공 | 진단 7칸 valid, **full 30칸 호출, rc=0** |

마지막 시험의 `run_set`은 호출 기록용 CPU stub이었다. 실제 평가나 GPU를 실행하지 않았다. 재검사기·관문·main은 사본 그대로 실행했다.

**수정 조건:** cell별 고정 명령, 종류, 기간, 전환 규칙을 외부 계약에서 가져와 meta와 실제 command 배열에 대조한다. shape/dtype/유한성, `cmd_hist`의 상태-행동 시간 대응, `cmd_a/b`, `sw`, action 요약값을 검사한다. heading-hold 같은 추가 인자가 이 고정 평가에서 꺼져 있어야 한다면 그 값도 검사한다. `checks_run=0`이라는 자기 보고를 실제 기록 검사의 대체물로 쓰지 않는다.

**범위:** 이번 실제 23실행은 별도로 command 배열을 모두 검사해 문제가 없었다(§4). 이 결함 때문에 기존 수치가 틀렸다고 주장하지 않는다. 앞으로 잘못된 수집을 승인할 수 있는 경로가 남았다는 판정이다.

### 3.2 격리 실패 94를 재시도하고 다음 모델로도 진행한다 · P1

**확인됨:** V4 `run_one():134~153`은 rc=98만 즉시 중단하며, 94·95·96·97 등도 일반 실패처럼 재시도한다. `run_set():248~253`도 코드/입력 변경이 아니면 실패를 기록한 뒤 다음 모델로 넘어간다.

사본의 자식 호출을 `returncode=94`인 CPU stub으로 바꾸고 sleep만 생략했다. 한 tag에 **3회 자식 호출**, 반환 `(94,3)`이었다. 이어 `run_one`이 94를 반환하도록 해 `run_set` 한 칸을 실행하니 **par, off, on을 모두 호출**했다. 실제 보호 코드를 우회해 실행한 것이 아니라, 보호 코드가 실패를 알렸을 때 상위 드라이버가 어떻게 반응하는지를 검사한 것이다.

**수정 조건:** 루트 밖 쓰기·격리 누락·충돌·루트 물리 참조 실패 등은 자동 재시도할 수 없는 실행 보호 실패로 분류하고, 첫 발생에서 전체 확대를 중단한다. 96이 v2의 basename 오검출일 가능성이 있어도 자동 반복으로 해결하지 않는다. 실패 attempt를 보존한 뒤 원인을 판별한다. GPU 여유 부족의 재시도를 허용한다면 그것도 명시한 제한과 기동 전 조건 아래에서만 허용한다. 일반 rc!=0 하나로 모든 실패를 같은 방식으로 처리하지 않는다.

### 3.3 ‘띄우기 전 동결 확인’은 재시도에는 적용되지 않는다 · P1

**확인됨:** V4 `:216`의 `frozen_now()`는 tag별 `run_one()` 호출 전에 한 번, `:231`은 모든 재시도가 끝난 뒤 한 번 실행된다. 내부 `run_one()`의 각 자식 기동 앞에는 없다.

CPU 반례: 첫 가짜 자식은 rc=1을 반환하면서 이후 `code_sha()`가 다른 q_post 해시를 보고하게 했다. 두 번째 자식은 **그대로 호출되고 rc=0**으로 끝났다. `run_one` 결과는 `(0,2)`였고, 그 뒤 검사에서야 `frozen_now=False, ['q_post.py']`가 나왔다. 기존 시험 V16은 실행 뒤 stamp를 막지만, 이 두 번째 기동은 막지 못한다.

**수정 조건:** 매 자식 기동 직전과 종료 직후에 같은 동결 계약을 검사한다. 코드를 바꾼 실행은 stamp만 거부하고 끝낼 일이 아니라 다음 자식 자체를 시작하지 않아야 한다. 중간 sleep도 STOP/마감에 반응해야 한다. 이번 반례는 CPU의 반환값/해시 주입이며 운영 코드를 실제로 바꾸지 않았다.

### 3.4 재검사기의 `frozen_ok`는 코드까지 동결됐다는 뜻이 아니다 · P2

**확인됨:** RV `:602~607`은 checkpoint/YAML을 `Reader.ext`에 넣지만 실행 코드 해시는 `code_now`에만 적는다. `Reader.recheck():149~165`와 bundle `:628`에는 해당 코드가 포함되지 않는다. q_post 모듈도 `:171~179`에서 캐시한다.

임시 사본에서 최종 `Reader.recheck()` 직전에 **임시 q_post 사본에 주석 한 줄만 추가**했다. 칸은 valid, `frozen_ok=true`, `changed_during_check=[]`였고 보고서의 q_post 해시는 옛 값이었다. 실제 파일은 다른 해시였다. 주석 추가라 수치가 달라졌다고 주장하는 시험은 아니다. **코드가 달라졌는데도 동결 상태가 참이라는 계약 결함**을 확인한 것이다. 시험 후 임시 코드도 원래 바이트로 되돌렸다.

**수정 조건:** 재검사기·q_post·q_metrics 및 직접 판정에 쓰는 코드도 읽은 바이트/적재 해시와 종료 재대조에 포함한다. 캐시된 모듈의 적재 해시가 현재 검사의 동결본과 같은지 확인한다. V4의 바깥 `frozen_now()`는 일부 변경을 추가로 잡지만, 독립적으로 보관하고 검토하는 재검사 보고서의 `frozen_ok`를 대신하지 않는다. 이번 실자료 검사 중에는 제출 사본과 의존 코드 해시가 유지됐으므로 이 반례가 실제 7칸의 수치를 무효화하지는 않는다.

## 4. 질문 2 · 기존 7칸 진단은 어디까지 확정 가능한가

- 모든 23실행에서 현재 q_post로 만든 `episodes.csv`, `cells.json`이 저장본과 바이트 동일했다. 옛 stamp에 q_post가 없다는 **출처 미확인**은 그대로 남는다. 현재 코드로 재현된다는 사실이 당시 코드의 동일성을 소급 증명하지 않는다.

## 5. 재개 순서와 v3 전환의 조건

**추정:** 다음 범위로 고치면 된다. 이미 통과한 관계없는 시험 전체를 반복할 필요는 없다.
