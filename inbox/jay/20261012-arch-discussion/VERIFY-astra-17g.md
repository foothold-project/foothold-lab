### 2.1 P1 · GPU 대기 중 코드가 바뀌어도 한 번 실행하고 나서야 막는다

**위치:** V5:302의 `frozen_now()` → 305의 `gpu_ready()` → 310의 `subprocess.run()` → 312의 사후 검사. `gpu_ready()`는 최대 600초 대기한다. 그 대기 뒤에는 실행 전 해시 재검사가 없다. `write_stamp()`의 363줄은 이를 “right before ... every launch”로 표현하므로 구현보다 강한 설명이다.

**CPU 재현:** 실제 `run_one()`과 `freeze()`·`frozen_now()`를 사용했다. 파일을 고치는 대신 `code_sha()`의 반환값을 대기 중 바뀌도록 하고, GPU 함수와 자식 실행만 메모리 안 가짜 함수로 바꿨다. 정상 대조군은 바뀌지 않는 해시다.

| 입력 | 실제 자식 호출 횟수 | 반환 |
|---|---:|---|
| 동결 뒤 변경 없음 | 1 | `cls=ok, tries=1` |
| `gpu_ready()` 안에서 q_post 해시가 바뀐 뒤 준비 완료 | **1** | `cls=frozen, tries=1`, “changed while launch 1 ran” |

잘못된 결과를 나중에 폐기하는 기능은 있다. 그러나 **동결과 다른 코드로 실행하지 못하게 하는 기능은 아니다.** 17e §3.3의 실행 전 거절 요구를 충족하지 못한다. D05와 D05b는 이전 시도·실행 중 변경을 검사하지만 이 대기 위치는 검사하지 않는다. 변형 목록의 “right before each launch”도 이 공백을 덮지 못한다.

필요한 수정은 다음이다.

- GPU 대기 완료와 시도 폴더 보존 처리 뒤, 자식 호출 직전에 STOP·마감·코드·입력을 다시 검사한다. 대기 중 변경 반례에서는 자식 호출이 **0회**여야 한다.
- v3 slot의 OS 잠금 대기도 별개다. 가변 경로를 그대로 실행한다면 잠금을 얻은 뒤 실제 평가 자식을 띄우는 지점까지 동결을 보장해야 한다. 실행용 불변 사본을 쓰거나 해당 경계에서 등록 manifest를 대조하는 방식이 가능하다. 이 두 번째 대기에서의 실제 Isaac 동작은 이번에 실행하지 않았으며 정적 확인에 따른 요구다.
- 승인용 manifest는 수정한 코드로 다시 만든다. 기존 `ac09...`에 맞추려고 새 코드 해시를 예외 처리하거나 옛 승인 JSON을 재사용해서는 안 된다.

### 3.1 P1 · v3를 부르면서 구형 registry를 갱신한다

**위치:** RL:863~875. 호출 파일은 `isaac_slot_v3.py`지만 `--registry`는 여전히 `_eval/slot/isaac_usd_registry.json`이다. V5가 분리한 `_v3.json`이 아니다. RL:858~860의 검색 경로는 `out_rand`, `out_branch`, `out_uncr`뿐이다. 실제 구형 branch 경로인 `out/branch`와 구형 registry가 가리키는 다른 로그 부모 폴더는 추가하지 않는다.

**CPU 재현:** 임시 JSON 하나에 구형 `isaac_slot.conflicts_of()`가 읽은 상태를 보관하고, v3 `registry_update()`로 새 항목을 쓴 뒤, 구형 `write_reg()`가 앞서 읽은 상태를 최종 기록하게 했다.

1. v3 쓰기 직후 `{절대 USD 경로: rand.log}`가 있었다.
2. 구형 최종 쓰기 뒤에는 `{구형 basename: gpu0.log}`만 남았다.
3. **RAND의 v3 기록이 사라졌다.** 실제 운영 registry는 사용하지 않았다.

이것은 추측만으로 제기한 경쟁 조건이 아니다. 이번 v5 시험 **L02 자체도 똑같은 구조의 유실을 재현**하며 파일 분리의 필요성을 검사한다. 같은 제출물에서 v5가 막은 구조를 RAND가 다시 사용하고 있다. 구형 쓰기 경로는 `<registry>.lock`을 따르지 않으므로 v3 쪽 잠금만으로 해결되지 않는다. 공통 변환 잠금도 양쪽의 모든 최종 registry 쓰기를 직렬화하지 않는다.

현재 GPU 0 프로세스가 이 구형 경로를 사용 중인지는 프로세스를 조사하지 않아 **미확인**이다. 그렇다고 GPU 0 학습이 진행 중이라는 계획에서 구형 파일에 써도 된다고 승인할 수는 없다.

**기동 전 요구:** v3 참여자는 분리된 v3 registry를 사용하고, 구형 registry는 읽기만 한다. `out/branch`, `out_branch`, 기존/신규 unseen·RAND 및 실제 참여자의 로그 위치를 검색 대상에 넣는다. 구형 registry 읽기 실패를 빈 목록으로 조용히 대체하지 말고 기동 전 확인 실패로 드러낸다. 같은 파일 공유 시 유실, 분리 시 보존을 RAND의 실제 명령 인자까지 연결한 CPU 시험으로 확인한다. 운영 중인 registry 파일을 바꾸거나 기존 항목을 이동하라는 뜻이 아니다.

### 3.2 P1 · 다른 방향으로 민 기록과 빠진 요청값을 정상으로 받는다

**위치:** RL:694~718. 세계 방향을 계산할 때 사건 JSON의 `heading_rad`를 사용하지만 그 방향을 같은 시점의 궤적 `heading_rad`와 연결하지 않는다. 요청 성분도 `abs(float(req.get(key, NaN)) - expected) > tolerance` 형태라 누락·NaN 비교가 실패로 판정되지 않는다.

**CPU 재현:** 제출된 `test_validate_attempt_mutations`의 정상 가짜 실행 폴더를 복사했다. 실제 `validate_attempt()`를 영상 전 프레임 검사까지 그대로 호출했다. checkpoint·시각자료·계약·로그·나머지 기록은 같은 정상 입력이다.

| 입력 변형 | `validate_attempt().ok` | 실패 검사 |
|---|---|---|
| 정상 대조군 | `True` | 없음 |
| 궤적 heading은 0인데 밀기 사건 heading을 π/2로 변경. 해당 heading의 세계 변화량·전후 속도·측정 변화량과 CSV/NPZ 밀기 열을 함께 맞춤 | **`True`** | 없음 |
| 정상 사건의 `request`를 빈 객체로 변경 | **`True`** | 없음 |

첫 반례에서 원래 요청은 몸통 옆 `+0.4 m/s`인데, 궤적에서 몸통이 바라보는 방향과 다른 기준으로 민 기록을 승인한다. 사건 내부 숫자가 서로 맞는다는 사실과 그 사건이 실제 궤적 방향에 맞는다는 사실은 다르다. 두 번째는 요청 출처가 없어져도 정상으로 판정한다. 단위 helper만 통과한 것이 아니라 영상 검사를 포함한 실행 자료 검사 전체가 통과했다.

초기 재현에서 대조 로그 경로를 잘못 지정해 세 경우 모두 로그 검사에서 실패했다. 이를 바로잡고 정상 대조군이 통과하는 것을 확인한 뒤 얻은 값이 위 표다.

**필요한 수정:** 요청의 필수 성분 존재·수치형·유한성을 먼저 검사한다. push callback과 저장 상태의 시간 관계를 정해 사건 heading과 궤적 heading을 연결한다. 각도 비교는 ±π 경계를 고려하고 허용 오차를 먼저 정한다. 그 방향으로 독립 계산한 변화량과 사건·전후 속도·CSV/NPZ를 함께 검사한다. 두 반례는 모두 거절돼야 한다. 사후에 맞지 않는 기록에 맞춰 허용 오차를 넓히지 않는다.

27개 시험 안의 기존 방향 반례는 요청·측정 변화량만 바꾸므로 지금 검사로 잡힌다. heading과 변화량을 함께 틀리게 한 경우, 요청 성분이 없는 경우는 다루지 않는다. 기존 27/27과 75개 내부 변형 통과만으로 이 결함을 부정할 수 없다.

**확인됨:** 두 번 모두 입력 253개, 묶음 해시 `e55975172405901a0178a8e2bd3541ce7e13b118d0a9ab723fb6028d69ef2b58`, `frozen_ok=True`였다. 실제 자료의 파일 목록·크기·mtime도 재검 전후 같았다. base의 hold 사유는 `episodes.csv`, 일부 `cells.json`의 재생성 바이트 불일치였다.

**아직 모르는 것:** Python 자체와 NumPy 중 무엇이 원인인지, 차이가 서식에 국한되는지, 수치·판정에 영향을 주는지. 두 변수가 함께 달라 인과를 분리할 수 없다. 이번에는 행·수치 차이 전체를 분석하지 않았다. 따라서 “해석기를 바꾸면 해결”, “무해한 float 표시 차이”라고 쓰면 틀린다.

17h §3의 보고를 승인 근거로 재사용한 것이 아니라, 지정 원자료를 새로 재검한 결과다. 합성 시험 50개, 실행 자료 23개, 진단 실행 21개, 평가 칸 7개를 분리해 기록했다.

**판정:** 절대 Python 경로 고정은 필요하지만 환경 식별 기록을 대신하지 않는다. V5의 `PY=sys.executable`은 같은 해석기를 자식에 전달하는 장점이 있으나 package가 바뀌어도 경로는 그대로다. 현재 manifest·stamp에는 Python/NumPy 버전이 없다. 이번 full 전에는 최소한 실제 `sys.executable`, Python 전체 버전, `numpy.__version__`·`numpy.__file__`, 판정 코드 해시를 재검 보고·기동 기록에 남기고 검증된 환경과 다른 경우 기동을 보류하도록 하는 편이 맞다. 자동 설치나 환경 변경은 하지 않는다.

base에서도 통과하도록 바이트 검사를 없애는 것은 해결이 아니다. 현재 full 관문은 직전 원자료를 다시 검사해 진단 7칸의 valid를 요구하므로, 이번에 확인한 base 차이는 **full 실행 전 보류되는 방향**이다. 두 환경 모두 지원하거나 원인을 완전히 규명하는 일까지 오늘 밤 full의 필수 조건으로 확대할 필요는 없다. 다만 검증 환경을 명시·확인하고 이 차이를 미해결로 남겨야 한다.

## 5. 실행 순서·시간·결과 해석

### 실행 순서

순서 자체는 **수정과 CPU 반례 확인 → RAND smoke만 → 실제 장치·기록·영상 확인 → RAND 네 장면 한 invocation → 승인된 unseen full/post**가 타당하다. CE12는 별도 CTS 관문이 통과한 경우에만 그 사이 빈 시간에 한 실행씩 넣는다. 이 보고서는 CE12 승인서가 아니다.

단, 75개 수집이 밤의 우선 과제라면 RAND 본 영상 네 장면과 선택적 CE12를 모두 먼저 끝내야 한다는 계획은 좋지 않다. RAND smoke에서 시간과 메모리를 잰 뒤 우선순위를 정해야 한다. smoke 실패 또는 보호 중단이 나면 다음 일을 자동 시작하는 예약을 두지 않는다.

- **실제 GPU 1 여유 10 GB, GPU 0 종료 05:40, 전체 종료 09:00은 이번에 재지 않은 값이다.** 화면용 GPU의 여유는 계속 변한다. v5의 시작 전 6,144 MiB와 실행 중 4,096 MiB는 모델·렌더의 최대 요구량을 예측한 수치가 아니다.
- RAND의 시작 전 하한 기본값도 4,096 MiB다. 여유 조회 실패 `None`은 RD:205~207에서 시작을 막지 않는다. 다른 guard가 있다는 이유로 이를 “시작 전 여유 확인 통과”라고 기록해서는 안 된다. 조회 실패는 미확인으로 보류하고, 실제 smoke의 최고 사용량·최소 여유·소요 시간으로 운영 여유를 정한다.
- NVML GPU 1, `CUDA_VISIBLE_DEVICES=1` 뒤 논리 CUDA 0, Kit 렌더 장치가 같은 물리 GPU/UUID인지 첫 실제 실행에서 대조한다. 환경 변수 하나만으로 렌더 장치 일치를 확인했다고 쓰지 않는다.
- README의 RAND 명령에는 `--deadline`이 없어 기본 0이다. 밤 계획에는 명시적 마감이 필요하다. 마감은 “새 시도를 시작하지 않음”인지 “진행 중 것도 중단”인지 구분한다. 이 판 코드의 시작 전 검사만으로 09:00까지 모든 자식·집계가 종료된다고 보장할 수 없다.
- 보호 코드·루트 참조 오류·registry/출처 오류·코드/입력 변경은 즉시 더 띄우지 않는다. 재시도는 새 USD 폴더와 보존된 실패 기록을 전제로 하며 v5의 GPU 99 최대 2회 추가만 구분한다. 지지면·영상 프레임·관측 기록 실패를 단순 메모리 부족으로 바꿔 부르면 안 된다.
- 실측 후 남은 시간으로 수용량을 계산한다. 예컨대 한 실행 100초를 **가정**해도 75개는 125분이다. 실제 기동·재시도·집계·렌더 시간을 더해야 하며 이 가정을 실측 견적으로 쓰지 않는다.

### 75개 계획과 정직한 결과 문구

**확인됨:** 원본 V5를 읽기 전용으로 적재해 `freeze()`·`registration()`·`manifest_sha()`·`plan_full()`만 호출했다. 등록 일치, manifest `ac09c26492f5fb553bf212a8f3b7aaff75b161649cb6c5b6875b413377377376`, `reuse_partial=no` 75개·yes 73개가 제출 manifest와 같았다. 기동·manifest 파일 생성 함수는 호출하지 않았다.

- full은 지형 10종 × 전진 명령 3개 = 30칸이다. 이 중 진단에서 끝낸 전진 5칸을 제외하면 새로 25칸 × par/off/on = 75개다.
- 후진 진단 2칸은 full 30칸과 별도이므로 합친 manifest는 32칸이다. 기존 자료 23개 중 진단은 21개, 부분 수집 2개는 `reuse_partial=no`에서 재사용하지 않는다. 75는 75개의 독립 학습 시드가 아니다.
- 시드 1042의 off/on은 동일 E1 부모에서 이어 학습한 한 짝이다. 평가 100 episode는 그 체크포인트·시험 설정 안의 표본이지 학습 시드 반복 100회가 아니다.
- old wrapper와 v3 wrapper의 혼합은 등록·짝 검사를 통과한 범위에서 출처를 남겨 허용한다. 이것을 과거 수집 때의 q_post 출처까지 복원했다는 말로 확대하지 않는다.
- README의 RAND 문구는 대체로 정직하다. 다만 “로봇 모든 shape의 지정 재질·고정 heading 속도 변화·평지 한 episode의 관측 잡음 없는 시연”이지 학습 무작위화 분포 전체의 재현이나 강건성 증명이 아니다. 로봇 쪽 마찰 0.0은 바닥 1.0과 average를 **가정**하면 접촉 0.5이며 런타임 결합 모드는 아직 미확인이다.

unseen 결과 보고에는 다음 범위 문장을 수치 바로 곁에 둬야 한다.

> 동일 E1 부모에서 이어 학습한 seed 1042의 CMD-R off/on 한 짝과 부모 체크포인트를, 고정된 미경험 지형·명령·평가 시드·관측 조건에서 비교한 조건부 회귀 평가다. 여러 학습 시드의 일반 효과, 실기 전이 또는 미경험 환경 전반의 개선을 입증하지 않는다. valid·짝 조건을 충족한 칸만 수치로 비교하고 미수집·보류 칸은 따로 밝힌다.
