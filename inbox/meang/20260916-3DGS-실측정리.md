### 1-3. 비교

**비교 범위는 지도 만들기 단계 하나다.** 특징점 뽑기와 짝맞추기는 COLMAP 의 결과를 그대로 물려 썼다. 전체 작업이 그만큼 빨라지는 것이 아니다. `실측`

**두 배수는 각 기재 시간의 비일 뿐이다.** COLMAP 의 37시간 16분 08초가 로그 내부 시간인지 프로세스 경과 시간인지 구분해 적지 않았다. 같은 시작과 종료 사건으로 맞춰 다시 재지 않았다. `미측정`

| 항목 | COLMAP [2] | GLOMAP [3] |
|---|---|---|
| 지도 만들기 시간 | 37시간 16분 08초 | **1시간 23분 52초** |
| 배수 (로그 내부 시간 기준) | | **26.7배** |
| 배수 (프로세스 경과 시간 기준) | | 25.4배 |
| 등록된 사진 | 2,711 (72.5%) | **3,416 (91.3%)** |
| 점 | 791,555 | 655,706 |
| 평균 트랙 길이 | 5.63 | **6.18** |
| 평균 재투영 오차 | **1.144px** | 1.771px |

**재투영 오차를 위치 정확도로 읽지 않는다.** 두 결과는 등록한 사진 집합도 트랙 구성도 달라, 평균 재투영 오차가 작다는 것이 실제 카메라 위치가 더 정확하다는 뜻이 되지 않는다. 공통 기준으로 포즈 정확도를 잰 적은 없다. `미측정`

이번 결과에서는 COLMAP 의 평균 재투영 오차가 더 작았고, GLOMAP 이 사진을 705장 더 등록했다. `실측`
8-1절에서 거리 기준 이상치 후보 92대를 분류했고 그중 76대가 GLOMAP 에만 있는 사진이었다. 나머지 16대는 두 결과에 공통이다. `실측`

### 1-4. 데크 자료 3DGS 학습 5회 (모두 30,000회)

**가우시안 수는 각 PLY 헤더의 `element vertex N` 을 직접 읽었다.** 파일 크기를 나눈 값이 아니다. `실측`

| 자료 | 추가 옵션 | 출력 경로 | 파일 크기 | 가우시안 | 표기 |
|---|---|---|---|---|---|
| COLMAP (카메라 2,711) | 없음 | `output/acc_full` | 117,688,443 B | **474,544** | `실측` |
| GLOMAP (카메라 3,416) | `--antialiasing` [4] 과 노출보정 [6] | `output/acc_glomap` | 37,749,611 B | **152,210** | `실측` |
| GLOMAP (카메라 3,416) | 없음 | `output/acc_glomap2` | 38,337,371 B | **154,580** | `실측` |
| GLOMAP 에 번들조정 47분 (카메라 3,416) | 없음 | `output/acc_ba` | 36,866,731 B | **148,650** | `실측` |
| **GLOMAP 에서 이상치 123대 뺌 (카메라 3,293)** | 없음 | `output/acc_cut` | 109,237,843 B | **440,469** | `실측` |

**PLY 스키마 실측.** 다섯 파일 모두 같다. 계단 영상 판(6-3절)도 같다. `실측`

```
element vertex N
property 62개 = x y z / nx ny nz / f_dc_0..2 / f_rest_0..44 / opacity / scale_0..2 / rot_0..3
가우시안 하나당 248 바이트 (float32 62개)
헤더 1,531 바이트
```

**초고의 오류.** 초고는 속성을 59개, 가우시안당 236 바이트로 적었다. 나열한 항목(3+3+48+1+3+4)의 합은 62이고 248 바이트다. 더한 값이 틀렸다. 그래서 초고의 네 숫자(498,700 / 159,900 / 162,400 / 156,200)는 모두 과대였다. `실측`

**「같은 자료」의 뜻.** 원본 촬영 묶음이 같다는 뜻이다. **학습에 들어간 카메라 수와 초기 점은 서로 다르다.** COLMAP 판은 2,711대에 791,555점, GLOMAP 판은 3,416대에 655,706점이다. 같은 조건의 대조 실험이 아니다. `실측`

**아직 안 적은 것** `미측정`
run ID, 난수 씨앗, 코드 커밋 해시, SH 차수 설정, 실제 실행 명령 전문. 다음 학습부터 함께 남긴다.

GLOMAP 자료로 돌린 세 회 모두 15만 개 근처였다. 추가 옵션을 빼도, 번들조정으로 재투영 오차를 낮춰도 **COLMAP 판과의 큰 차이를 해소하지 못했다.** 세 값 자체는 조금씩 다르다. `실측`

**이상치 후보 123대를 빼자 440,469 가 됐다.** 추가 옵션이 같은 `acc_glomap2` 154,580 대비 2.85배다. 8-1절에 대조를 적었다. `실측`

**노출보정의 출처.** 공식 3DGS README 는 이 affine 노출보정을 Hierarchical 3DGS [6] 의 방식이라고 적는다. 초고가 VastGaussian [5] 을 출처로 단 것은 부정확했다. `확인됨`

### 1-5. 번들조정 실측

```
colmap bundle_adjuster --input_path <glomap 결과> --output_path <새 폴더> \
  --BundleAdjustment.max_num_iterations 30
```

출력 원문:

```
Residuals : 8107380      Parameters : 1987565
Iterations : 31          Time : 2846.61 [s]
Initial cost : 1.66692 [px]
Final cost   : 1.51678 [px]
Termination  : No convergence
```

47분 27초가 걸렸고 30회 제한에 걸려 끊겼다. 비용 함수 값이 9.0% 내려갔다. **위치 정확도가 9% 좋아졌다는 뜻이 아니다.** `실측`

**주의.** `model_analyzer` 의 `Mean reprojection error` 는 조정 뒤에도 원본과 소수점 6자리까지 같게 나온다. 점 파일에 저장된 옛 오차값을 평균낸 것으로 보인다 `추측`. 파일 내용이 실제로 바뀐 것은 `md5sum images.bin` 으로 확인했고 값이 달랐다 `확인됨`.

### 1-6. 자원 사용

| 항목 | 값 | 표기 |
|---|---|---|
| 3DGS 학습 프로세스 메모리 (사진 3,416장, 1600px, `--data_device cpu`) | 137 ~ 143.7 GB | `실측` |
| 같은 조건, 사진 3,293장 (`acc_cut`) | **79.66 GB** | `실측` |
| 파드 메모리 한도 | 206,158,430,208 B = 192.0 GiB | `실측` |
| 그래픽 메모리 | 6.8 ~ 8 GB / 32 GB | `실측` |
| 학습 시간 (30,000회) | 42분 | `실측` |
| 사진 메모리 적재 시간 | 약 9 ~ 13분 | `실측` |

적재 구간은 로그에 진행이 안 찍힌다. 멈춤과 구분하려면 프로세스 메모리를 봐야 한다. `확인됨`

**이론량 계산.** 장수 곱하기 가로 곱하기 세로 곱하기 3색 곱하기 4바이트(float32) 다.
`3,416 x 1600 x 1200 x 3 x 4 = 78,704,640,000 B` 이고 **78.70 GB (73.30 GiB)** 다. `확인됨`

**두 판의 실측이 서로 다르다.** `실측`

| 판 | 사진 | 이론량 | 실측 | 차이 |
|---|---|---|---|---|
| `acc_glomap` | 3,416 | 78.70 GB | 137 ~ 143.7 GB | +58 ~ 65 GB |
| `acc_cut` | 3,293 | 75.87 GB | **79.66 GB** | +3.79 GB |

`acc_cut` 판의 다섯 표본 중 최댓값은 79.66GB 로 이론량보다 3.79GB 컸다. 경과 3분 36초부터 14분 54초까지 다섯 번 재서 35.0 → 65.4 → 76.9 → 79.66 → 79.66 GB 였다. **137GB 를 한 번도 보지 못했다.** `실측`

**다만 몇 분 간격으로 다섯 번 본 것이라 적재 중 짧은 최고점을 놓쳤을 수 있다.** 어느 쪽이 맞는지 확정하려면 할당 프로파일을 떠야 한다 `미측정`.

바이트가 아니라 비트로 계산하면 8배 어긋난다. 단위를 확인할 것.

**1600px 이 되는 조건.** 3DGS 공식 구현 `utils/camera_utils.py` 는 `orig_w > 1600` 을 검사한다. **가로 길이 기준이고 긴 변 기준이 아니다.** 가로로 찍은 4000x3000 에는 맞지만 세로 사진에는 다르게 동작한다. `코드확인`

## 2. 판 호환성 함정

### 2-1. 시험한 COLMAP 4.2 빌드가 V100(sm_70)에서 실행되지 않았다

```
no kernel image is available for execution on the device
```

conda-forge 의 `colmap 4.2.0` GPU 빌드를 V100 에서 돌렸을 때 위 오류가 났다 `실측`. 이 오류는 해당 바이너리에 그 아키텍처용 코드가 없을 때 난다 `확인됨`.

**이것만으로 COLMAP 4.2 전체가 V100 에서 불가능하다고 말할 수 없다.** 실패한 빌드의 정확한 식별자와 빌드 아키텍처 목록을 남기지 않았다 `미측정`. 다른 빌드에서는 될 수 있다.

## 3. 판정 잣대의 함정

### 3-1. 서로 다른 내용의 화면을 PSNR 로 순위 매기지 않는다

`render.py` 로 3,416쌍을 만들어 PSNR 을 쟀다. **경로가 `train/ours_30000` 이므로 이 값은 학습에 쓴 시점의 재현 오차다. 따로 떼어둔 평가용 시점의 점수가 아니다.** `실측`

| 항목 | 값 |
|---|---|
| 평균 | 17.98 dB |
| 중앙값 | 17.79 dB |
| 최저 | 5.54 dB |
| 최고 | 28.60 dB |

**이번 표본에서 최고점 화면이 평평한 콘크리트 바닥 근접샷이었다.** 복원본은 눈으로 봐도 뭉개져 있는데 점수는 1등이다 `확인됨`. PSNR 은 기준 그림과의 픽셀 오차만 재므로 이 순위가 세부 형상 복원 순위와 같지 않다.

**다만 「내용이 없는 화면일수록 점수가 높다」는 틀린 말이다.** PSNR 은 MSE 만의 함수이고 장면 복잡도 항이 없다. 검정 원본에 흰 복원본을 넣으면 평탄해도 0dB 다. `확인됨`

**최저점 화면은 덤불 근접샷이었고 복원본은 거의 빈 그라디언트였다** `확인됨`. 다만 이것이 「그 자리에 가우시안이 아예 없다」는 증거는 아니다. 큰 가우시안이 뭉개져 섞였거나 포즈가 어긋났거나 가려졌을 수도 있다 `추측`.

Mip-NeRF 360 [9] 이후 이 분야는 PSNR, SSIM, LPIPS 를 함께 보고한다. PSNR 단독은 구조 왜곡에 둔감하다 `확인됨`.

**정리.** 서로 다른 내용의 화면을 PSNR 만으로 선명도 순위화하지 않는다. 모델끼리 비교할 때는 공통 평가 시점, 같은 해상도, 같은 노출 처리에서 PSNR 과 SSIM 과 LPIPS 를 함께 보고 눈으로도 본다. 이번에는 그 조건을 갖추지 못했다. `미측정`

### 3-2. 가우시안 수를 진단 지표로 함께 기록한다

개수는 PLY 헤더의 `element vertex` 를 읽는다 (1-4절).

**공식 구현의 밀도 조절 구간.** `train.py` 에서 `densify_and_prune()` 과 불투명도 초기화 둘 다 `iteration < densify_until_iter` 안에 있다. 기본값 15,000 이다. **15,000회 이후에는 증가도 삭제도 불투명도 초기화도 멈추고 개수가 고정된 채 매개변수만 최적화된다.** 증가 시작도 `iteration > 500` 과 100회 주기 때문에 첫 실행은 600회다. `코드확인`

**우리 파일이 그대로 보여준다.** `실측`

### 5-1. 설정

**노출 잠금의 이유.** 자동노출은 사진마다 밝기를 바꿔 SfM 의 특징점 대응을 어렵게 한다 [27a]. 밝기 변화를 사후에 흡수하는 연구가 따로 있을 만큼 실제 문제다. VastGaussian [5] 의 분리형 외관 모델링이 그 예다. 찍을 때 잠그면 **이 변화 요인을 줄인다.** 다만 장면 조명 자체가 고정되는 것은 아니다. `확인됨`

**흔들림.** Gaussian Splatting on the Move [10] 는 손으로 든 스마트폰 촬영의 모션블러와 롤링셔터 보정을 다룬다. 스마트폰 3종으로 찍은 11개 시퀀스를 쓰고, 움직임 기반으로 프레임을 고른다. `확인됨`

> 초고는 이 논문이 1/24초와 1/240초로 찍었다고 적었다. **arXiv v1 과 현재 판의 본문과 부록에서 그 수치를 찾지 못했다.** 삭제했다. 1/125초를 이 논문의 권장값으로 연결할 근거도 없다. `확인됨`

**동영상 30fps 는 우리 선택이다.** PlayCanvas 공식 안내 [27a] 는 영상에 **60fps 이상**을 권한다. 초고가 「60과 120은 낭비」라고 적으며 이 출처를 단 것은 틀렸다. 높은 프레임률로 찍어도 뽑는 간격을 늘리면 처리 장수는 그대로다. `확인됨`

흔들림 보정은 표준까지만 쓴다. **카메라 내부값이 바뀔 수 있는 전자식 보정 모드(시네마틱, 하이퍼스테디)는 이번 시험에서 껐다.** 이 모드들이 화면을 잘라 휘게 만든다는 설명을 [27a] 에서 확인하지는 못했다. `미확인`

넓은 화각에서는 카메라 내부값 자체를 학습 중에 다시 맞추는 연구가 있을 만큼 내부값 일관성이 중요하다 [22]. 렌즈를 바꾸거나 줌을 쓰면 그 일관성이 깨진다. `확인됨`

### 5-2. 조건

| 항목 | 값 | 출처 구분 |
|---|---|---|
| 날씨 | 흐린 날, 바람 없는 날 | 외부 안내 [28] |
| 시간 | 사람 없는 시간. 해 뜬 직후 | 우리 선택 |
| 총 시간 | 30 ~ 40분 안에. 해가 움직이기 전에 | **우리 선택. 근거 미확인** |
| 포기할 것 | 유리, 물, 광택 금속, 하늘 | 논문 [13][14][20] |

**반사면을 포기하는 이유.** 일반 3DGS 의 구면조화는 방향별 주파수가 낮아 거울 반사를 표현하기 어렵다 [14]. 반사를 흉내내려고 허공에 가짜 가우시안이 생겨 주변 형상까지 해칠 수 있다 [13][14]. `확인됨`

**바람까지 피하는 이유.** 지금 방식들은 통제된 환경을 전제한다. 움직이는 사람이 없고, 바람에 흔들리는 것이 없고, 조명이 일정해야 한다 [15][16]. 움직이는 물체는 복원 정확도를 해친다 [23]. `확인됨`

**하늘을 포기하는 이유.** 3DGS 는 하늘을 그릴 때 떠다니는 조각을 만들어 불필요한 가우시안을 대량 생성하고 다중시점 일관성을 깨뜨린다 [20]. 하늘 분할망을 따로 붙이는 연구가 있을 정도다. `확인됨`

### 5-3. 동선

| 회차 | 걷는 곳 | 카메라 방향 | 높이 |
|---|---|---|---|
| 1 | 대상(건물, 벽) 바로 앞을 따라 한 바퀴 | 대상 쪽 | 가슴 |
| 2 | 15 ~ 20m 떨어져서 큰 한 바퀴 (거리는 우리 시험값) | 대상 쪽 | 팔 뻗어 머리 위 |
| 3 | 가로지르며 지그재그 | 45도 아래(바닥) | 허리 |
| 4 | 조형물이 있으면 그 둘레 | 조형물 쪽 | 가슴 |
| 5 | 출발점으로 정확히 복귀. 처음 찍은 곳을 다시 찍기 | 처음과 같은 곳 | |

**핵심은 하나다.** 같은 면이 **거리와 각도가 충분히 다른 여러 시점**에 겹쳐 보이게 움직인다. 시점 간 이동 거리(baseline)가 깊이를 만든다. `확인됨`

**멈춰서 찍어도 된다.** 걷다가 멈춰 찍으면 앞서 찍은 위치와의 시점 차이는 그대로 남고 모션블러는 줄어든다. **다만 같은 자리에서 연속으로 여러 장 누르면 그 장들끼리는 시점 차이가 없다** (6-2절). `확인됨`

**제자리 회전은 피한다.** 회전만으로는 시점 차이가 생기지 않아 깊이를 얻을 수 없다. 훈련받지 않은 사용자는 카메라를 옮기기보다 돌리려는 경향이 있고 그러면 SfM 이 실패한다 [17]. `확인됨`

**출발 구간을 다시 찍으면** 폐루프 제약을 얻는 데 도움이 될 수 있다. 다만 그것이 변형을 막아준다고 보장할 수는 없다. 이번 결과에서 건물이 휘어 있었던 것은 관찰이고, 원인을 분리해 재지는 않았다. `추측`

**겹침.** 인접한 사진끼리 70 ~ 80% 겹치게 한다 [27a]. `확인됨`

**같은 지점이 3 ~ 5장.** 이 숫자의 근거를 [27a] 와 [29] 에서 찾지 못했다. 우리 기준으로 둔다. `미확인`

**자료집 규모는 참고만 한다.** 아래는 자료집 전체의 정의가 아니라 흔히 인용되는 규모다. 우리 3,741장이 많은지 적은지 판단하는 기준으로 쓰기에는 조건이 다르다. `추측`

| 자료집 | 흔히 인용되는 규모 |
|---|---|
| Mip-NeRF 360 [9] | 한 장면당 100 ~ 330장 |
| Tanks and Temples | 한 장면당 수백 장 |
| Hierarchical 3DGS [6] | 수만 장. 수 km 궤적 |

**우리 광장과 데크는 안에서 바깥을 보는 유형이다.** Mip-NeRF 360 [9] 처럼 물체를 둘러싸고 도는 궤적이면 모든 면이 수십 장에 나온다. 우리 경우는 각 면이 적은 수의 사진에만 나오기 쉽다. 같은 곳을 여러 번 지나가는 이유다. `확인됨`

### 5-4. 피해야 할 것

| 하지 말 것 | 왜 | 표기 |
|---|---|---|
| 같은 자리에서 연속으로 여러 장 누르기 | 그 장들끼리 시점 차이가 거의 없다. 일반 권고다 | `확인됨` |
| 나무와 덤불을 가까이서 찍기 | 바람에 흔들리고 다중시점 관측이 부족해 복원이 어렵다. 이런 화면의 복원본이 거의 빈 그라디언트였다 (PSNR 5.54 dB) | `실측` |
| 매끈하고 넓은 데크나 도장면을 크게 찍기 | 복원본에서 그 면도 주변 난간도 누락됐다. 무늬 부족이 얼마나 기여했는지는 미측정 | `실측` |
| 제자리에서 몸만 돌리기 | 시점 차이가 안 생긴다 [17] | `확인됨` |
| 하늘을 화면에 크게 담기 | 떠다니는 조각이 생긴다 [20]. 30% 라는 선은 우리 기준이고 근거 없음 | `확인됨` |

무늬 없는 면을 꼭 찍어야 하면 1 ~ 2m 까지 가까이 가고, 낮고 비스듬한 각도로 보고, 화면에 항상 난간이나 모서리나 이음매가 걸리게 한다. `추측`

**초기 점의 중요성.** SfM 초기 점 대신 무작위 초기화를 쓴 비교 연구 [12] 의 표 1에서, 재실행 평균 PSNR 은 COLMAP 29.09 dB 였고 무작위 초기화 조건들은 27.28 / 23.15 / 27.75 dB 였다. 차이는 각각 **1.81 / 5.94 / 1.34 dB** 다. `확인됨`

> 초고의 「약 6dB」는 1.5배 경계상자 조건 하나에만 해당한다. 일반화였다.

3DGS 는 기존 가우시안을 복제하고 분할해서 늘린다 [1]. **초기 점이 부족한 영역은 복원이 어려울 수 있다.** 다만 위치 최적화와 분할이 함께 도는 알고리즘이라 영구히 채워지지 않는다고 단정할 수는 없다. `추측`

### 5-5. 크기를 확정하는 법

SfM 결과는 크기와 방향이 정해져 있지 않다. 실제 치수 하나가 필요하다. `확인됨`

**원칙.** 실제로 자로 잰 표식이면서, 재구성 결과에서 그 지점을 확실히 집을 수 있는 것을 쓴다. 정확도 순위는 실제로 재보기 전에는 매기지 않는다.

| 방법 | 조건 | 표기 |
|---|---|---|
| 계단 한 단 높이를 자로 재기 | 현장에서 재야 한다. 단마다 다를 수 있으니 여러 단을 잰다 | 권함 |
| 길이를 아는 물건(줄자, 막대)을 바닥에 두고 찍기 | 양 끝이 복원본에서 보여야 한다 | 권함 |
| 점자블록(노란 돌기 블록) | 규격이 정해져 있다고 들었으나 **출처를 확인하지 못했다** | `미확인` |
| 지도 거리재기로 잰 광장 길이 | 100m 를 1m 오차로 재면 1%. 양 끝을 복원본에서 집어야 한다 | 참고 |
| 촬영자 체격 | **근거 없음.** 쓰지 말 것 | `미확인` |

계단이 4단이라는 것만으로는 실제 높이가 정해지지 않는다. 자로 재야 한다.

### 7-6. 두 SfM 결과를 공통 좌표계에서 비교하기

공통 카메라로 Umeyama 정렬(회전, 이동, 배율)을 건 뒤 반지름을 잰다. 정렬 없이 두 결과의 반지름을 직접 비교하면 좌표 배율 차이와 실제 왜곡이 섞인다. `코드확인`

```python
def umeyama(P, Q):                      # P 를 Q 에 맞춘다
    a, b = P.mean(0), Q.mean(0)
    X, Y = P - a, Q - b
    u, d, v = np.linalg.svd((Y.T @ X) / len(P))
    S = np.eye(3)
    if np.linalg.det(u) * np.linalg.det(v) < 0:
        S[2, 2] = -1
    r = u @ S @ v
    s = float((d * np.diag(S)).sum() / ((X ** 2).sum() / len(P)))
    return s, r, b - s * (r @ a)
```

매 회 **전체 공통 카메라**의 잔차를 다시 계산해 작은 순으로 80% 를 골라 다시 맞춘다. 누적해서 깎는 것이 아니라 회마다 다시 고르므로 한 번 빠진 것도 다시 들어올 수 있다. 여섯 번 맞추고 집합 갱신은 다섯 번 한다.

**잘 맞는 것만 고르는 방식이라 선택 집합의 일치는 낙관적일 수 있다.** 잔차의 중앙값과 90분위와 최댓값은 선택 집합이 아니라 공통 카메라 전체에서 계산해 함께 본다.

### 왜 그런가

장면 반지름이 커지면 `percent_dense` 가 곱해지는 크기 기준도 커지고 위치 학습률도 반지름에 비례해 커진다 `코드확인`. 이 둘이 밀도 조절을 막은 것으로 본다 `추측`.

**어느 연산이 막혔는지는 아직 모른다.** 분할과 복제와 삭제 횟수를 세지 않았다 `미측정`. 반지름이 커지면 크기 기준 삭제 문턱도 커져 큰 가우시안이 덜 지워지는 반대 방향 효과도 있다 `추측`.

**관련 연구.** 다만 이 연구들이 우리 반지름 문제를 입증하는 것은 아니다. `확인됨`

- **AbsGS** [8]. 많은 픽셀을 덮는 큰 가우시안은 픽셀마다 기울기 방향이 엇갈려 상쇄되고, 그 결과 기울기 크기가 밀도 증가 문턱을 넘지 못한다. **우리는 그 상쇄를 측정하지 않았다.**
- **Pixel-GS** [7] (ECCV 2024). 시점별 기여도의 불균형을 다룬다. 주된 해법은 **각 시점에서 덮는 픽셀 수로 가중한 기울기 평균**이다. 거리 기반 기울기 조절은 카메라에 가까운 떠다니는 조각의 증가를 억제하기 위한 **별도 해법**이다.

> 초고는 Pixel-GS 의 해법을 거리 기반 조절이라고 적었고, 두 논문의 공통 지적을 「장면 규모 민감성」으로 묶었다. 둘 다 고쳤다. VastGaussian [5] 과 Hierarchical 3DGS [6] 가 장면을 나누는 동기에는 메모리, 최적화 비용, 외관 변화 등도 있다.

**해볼 것** `미검증`

| 안 | 내용 | 무엇을 보나 |
|---|---|---|
| 가 | **반지름만 바꾸는 통제 실험.** 같은 사진, 같은 초기 점, 같은 옵션, 같은 난수에서 `cameras_extent` 만 바꾼다 | 반지름의 기여도를 분리한다. 후보 제거 재학습은 이미 했고 넷이 함께 바뀌어 분리가 안 됐다 |
| 나 | `--percent_dense 0.0011` (0.01 나누기 8.871) | 크기 기준만 COLMAP 과 맞춘다. 학습률 문제는 남는다 |
| 다 | `--densify_grad_threshold` 낮추기 | 증상 완화. AbsGS [8] 와 Pixel-GS [7] 는 문턱 자체의 설계를 바꾼다 |

**교훈.** 새 SfM 도구로 바꿨을 때는 등록 장수만 보지 말고 카메라 반지름을 잰다 (7-5절). 그리고 두 결과를 견줄 때는 정렬을 먼저 건다 (7-6절).

### 8-2. 위쪽 방향 찾기. 미해결

SfM 결과의 좌표에는 중력 방향과 미터 단위가 들어 있지 않다. 영상만으로는 정해지지 않는다 `확인됨`. 뷰어에서 장면이 비스듬히 누워 보이는 것이 이 때문이다. Isaac Sim 에 넣으려면 반드시 세워야 한다. 기울어진 채로 넣으면 로봇이 비탈에 서게 된다.

| 방법 | 결과 | 표기 |
|---|---|---|
| 1 점구름에서 가장 큰 평면 찾기 (RANSAC) | 실패. 후보 5개 모두 카메라 무리를 가로질렀다 | `실측` |
| 2 카메라들에 평면 맞추기 (주성분 분석) | 애매. 점 높이 분포가 뭉개져 층이 안 갈렸다 | `실측` |
| 3 건물 벽(수직면)들의 법선으로 구하기 | 미시도 | `미측정` |
| 4 카메라 자체의 아래 방향 평균 | 미시도 | `미측정` |
| 5 COLMAP 의 맨해튼 월드 정렬 기능 | 미시도 | `미측정` |

3번의 원리는 건물 벽의 법선이 모두 수평이라는 것이다. 여러 벽의 법선에 평면을 맞추면 그 평면의 법선이 곧 중력 방향이다. 맨해튼 월드 가정이다. COLMAP 에 같은 가정을 쓰는 기능이 있다 `확인됨`.

이번 장면은 촬영 높이를 3단으로 바꿔가며 찍었다. 고관절, 쇄골, 팔 높이다. 그리고 데크면과 잔디면 두 층이 계단 4단으로 나뉘어 있다. 층이 갈리면 그 간격을 크기 확정에 쓸 수 있으나, **실제 계단 높이를 자로 재 와야 한다** (5-5절). `추측`

### 8-3. 떠다니는 조각 제거. 미착수

하늘과 먼 배경에 안개 같은 가우시안이 남는다 `확인됨`. 시점 차이가 부족해 깊이를 정하기 어려운 것이 알려진 원인 중 하나다 [20]. 모든 떠다니는 조각의 원인이 그것 하나는 아니다 `추측`.

**공식 구현에 이미 대책이 있다.** 3DGS 저장소는 깊이 규제를 지원한다. 설명서는 무늬 없는 부분(예: 도로)에 가장 잘 듣고 떠다니는 조각을 없앨 수 있다고 적는다 `확인됨`. 깊이 그림은 Depth Anything V2 [11] 로 만든다.

**절차가 세 단계다.** `코드확인`

```bash
# 1. 깊이 그림 만들기 (Depth Anything V2). 모델 가중치와 출력 이름 규칙은 공식 README 의 깊이 규제 절차를 따른다
# 2. SfM 좌표에 맞추는 정보 만들기
python utils/make_depth_scale.py --base_dir <자료> --depths_dir <깊이폴더>
# 3. 학습
python train.py -s <자료> -m <출력> -d <깊이폴더> \
  --depth_l1_weight_init 1.0 --depth_l1_weight_final 0.01
```

> 초고는 `--depth_l1_weight 1.0` 이라고 적었다. **그런 인자는 없다.** 공식 `OptimizationParams` 에 넣으면 `ambiguous option` 으로 종료 코드 2가 난다. 실제 인자는 `--depth_l1_weight_init` 과 `--depth_l1_weight_final` 이다. 2단계 전처리도 빠져 있었다.

같은 방식을 쓴 연구가 있다. Robust and Efficient 3DGS for Urban [19] 은 Depth Anything V2 [11] 로 깊이를 뽑아 hard 규제와 soft 규제를 번갈아 적용하며 떠다니는 자국을 줄인다고 보고한다 `확인됨`. TIDI-GS [21] 는 주기적 청소와 단안 깊이 규제를 함께 쓴다 `확인됨`.

**GASE 수치는 조건을 붙여야 한다.** 표 3의 조작 과제 셋에서 sim2real 성공률은 73 / 60 / 67% 이고 real2real 은 73 / 67 / 67% 다. 과제별 차이는 0 / 7 / 0 %p 다. 두 번째 과제의 상대 감소율이 약 10.45% 다. 표 4의 항법 실험에는 real2real 열이 없다. **우리 Go2 결과가 아니다.** `확인됨`

> 초고는 「성공률 60% 넘고 real-to-real 대비 성능차 10% 안」이라고 적었다. % 와 %p 를 섞었다.
