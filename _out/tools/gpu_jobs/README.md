# GPU 작업 관리판

`python _out/tools/gpu_jobs/gpu_jobs.py status`는 등록부와 실제 `PRIORITY_BUSY`, `chain2.log`, 렌더 대기열 상태를 읽는다. `gate <id>`는 **다음 작업 한 건**을 시작할 수 있는지 판단한다. 이 명령은 어떤 프로세스도 띄우거나 멈추지 않는다.

P0 승인된 학습 > P1 판정용 평가 > P2 진단·평가 > P3 시드 반복 > P4 영상 렌더 순서다. 낮은 작업이 이미 한 건을 실행 중이면 그 건은 끝내고, 다음 건 전에 다시 `gate`를 호출한다. 높은 작업이 준비되면 낮은 작업의 다음 건은 대기한다. 높은 작업이 새 저장본을 기다리고 GPU1 표식이 비면 낮은 작업이 틈을 쓸 수 있다. 다시 높은 작업이 생기면 다음 경계에서 비킨다.

현장 연결: EX-35 평가 감시기 PID 34976이 `PRIORITY_BUSY`를 쓰며, `render_queue_26d.py` e202543a는 매 렌더 건 앞에서 그 표식과 사슬의 저장본 대기를 검사한다. 이 관리판은 같은 두 자료를 읽는다. 진행 중인 runner는 이 관리판의 P3 등록부를 읽지 않으므로, **P3 실행을 등록하기 전에 runner가 P3 진입도 확인하도록 별도 연결**해야 한다. 현재 P3는 `turn_probe.py`에서 시드 42가 고정되어 seed 43·44 실행 CLI가 없어 `executable=false`로 봉쇄했다. 준비되지 않은 명령을 실제 기동 명령으로 바꾸지 않는다.

`jobs.json`은 등록 시각의 명부다. PID와 생성 시각을 함께 확인해 재사용 PID를 살아 있는 작업으로 오인하지 않는다. PID 종료만으로 성공·실패를 확정하지 않으며, 완료 영수증이 나온 뒤 주인 세션이 상태·끝 시각·산출 경로를 갱신한다. 렌더 대기열의 현재 항목은 외부 상태 파일을 우선 읽는다. `status`는 관찰 시점의 화면이며 승인이나 결과 판정이 아니다.

CPU 시험: `python -m unittest _out/tools/gpu_jobs/test_gpu_jobs.py -v`. 시험은 가짜 사슬 로그·표식·렌더 상태로 P1 점유, P1 대기, 렌더 한 건 경계, 재등장한 P1, 미설정 P3을 확인한다.

### 이미 직접 띄운 GPU 작업 등록

GPU 작업판의 작업 목록에 실행 중인 학습, 평가, 메시 생성을 기록한다. `FOOTHOLD_OPS_MACHINE_PROFILE`은 평소 작업판과 같은 프로필을 사용한다.

```bash
python _out/tools/gpu_jobs/dispatch.py queue external --title "EX-42 학습" --gpu 0 --gpu 1 --priority 0 --start "11-11 01:42" --end "11-11 04:00" --log /absolute/path/to/train.log --pid 12345
```

GPU 한 장이면 `--gpu`를 한 번만 쓴다. 여러 장은 같은 추적 PID에 대해 GPU별 행이 생긴다. PID는 실행 전체의 수명을 대표하는 프로세스(예: torchrun 부모)를 고른다. `--end`는 예상치이며 실행을 제한하지 않는다. 등록은 작업을 띄우거나 멈추지 않는다.

프로세스 종료 또는 PID 재사용이 확인되면 작업 목록은 자동으로 `끝`으로 표시한다. 이는 성공을 뜻하지 않으며 종료 코드는 미확인으로 남긴다. 작업판은 큐를 읽기만 하고, 종료 상태의 파일 반영은 다음 dispatcher 주기 또는 큐 변경 때 한다. GPU 카드의 학습 PID는 추적 PID와 별개로 드라이버의 GPU별 사용량이 가장 큰 곳에 표시한다.
