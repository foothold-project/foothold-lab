> 웹 판: https://foothold-project.vercel.app/collab.html

## 1. 왜 이렇게 일하는가: 원칙 셋

1. **기록이 우리를 증명한다.** 12월에 "누가 뭘 했나"를 기억으로 복원할 수 없다. 지금 남기지 않으면 그때는 없다.
2. **측정 없이 판단하지 않는다.** "잘 되는 것 같다"는 인상이지 기록이 아니다. 숫자를 먼저 잰다.
3. **침묵을 성공으로 착각하지 않는다.** 조용히 넘어간 것은 확인된 것이 아니다. 안 되는 것은 소리를 내게 만든다.

## 2. 팀 역할 원칙: 파트를 소유하지 않는다

이 프로젝트는 환경→학습→평가→이관이 직렬로 이어진 **한 파이프라인**이라, 파트를 쪼개 소유하면 이음새에서 무너진다.
멘토도 같은 말을 했다: *"선 긋지 말고, 얘가 힘들 때 내가 대타 뛸 수 있는 수준이 돼야"* (8/6 회의).

- **전원이 전체 흐름을 이해한다**. plan.html 의 7단계가 그 지도다.
- 각자는 관심 영역의 **리드**다. 소유가 아니라 **리드 + 상호 백업**.

| 리드 | 영역 (rl 폴더) |
|---|---|
| 임석헌 · 이민우 | policies: 정책·학습 |
| 맹라현 | envs: 지형·환경 |
| 오현민 | perception: 인지·데이터 |
| 오흥재 | 전체 조망(PM) + deploy·eval + 디지털 트윈 축 |

## 2.5 일감의 계층: 갈래 5개가 부모, 시기는 마일스톤

이슈를 만들 때 **«어느 갈래의 일인가»** 를 고르면 그 갈래 부모 밑에 자동으로 매달린다.
부모는 `foothold-rl` 한 곳에만 있고(sub-issue 는 저장소를 넘어 연결된다),
하위가 닫힐 때마다 부모에 진행률이 자동으로 올라간다.

| 갈래 | 무엇이 모이나 |
|---|---|
| **평가 체계** | 통과율 정의 · 100회 자동 평가 · 기준선 (Q3·Q6·Q8) |
| **험지 환경** | 지형 조각 · 계곡형 조합 · 3DGS (Q4·Q5) |
| **정책 학습** | 학습 실행 · 보상·랜덤화 · 실험 (Q7·Q8) |
| **실기 전이** | 정합성 6종 · sim2sim · ROS2 · 안전 사다리 (Q9~Q12·보스전) |
| **운영** | 문서 · 회의 · 인프라 · 발표 · 현장조사 |

- **시기는 마일스톤**이 담당한다. 부모가 아니다. 2026-08-27 에 네 관문으로 재정의했다:
  `A-정책 9/12` · `MVP · 중간발표 9/30` · `NAV · 실기 항법 11/7` · `FINAL · 최종발표 12/11`
- **퀘스트(Q0~Q12)**는 설계도 §3 의 진행 순서다. 부모가 아니라 이슈 제목·설명에 번호로 남긴다.
- 7단계(땅 보러 가기…)는 소통용 지도다. 관리 도구에는 등장하지 않는다.
- 부모는 미리 만들지 않는다. 그 갈래의 첫 이슈가 올라올 때 워크플로가 만든다.

### 3-1. 팀원 제출함: `lab/inbox/<이름>/` (확정 2026-08-12)

일주일에 한 번 각자의 연구·리서치 결과를 공유하는 자리다. **자기 폴더에만 쓴다.**
남의 폴더를 건드리지 않으면 git 충돌이 원천적으로 없다.

| 경로 | 성격 | 웹 게시 |
|---|---|---|
| `lab/docs/` | **정본.** 팀장이 큐레이션한 것만 | ★ 게시되는 유일한 경로 |
| `lab/inbox/meang·oh·lim·lee/` | **제출함.** 각자 자기 폴더에만 | 게시되지 않음 |

- **규칙은 하나**: 파일 맨 위에 `작성 YYYY-MM-DD` 와 `요지: 한 문장`.
  이 두 줄이 있어야 큐레이션과 주간 다이제스트 자동 초안에 물린다.
- 흐름: `inbox/<나>/` 제출 → 팀장 검토·보완 → `docs/` 반영 → 웹 게시 → **주간 다이제스트에 요약**
- 10MB 넘는 파일은 git 에 넣지 않는다 (팀 채널로, 추후 NAS)
- 상세: [inbox/README.md](../inbox/README.md)

### 3-2. 주간 다이제스트: «이번 주 알게 된 것» (확정 2026-08-12)

주간 리포트(무엇을 **했나**)와 별개로, **무엇을 알게 됐나**를 3~6개 항목으로 요약한다.
각 항목 = 한 문장 + 증거 링크 하나. `docs/digest/` 에 쌓이고 웹의 연구 기록 페이지 상단에 걸린다.
초안은 문서들의 `요지:` 줄에서 자동으로 모으고, **확정은 사람이 한다** (자동 나열은 안 읽힌다).

## 4. 일의 흐름: 손으로 하는 건 두 가지뿐

<!--SVG:flow-->

**① 시작 = 레포에서 이슈 만들기.** 문서·조사 → lab, 코드·실험 → rl. 템플릿 빈칸을 채운다(특히 "끝났다는 기준").
자동으로 따라오는 것: 보드 등록 · **담당자 = 만든 사람** · 시작일 = 오늘 · 마감 = +7일 · 디스코드 "새 작업".

**② 끝 = 커밋 메시지에 `Closes #번호`.**
자동으로 따라오는 것: 이슈 닫힘 · 보드 Done · 디스코드 "완료".

그리고 **매주 월요일 09:00** 지난주 요약이 디스코드로 온다(자동).

**⚠️ 보드에서 `+ Add item` 타이핑 금지**. 레포에 없는 초안(draft)이 되어 자동화가 전부 죽는다.
보드 상단 "Create new issue" 버튼은 진짜 이슈를 만드니 괜찮다.

## 4-1. AI 로 작업할 때 (2026-08-26 신설)

팀원 대부분이 Cursor · Claude Code · Codex 같은 도구로 작업한다. 그래서 사람 규칙과
별개로 **「AI 가 읽는 규칙」** 이 필요하다. 저장소 맨 위 `AGENTS.md` 가 그것이다.

| 도구 | 자동으로 읽는 파일 |
|---|---|
| Cursor · Codex | `AGENTS.md` |
| Claude Code | `CLAUDE.md` (내용은 `AGENTS.md` 를 가리킨다) |

규칙은 `AGENTS.md` **한 곳에만** 쓴다. 두 곳에 나눠 적으면 반드시 갈라진다.
`AGENTS.md` 에는 **공통 규칙만** 둔다. 각자 작업 방식은 `inbox/<이름>/AGENTS.md` 를 만들거나 로컬 설정(gitignore 대상)으로 둔다. 에이전트마다 쓰는 도구가 달라, 공통 파일에 개인 설정이 섞이면 다른 사람의 에이전트가 그것을 규칙으로 읽는다 (2026-08-27 개정).

> **왜 웹페이지로 충분하지 않은가.** 자동화 지도는 사람이 보는 화면이다.
> 팀원의 AI 는 그 화면을 보지 않는다. **AI 가 시스템적으로 닿는 곳은 저장소 안**이다.

### 작업을 시작하기 전에 `git pull origin main`

**이 한 줄을 빠뜨려서 이틀에 두 번 사고가 났다.** 규칙이 아니라 사고 기록이다.
옛 상태의 main 에서 갈라진 브랜치로 PR 이 올라왔고, 머지했다면 이렇게 됐다.

| 회의록 | 지금 정본 | 머지했다면 |
|---|---|---|
| 8/13 | 10,317자 | 2,335자 |
| 8/14 | 5,444자 | 1,841자 |
| 8/19 | 5,482자 | 2,667자 |
| 8/20 | 7,135자 | 2,738자 |
| 8/21 | 5,975자 | 3,672자 |

없애기로 한 인쇄 시스템이 되살아나고, 「계획」으로 옮긴 문서가 다시 「회의록」이 됐다.
**git 이 충돌을 내서 막았다. 충돌이 안 났으면 조용히 덮였다.**

**원인은 AI 가 아니다.** 8/23 에 딴 브랜치로 작업하면 AI 는 **8/23 시점의 저장소만** 본다.
그 뒤 main 에 쌓인 12개 커밋을 모른 채 답을 낸다.
**오래된 상태를 주면 오래된 답이 나온다.**

작업이 하루 넘게 걸리면 **중간에 한 번 더** `git pull origin main` 한다.
이 저장소는 하루에도 여러 번 갱신된다.

### AI 가 거의 확실하게 걸리는 것 셋

| 걸리는 것 | 어떻게 되나 | 어떻게 |
|---|---|---|
| 긴 줄표(em dash) | **빌드가 배포를 멈춘다** | `·` 나 마침표로 바꿔 달라고 한다 |
| 선으로 그린 글자 도식 | 배포가 멈춘다 | 표로 바꾼다 |
| 근거 없는 단정 | 승격이 막힌다 | `확인됨` · `추측` · `미확인` · `미측정` 을 단다 |

**재보지 않은 것에 「확인했다」를 쓰지 않는 것**이 이 팀 문서의 핵심이다.

### 올리기 전에 스스로 본다

```bash
python3 .github/scripts/review_inbox.py inbox/내이름/*.md
```

무엇이 빠졌는지 문장으로 알려준다. PR 을 올리면 **이것이 자동으로 돌고
팀장 텔레그램으로 결과가 간다.** 따로 보고하지 않아도 된다.

## 5. 브랜치와 커밋

<!--SVG:branch-->

| 레포 | 규칙 |
|---|---|
| **rl** | 코드를 바꿀 때만 브랜치를 판다: **`feature/작업명-이름`**(예: `feature/terrain-lim`) → PR 로 `dev` → 검증된 상태만 PR 로 `main`. main 직접 push 금지(룰셋) |
| **lab** | main 직접 커밋은 **팀장만**(2026-08-13). 팀원은 브랜치 → PR. inbox 제출은 **최소 규칙만 맞으면 된다**: 기계가 읽고 부족한 곳을 짚어 «보완» 커밋을 따로 올리며, 팀장이 확인 후 머지한다 (2026-08-25 개정) |
| site · brand | 파이프라인/담당(Codex)이 관리: 직접 커밋하지 않는다 |

- **이슈마다 브랜치를 만들 필요는 없다.** 브랜치는 이슈가 아니라 **"PR 로 합칠 코드 변경" 단위**다
  조사·회의·막힘 이슈는 브랜치가 아예 필요 없고, 작은 이슈 여럿을 브랜치 하나로 처리해도 된다
  (`Closes #12 #13` 처럼 한 커밋으로 여러 개를 닫을 수 있다).
- **이슈 번호를 브랜치 이름에 넣지 않는다** (2026-08-27 통일). `feature/작업명-이름` 형식이다.
  흐름의 정본은 [작업 흐름](WORKFLOW.md)이다. 이슈 화면의 "Create a branch"
  버튼을 쓰면 이름이 자동으로 지어진다. merge 된 브랜치는 지운다(브랜치는 소모품이다).
- 추적의 핵심은 브랜치 이름이 아니라 **커밋·PR 의 `Closes #번호`** 다. 이것만은 반드시.

## 6. 보드와 일정: 계획과 실적을 둘 다 남긴다

| 필드 | 의미 | 누가 |
|---|---|---|
| start date / end date | **계획.** 자동값(오늘/+7일)은 초기값일 뿐: **고치는 것이 정상 행위** | 사람 |
| done date | **실적.** 이슈 닫힐 때 자동 기입 (구축 중) | 자동 |

- 미리 등록(9월 계획을 8월에)하면 start 를 9월로 고친다. 밀리면 또 고친다. 계획이니까.
- 계획 변경의 이력은 **주간 리포트 아카이브**가 자동으로 남긴다.
- **계층**: 큰 단계(부모 이슈) 아래 실제 작업(자식 이슈). 템플릿의 "단계" 드롭다운으로 자동 연결(구축 중).
- 마감 초과 시 디스코드 알림(구축 중).

## 6-1. inbox 제출: 어디까지 맞춰 오면 되나 (2026-08-25 개정)

**최소 규칙만 맞으면 된다.** 잘 만들어 왔으면 그대로 올라간다. 완벽하게 다듬느라
안 올리는 것이 가장 나쁘다.

| 최소 규칙 | 왜 |
|---|---|
| 본인 폴더 `inbox/본인폴더/` | 누가 낸 것인지 경로로 안다 |
| 개인정보 없음 | 공개 사이트로 나간다 |
| em dash · 글자 도식 없음 | 빌드가 멈춘다 |
| 확인한 것과 추측을 구분 | 안 하면 어디까지 믿을지 알 수 없다 |

**부족한 것이 있어도 남의 글을 고치지 않는다.**

1. 기계가 읽고 무엇이 부족한지 판정한다 (자동)
2. 보완이 필요하면 **같은 PR 에 «보완» 커밋을 따로** 올린다. 원문 커밋과 섞지 않는다
3. 무엇을 왜 보탰는지 요약해 팀장 텔레그램으로 (자동)
4. 팀장이 PR 에서 확인하고 승인하거나 피드백한다
5. 승인되면 머지 · 웹 게시 (자동)

보완을 별도 커밋으로 두는 이유는 «어디까지가 본인이 쓴 것인가» 가 남아야 하기
때문이다. 제출자 이름으로 나가는 글이다. 팀장 피드백은 PR 코멘트로 남겨
제출자도 보게 한다.

> **한계 (명시)**: 2번의 «보완» 은 아직 완전 자동이 아니다. 판정까지는 기계가
> 혼자 하지만, 문장을 보태고 출처를 검증하는 것은 워크스테이션 세션이 붙어야

## 7. 문서 규칙

- `docs/research/` 조사 · `docs/meetings/` 회의록 · `docs/ops/` 운영 · 루트 = 기획/규칙
- 파일명은 소문자-하이픈. 회의록은 `YYYYMMDD-slug.md` 날짜당 하나. HTML·PDF는 새로 만들지 않는다.
- **출처 등급**: 공식 문서 > 교재 > 논문 > 해설 블로그 > 백과. **숫자 인용은 논문·공식만.**
- 확인 못 한 것은 **`미확인`** 이라 쓴다. 미확인을 근거로 판단하지 않는다.
- 웹에 올라가는 구조도는 **ASCII 금지**. SVG·이미지·표로.

## 8. 하지 말 것. 전부 실제 겪었거나 겪을 뻔한 것

1. **체크포인트(.pt)·대용량을 git 에 커밋하지 않는다**. 한 번 들어가면 히스토리에서 못 지운다.
2. **타인 저작물 원문을 올리지 않는다**. 비공개 레포여도. 링크로 대신한다.
3. **토큰·웹후크 URL 을 채팅·문서에 붙이지 않는다**. 실제로 한 번 유출돼 재발급했다. 유출 시 즉시 재발급.
4. **site 를 직접 수정하지 않는다**. 다음 빌드에 덮어써진다.
5. **결과를 보고 판정 기준을 바꾸지 않는다**. 통과선은 실험 전에 적는다.
6. **추측을 결론 자리에 앉히지 않는다**. 물어볼 수 있는 것은 먼저 묻는다. (RunPod GPU 건에서 실제로 틀렸다)

## 9. 새 레포가 필요할 때: 기준 셋

별도 빌드 체계(예: ROS2 워크스페이스) / 별도 실행 환경(예: 3DGS 도구) / 단독 공개물.
**그 외는 전부 폴더로.** 역할·파트는 레포가 아니라 폴더 + 담당자로 표현한다.

## 10. 막혔을 때: 30분 룰

30분 막히면 **[막힘 이슈]** 를 만든다(기대 vs 실제 · 재현 · 환경 · 로그 · 해본 것).
혼자 3시간 파는 것이 팀에는 더 비싸다. 같은 에러를 두 번 겪으면 그건 문서감이다. `docs/ops/` 에 남긴다.

## 11. 회의 규칙

1. **회의는 무조건 녹음한다.** 시작할 때 한 마디로 고지한다.
2. 파일은 NAS `foothold/meetings/` 에 `YYMMDD_제목.m4a`.
3. 전사→보고서는 파이프라인이 만든다 (반자동 → WS+MOSS 화자분리로 자동화 예정).
4. 보고서의 모든 인용에 **타임코드**: 원문 대조가 가능해야 한다.
5. 금액·개인정보가 든 회의록은 **lab(비공개)까지만.** 공개 사이트에 내보내지 않는다.

## 12. 결정 기록

결정이 나는 순간 **`docs/DECISIONS.md`** 에 한 줄(무엇 · 왜 · 출처). 채팅은 휘발이다.
뒤집을 때 지우지 않는다. 취소선 + 새 행. 미결은 D번호로 관리하며 그것이 곧 회의 안건이다.

## 13. 실험 규율: 팀 공통 규칙이다

**한 번에 하나만 바꾼다** · **기준선과 대조한다** · **통과선을 먼저 적는다** ·
결과는 채택이든 폐기든 **EXPERIMENTS.md 에 한 줄**. 실험 1회 ≈ **2시간 15분**(1,500 iter **실측 133분**: 2026-08-12)임을 알고 계획한다.
