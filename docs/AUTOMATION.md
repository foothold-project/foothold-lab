## 0. 한눈에 보는 그림

automap


**읽는 법.** 왼쪽이 사람, 가운데가 기계, 오른쪽이 도착지입니다. 사람이 하는 것은
**이슈를 여는 것 하나**이고, 나머지는 이어서 저절로 갑니다. 아래 띠에 있는 셋만
이 PC 를 켜야 도는데, 그건 시간에 맞춰 도는 일이 아니라 사람이 부르는 일입니다.

## 1. 손으로 하는 것은 하나뿐이다

| 순서 | 무엇을 한다 | 보드 | 누가 |
|---|---|---|---|
| 1 | 이슈를 만든다. 본인에게 배정하고 기간을 넣는다 | Todo | 자동 |
| 2 | 폼에서 「작업 영역」과 「어느 관문까지」를 고른다 | 라벨 · 마일스톤 | 자동 |
| 3 | 작업 전 브랜치를 판다 | | 본인 |
| 4 | **이슈를 In Progress 로 옮긴다** | In Progress | **본인 (손으로)** |
| 5 | 작업하고 커밋한다 | | 본인 |
| 6 | PR 을 연다. 본문에 `Closes #번호` | In Progress | 자동 |
| 7 | 팀장이 확인한다 | | 팀장 |
| 8 | 머지되면 이슈가 자동으로 닫힌다 | Done | 자동 |

**4번 하나만 손으로 합니다.** 나머지는 전부 자동입니다.

> `Closes #29` 는 PR 을 **열 때가 아니라 머지될 때** 이슈를 닫습니다.
> 그래서 PR 이 먼저입니다. `main` 에 안 들어간 작업은 아직 끝난 것이 아닙니다.

## 2. 이슈를 만들면 무엇이 일어나나

| 언제 | 무엇이 | 어디서 |
|---|---|---|
| 이슈 생성 | 보드에 Todo 카드가 생긴다 | GitHub Projects |
| 이슈 생성 | 시작·종료 날짜가 박힌다 | `issue-dates.yml` |
| 이슈 생성 | 담당자가 작성자로 지정된다 | GitHub Projects |
| 이슈 생성·수정 | **폼의 답이 라벨·마일스톤이 된다** | `issue-triage.yml` |
| 이슈 생성·수정 | 팀장 텔레그램으로 알림 | `issue-triage.yml` |
| 이슈 닫힘 | 보드가 Done 으로 | GitHub Projects |

**폼의 답이 옮겨지는 것이 핵심입니다.** 전에는 「어느 갈래인가」를 물어놓고 그 답이
본문 글자로만 남아 보드에서 묶이지 않았습니다. 팀원이 안 적어서가 아니라
**적은 것이 옮겨지지 않아서** 팀장이 손으로 분류하고 있었습니다.

작업 영역을 안 고르면 팀장 텔레그램에 **「분류 안 됨」** 이 갑니다. 조용히 넘어가지 않습니다.

### 이슈 템플릿

| 템플릿 | 언제 | 어디 |
|---|---|---|
| 작업 등록 | 이런 작업을 하겠다고 미리 올릴 때 | lab · go2 |
| 실험 기록 | 가설 하나, 변경 하나. 결과를 숫자로 판정할 때 | go2 |
| 리서치 | 답을 모르는 질문이 있을 때 | lab |
| 막힘·오류 | 안 되는 것이 있을 때 | lab · go2 |

**빈 이슈로 만들지 않습니다.** 목록에서 골라야 폼이 뜨고, 폼이 있어야 자동 분류가 됩니다.

## 3. 문서를 올리면 무엇이 일어나나

```
inbox/<내이름>/ 에 md 를 올리고 PR
        ↓
① 디스코드 알림                          팀에 새 제출을 알린다
② 팀장 텔레그램 검수 결과                 무엇이 갖춰졌고 무엇이 빠졌나
③ PR 코멘트: 채워진 머리 다섯 줄          복사해서 붙이면 끝
        ↓
팀장이 확인하고 머지
        ↓
④ [승격 검토] 이슈 생성                   남은 일(정본으로 옮기기)만 추적
        ↓
팀장이 docs/ 로 승격
        ↓
⑤ 다음 웹 빌드에 페이지로 나간다
```

**③이 새로 생긴 것입니다.** 문서 머리 다섯 줄이 없으면 봇이 **채워진 블록을 코멘트로**
달아 줍니다. 무엇을 어떻게 쓰라고 설명하는 것보다 **완성된 예시를 주는 게 빠릅니다.**

봇이 채우는 것과 못 채우는 것이 갈립니다.

| 줄 | 봇이 채우나 |
|---|---|
| `> 작성: 이름 · 날짜 시각` | 채운다 (PR 작성자를 이름으로 바꿔서) |
| `> 상태: 초안` | 채운다 |
| `> 분류:` `> 근거:` `> 요지:` | 못 채운다. 내용을 읽어야 안다 |

## 4. 그 밖에 저절로 도는 것

| 언제 | 무엇 | 워크플로 |
|---|---|---|
| PR 이 열리면 | 디스코드 알림 | `pr-notify.yml` |
| PR 이 머지되면 | 디스코드 알림 | `merge-notify.yml` |
| 이슈가 닫히면 | 완료 날짜 기록 | `done-date.yml` |
| 월요일 09시 | 주간 리포트 + **WBS 엑셀 생성** | `weekly-report.yml` |
| 일요일 21시 | **다이제스트 재료 수집** | `weekly-digest.yml` |
| 조선대 자료가 올라오면 | 감지 알림 | `lecture-watch.yml` |
| 마감이 다가오면 | 알림 | `deadline-alert.yml` |
| `main` 에 직접 push 하면 | 감지하고 안내 | `main-guard.yml` |
| 09:00 · 21:00 | **RunPod 잔액 감시** (경고 $50 · 위험 $20) | `runpod-balance.yml` |
| 이슈가 열리거나 닫히면 · 매일 06시 | **원장 열린 이슈 전수 집계** | `ledger-sync.yml` |

### 원장은 어디까지 기계가 쓰나

`docs/LEDGER.md` 의 「열린 이슈 전수」 절은 **기계가 다시 씁니다.** 사람이 세어 적던
동안 같은 날 안에서도 수가 51 · 57 · 60 · 71 · 72 · 81 · 79 로 흔들렸고, 그때마다
관문 `[3.8]` 이 배포를 세웠습니다 (`#161`).

기계가 쓰는 자리는 마커 안뿐입니다.

| 자리 | 누가 쓰나 | 왜 |
|---|---|---|
| 절 제목의 날짜와 건수 · 「관문에 걸린 것」 · 「사람별로 열린 것」 | 기계 | GitHub 이 답을 갖고 있는 사실입니다 |
| 「손이 오래 안 간 것」 · 「막고 있는 것」 | **사람** | 「왜 남아 있나」 「무엇을 막나」 는 판단입니다. API 에 답이 없습니다 |

마커 밖은 한 글자도 건드리지 않습니다. 다만 사람이 쓰는 두 표에 **닫힌 이슈가
남아 있으면 경고만** 띄웁니다. 지울지 다시 판단할지는 사람이 정할 일입니다.

### 다이제스트는 왜 「재료」만 모으나

다이제스트는 **「무엇을 알게 됐나」** 를 쓰는 문서입니다. 그건 판단이라 기계가 대신
못 씁니다. 커밋 목록에서 「보상이 높다고 걷는 것이 아니다」 같은 문장은 나오지 않습니다.
**기계가 흉내 내면 그럴듯하고 틀린 글이 남습니다.**

그래서 모으는 일만 자동으로 합니다. PR · 닫힌 이슈 · 새 문서 · 커밋을 모아
팀장 텔레그램으로 보냅니다. 쓰는 일은 사람이 합니다.

## 5. 아직 자동이 아닌 것

| 무엇 | 왜 사람이 하나 |
|---|---|
| Todo → In Progress | 「지금 시작했다」는 본인만 안다 |
| inbox → `docs/` 승격 | 무엇을 정본으로 올릴지는 판단이다 |
| 다이제스트 본문 | 위 참조 |
| 산출물 상태를 `확정` 으로 | 완료 기준을 보고 사람이 판정한다 |
| 마일스톤 지정 | 「언제까지 끝나야 하나」는 담당자만 안다 |

## 6. 브랜치와 커밋

```
feature/주제-이름      새로 만드는 것
fix/무엇이안되나-이름    고치는 것
docs/문서명-이름        문서만
```

**이슈 번호를 붙이지 않습니다.** 뒤에 자기 이름을 붙입니다.
다섯이 같은 주제를 만져도 브랜치가 안 겹칩니다.

| 이름 | 임석헌 | 맹라현 | 오현민 | 오흥재 | 이민우 |
|---|---|---|---|---|---|
| 브랜치 약자 | `lim` | `meang` | `oh` | `jay` | `lee` |
| GitHub 핸들 | `IQ152` | `maengu86` | `less82` | `vfxpedia` | `lmw0207` |

**추적의 핵심은 브랜치 이름이 아니라 커밋·PR 의 `Closes #번호` 입니다.** 이것만은 반드시.

`foothold-go2` 는 한 단계가 더 있습니다. 코드 저장소라 검증된 것만 `main` 에 둡니다.

```
feature/…  ->  PR  ->  dev  ->  검증된 것만 PR  ->  main
```

머지된 브랜치는 지웁니다. 브랜치는 소모품입니다.

## 7. 어디에 무엇을 올리나

| 무엇 | 어디에 | 어떻게 |
|---|---|---|
| **문서** (정리 안 된 것 포함) | `inbox/<내이름>/` | PR. 팀장이 확인하고 머지 |
| **코드** | `sim/` `nav/` `common/` | 브랜치 → PR. **inbox 를 거치지 않는다** |
| 정본 문서 `docs/` | 직접 고치지 않는다 | 팀장이 inbox 에서 승격 |

**코드가 inbox 를 안 거치는 이유**: 문서는 팀장이 옮겨도 뜻이 안 변하지만
**코드는 옮기면 도는지 보장할 수 없습니다.**

### 폴더가 작업 영역과 짝을 이룹니다

| 작업 영역 | 폴더 | 주담당 |

| `A/지형씬제작` | `sim/terrain/` | 맹라현 |
| `A/평가` | `sim/eval/` | 오현민 |

## 8. AI 를 쓸 때

### AI 가 썼어도 올리는 사람은 본인이다

AI 가 만든 글이든 코드든 **PR 을 올린 사람이 책임집니다.** 읽지 않고 올리지 않습니다.

### 지어낸 것을 거른다

AI 는 없는 함수·없는 논문·없는 수치를 **자신 있게** 만들어 냅니다.
**숫자와 출처는 반드시 눈으로 확인**하십시오.

### 직접 본 것과 들은 것을 구분한다

주장에 신뢰도를 답니다. 이게 이 팀 문서의 핵심 규칙입니다.

```
`확인됨`   직접 보거나 재서 확인한 것
`추측`     그럴듯하지만 확인 안 한 것
`미확인`   확인이 필요한 것
`미측정`   재보지 않은 수치
```

**재보지 않은 것에 「확인했다」를 쓰지 마십시오.** 확인 비용이 2분이면 확인하십시오.

### 비공개 자료를 통째로 넣지 않는다

조선대 강의 자료 원본 · 팀 내부 문서 · 계정 정보 · 개인정보는 AI 에 넣지 않습니다.

### 코드는 돌려보고 올린다

AI 가 준 코드가 **도는지 확인하고** 올립니다. 「그럴듯한 코드」와 「도는 코드」는 다릅니다.

### AI 사용을 숨길 필요는 없다

우리는 AI 를 씁니다. 문제는 쓰는 것이 아니라 **확인 없이 올리는 것**입니다.

## 9. AI 에이전트에게 시킬 때 걸리는 것

### 작업 전에 반드시 `git pull origin main`

옛 상태에서 갈라진 브랜치로 작업하면 AI 는 **그 시점의 저장소만** 봅니다.
오래된 상태를 주면 오래된 답이 나옵니다. 8/25 와 8/26 에 같은 사고가 두 번 났습니다.

### 저장소 루트의 `AGENTS.md` 를 읽게 하십시오

Cursor 와 Codex 는 자동으로 읽습니다. Claude Code 는 `CLAUDE.md` 를 읽는데
그것도 같은 곳을 가리킵니다. **여러분이 따로 하실 일은 없습니다.**

개인 작업 방식은 `AGENTS.md` 에 적지 말고 `inbox/<이름>/AGENTS.md` 를 만들거나
로컬 설정(gitignore 대상)으로 두십시오. 공통 파일에 개인 설정이 섞이면
**다른 사람의 에이전트가 그것을 규칙으로 읽습니다.**

### AI 가 거의 확실하게 걸리는 것

| 무엇 | 왜 |
|---|---|
| **em dash** (긴 줄표) | AI 가 습관처럼 씁니다. 빌드가 배포를 멈춥니다 |
| 선으로 그린 글자 도식 | 표로 바꿔야 합니다 |
| 근거 표기 없는 단정 | `확인됨`/`추측`/`미확인` 을 답니다 |
| 머리 다섯 줄 누락 | PR 봇이 채워진 블록을 줍니다 |

## 10. 웹 배포 관문

**PR 은 막지 않습니다. 알려만 줍니다.** 막는 것은 **웹을 배포할 때**입니다.

규칙을 문서에만 적으면 안 지켜지고, **관문을 한 자리에만 달면 나머지 자리에서
조용히 무너집니다.** 실제로 하루에 같은 부류를 다섯 번 봤습니다 (커널 철칙 4).

- `[3.56]` 표 정렬: 모바일 CSS 가 표를 내용 너비로 줄여 좁은 표만 왼쪽으로 쏠렸습니다

## 11. 실수로 `main` 에 push 했다면

### 팀원이 할 것 (세 가지뿐)

1. **더 만지지 마십시오.** 되돌리려다 더 꼬입니다
2. 팀장에게 알리십시오. 무엇을 push 했는지만
3. 기다리십시오

### 팀장이 할 것

되돌릴지 그대로 둘지 판단하고 처리합니다. `main-guard.yml` 이 감지해서 알려 줍니다.

## 12. 신경 쓰지 않아도 되는 것

| 무엇 | 왜 |
|---|---|
| 웹 배포 | 팀장이 빌드합니다. `foothold-site` 를 직접 고치지 마십시오 (미러입니다) |
| 라벨·마일스톤 붙이기 | 폼에서 고르면 자동입니다 |
| 보드 카드 만들기 | 이슈를 만들면 자동입니다 |
| 문서 형식 완벽하게 맞추기 | `inbox/` 는 자유입니다. 봇이 알려 줍니다 |

## 13. 기억할 것은 이것뿐입니다

```
1. 작업 전에 git pull origin main
2. 이슈를 만들고 「작업 영역」을 고른다
3. 시작하면 In Progress 로 옮긴다
4. 커밋·PR 에 Closes #번호
```

**나머지는 자동입니다.** 막히면 「막힘·오류」 이슈로 올려 주십시오.
