# PR 체크 구조: 어느 워크플로가 무엇을 막는가

> 분류: 운영
> 작성: 오흥재 · 2026-09-08 16:40
> 근거: 실측 (워크플로 20종 전수 · 19종 감사 + `ledger-sync` 신설 · Actions API 런 기록 · 실패 런 로그 원문 · 로컬 시험 16건)
> 요지: PR 을 막던 것은 «head 브랜치 워크플로»가 아니라 «알림 실패가 관문 실패로 보인 것»이었다. 알림 워크플로 둘을 어떤 이유로도 실패하지 않게 바꿨다.
> 상태: 확정
> 판: v1.2

이슈 `#307` 의 답이다. 결론부터: **`#307` 이 적어 둔 원인 진단은 이미 지난 것이었다.**
`가`와 `나`는 2026-08-26 에 이미 적용돼 있었고, 실제로 PR 을 막던 것은 다른 것이었다.

## 1. 워크플로 20종 전수

**워크플로 파일을 «어느 브랜치에서» 읽는가**가 이 문제의 핵심이다. 트리거가 정한다.

| 트리거 | 파일을 읽는 곳 | 해당 워크플로 |
|---|---|---|
| `schedule` · `workflow_dispatch` | 기본 브랜치(main) 고정 | `deadline-alert` `failure-watch` `lecture-watch` `notice` `project-views` `runpod-balance` `weekly-digest` `weekly-report` `ledger-sync` |
| `issues` · `issue_comment` | 기본 브랜치(main) 고정 | `discord-notify` `done-date` `issue-dates` `issue-triage` `merge-on-comment` `promote` `ledger-sync` |
| `push: [main]` | 밀린 브랜치 = main | `discord-notify` `inbox-alert` `main-guard` `merge-notify` |
| **`pull_request_target`** | **base(main)** | **`inbox-pr-alert` `pr-notify`** |
| `pull_request` | head(PR 브랜치) | **없음** |

**PR 에서 도는 것은 20종 중 둘뿐이고, 둘 다 이미 `pull_request_target` 이다.**
`pull_request` 를 쓰는 워크플로는 하나도 없다. Actions API 로 확인했다.
`event=pull_request` 인 마지막 런은 **2026-08-26T00:02Z** 이고 그 뒤로 0건이다.

체크아웃도 함께 봐야 한다. 트리거가 base 를 읽어도 체크아웃이 head 를 받으면 소용이 없다.

| 워크플로 | `actions/checkout` | 무엇을 받나 |
|---|---|---|
| `pr-notify.yml` | 없었음 (이번에 base 체크아웃 추가) | API 메타데이터만. head 의존 0 |
| `inbox-pr-alert.yml` | `ref` 없음 = base(main) | 스크립트는 main 것. head 에서는 `inbox/` **데이터만** 꺼낸다. 실행하지 않는다 |

나머지 17종은 PR 에서 돌지 않으므로 head 의존이 성립하지 않는다.

## 2. 그럼 무엇이 닷새를 막았나 (실측)

`#307` 은 「head 브랜치 워크플로로 돌아서」라고 적었다. **런 로그를 열어 보면 아니다.**

블록됐던 `#250` 의 재실행(run `33955321883` attempt 2)을 받아 읽었다.

```
2026-09-08T06:20:47Z  텔레그램 HTTP 400
2026-09-08T06:20:47Z  전송 실패
2026-09-08T06:20:47Z  ##[error]Process completed with exit code 1
```

`review_inbox.py 가 없습니다` 는 **한 번도 실제로 나오지 않았다.** 로그에 보이는 그 줄은
실행된 것이 아니라 셸이 스크립트를 그대로 찍어 준 것이다. 즉 `#306` 의 진단은 빗나갔고,
진짜 원인은 `#302` 의 텔레그램 400(본문 길이 초과) 이었다.

### 왜 고쳐도 안 닿았나

여기가 `#307` 이 잡아낸 진짜 구조 문제다. **GitHub 는 «재실행»을 원래 런에 묶인
워크플로 판으로 돌린다.** `pull_request_target` 이어도 그렇다.

| 시각 (UTC) | 일 |
|---|---|
| 05:46 | `#302` 고침이 main 에 들어감 (파일 15개 제한 · 3500자 컷) |
| 06:20 | `#250` 을 **재실행**. 여전히 HTTP 400 으로 실패 |
| 06:22 | 브랜치에 손으로 main 을 머지. 새 이벤트가 나고 그제야 통과 |

재실행이 옛 판을 돌렸다는 것은 추정이 아니라 **로그로 확인**했다.

| 로그에서 찾은 것 | 결과 |
|---|---|
| `names[:15]` (#302 의 제한) | 0건 |
| `외 %d개` | 0건 |
| `3500` (길이 컷) | 0건 |
| `for line in os.environ.get('FILES', '').split(...)` (옛 무제한 반복) | 있음 |

main 에는 34분 전에 들어간 고침이, 재실행에는 없었다. **재실행으로는 열린 PR 을 못 푼다.**
사람이 브랜치마다 main 을 넣어야 하고, 잊으면 영원히 막힌다.

## 3. 네 갈래 판정

| | 방법 | 판정 |
|---|---|---|
| 가 | `pull_request_target` 으로 바꾼다 | **이미 돼 있다.** 2026-08-26 에 적용. 고를 것이 없다 |
| 나 | 스크립트를 main 에서 받아 쓴다 | **이미 돼 있다.** 체크아웃이 base 라 스크립트는 늘 main 것이다. 다만 «재실행 고정» 은 이것으로도 안 풀린다. 체크아웃 자체가 원래 런의 SHA 에 묶이기 때문이다 |
| **다** | **알림을 필수 체크에서 뺀다** | **이것을 골랐다.** 근거는 아래 |
| 라 | 손으로 넣는다 | 폐기. 사람이 잊으면 영원히 막힌다. 실제로 닷새 막혔다 |

### 왜 「다」인가

**셋 다 «알림 실패가 검수 실패로 보이는 것»을 못 막는데, 「다」만 막는다.**
`가`·`나`를 아무리 잘 해 놔도 전달이 한 번 400 을 내면 PR 은 빨간불이 된다. 실제로
그렇게 됐다. 반대로 알림이 PR 을 못 막게 하면, 워크플로 판이 낡았든 재실행이 옛 것을
돌리든 **멀쩡한 PR 이 막히는 일 자체가 사라진다.** 가장 얕은 곳이 아니라 가장 넓은 곳이다.

**잃는 것이 없다.** 이 둘은 검수를 하지 않는다. 디스코드·텔레그램으로 알리고 안내
코멘트를 다는 것이 전부다. 관문 기능이 0 이므로 관문에서 빼도 잃는 판정이 없다.

**애초에 «필수 체크» 라는 것이 없다.** 이 저장소는 비공개이고 요금제상 브랜치 보호와
룰셋을 못 쓴다. API 가 `403 Upgrade to GitHub Pro` 를 준다. 즉 빨간불은 머지를 기술적으로
막지는 않고 **사람을 오도할 뿐이다.** 그래서 «체크에서 빼기» 는 설정이 아니라
**워크플로 안에서** 해야 한다.

### 「다」의 위험과 그 처리

`#307` 이 적은 위험은 「진짜 실패도 안 보인다」 였다. 맞는 지적이다. 셋으로 막았다.

1. **일시적 실패는 되시도한다.** `429` `5xx` `000` 은 3회까지, 3초·6초 간격. 09-08 에
   실제로 `429` 로 죽은 런이 있었다(run `34193264785`). 그 부류는 이제 저절로 산다
2. **끝내 실패하면 세 자리에 남긴다.** `::warning::` 주석 · 런 요약 한 줄 ·
   **다른 채널로 짧은 통보**. 원인이 «본문이 길어서» 인 경우 짧은 한 줄은 들어간다
3. **판정 단계를 마지막에 둔다.** `if: always()` 로 늘 돌면서 「몇 건 보냈고 몇 건
   실패했는지」를 런 요약에 적는다. 아무것도 안 보낸 경우도 **그렇다고 적는다.**
   조용한 성공과 조용한 실패가 구별되지 않으면 감시가 없는 것과 같다

## 4. `pull_request_target` 시크릿 노출 검토

`가`가 이미 적용돼 있으므로 이 검토는 «새로 도입할지» 가 아니라 **«지금 안전한지»** 다.
이 이벤트는 시크릿을 쥐고 돌기 때문에 근거 없이 넘어가면 안 된다.

**위험의 정체는 이벤트가 아니라 «PR 이 준 코드를 실행하는 것»이다.** 외부인이 PR 로
스크립트를 고쳐 올리고 그것이 시크릿을 쥔 채 실행되면 토큰이 샌다.

| 점검 | 실측 |
|---|---|
| 체크아웃이 head 를 받나 | **아니다.** `ref` 를 주지 않아 base(main) 를 받는다 |
| head 의 코드를 실행하나 | **아니다.** `git checkout refs/remotes/pr/N -- inbox/` 로 `inbox/` **한 경로만** 꺼낸다. `.github/` 와 스크립트는 어떤 경우에도 안 덮인다 |
| 꺼낸 파일을 실행하나 | **아니다.** `find inbox -type f` 로 세기만 한다. `inbox/` 안에 `.py` 가 실제로 들어 있지만 (`inbox/jay/20260904-launch/scripts/*.py`) 부르는 자리가 없다 |
| 누가 PR 을 열 수 있나 | 비공개 저장소. 초대된 팀원만. 포크 PR 경로가 사실상 없다 |
| 권한 | `contents: read` · `pull-requests: write`. 쓰기는 코멘트용 하나 |

**결론: 지금은 안전하다. 단, 안전은 «한 줄»에 걸려 있다.**

> ⚠️ `inbox-pr-alert.yml` 에 **`inbox/` 아래 파일을 실행하거나 소싱하는 단계를
> 절대 추가하지 말 것.** `python inbox/...` · `bash inbox/...` · `pip install -r inbox/...`
> 전부 해당한다. 그 한 줄이 들어가는 순간 이 워크플로는 시크릿 탈취 경로가 된다.
> 체크아웃에 `ref: ${{ github.event.pull_request.head.sha }}` 를 더하는 것도 같다.

## 5. 무엇을 바꿨나

**새 파일** `.github/scripts/notify_send.sh` · 전달 전담. 되시도 · 길이 자르기 ·
실패 보고 · 다른 채널 우회를 여기 모았다. **어떤 경우에도 0 을 돌려준다.**

**`inbox-pr-alert.yml`** 과 **`pr-notify.yml`** 에서 PR 을 빨갛게 만들 수 있던 자리를
전부 없앴다.

| 자리 | 전 | 후 |
|---|---|---|
| 디스코드 비 2xx | `exit 1` | 경고 + 요약 + 텔레그램 우회 |
| 텔레그램 비 2xx | `exit 1` | 경고 + 요약 + 디스코드 우회 |
| 웹훅 미설정 | `exit 1` | 경고 후 계속 |
| 안내 코멘트 생성 실패 | `exit 1` | 경고 + 요약 |
| 코멘트가 안 늘어남 | `exit 1` | 경고 + 요약 |
| `git fetch` 실패 | `set -e` 로 사망 | 경고 후 계속 (API 로 목록을 읽으니 알림은 나간다) |
| PR 파일 목록 조회 실패 | `set -e` 로 사망 | 경고 후 생략 |

길이 자르기는 **한 자리로 모았다.** 전에는 `inbox-pr-alert.yml` 안에만 있었고
**`pr-notify.yml` 에는 아예 없었다.** 제목이 길면 그쪽도 400 이 날 수 있었다.
자르기는 «보내는 쪽»의 일이라 전달기로 옮겼다. 규칙이 사는 자리를 세지 않으면
한 곳은 늘 빠진다.

## 6. 시험 결과

### 로컬 · 알려진 답 (16건 전부 통과)

가짜 `curl` 로 HTTP 코드를 지정해 두고 기대값과 대조했다.

| 넣은 것 | 기대 | 실제 |
|---|---|---|
| `200` | 1회 시도 · 성공 · RC 0 | 같음 |
| `400` | **되시도 안 함** · 실패 기록 · **RC 0** | 같음 |
| `429 429 200` | 3회째 성공 · RC 0 | 같음 |
| `429` 계속 | 3회 후 포기 · **RC 0** | 같음 |
| `503 200` | 2회째 성공 | 같음 |
| `000` (못 붙음) | 3회 후 포기 · RC 0 | 같음 |
| 6000자 본문 | 3516자로 잘림 · UTF-8 정상 | 같음 |
| 짧은 본문 | 안 자름 | 같음 |
| 시크릿 없음 | 건너뛰고 RC 0 | 같음 |
| 상태 파일 빈 채 판정 | 「보낸 알림 없음」 | 같음 |

**실제 워크플로 단계를 그대로 실행해서도 확인했다.** 파일 42개짜리 PR 을 만들어
텔레그램 400 을 먹였다. 닷새를 막았던 바로 그 조합이다.

```
telegram HTTP 400 (1/3)
::warning::알림 전달 실패 · inbox 제출 · 텔레그램 · telegram HTTP 400. PR 내용과는 무관합니다
우회 통보 디스코드 HTTP 204
RC=0            <- 전에는 1 이었고 그래서 PR 이 빨간불이었다
```

본문은 42개를 다 찍지 않고 15줄 + `외 27개` 로 줄었다.

### 문법

`python -c "import yaml; yaml.safe_load(...)"` 로 둘 다 파싱을 확인했다.
`inbox-pr-alert` job 1개 step 7개 · `pr-notify` job 1개 step 4개.
`run` 블록 9개를 전부 뽑아 `bash -n` 을 돌렸다. 오류 0.

> **곁다리 교훈 하나.** 처음에 `bash -n` 을 파이프로 먹였더니 두 건이 «문법 오류» 로
> 나왔다. 스크립트가 아니라 **파이프가 한글을 cp949 로 뭉갠 것**이었다. UTF-8 파일로
> 써서 다시 돌리니 9개 전부 통과했다. 도구가 낸 실패도 결과가 아니다.

## 7. 남은 것

1. **재실행 고정 자체는 GitHub 동작이라 못 없앤다.** 다만 이제 알림이 PR 을 막지
   못하므로 «막힌 채로 남는» 결과가 안 생긴다. 워크플로에 **진짜 관문**을 새로 만들
   때는 이 성질을 반드시 기억할 것. 고치고 재실행해도 안 닿는다. 새 이벤트가 필요하다
   (커밋을 얹거나 PR 을 닫았다 여는 것이 브랜치에 main 을 머지하는 것보다 싸다)
2. **`failure-watch.yml` 은 이제 이 둘의 전달 실패를 못 본다.** 실패한 런만 세기
   때문이다. 지금은 다른 채널 우회 통보가 그 자리를 대신한다. 두 채널이 동시에 죽으면
   런 요약에만 남는다. **그래도 감시를 안 늘린 이유는 아래 8절에 적었다**
3. **em dash 가 워크플로에 15군데 남아 있었다.** `#316` 으로 빼서 `#321` 에서 전부
   지웠다. 그중 `weekly-report.yml` 의 셋은 주석이 아니라 **매주 디스코드로 나가는
   출력 문자열**이었다. 빌드 관문이 웹 산출물만 보기 때문에 `.github/` 는 검사되지
   않는다. **관문 자체는 아직 없다.** 규칙이 사는 자리를 다 세지 않은 전형적인 경우다
4. `#306` 의 진단(「옛 브랜치에 검수기가 없다」)은 빗나간 것이었다. 코드 자체는
   그대로 두어도 해롭지 않아 남겼다. 진짜 원인은 `#302` 였다

## 8. 왜 감시를 안 늘렸나 (2026-09-08 팀장 확정)

7절 2번을 읽고 「그러면 전달 실패를 아무도 못 보는 것 아닌가」라고 물을 사람을 위해
적어 둔다. **판정 결과를 따로 적어 `failure-watch.yml` 이 읽게 만드는 것을 검토했고,
지금은 하지 않기로 했다.**

근거는 하나다. **채널이 통째로 죽은 사례가 없다.** 지금까지 겪은 전달 실패는 전부
우리 쪽 버그였다.

| 무엇 | 언제 | 실제 원인 |
|---|---|---|
| 텔레그램 `400` | 2026-09-08 | 우리가 파일 목록을 안 잘라 4096자를 넘겼다 (`#302`) |
| 텔레그램 `429` | 2026-09-08 | 우리가 재실행을 여러 번 걸어 속도 제한에 걸렸다 |
| 텔레그램 배치 보고 2회 누락 | 2026-09-04 | Bash 가 Windows 경로의 백슬래시를 먹어 스크립트가 인수 없이 돌았다. **종료코드는 0 이었다** |

**셋 다 채널 장애가 아니다.** 그리고 이번 판에서 앞의 둘은 구조적으로 막혔다.
길이는 보내는 쪽에서 자르고, `429` 는 되시도한다.

두 채널이 **동시에** 죽어야 우리가 눈이 머는데, 그런 일이 일어난 적이 없고 그때도
런 요약에는 남는다. **관측된 적 없는 실패를 위해 감시 장치를 먼저 세우는 것은 지금
근거로는 과하다.** 안 쓰는 장치는 썩고, 썩은 장치는 있는 것이 없는 것보다 나쁘다.

> **다시 볼 조건.** 디스코드나 텔레그램이 **우리 버그가 아닌 이유로** 죽는 것이 한 번이라도
> 관측되면 이 결정을 되돌린다. 그때는 판정 결과를 파일이나 이슈로 남기고 감시가 그것을
> 읽게 만든다. 지금은 우회 통보와 런 요약으로 충분하다.

**자동 차단 계획은 없다.** 이 저장소는 요금제상 필수 체크를 못 쓰고(4절), `PR-REVIEW-FLOW`
도 **사람이 판단하는 것**으로 썼다. `inbox-pr-alert.yml` 이 나중에 관문이 될 일은 없다.
검수를 기계로 막을 생각이 생기면 **이 워크플로가 아니라 별도 관문**을 세워야 한다.
