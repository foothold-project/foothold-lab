# PR 검수 흐름: 누가 무엇까지 결정하는가

> 분류: 운영
> 작성: 오흥재 · 2026-09-08 15:10
> 근거: 팀장 지시 2026-09-08 · 실측 (열린 PR 6건 · inbox 적체 35건)
> 요지: 팀원 PR 검수와 승격을 site 세션이 맡고 supervisor 는 보고만 받는다. 자율로 처리할 것과 올려야 할 것을 갈라 둔다.
> 상태: 확정
> 판: v1.2

## 왜 만드나

**supervisor 가 병목이 됐다.** 팀장이 2026-09-08 에 지적했다.

> 내가 지금 여기서 전체 흐름을 보고 있는데 여기서 만약에 내가 병목이 지금처럼 일어나면
> 팀원들이 PR 요청하고 올렸던 것들이 하나도 반영이 안 된다.

실측하면 이렇다. **PR 은 막혀 있지 않았다.** 오현민 `#106` `#63`, 이민우 `#127`, 임석헌
`#278`, 맹라현 `#276` `#277` 모두 머지됐다.

**막힌 것은 그 다음이다.**

| 단계 | 상태 |
|---|---|
| PR 머지 | 잘 된다 |
| inbox 적재 | 된다 |
| **승격** | **35건이 쌓여 있다** (oh 5 · lee 2 · lim 8 · meang 14 · jay 6) |
| **웹 반영** | 승격 안 된 것은 안 보인다 |

승격 검토 이슈는 자동으로 열리는데 **닫는 사람이 없다.** 그래서 팀원이 낸 것이
저장소에는 있고 웹에는 없다. 낸 사람 입장에서는 **반영이 안 된 것과 같다.**

## 누가 무엇을 하나

```
팀원      PR 을 올린다
site      검수 · 머지 · 승격 · 웹 반영
supervisor 보고를 받고 팀장에게 전한다
팀장      방향을 정한다
```

**supervisor 가 PR 을 직접 만지지 않는다.** 보고만 받는다. 그래야 팀장이 방향을 논의하는
동안에도 팀원 산출물이 흐른다.

## site 가 자율로 처리하는 것

**아래 넷을 모두 만족하면 묻지 말고 머지한다.**

1. `inbox/` 아래 문서와 그림·영상만 바뀐다
2. `sim/` `_build/` `.github/` 를 건드리지 않는다.
   **`docs/research/` 로의 승격은 예외다.** 승격이 site 일이니 당연히 건드린다.
   다만 승격 말고 `docs/` 를 고치는 것(운영 문서 · 정본 규칙)은 올린다
3. 빌드 관문이 통과한다
4. 대외비가 없다 (아래 참조)

**머지한 뒤 승격까지 판단한다.** 승격 기준은 다음 절에 있다.

## site 가 supervisor 에게 올리는 것

**하나라도 걸리면 머지하지 말고 보고한다.**

| 무엇 | 왜 |
|---|---|
| 코드 변경 (`sim/` `_build/` `.github/`) | 평가와 자동화가 걸린다. 되돌리기 어렵다 |
| 정본 실측 결과 수정 | 숫자가 바뀌면 그 위에 선 문서가 전부 흔들린다 |
| 충돌이 난 PR | 어느 쪽을 살릴지가 판단이다 |
| 관문이 실패한 PR | **왜 실패했는지 먼저 본다.** 알림 실패와 검수 실패는 다르다 |
| 팀원 문서를 «고쳐야» 하는 경우 | 남의 글은 고치지 말고 PR 로 컨펌받는다 |
| 판단이 애매한 것 | 애매하면 올린다. 잘못 머지하는 것보다 싸다 |

**관문 실패를 그냥 넘기지 않는다.** 2026-09-08 에 `#301` 이 빨간불이었는데 원인이
텔레그램 400 이었다. 영상 42개라 알림 본문이 길이 제한을 넘은 것이고 **내용에는 문제가
없었다.** 알림이 죽은 것을 검수가 죽은 것으로 읽으면 멀쩡한 PR 이 막힌다.

## 승격 기준

**inbox 는 제출함이고 승격은 정본 인정이다. 전부 올리는 것이 아니다.**

| 올린다 | 두고 본다 |
|---|---|
| 실험 결과와 실측 | 개인 학습 기록 |
| 연구 대조 · 문헌 정리 | 회의 메모 |
| 팀이 근거로 쓸 문서 | 초안 · 작업 중인 것 |
| 다른 문서가 인용하는 것 | 한 번 쓰고 마는 것 |

**「다른 문서가 인용하는 것」이 특히 중요하다.** 인용되는 문서가 inbox 에 있으면 근거를
못 보는 상태가 된다. 2026-09-07 에 `rails-diagnosis` 가 그랬다. 발 높이 33.5 cm 를
세 문서가 근거로 쓰는데 정작 그 문서가 웹에 없었다.

**승격에 필요한 것 셋.** 없으면 갖춰서 PR 로 컨펌받는다. 직접 고치지 않는다.

- 머리 다섯 줄 (분류 · 작성 · 근거 · 요지 · 상태)
- `> 판: vX.Y`
- `## 판 이력` 표

## 사람 이름은 지어내지 않는다

**문서에 사람 이름을 쓸 때는 `docs/ROLES.md` 에 있는 것만 쓴다.** 거기 없으면
**직함으로 적는다**(「팀장」 · 「멘토」).

**추측으로 쓰지 않는다.** 틀리면 그 사람을 잘못 부르는 것이고, 문서에 남으면
**다음 사람이 그것을 옳은 것으로 읽는다.**

**왜.** 2026-09-09 에 없는 이름(「방재혁」)이 문서 셋의 머리말 `> 작성:` 줄에
들어갔다. 팀장이 직접 지적해서 알았다. 같은 날 다른 세션 산출물은 전부
`ROLES.md` 에 있는 이름이었고 그 셋만 달랐다.

**같은 자리에서 나도 틀렸다.** `tools/isaac/README.md` 에 「방재준 팀장」이라고
적었는데 그 이름도 확인한 적이 없었다. 지적받은 것은 앞의 셋이지만 같은
부류라 함께 지웠다(`#353`).

**지금 `ROLES.md` 에 있는 이름은 다섯이다.** 오흥재 · 임석헌 · 맹라현 ·
오현민 · 이민우. **팀장 이름은 저장소 어디에도 표기가 없다.** 그래서
직함만 쓴다. 표기가 정해지면 `ROLES.md` 에 넣고 이 줄을 고친다.

**하위 세션에 일을 시킬 때 이 규칙을 지시서에 넣는다.** 세션은 이름을 알 수
없으므로, 적으라고 하면 지어낸다.

## 대외비

**금액은 하나만 가린다.** 우리가 Go2 를 대여하는 비용이다. 조달 공고 금액 · 기사 금액 ·
장비 정가는 공개해도 된다. 2026-09-04 팀장 확정이다.

**ID 와 비밀번호는 웹에 올리지 않는다.** 디스코드 resources 채널에만 둔다.

**조선대 자료는 외부 유출 금지다.**

## 보고

**의미 단위가 끝날 때마다 supervisor 에게 보낸다.** 다음을 담는다.

```
머지한 것       번호 · 작성자 · 무엇
승격한 것       무엇을 왜
웹에 뜬 것      «라이브에서 열어 확인한» 결과
올릴 것         판단이 필요한 것과 그 이유
```

**「머지했다」로 끝내지 않는다.** 라이브에서 열어 본 결과를 적는다. 배포가 됐다는 것과
그 페이지가 실제로 고쳐졌다는 것은 다르다.

## 이 흐름에 아직 구멍이 있다

**lab 에 승격했는데 웹에 안 뜬 상태를 아무도 안 잡는다.** lab CI 는 lab 만 본다.
2026-09-07 에 `#286` 이 CI 를 통과했는데 웹에는 없었다. 사람이 라이브를 열어보지 않았으면
「승격 완료」로 보고하고 넘어갔을 것이다.

**승격 PR 이 머지되면 site 빌드가 자동으로 돌게 하는 것**이 맞다. 지금은 사람이 두 번
움직여야 한다. 업무 철칙 4(관문은 한 층위만 보면 안 된다) 그대로다.
