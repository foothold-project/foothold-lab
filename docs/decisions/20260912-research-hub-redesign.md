## 1. 보존 계약 · 카드가 담는 것 전부

**대상은 `hub-research.html` 이다.** `research.html` 은 별도의 38장 목록이라
섞으면 안 된다.

「37장」은 **일반 목록 카드 36장 + 출발선 1장**이고 markup 이 다르다.

| 번호 | `.ex3` · 묶음마다 다시 시작하는 표시 순번. **문서 ID 가 아니다** | 36 |
| 왼쪽 | 수치 `.en3` (숫자 11 · `·` 9) **또는** 출처 `.en3.src.s-*` | 20 / 16 |

개선이 아니다.

## 2. 배치 · 「얹기」가 아니라 「바꾸기」

**v1.0 의 「카드 위에 얹는다」는 틀렸다.** 실측:

| | PC 1440 | 휴대폰 390 |
|---|---:|---:|
| 지금 첫 목록 카드 y | 1263.02 | 3342.88 |
| 입구만 더하면 | **+128** | **+180** |

이미 첫 카드가 두 번째 화면 아래에 있는데 더 밀면 나빠진다.

그래서 **출발선과 보드를 새 배포 요약으로 «대체»한다.**

| 차례 | 영역 | 무엇이 바뀌나 |
|---|---|---|
| 1 | 배포 요약 | **지금의 출발선 블록을 대신한다.** 출발선 문서는 목록에 남는다 |
| 2 | 찾는 입구 | 목록 «머리» 로 붙는다. 큰 카드 6장이 아니라 **짧은 거르개 단추** |
| 3 | 전체 문서 | 지금 카드 그대로. 거르개가 걸린다 |
| 4 | 지형 공략 | **목록 뒤로 내리거나 접는다.** 우선 점검은 배포 요약에 한 줄 |

지형 보드를 없애지 않는다. **자리를 옮긴다.** 목록 앞에 긴 보드를 다시
쌓지 않는 것이 요점이다.

## 6. 핵심 수치와 썸네일

### 6-1. 수치는 이미 자동이다

`num_in()` 이 뽑는다. **사람이 적는 것이 아니다.** 20자리 중 11개가 숫자이고
9개가 `·` 인 것은 뽑을 것이 없었다는 뜻이다.

그러니 할 일은 「사람이 적게 하기」가 아니라 **뽑기 규칙을 넓히고, 못 뽑은
자리는 원장이 덮어쓰게** 하는 것이다.

```
1. num_in() 이 뽑은 값
2. 원장의 metric_selector 가 있으면 그것이 이긴다
3. 둘 다 없으면 그 자리를 비운다 (`·` 도 안 넣는다)
```

### 6-2. 썸네일 우선순위를 못 박는다

v1.0 은 「첫 그림 우선」과 「원장이 이긴다」가 충돌했다. 순서를 정한다.

```
1. 원장의 thumbnail_selection   (사람이 고른 것이 언제나 먼저)
2. 그 문서 markdown 의 첫 ![](…)
3. 생성 보고서는 markdown 이 없다 -> 원장만
4. 영상은 포스터를 쓴다
5. 없으면 자리를 비운다 (회색 상자를 안 넣는다)
```

## 7. 원장 · 이관까지 적는다

**파일 이름을 하나 정했다고 원장이 하나가 되지 않는다.** 지금 흩어진 것을
어디로 옮기고 어느 코드가 무엇을 읽을지 적어야 한다.

`foothold-lab/docs/ops/research-catalog.json`

```
schema_version
groups[]
documents[id]
  source · function · areas_override · terrains · stages
  validity · supersedes · valid_for_release
  metric_selector · thumbnail_selection
releases[id]
  revision · source_refs · summary_scope
  headline · report_id · current_explanation_id
  published_document_snapshot · attention_ids
terrain_attention[]
  release · terrain · stage · evidence_id · issue_refs
```

**제목 · 요약 · 작성자 · 작성 시각 · 본문 상태 · 수치는 원본에서 읽는다.**
원장에는 «판단» 만 남긴다.

| 지금 어디 | 옮길 곳 |
|---|---|
| `doc-graph-overrides.json` 의 purpose | 원장 `function` |
| `release.json` 의 headline · report · note | 원장 `releases[]` |
| 보드의 단계·지형 수동 지정 | 원장 `terrain_attention[]` |
| **안 합치는 것** | GitHub 이슈 상태 · `page_overrides.json` · 브랜드 · 검사기 |

`purpose` 의 옛 값(`본PoC` · `PoC시험`)을 새 여섯 입구로 **덮어쓰지 않는다.**
다른 소비자가 깨진다. 옛 값은 `legacy_purpose` 로 두고 새 분류는 `function`.

## 8. 빌드가 저장소 밖이다

**이 설계는 세 저장소를 함께 바꾼다.**

```
C:/Users/AI-WS01/Desktop/jay/MAI_UNIVERSE/03_PROJECTS/doyak-final/05_deliverables/_build/
  hub3.py        허브 렌더
  docgraph.py    문서 그래프 · purpose
  terrain5.py    지형 보드
  docs_pages.py  문서 쪽 생성
```

| 저장소 | 맡는 일 |
|---|---|
| `foothold-lab` | 원장 · 문서 메타데이터 · 갤러리 색인 생성기 |
| `MAI_UNIVERSE` | 원장 소비 · 허브 렌더 · 보드 · 검사기 |
| `foothold-site` | 검사를 통과한 **생성물만** |

세 커밋을 **한 검수 기록에 묶는다.**

**빌드 입력은 이미 고정돼 있다.** `docs_pages.py:42` 가 `_lab-main` 을
`foothold-lab` 보다 먼저 고르는 것은 **결함이 아니라 설계**다. 주석이 그
까닭을 적어 두었다.

> `foothold-lab` 은 여러 세션이 함께 쓰는 작업 디렉터리라 브랜치가 수시로
> 바뀐다 (하루에 `reset --hard` 가 열 번 넘게 돌았다). 빌드가 그것을 읽으면
> 같은 소스로 돌려도 산출물이 달라져 연속 빌드 재현을 보장할 수 없다.
> `_lab-main` 은 `origin/main` 에 고정된 별도 워크트리다.

그러므로 **작업 순서가 정해진다.**

```
1. foothold-lab 에 원장·생성기를 넣고 origin/main 에 push
2. _lab-main 워크트리를 그 커밋으로 맞춘다
3. MAI_UNIVERSE 의 빌드를 고치고 돌린다
4. foothold-site 에 생성물이 나온다
```

push 하지 않은 변경은 빌드가 못 본다. 이것을 잊으면 「고쳤는데 화면이 안
바뀐다」가 된다.
