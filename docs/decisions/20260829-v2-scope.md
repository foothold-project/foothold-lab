## 0. 왜 이 문서가 필요한가 `실측`

`v2.0.0` 이라는 말이 `LEDGER` 와 관계표 등 **네 곳**에 나온다.
그런데 **무엇이 끝나면 v2.0.0 인지는 어디에도 없다.**

끝나는 선이 없으면 일이 안 끝난다. 실제로 그랬다.

```
2026-08-28 하루 실측
  이슈 개설 24개  ·  이슈 종료 4개
  커밋 20개 중 대부분이 빌드 관문·인프라
  빌드 관문 5개 신설 ([1.35] [3.56] [3.62] [3.8] [3.9])
  빌드 스크립트 50개 · 빌드 1회 61초
```

관문 하나하나는 진짜 문제를 잡았고 고친 것도 진짜다. **그런데 이 고리는
스스로 멈추지 않는다.** 관문을 만들면 관문이 문제를 잡고, 고치다 새 문제를
보고, 관문을 또 만든다.

**멈추는 장치가 필요하다. 그것이 이 문서다.**

## 1. 순서는 이미 정해져 있다

```
v2.0.0 리빌딩  ->  정리된 자료로 제출물 작성  ->  9/4 기획발표
```

**리빌딩이 먼저다** (팀장 확정). 문서 관계와 분류가 정리돼야 그것을 근거로
기획서를 쓴다. 백지에서 쓰지 않는다.

그러니 리빌딩은 **빨리 끝나야 하는 일**이지 미룰 일이 아니다.
아래 목록 밖으로 번지지 않는 것이 요령이다.

예외는 하나뿐이다. **v2.0.0 작업이 그것 때문에 막힐 때.**

## 3. 남은 순서

앞의 결과가 뒤의 재료가 되는 순서다.

| 차례 | 무엇 | 왜 이 순서인가 |
|---|---|---|
| 1 | **허브를 축에서 파생** (#76 · #73) | 손 목록을 없앤다. 이게 되어야 나머지 허브 작업이 반복 노동이 안 된다 |
| 2 | **표지 노출 기준 적용** (#76) | `web_worthy` 를 실제로 쓴다. 무엇을 앞세울지가 정해진다 |
| 3 | **기술 허브 신설 · wiki 흡수** (#71 · #72) | 1 이 끝나야 새 허브가 공짜로 만들어진다 |
| 4 | **NEW 배지 · WBS 도달 · 브랜드** (#75 · #77 · #85) | 화면 마감 |
| 5 | **일정 시스템 · 도구 백과** (#74 · #6) | 남은 둘 |

**승격 흐름 개조는 v2.0.0 밖이다.** 팀원 투고를 자동 분류하는 일은
설계까지 해뒀고(`info-model` §4), 코드는 v2.1 에서 한다.
지금은 문서가 이미 다 들어와 있어 급하지 않다.

## 4. 끝났는지 어떻게 아나

| 조건 | 어떻게 확인 |
|---|---|
| 이슈 아홉이 전부 닫힘 | `gh issue list` |
| 허브 묶음에 손 목록이 없음 | `_build/` 에 슬러그 나열이 없다 |
| 빌드 `--check` 종료코드 0 | 관문 전부 통과 |
| 표지가 무엇을 앞세우는지 근거가 있음 | `web_worthy` 로 뽑았다고 화면이 말한다 |

## 5. 이 문서가 막는 것

- **눈앞의 결함에 반응해 범위를 넓히는 것.** 새 결함은 이슈로만 남긴다
- **관문을 더 만드는 것.** 지금 13개면 충분하다. v2.0.0 안에서는 안 늘린다
- **「무엇을 만들까」부터 시작하는 것.** 매번 「이미 무엇이 있나」를 먼저 연다.
