센서가 경로를 정하고, 기존 정책이 걷는다

Isaac Sim 안의 Go2 에 센서 → 지도·비용 → Nav2 → 속도 명령 → 기존 RL 보행 정책을 잇는 구조다. 학원 앞 광장을 옮긴 환경에서 지도 작성 · 위험 인식 · 목적지 이동을 연결하는 것이 목표이고, 보행 정책은 손대지 않는다 · 정책은 지금처럼 proprioception 과 height_scan 만 받는다.

확인 완료 카메라·RTX LiDAR 부착과 데이터 취득  ·  구현 예정 지도·비용·Nav2·연결 코드  ·  미확인 실기 장착·토픽·성능
이 페이지의 성격

아래 구조는 제안이다. 팀이 확정한 필수 범위가 아니고, 팀원의 현재 학습 코드를 확인한 것도 아니다. 「확인 완료」 배지는 Isaac-CV/08-wiki-exact-sensors/ 의 run02 원물(verification.json · configuration_check.json)로 확인한 것에만 붙였다.

15단계 구조 · 두 정보 흐름

  1. LiDAR · 깊이 카메라 → 형상 관측 → 지도 작성. 어디가 막혀 있고 어디가 높은지.
  2. RGB → 사람·지면·물체 분류 → 깊이·좌표 변환과 결합 → 위험 대상의 위치와 비용. 박스 하나로는 안 되고 「몇 m 앞, 지도 어느 칸」까지 가야 한다.
  3. 장애물·지형 비용 지도 + 로봇 위치 + 목적지 → Nav2 경로 계획·추종.
  4. Nav2 의 vx · vy · wz → 연결 코드 → 기존 RL 보행 정책 → 관절 제어. 정책은 이 속도 명령을 지금까지 받던 velocity_commands 자리로 받는다.
  5. 기존 정책은 별도로 proprioception 과 height_scan 을 계속 입력받는다. 위 1~4 의 센서는 정책 입력에 합류하지 않는다.

따라서 187개 숫자를 LiDAR 값으로 채워 넣는다고 같은 정책이 되지 않는다. 센서로 발 디딤 지형까지 판단하게 하려면 관측 표현을 맞추고 성능을 검증해야 하고, 필요하면 재학습·학습 설계 변경이 따른다. 이 페이지의 범위(상위 CV·Nav2 연결)에서는 그 일을 하지 않는다 · 그래서 RL 담당이 학습 env 에 카메라·RTX LiDAR 를 달 필요도 당장은 없다. 조건 팀원의 학습 코드가 run02 와 같은 관측 구조라는 전제이며, 그 코드는 확인하지 않았다.

run02 rails 녹화에서 확인한 것 확인 완료

참조 벤치마크 10종 지형 중 env 5 rails(1×10 배치, seed 42, 난이도 0.5, rail 높이 0.115 m, 명령 vx 0.5 m/s, 300 step / 6 s)에 카메라 · XT-16 근사 RTX LiDAR · L1 시야 비교용 센서를 붙여 녹화했다. 정책은 foothold-v1.pt(SHA256 c7612aef…ee7aca), 기존 환경 설정은 센서 3필드 추가 외 무변경(existing_config_unchanged: true, added_scene_fields: front_camera · xt16_geometry · l1_fov_comparison). 저장 60샘플 중 RTX 점군이 비어 있지 않은 것 57, 스캔 수신 시각 24개 · 10 Hz 저장이 10 Hz 새 스캔은 아니다.

이 녹화가 입증한 것은 「센서를 달고 데이터를 받았다」까지다. 센서 기반 지도 작성 · SLAM · Nav2 · 사람 인식으로 실제 행동이 바뀐 것은 입증되지 않았다. 참고 영상은 바닥이 검고 재녹화는 밝은 타일이며, 원본 에피소드를 프레임까지 복제한 것도 아니다.

우하단 점군 패널은 raw point cloud 의 XY 표시이지 rail 인식 결과가 아니다. 표시 색 범위 0~1.2 m 와 1 px 점이 0.115 m rail 을 읽기 어렵게 하는 것도 맞지만, 색을 바꾸면 있는 점이 보일 뿐 없는 관측이 생기지 않는다. XT-16 근사 ±15° 수직 시야 · 센서 높이 0.62 m 수평 자세 가정에서 최저 광선이 바닥에 닿는 수평 거리는 약 2.31 m, rail 상면(0.115 m)은 약 1.89 m 다(rails_returns_diagnosis.json · 자세가 바뀌면 달라지는 예시값이고 기기 최소 측정 거리가 아니다). 알려진 rail 위치·높이 근방 점 수는 t=0.3 s 안쪽 0 / 바깥 4,949, t=3.0 s 안쪽 685 / 바깥 5,002 · 기하 ROI 집계이지 인식 정답·정확도가 아니다. 영상은 C3 에 싣는다(작업 B).

3지도 세 종류 · 3D 관측을 2D 비용으로

지도무엇을 담나어디서 오나Nav2 와의 관계
장애물 지도(점유)칸마다 막힘/빈 곳/미관측LiDAR · 깊이기본 costmap_2d 가 바로 먹는 형태
높이 지도(2.5D)칸마다 높이 · 단차 · 경사LiDAR · 깊이 점군을 누적그대로는 못 먹는다 · 높이·경사·불확실성을 비용으로 바꾸는 로직이 필요
의미 지도칸마다 종류(사람 · 잔디 · 보도 …)RGB 분류 + 깊이·TF 로 칸에 투영종류별 비용(사람 = 정지/우회, 잔디 = 감속 등)으로 변환해 layer 에 넣는다

기본 Nav2 계획은 2D 비용 지도 기반이다. 3D 점군·voxel 입력을 받는 layer 가 있다는 것과, 험지를 통과할 수 있는지를 판단하는 것은 다른 문제다. 3D 관측을 2D 비용으로 바꾸는 자리에서 결정할 것:

  • ground filtering · 바닥 점을 장애물로 넣지 않기. 높이 문턱 하나로 하면 경사에서 깨진다.
  • 높이·경사 → 비용 · 단차 몇 cm 부터 비용을 올릴지, 경사 몇 도부터 막을지. 이 값은 정책의 실측 한계(20 지형 한계선)와 맞춰야 한다.
  • 미관측 칸 · 안전한 바닥으로도 구덩이로도 자동 치환하지 않는다. 「모름」 비용을 따로 둔다.
  • 잔디 분류 ≠ 통과 안전 · 구덩이 · 낮은 턱 · 급경사는 의미 지도가 아니라 기하 분석으로 따로 본다.

4혼동하면 안 되는 것

디지털 트윈 vs 로봇의 지도
사진으로 구축한 트윈은 시뮬레이터의 세계다. 로봇이 센서로 재구성한 지도는 로봇의 관측 결과다. 같은 것이 아니다.
Mapping · Localization · SLAM
Mapping = 관측을 공간에 누적, Localization = 자기 위치 추정, SLAM = 둘을 함께 추정. 시뮬레이터 정답 위치로 지도 작성·항법을 검증하는 단계는 정당하지만, 그것을 「센서 기반 SLAM 달성」으로 표시하면 안 된다.
박스 표시 vs 행동 변경
사람 박스가 화면에 뜨는 것과, 그 때문에 로봇이 감속·정지·경로 변경을 하는 것은 다른 단계다. CV 의 기여를 말할 때는 CV 켬/끔 비교와, 기하 기반 장애물 회피만으로도 멈추는 경우와의 차이를 같이 보여야 한다.
Detection2DArray 만으로는 안 붙는다
표준 메시지를 발행한다고 Nav2 와 자동으로 연결되지 않는다. 깊이 · 센서 보정 · 동기화 · TF · 추적 또는 시간 만료 · 비용 지도 반영 또는 정지 로직이 전부 우리 코드다(CV 교재 C4-5).
「기하는 LiDAR, 의미는 카메라」
입문용 역할 분담 예시다. RGB-D · visual SLAM 을 배제하는 법칙이 아니다.

자체 RL 정책 실기 배포

Go2 ↔ ROS 2 연동

우리 Go2가 EDU인지 Air/Pro인지. EDU만 이더넷+DDS 공식 API가 열려 있다. Air/Pro는 WebRTC 기반 비공식 SDK(go2_ros2_sdk)를 써야 하며, 이 답이 아키텍처 전체를 결정한다. (09-11 이후: EDU 로 전달받음 · 라벨 미확인)

  • go2_ros2_sdk (비공식) · Wi-Fi(WebRTC)·이더넷(CycloneDDS), IMU·L1 포인트클라우드(~7Hz)·카메라·LaserScan 변환·텔레옵에 slam_toolbox + Nav2 통합. GitHub
  • unitree_ros2 (공식) · SDK2의 DDS 토픽을 ROS 2에서 직접 구독/발행. EDU 전제. GitHub
