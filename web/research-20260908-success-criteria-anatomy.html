1. 네 축은 각각 무엇을 재는가

판정 식은 전부 sim/eval/metrics.py 의 순수 함수다. 하네스(eval_generalization.py)는 시뮬레이터에서 값을 모으기만 하고 판정을 하지 않는다 (eval_generalization.py:6-7). 그래서 판정 기준을 알고 싶으면 이 파일 하나만 보면 된다.

1-1. 생존 · survival_success

Python
# sim/eval/metrics.py:229-231
def survival_success(timed_out, terminated):
    """넘어지지 않고 제한 시간을 채웠나. 스냅샷 503~506행."""
    return bool(timed_out and not terminated)

제한 시간을 다 채웠고(timed_out) 조기 종료되지 않았어야(not terminated) 통과다.

  • timed_out · terminated 는 시뮬레이터가 준다 (eval_generalization.py:593).
  • terminated 를 만드는 조건은 몸통(base) 접촉 하나뿐이다. 임계 1.0 N. ``python base_contact = DoneTerm(func=mdp.illegal_contact, params={"sensor_cfg": SceneEntityCfg("contact_forces", body_names="base"), "threshold": 1.0}) ` (inbox/lee/20260908-pit진단.md:596-598 인용. 원본은 저장소 밖 Isaac Lab 파일이고 docs/research/go2-rough-training.md:378` 이 같은 줄을 전사한다)
  • 평가 하네스는 이 종료 조건을 덮어쓰지 않는다 확인됨. generalization_env_cfg.py 의 __post_init__ 에 self.terminations.* 줄이 하나도 없어 상위 설정값을 그대로 물려받는다.

임계값의 출처: 시간은 --eval_duration (eval_generalization.py:86, 기본 20.0), 종료 조건은 인자가 아니라 환경 설정이다. 명령줄로 못 바꾼다.

1-2. 전진 · progress_success

Python
# sim/eval/metrics.py:234-236
def progress_success(forward, min_progress):
    """충분히 전진했나. 스냅샷 508~510행."""
    return bool(forward >= min_progress)

forward 는 끝점 전진거리다. 경로를 적분하지 않고 시작점에서 끝점까지의 변위를 전방축에 투영한 값이다 (metrics.py:72-88). 문서가 오래 「누적·적분」이라 적어 온 자리이고 그것이 오기였다 (metrics.py:76, #125 7번).

min_progress 의 출처가 조금 꼬여 있다.

층무엇어디
명령줄--min_progress_m (기본 10.0, 미터로 직접)eval_generalization.py:90
하네스min_progress_ratio = min_progress / ideal_distance 로 비율로 되바꿔 넘긴다eval_generalization.py:476
판정min_progress_m(ratio, ideal) = ratio × ideal 로 다시 미터로 되돌린다metrics.py:200-202, :328

즉 미터 → 비율 → 미터를 왕복한다. 스냅샷이 비율로 받았기 때문에 남은 구조이고, 값은 같다.

ideal_distance = command_vx × eval_duration (metrics.py:195-197). 기본값이면 1.0 × 20 = 20 m 이고 통과선 10 m 는 비율 0.5 다.

1-3. 속도추종 · tracking_success

Python
# sim/eval/metrics.py:239-241
def tracking_success(vel_mae, max_velocity_mae):
    """명령 속도를 따랐나. 스냅샷 512~514행."""
    return bool(vel_mae <= max_velocity_mae)

vel_mae 는 에피소드 전체 스텝의 평균 절대 속도 오차다.

Python
# sim/eval/metrics.py:217-219
def velocity_mae_mps(velocity_error_sum, sample_count):
    return velocity_error_sum / step_count(sample_count)

임계값 max_velocity_mae 는 --max_velocity_mae (eval_generalization.py:92, 기본 0.25 m/s).

이 축의 성질을 정확히 적어 둔다. 스텝마다의 오차를 평균한다. 최댓값도 분위수도 아니다. 그래서 6초 중 1초를 완전히 멈추면 그 1초가 평균을 0.17 만큼 밀어 올린다(명령 1.0 m/s 기준). 임계가 0.25 이므로 한 번의 짧은 정지가 예산의 3분의 2를 먹는다. 5절의 쟁점이 여기서 나온다.

1-4. 방향 · direction_success 와 gate_direction_success

두 갈래가 있고, 정본은 통과선 쪽이다.

Python
# sim/eval/metrics.py:244-255  (갈래 A · 끝점)
def direction_success(lateral, max_lateral_drift):
    return bool(lateral <= max_lateral_drift)

# sim/eval/metrics.py:181-190  (갈래 B · 통과선)
def gate_direction_success(gate_lateral, max_lateral_drift):
    if gate_lateral is None:
        return False
    return bool(gate_lateral <= max_lateral_drift)

무엇이 고르는가는 episode_metrics 의 gate_progress_m 인자다.

Python
# sim/eval/metrics.py:336-339
if gate_progress_m is None:
    direction = direction_success(lateral, max_lateral_drift)
else:
    direction = gate_direction_success(gate_lateral, max_lateral_drift)

하네스는 항상 통과선을 넣는다 확인됨.

Python
# sim/eval/eval_generalization.py:630
gate_progress_m=min_progress,

min_progress 는 --min_progress_m 그대로다 (eval_generalization.py:475). 즉 전진 통과선과 방향 통과선이 같은 값이다. 10 m 를 요구하면 방향도 10 m 지점에서 잰다.

왜 옮겼나. 멘토 기준은 「목표점에 도달했을 때 좌우 5 cm」인데, 20초 × 1.0 m/s 면 끝점이 20 m 라 목표점 10 m 의 두 배 지점을 재게 된다 (eval_generalization.py:20-24, metrics.py:140-151). 통과선을 한 번도 못 넘겼으면 None 이고 실패로 친다. 0.0 으로 돌려주면 「도착했고 완벽하게 곧았다」와 구별이 안 되기 때문이다 (metrics.py:150-151, :184-189).

임계값은 --max_lateral_drift (eval_generalization.py:94, 기본 0.05 m). 다만 험지 10종의 팀 정본은 1.5 m 다 (docs/DECISIONS.md:124). 평지 통과선이 10 m 이고 험지가 3 m 라 같은 5 cm 를 걸면 험지가 3.3배 엄격해지기 때문이다.

1-5. 판정에 안 쓰는 관측 열 둘

Python
# sim/eval/metrics.py:20
ADDED_COLUMNS = ("peak_lateral_drift_m", "gate_lateral_drift_m")

peak_lateral_drift_m 은 경로 전체의 최대 좌우 이탈이다. 판정에 쓰지 말라고 함수 주석에 명시돼 있다 (metrics.py:108-109). 끝점만 보면 옆으로 크게 밀렸다가 돌아온 지그재그가 안 잡히므로 진단용으로 남긴 것이다 (docs/DECISIONS.md:118).

2. 판정이 어떻게 합쳐지나

Python
# sim/eval/metrics.py:258-260
def overall_success(survival, progress, tracking, direction):
    """네 축을 모두 통과했나. 스냅샷 520~525행."""
    return bool(survival and progress and tracking and direction)

순수한 AND 다. 가중치도, 부분 점수도, 등급도 없다.

함의 셋

① 축이 늘어날수록 성공률은 반드시 떨어진다. 각 축이 독립이고 통과율이 각각 90 %면 넷을 AND 하면 0.9⁴ = 65.6 % 다. 축을 하나 더하는 것은 언제나 성공률을 깎는 방향이고, 절대 올리지 않는다. 7절의 라이다 제안을 판정에 넣지 말자는 근거가 여기서 나온다.

② 「거의 성공」이 「완전 실패」와 같은 칸에 들어간다. 임계 0.25 에 대해 0.2501 인 판과, 넘어져서 1.54초에 끝난 판이 CSV 의 overall_success 열에서 똑같이 False 다. 이민우 진단이 실측한 바로는 14 cm 에서 구덩이를 나온 89 에피소드의 속도오차가 0.13 에서 0.50 까지 이어진 한 덩어리이고 두 무리로 갈라지지 않는다 (inbox/lee/20260908-pit진단.md:284-287). 임계 0.25 가 그 한복판을 지나고 0.24 ~ 0.26 칸 하나에만 11 에피소드가 걸쳐 있다.

③ 어느 축에서 떨어졌는지는 원자료에만 남는다. 다행히 네 축이 전부 CSV 열이라(metrics.py:23-45) 사후 재집계가 된다. 0절의 표를 만들 수 있었던 이유다. report.py:22-28 이 축별 성공률을 따로 뽑아 준다.

AND 자체는 합당하다. 「빠르지만 넘어진다」와 「안 넘어지지만 안 간다」를 평균 내면 둘 다 감춰진다. 쟁점은 AND 가 아니라 어느 축을 AND 안에 넣을 것인가다.

3. 실패 사유 둘의 정의

Python
# sim/eval/metrics.py:263-265
def termination_reason(timed_out):
    """종료 사유. 스냅샷 537~541행."""
    return "timeout" if timed_out else "base_contact"
값뜻성공일 수 있나
timeout제한 시간을 다 채우고 끝났다있다. 생존 통과의 필요조건이다
base_contact시간 전에 끝났다없다. survival_success 가 반드시 False

여기에 함정이 하나 있다 확인됨.

termination_reason 은 접촉을 읽지 않는다. timed_out 이 아니면 무조건 "base_contact" 라고 적는 추론이다. 어느 링크가 닿았는지도, 정말 접촉 때문이었는지도 확인하지 않는다.

지금은 종료 조건이 base_contact 하나뿐이라 결과가 맞다. 그러나 종료 조건을 하나라도 더하는 순간 이 열은 조용히 거짓말을 시작한다. 새 종료 사유로 끝난 판이 전부 "base_contact" 로 기록되고, 오류는 나지 않는다. 7절에서 「라이다 접촉을 종료 조건에 넣자」를 검토할 때 이것이 비용으로 계산돼야 한다.

「낙상」이라는 말도 정확히는 「몸통이 1 N 이상 닿았다」다. 다리가 접혀 주저앉아도 몸통이 안 닿으면 종료되지 않고, 머리를 세게 박아도 종료되지 않는다 (7절).

4. 원장과 코드가 어긋나 있는 자리

방향 판정에 대해 원장과 코드가 서로 다른 말을 한다. 문서로 남겨 둔다.

무엇이라 하나근거
원장 DECISIONS.md:118「좌우 이탈은 «끝점»으로 판정하고 «최대값»을 관측 열로 남긴다」 팀장 확정09-02
코드 (지금)통과선으로 판정한다eval_generalization.py:630
원장 DECISIONS.md:129-145「팀장이 정해야 한다. 정할 때까지 두 값을 함께 기록한다」미결

원장은 이 어긋남을 이미 알고 있고 미결로 열어 두었다 (docs/DECISIONS.md:144). 같은 100 에피소드를 두 자로 재면 통과선 기준 이탈 평균 0.085 m, 끝점 기준 2.143 m 로 크게 다르고, 기획서가 인용한 직진성 33/100 은 통과선 기준이며 끝점으로 재면 0/100 이다 (docs/DECISIONS.md:142).

그리고 정본 실측은 코드보다 먼저 돌았다 확인됨. 20260903-rough10-1.0mps/generalization_raw.csv 의 헤더는 20열이고 gate_lateral_drift_m 이 없다. 즉 정본 1,000 에피소드는 끝점으로 채점됐다. 지금 코드로 같은 명령을 다시 돌리면 방향 축이 통과선으로 바뀌어 숫자가 재현되지 않는다.

팀장 결정이 필요한 항목 1. 방향을 끝점으로 잴 것인가 통과선으로 잴 것인가. 코드는 이미 통과선을 쓰고 있으므로, 끝점이 정답이면 코드가 원장을 어기고 있는 상태이고, 통과선이 정답이면 원장 09-02 행을 정정해야 한다.

5. 합당성 검토

5-1. 세 축은 합당하다

축왜 합당한가
생존넘어지면 실패라는 데 이견이 없다. 다만 「넘어짐」의 정의가 몸통 접촉뿐인 것은 7절의 쟁점
전진「걸었는가」를 재는 최소 조건. 없으면 제자리에서 버티기만 해도 성공이 된다

5-2. 속도추종은 쟁점이다

논지: 턱이나 구덩이를 넘으려면 잠깐 느려져야 하는데, 그 순간이 곧 벌점이고 그 판이 실패로 셈해진다.

근거 ① 실측 · 「나왔는데 느려서 떨어진」 판이 실패의 다수인 구간이 있다

이민우 pit 진단이 깊이를 8 ~ 22 cm 로 훑어 800 에피소드를 냈다 (inbox/lee/20260908-pit진단.md:241-253).

「14 cm 실패 49 에피소드 중 36 에피소드(73 %)이 「구덩이는 나왔고 방향도 지켰는데 속도만 못 따라간」 판이다. 갇힌 판은 7 에피소드뿐이다. inbox/lee/20260908-pit진단.md:253-254

조건을 밝혀 둔다. 이 실험은 6초 · 통과선 3 m · 1.0 m/s · 좌우 임계 1.5 m 로 돌았다 (inbox/lee/20260908-pit진단.md:18). 이것이 험지 10종의 팀 정본 조건이다 (docs/DECISIONS.md:125, :124). 평지 기준선의 20초 · 10 m · 5 cm 와 다르다.

근거 ② 정본 1,000 에피소드 재집계도 같은 방향을 가리킨다

0절의 표를 다시 본다. 정본 실측 원자료를 팀 정본 임계 1.5 m 로 재채점해 축별로 센 값이다 확인됨.

rails 에서 속도추종은 사실상 유일한 관문이다. 살아남고 거리도 가고 옆으로도 안 샌 42 에피소드 중 38 에피소드를 이 축 하나가 떨어뜨린다.

맹라현 rails 진단과 이민우 pit 진단이 서로 독립적으로 같은 결론에 도달했다 (inbox/lee/20260908-pit진단.md:546-552).

두 지형이 같은 병목을 공유한다. 「넘을 힘은 있는데 속도추종에서 떨어진다」가 rails 와 pit 에서 각각 독립적으로 나왔다.

근거 ③ 힘이 모자라서가 아니다

  • 관절 가동범위 실측: 최대 발 높이 앞 31.0 cm · 뒤 30.1 cm (inbox/jay/20260907-go2-관절한계-실측.md). 14 cm 는 그 절반도 안 된다 확인됨.
  • 요구 토크 미달 0.50 ~ 5.67 % (inbox/lee/20260908-pit진단.md:711).
  • 즉 「못 넘는다」가 아니라 「넘느라 느려진다」 이다.

근거 ④ 학습 보상이 같은 방향으로 기울어 있다

Go2 험지 설정이 공통 기본값을 덮어쓴다 (docs/research/rails-diagnosis.md:332-334).

보상 항공통 기본값Go2 험지 설정뜻

학습과 평가가 같은 방향으로 기울어 있다. 학습은 속도 추종에 1.5배 상을 주고 발을 드는 시간에는 12.5분의 1만 준다. 평가는 그 위에 속도추종 임계를 AND 로 얹는다. 「느리더라도 확실히 넘는」 정책은 학습에서도 평가에서도 보상받을 자리가 없다.

보상에 발 높이 항이 아예 없다는 것은 팀이 두 번 독립적으로 확인했다 (docs/research/rails-diagnosis.md:191, docs/research/발보상-시간아니고높이아님.md). feet_air_time 은 뜬 «시간»에 점수를 주고 높이는 안 본다.

단, 1.0 → 1.5 는 저장소 안의 코드가 아니라 저장소 밖 Isaac Lab 파일의 전사다 확인됨(전사) / 미확인(원본 대조). foothold-lab 에는 rough_env_cfg.py 가 없다. 출처는 source/isaaclab_tasks/isaaclab_tasks/manager_based/locomotion/velocity/config/go2/rough_env_cfg.py 이고, 우리 문서 세 곳이 같은 값을 적는다 (docs/research/rails-diagnosis.md:333 · docs/research/go2-rough-training.md:373 · inbox/jay/20260907-go2-관절한계-실측.md:76).

5-3. 반대 논거도 적는다 (속도추종을 그대로 두어야 할 이유)

공정하게 반대쪽을 적는다. 이 축을 빼자는 주장이 자동으로 옳지는 않다.

  1. 명령 추종은 평가 대상 그 자체다. 우리가 재는 정책은 (vx, vy, wz) 명령을 받는 속도 추종 정책이다. 명령을 안 따라도 성공이라 하면 무엇을 평가하는지가 흐려진다.
  2. 속도추종을 빼면 「기어가기」가 성공이 된다. 6초에 3 m 만 넘으면 되므로 평균 0.5 m/s 로 느릿느릿 넘는 정책이 만점을 받는다. 전진 축이 하한을 지키지만 그 하한은 명령의 절반이다.
  3. 실기 이식에서 속도는 요구사항이다. 현장 임무에 시간 예산이 있으면 「넘긴 넘었는데 3배 걸린다」는 실패일 수 있다.
  4. 정본 1,000 에피소드 전체로 보면 이 버킷은 51/496 = 10.3 %다. 나머지 445 에피소드의 실패는 낙상(stepping_stones 80 에피소드 · gap 79 에피소드 · floating_ring 14 에피소드)과 전진 미달이 지배한다. 10종 전체의 성공률을 끌어올리는 데 이 축이 최대 병목은 아니다. 최대 병목인 지형은 rails 와 pit 둘이다.

그러므로 「속도추종을 없애자」가 아니라 「속도추종이 무엇을 재는 자인지 다시 정하자」가 정확한 문제 설정이다.

6. 재설정 선택지와 각각의 대가

결론을 단정하지 않는다. 선택지를 늘어놓고 대가를 적는다. 고르는 것은 팀장이다.

선택지 A · 그대로 둔다

바꾸는 것없음
얻는 것정본 실측과의 비교가 끊기지 않는다. 기준이 하나다

선택지 C · 속도추종을 AND 에서 빼고 관측 열로 내린다

바꾸는 것metrics.py:258-260 에서 tracking 을 뺀다. 열은 그대로 남긴다

선택지 D · 속도추종의 «자»를 바꾼다 (평균 대신 회복 시간)

바꾸는 것새 열을 더한다. 판정 식은 나중에 정한다

잃는 것설계·구현 비용. 새 지표라 과거 기록에 없다
후보 열구간별 MAE(vel_mae_0_2s 등) · 명령 속도의 80 % 를 회복하기까지 걸린 시간 · 최저 속도와 그 시각

선택지 C 의 완화책(성공을 두 층으로)과 선택지 D(회복 시간 열)는 서로 배타적이지 않다. 둘 다 «판정을 바꾸지 않고 먼저 재 본다»는 성격이라 함께 넣어도 비교가 안 끊긴다.

7. 제안 하나 · 라이다 접촉

지금 상태

판정에 없다 확인됨. sim/eval/ 전수 검색에서 lidar · 라이다 · ray_caster · height_scanner · Head_upper · Head_lower 에 대한 코드가 하나도 없다. 접촉 관련 문자열은 metrics.py:265 와 report.py:143 의 "base_contact" 문자열 리터럴뿐이고, 접촉력 센서를 읽는 코드는 없다.

실기 Go2 는 그 자리에 라이다가 있다 (docs/ROBOT-SPEC.md). 팀장 질문 「라이다가 닿으면 실기에서는 문제 아닌가」는 타당하다.

검토 결과: 별도 지표로 재는 데 동의한다. 근거를 넷 댄다

① 판정에 넣으면 성공률이 반드시 떨어진다. 2절 함의 ①. AND 에 축을 더하는 것은 결코 성공률을 올리지 않는다. 지금 rails 4 % · pit 3 % 인 상태에서 축을 더하면 바닥에서 바닥을 재게 된다. 개선을 재는 눈금으로서 쓸모가 준다.

② 임계값을 정할 근거가 우리에게 없다. 이것이 가장 결정적이다.

「몇 N 부터 부서지는가」의 기준은 우리에게 없다 미확인. 팀 문서에도 없다. inbox/lee/20260908-pit진단.md:608

임계 없이 판정에 넣으면 「닿기만 해도 실패」가 되는데, 정강이(calf)는 정상 보행에서도 8 cm 대조군에서 124.5 N 이 걸린다 (pit진단:524-526). 접촉 자체는 실패가 아니다. 숫자 없이 관문을 만들면 그 관문은 임의값이 된다.

③ 정책이 보수적으로 변한다는 우려에 동의하되, 경로를 정확히 적는다. 지금 이 지표는 평가에만 들어가고 학습 보상에는 안 들어가므로, 평가 축 하나를 더한다고 정책이 곧바로 보수적으로 바뀌지는 않는다. 위험은 간접적이다. 성공률로 체크포인트를 고르는 순간 「머리 안 대는 정책」이 선택되고, 5-2 근거 ④ 에서 봤듯 몸을 올리는 것은 이미 lin_vel_z_l2 로 벌받고 있어 「낮게 기어서 통과」쪽으로 선택압이 걸린다. 즉 우려는 옳지만 기전은 학습이 아니라 선택이다.

④ 종료 조건으로 넣으면 기존 열이 조용히 망가진다. 3절에서 본 대로 termination_reason 은 timed_out 만 보고 사유를 추론한다. 머리 접촉을 DoneTerm 으로 더하면 그 판이 전부 "base_contact" 로 기록되고 오류는 나지 않는다. 넣으려면 termination_reason 을 실제 사유를 읽도록 함께 고쳐야 한다. 이 비용이 계산에 들어가야 한다.
